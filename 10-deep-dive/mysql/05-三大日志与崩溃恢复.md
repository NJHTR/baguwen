# 三大日志与崩溃恢复（Redo / Undo / Binlog）

> 面试权重：5/5　｜　追问深度：**L5（InnoDB 日志子系统与两阶段提交恢复源码）**
> 一句话定位：MySQL 敢说"提交了就不丢"，靠 redo log；能回滚、能 MVCC，靠 undo log；能主从复制、能归档审计，靠 binlog。三者的分工与两阶段提交，是后端面试从 CRUD 走向存储引擎的第一个分水岭。

**本文件用法**：从 L1 往下读，每读完一层，合上书自问自答。**停在答不出的那一层，就是你的真实水平线。**

## L1 一句话答案（10 秒能说出口）

redo log 是 InnoDB 的物理日志，用 WAL 先把日志顺序写盘、脏页异步刷，环形结构 + LSN 保证崩溃后能重放到一致状态；undo log 是逻辑日志，存旧值，负责回滚和 MVCC 版本链；binlog 是 Server 层的逻辑日志，负责主从复制和归档。redo 与 binlog 靠两阶段提交（redo prepare → binlog → redo commit）保持一致。

## L2 原理层：三种日志怎么分工、怎么配合

### 2.1 三者对比

| 维度 | redo log | undo log | binlog |
|---|---|---|---|
| 归属 | InnoDB 引擎层 | InnoDB 引擎层 | Server 层 |
| 类型 | 物理日志（页号 + 偏移 + 改了哪些字节） | 逻辑日志（旧值 / 反向操作） | 逻辑日志（SQL 或行变更） |
| 写法 | 环形写、循环覆盖 | 追加写、按事务/回滚段管理 | 追加写、文件滚动 |
| 生命周期 | checkpoint 推进后可覆盖 | 提交后 update undo 等 purge，insert undo 提交即删 | 保留到过期时间（`binlog_expire_logs_seconds`） |
| 作用 | 崩溃恢复（crash-safe） | 回滚 + MVCC | 主从复制、备份恢复、Canal 订阅 |
| 刷盘参数 | `innodb_flush_log_at_trx_commit` | 无 | `sync_binlog` |

### 2.2 redo log 的环形结构与 LSN

```
#innodb_redo 目录下多个 redo 文件（8.0 默认 32 个，容量 innodb_redo_log_capacity）
┌──────────────────────────────────────┐
│  checkpoint pos ──► 可覆盖区 ──► write pos │
└──────────────────────────────────────┘
                     write pos 追上 checkpoint pos = 日志写满
                     → 必须推进 checkpoint（刷脏页），否则写入阻塞
```

| 概念 | 含义 | 用途 |
|---|---|---|
| LSN | 单调递增的日志字节偏移 | 全局定位"日志写到哪" |
| `log_sys->lsn` | 已写入 redo 的总量 | 判断是否还能写 |
| `flushed_to_disk_lsn` | 已 fsync 落盘的位置 | 崩溃后重放的上限 |
| `checkpoint_lsn` | 数据页已持久化的位置 | 小于它的 redo 可被覆盖 |
| page LSN | 每个数据页头里记录的 LSN | 恢复时判断该页是否已更新过，避免重复重放 |

### 2.3 WAL 与 `innodb_flush_log_at_trx_commit` 三档

WAL（Write-Ahead Logging）：事务提交时只把 redo 顺序写入并落盘，脏页异步刷回磁盘。这样把"随机写数据页"变成"顺序写日志"，既快又能在崩溃后恢复。

| 值 | 行为 | 丢数据风险 | 性能 |
|---|---|---|---|
| 0 | 每秒后台刷 redo，提交时不刷 | MySQL 崩溃 / OS 崩溃都会丢约 1 秒 | 最高 |
| 1（默认） | 每次提交 fsync redo | 不丢 | 最低，金融级必选 |
| 2 | 每次提交 write 到 OS cache，每秒 fsync | MySQL 崩溃不丢，OS 崩溃丢约 1 秒 | 折中 |

配合 `sync_binlog`：0 由 OS 决定，1 每次提交 fsync binlog，N 每 N 次提交 fsync。金融级"双 1"配置 = `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`。

### 2.4 两阶段提交与崩溃恢复两条规则

如果 redo 和 binlog 各写各的，会出现两种不一致：

- redo 提交了、binlog 没写：主库有数据、从库没有，备份恢复后主从分叉；
- binlog 写了、redo 没提交：从库有数据、主库回滚后没有。

所以引入两阶段提交（2PC，这里的"两阶段"指的是 redo 的 prepare/commit 与 binlog 的配合）：

```
① prepare：写 redo，事务标记为 prepare（记录 XID），fsync
② 写 binlog，fsync（由 sync_binlog 控制）
③ commit：redo 标记为 commit（组提交时可批量刷）
```

崩溃恢复时 InnoDB 先重放 redo，遇到 prepare 状态的事务，按两条规则处理：

1. redo 是 prepare，且对应 XID 的 binlog **完整存在** → 提交（补写 commit 标记）；
2. redo 是 prepare，但 binlog **不存在或不完整** → 回滚（用 undo 撤销）。

### 2.5 组提交（group commit）

单条事务一次 fsync 太浪费磁盘 IO，于是把多个事务的刷盘合并。binlog 组提交分三阶段：

1. flush：多个事务的 binlog 合并写入文件；
2. sync：一次 fsync 覆盖多个事务；
3. commit：引擎层提交，redo 的刷盘也可合并。

调参：`binlog_group_commit_sync_delay`（等待微秒数，攒批）、`binlog_group_commit_sync_no_delay_count`（攒够多少事务立即 fsync）。组提交是 `sync_binlog=1` 还能扛住高并发的原因。

### 2.6 binlog 三种格式

| 格式 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| STATEMENT | 记录 SQL 原文 | 日志小 | NOW()/RAND()/UUID/无 order 的 limit 会导致主从不一致 |
| ROW（8.0 默认） | 记录每行 before/after 镜像 | 最准确、可回放 | 批量更新日志放大严重 |
| MIXED | 按语句自动切换 | 折中 | 不确定性仍在，排查困难 |

`binlog_row_image`：FULL（默认，记录所有列）/ MINIMAL（只记主键和变更列，日志小但部分工具不兼容）。大批量数据处理时，ROW 格式下更新 10 万行就是 10 万条事件，这也是批量任务要控制批大小的原因之一。

### 2.7 主从复制与半同步

```
从库 IO 线程 → 连主库 dump 线程 → 请求 binlog（file+position 或 GTID）
主库 dump 线程 → 推送 binlog event
从库 IO 线程 → 写 relay log
从库 SQL 线程 → 重放 relay log
```

- 异步复制：主库提交即返回，主库宕机可能丢未同步的 binlog。
- 半同步：主库等至少一个从库 ACK 再返回；`rpl_semi_sync_master_wait_point` 有 AFTER_COMMIT（客户端先看到提交，仍有丢窗口）和 AFTER_SYNC（先收 ACK 再返回客户端，更安全）。
- GTID：用全局事务 ID 替代 binlog 文件名+位点，主从切换、重搭更简单。
- 从库一般设 `read_only=ON`（或 `super_read_only`）防误写。

## L3 底层层：redo block、mtr 与恢复流程

### 3.1 redo 的物理结构

- redo 文件由 512 字节的 log block 组成：12B 头（block 号、数据长度、first_rec_group、checkpoint 号）+ 数据区 + 4B 尾（checksum）。
- mtr（mini transaction）：InnoDB 内部把一组页修改打包成一个 mtr，mtr 提交时把 redo 写进 log buffer；真正落盘时机是事务提交、log buffer 超过一半、或 checkpoint。
- `innodb_log_buffer_size` 默认 16MB，redo 落盘是顺序 IO，这是 WAL 性能优势的来源。

### 3.2 崩溃恢复流程

1. 从 redo 文件里找到 checkpoint，从该 LSN 开始重放 redo；
2. 重放每个页时比较 page LSN，已经更新的页跳过（幂等）；
3. 重放完后，用 undo 回滚未提交事务；
4. 对 prepare 状态的事务，读 binlog 判断是提交还是回滚（`ha_recover` / `trx_recover`）。

### 3.3 源码入口

- `log0log.cc`：`log_write_up_to()`、`log_sys`、`log_checkpoint()`；
- `log0recv.cc`：`recv_recovery_from_checkpoint()` 崩溃恢复主流程；
- `trx0trx.cc`：`trx_prepare()` / `trx_commit()`；
- `binlog.cc`：`MYSQL_BIN_LOG::ordered_commit()` 三阶段组提交；
- 半同步：`semisync_master.cc` 的 `ReplSemiSyncMaster::commitTrx()`。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**
### 第 1 层｜redo log、undo log、binlog 分别是什么？
**答**：redo 是 InnoDB 物理日志，保证崩溃恢复；undo 是 InnoDB 逻辑日志，存旧值，负责回滚和 MVCC；binlog 是 Server 层逻辑日志，负责主从复制和归档。
### 第 2 层｜为什么需要 redo log？直接刷数据页不行吗？
**答**：数据页刷盘是随机 IO，量大且慢；redo 是顺序写，事务提交只写 redo 就返回，脏页异步刷。崩溃后用 redo 重放即可恢复，这就是 WAL。
### 第 3 层｜redo log 为什么是环形写？写满了怎么办？
**答**：redo 是固定大小的循环文件，用 write pos 和 checkpoint pos 管理。写满时不能直接覆盖未刷盘的日志，必须推进 checkpoint（把对应脏页刷盘），刷盘跟不上时写入会阻塞——所以 redo 太小会导致"日志写满卡住业务"。
### 第 4 层｜LSN 是什么？为什么数据页头里也要存 LSN？
**答**：LSN 是单调递增的日志字节偏移，表示"日志写到哪"。数据页头里的 page LSN 记录该页最后一次修改对应的 LSN；崩溃恢复重放时比较 redo 的 LSN 与 page LSN，已经包含的修改跳过，保证重放幂等。
### 第 5 层｜`innodb_flush_log_at_trx_commit` 三档怎么选？
**答**：1 最安全（每次提交 fsync，不丢），默认也是 1；2 提交时 write 到 OS cache、每秒 fsync，MySQL 崩溃不丢但机器断电丢约 1 秒；0 每秒刷，性能最好但崩溃丢约 1 秒。金融/订单选 1，日志类可 2，追求吞吐可 0。
### 第 6 层｜为什么需要两阶段提交？不用会怎样？
**答**：redo 和 binlog 是两个独立的日志系统，各写各的会出现"一边有一边没有"：redo 提交但 binlog 没写，主库有从库没有；binlog 写了但 redo 没提交，从库有主库回滚。两阶段提交用 prepare/commit 把两者绑定，崩溃恢复时以 binlog 是否完整作为裁决依据。
### 第 7 层｜崩溃恢复的两条规则具体是什么？
**答**：重放 redo 后遇到 prepare 事务：binlog 里存在完整事务 → 提交；binlog 不完整或不存在 → 用 undo 回滚。判断依据是 XID，redo 里的 XID 与 binlog 事件里的 XID 对应。
### 第 8 层｜binlog 三种格式的区别？线上为什么默认 ROW？
**答**：STATEMENT 记 SQL，日志小但非确定函数会导致主从不一致；ROW 记每行前后镜像，最准确、可回放，但批量更新日志放大；MIXED 自动切换。8.0 默认 ROW 是因为一致性优先，且 CDC/Canal 只支持 ROW。
### 第 9 层｜`sync_binlog` 怎么配？组提交优化了什么？
**答**：1 每次提交 fsync，最安全；0 交给 OS 可能丢；N 每 N 次刷。组提交把多个事务的 binlog flush/sync/commit 合并，一次 fsync 覆盖一批事务，所以 `sync_binlog=1` 也能有不错的吞吐。
### 第 10 层｜主从复制流程？半同步比异步强在哪？
**答**：从库 IO 线程拉取主库 binlog 写 relay log，SQL 线程重放。异步复制主库提交即返回，宕机可能丢；半同步要等至少一个从库 ACK 再返回，AFTER_SYNC 模式下能避免"客户端已确认但数据丢失"。但半同步仍不是强一致，超时会退化为异步。
### 第 11 层｜undo log 和 MVCC 是什么关系？
**答**：undo 记录旧版本，`DB_ROLL_PTR` 把版本串成链，ReadView 判断可见性时沿链找旧版本。update undo 在提交后要等 purge 确认没有快照需要它才能删，所以长事务会卡住 undo 回收（详见 02 文件）。
### 第 12 层（终局）｜这些逻辑在源码里的入口？
**答**：恢复：`log0recv.cc` 的 `recv_recovery_from_checkpoint()` 重放 redo，`trx0recv.cc`/`ha_recover` 处理 prepare 事务并裁决；两阶段提交：`trx0trx.cc` 的 `trx_prepare()`/`trx_commit()`；组提交：`binlog.cc` 的 `MYSQL_BIN_LOG::ordered_commit()` 依次执行 flush/sync/commit 三个阶段。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| redo log | InnoDB 物理日志 | 崩溃恢复、WAL 顺序写 | 环形结构、写满怎么办 |
| undo log | InnoDB 逻辑日志（旧值） | 回滚 + MVCC | 两类 undo、purge |
| binlog | Server 层逻辑日志 | 主从复制、归档、CDC | 三种格式、行镜像 |
| WAL | 先写日志再刷数据页 | 随机写变顺序写 | 与刷脏页的关系 |
| LSN | 日志序列号（字节偏移） | 定位、幂等重放 | page LSN 的作用 |
| checkpoint | 已持久化的日志位置 | 控制 redo 可覆盖范围 | 写满为何阻塞 |
| XID | 事务 ID（redo/binlog 都有） | 崩溃恢复时关联两者 | 两阶段提交的裁决依据 |
| 2PC | 两阶段提交（prepare/commit） | 保证 redo 与 binlog 一致 | 两条恢复规则 |
| `sync_binlog` | binlog 刷盘策略 | 数据安全与吞吐折中 | 双 1 配置 |
| relay log | 从库中继日志 | 复制解耦 IO 与 SQL 线程 | 复制流程 |
| GTID | 全局事务 ID | 简化主从切换/重搭 | 与 file+position 区别 |
| 半同步复制 | 等从库 ACK 再返回 | 降低丢数据风险 | AFTER_COMMIT vs AFTER_SYNC |

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「binlog 是 InnoDB 的日志」 | binlog 在 Server 层，任何存储引擎都能用 |
| 「redo log 是逻辑日志」 | redo 是物理日志（页 + 字节级修改），undo 才是逻辑日志 |
| 「redo 写满就覆盖最旧的日志」 | 未刷盘的部分不能覆盖，写满会推进 checkpoint，推不动就阻塞 |
| 「两阶段提交是分布式事务的 2PC」 | 这里指 redo 与 binlog 的一致性提交，机制类似但对象不同 |
| 「有了 binlog 就不需要 redo」 | binlog 是逻辑日志、只能重放 SQL/行事件，崩溃恢复要靠 redo 的物理重放 |
| 「半同步就是强一致」 | 超时会退化成异步，且只保证至少一个从库收到 |
| 「`innodb_flush_log_at_trx_commit=2` 一定不丢」 | MySQL 进程崩溃不丢，操作系统/断电会丢约 1 秒 |
