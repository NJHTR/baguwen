# 锁机制与死锁（Lock & Deadlock）

> 面试权重：5/5　｜　追问深度：**L5（InnoDB 锁子系统与死锁检测源码）**
> 一句话定位：MySQL 的锁不是"锁行"，而是"锁索引记录"。所有「为什么没走索引就锁表」「间隙锁为什么能防幻读」「死锁谁回滚」的追问，最终都落在 next-key lock + 意向锁 + wait-for graph 上。

**本文件用法**：从 L1 往下读，每读完一层，合上书自问自答。**停在答不出的那一层，就是你的真实水平线。**

## L1 一句话答案（10 秒能说出口）

InnoDB 的行锁加在**索引记录**上，默认是 RR 下的 next-key lock（记录锁 + 间隙锁），用来防幻读；如果 WHERE 没用到索引，就会扫描并锁住所有记录和间隙，表现为"锁表"。死锁是多个事务互相持有对方需要的锁形成环，InnoDB 用 wait-for graph 检测，回滚"undo 量最小"的事务，报 1213。

## L2 原理层：锁的类型、加锁规则、死锁条件

### 2.1 锁的层级

| 层级 | 锁 | 说明 |
|---|---|---|
| 全局 | FTWRL（`FLUSH TABLES WITH READ LOCK`） | 全库只读，备份用，会阻塞写 |
| 表级 | 表锁（`LOCK TABLES`）、MDL 元数据锁 | DDL 与 DML 冲突，长事务占 MDL 会堵住 DDL 和后续查询 |
| 行级 | 记录锁 / 间隙锁 / next-key / 插入意向锁 | InnoDB 独有，加在索引记录上 |

### 2.2 行锁四件套

| 锁 | 英文 | 锁什么 | 作用 |
|---|---|---|---|
| 记录锁 | Record Lock | 某条索引记录 | 锁住这一行 |
| 间隙锁 | Gap Lock | 两条记录之间的间隙（开区间） | 阻止插入，防幻读 |
| 临键锁 | Next-Key Lock | 间隙 + 右侧记录，左开右闭 `(prev, cur]` | RR 默认加锁单位 |
| 插入意向锁 | Insert Intention Lock | 插入位置所在的间隙 | 插入前先声明，多个插入意向锁**互相兼容**，但与 gap lock 冲突 |

**意向锁 IS/IX**：表级锁。事务准备给表中某些行加 S/X 锁时，先给表加 IS/IX，这样别的表锁请求不用逐行检查就能判断兼容性。兼容矩阵：IS 与 IS/IX 兼容，IX 与 IS/IX 兼容；表级 S/X 与 IS/IX 冲突。

### 2.3 加锁规则（背下来，面试现场推演）

1. 加锁的基本单位是 **next-key lock**，范围是**前开后闭**。
2. 查找过程中**访问到的对象**才加锁（没访问到的不加）。
3. 唯一索引**等值命中**：next-key lock 退化为**记录锁**。
4. 非唯一索引等值查询：命中记录的 next-key 锁住；再向右遍历，**最后一个不满足条件的值退化为间隙锁**。
5. 唯一索引**范围查询**：会访问到第一个不满足条件的值为止（多锁一个）。
6. 无索引 / 索引失效：扫描全表记录并加 next-key → 近似锁全表。

### 2.4 RC 和 RR 的锁差异

- **RC 基本没有间隙锁**（只有外键检查、唯一性检查时例外），所以 RC 下当前读会幻读，但锁范围小、冲突少、死锁概率低。
- **RR 有间隙锁**，能防当前读的幻读，代价是锁范围大、容易死锁。
- 这就是"为什么互联网公司常用 RC"的核心原因。

### 2.5 死锁的四个必要条件 + InnoDB 的处理

四个条件：互斥、请求并保持、不可剥夺、循环等待。
InnoDB 的处理：

```
事务 A 持有 lock1，请求 lock2（被 B 持有）→ A 进入等待队列
事务 B 持有 lock2，请求 lock1（被 A 持有）→ B 进入等待队列
innodb_deadlock_detect=ON：定期用 wait-for graph 做 DFS 找环
找到环 → 选「undo 记录数最少」的事务回滚 → 报 ERROR 1213 (40001)
innodb_deadlock_detect=OFF：靠 innodb_lock_wait_timeout（默认 50s）超时
```

**注意**：死锁检测本身有成本（O(n) 级），高并发热点行下 `innodb_deadlock_detect=ON` 可能 CPU 飙高，这也是"热点行更新"要排队/拆分的理由。

## L3 底层层：锁在内存里长什么样

### 3.1 锁结构 `lock_t`

```
lock_sys_t（全局锁系统）
├── 按「表/页」组织的锁哈希表
└── lock_t {
      lock_mode      // S / X / IS / IX / GAP / REC_NOT_GAP ...
      lock_type      // 表锁 or 行锁
      lock_table_id
      lock_index
      lock_rec       // 页内记录号（heap_no）
      lock_data      // 锁住的索引键值
      bitmap         // 位图：这一页里哪些 heap_no 被这个锁覆盖
    }
```

- **行锁本质是"页内位图"**：一个锁对象可以一次锁住同一页的多条记录（比如全表扫描时）。
- **锁加在索引上**：`UPDATE t SET ... WHERE name='x'` 若 name 无索引，InnoDB 扫描聚簇索引，给访问到的每条记录加 next-key lock，效果接近锁表。
- **锁的兼容性**：纯 gap lock 之间**互相兼容**（两个事务可以同时锁同一个间隙），但插入意向锁与 gap lock 冲突；next-key lock 的 record 部分与 X 锁冲突、gap 部分不冲突。

### 3.2 MDL：比行锁更容易出事的锁

- Server 层为每个表维护 MDL：DML 请求 MDL 读锁，DDL 请求 MDL 写锁。
- 长事务（哪怕只是 `BEGIN` 后没提交的 `SELECT`）持有 MDL 读锁 → DDL 被阻塞 → **后续所有查询都排在这个 DDL 后面**（因为 MDL 请求会排队），表现为整张表"不可用"。
- 线上事故排查顺序：`SHOW PROCESSLIST` 看到大量 `Waiting for table metadata lock` → 查 `information_schema.innodb_trx` 找到长事务 → kill。

### 3.3 死锁检测源码路径

- `lock0lock.cc`：`lock_rec_lock()` 尝试加锁；`lock_rec_has_to_wait()` 判断是否需要等待；需要等待时 `lock_add_to_waiting()` 入队。
- 等待时触发 `Deadlock::check_and_resolve()`（`lock0lock.cc` 中的 `Deadlock` 类），`lock_deadlock_recursive()` 沿等待边 DFS 找环；找到环后比较两个事务的 `undo_n_recs`，回滚较小的那个。
- 回滚的牺牲者会收到 `ER_LOCK_DEADLOCK`（1213），应用层应捕获并**重试**（不是当成业务错误）。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**

### 第 1 层｜MySQL 有哪些锁？
**答**：按粒度分全局锁、表锁（含 MDL）、行锁；行锁分记录锁、间隙锁、next-key lock、插入意向锁，另外有意向锁 IS/IX 用于表级兼容判断。按模式分共享锁 S 和排他锁 X。

### 第 2 层｜为什么 UPDATE 没走索引会锁表？
**答**：行锁加在索引记录上。没有可用索引时，InnoDB 只能全表扫描聚簇索引，给扫描到的每条记录加 next-key lock（以及间隙锁），等于把所有行都锁住，其他事务的写基本都被阻塞。

### 第 3 层｜间隙锁是干什么的？RC 为什么没有？
**答**：间隙锁锁住两条记录之间的"空隙"，阻止其他事务插入，从而防止当前读的幻读。RC 隔离级别下不需要防幻读，所以基本不加间隙锁，锁范围小、并发高，代价是 RC 下当前读会幻读。

### 第 4 层｜能推演一下 `WHERE id = 5 FOR UPDATE`（id 唯一索引，5 不存在）加什么锁吗？
**答**：唯一索引等值查询但值不存在 → 定位到第一个大于 5 的记录，next-key lock 退化为**间隙锁**，锁住 `(4, 6)` 这个区间（4/6 是相邻索引值），作用是阻止别人插入 id=5。

### 第 5 层｜非唯一索引等值查询加什么锁？
**答**：假设 `idx_user (user_id)` 有 10 的记录两条：命中记录的 next-key lock 锁住；向右遍历到第一个不满足条件的记录，next-key 退化为间隙锁。也就是"命中记录的前后间隙都会被锁"，所以两个事务同时给不同 user_id 插入也可能互相阻塞。

### 第 6 层｜插入意向锁是什么？和间隙锁什么关系？
**答**：插入前，事务在目标间隙上加插入意向锁（一种特殊的 gap lock）。多个插入意向锁之间互不冲突（所以并发插入不同位置没问题），但插入意向锁与间隙锁冲突——这正是间隙锁防幻读的机制：别人锁了间隙，你就插不进去。

### 第 7 层｜死锁怎么产生的？举一个真实场景。
**答**：两个事务以相反顺序更新两行。A 先更新 id=1 再更新 id=2，B 先更新 id=2 再更新 id=1，各持有对方要的锁 → 形成等待环。电商里"扣库存 + 扣余额"两个事务顺序不一致是高发场景，按固定顺序（先库存后余额）能避免。

### 第 8 层｜死锁怎么检测、怎么处理？谁被回滚？
**答**：`innodb_deadlock_detect=ON`（默认）时，InnoDB 用 wait-for graph 检测，发现环就选 undo 记录数最少的事务回滚，报 1213。关闭检测则靠 `innodb_lock_wait_timeout`（默认 50s）超时，高并发下会雪崩，不建议关。

### 第 9 层｜线上出现死锁怎么排查？
**答**：① `SHOW ENGINE INNODB STATUS\G` 的 `LATEST DETECTED DEADLOCK` 段，能看到两个事务的 SQL、持有的锁、等待的锁；② 开 `innodb_print_all_deadlocks=ON` 把每次死锁写 error log；③ 8.0 查 `performance_schema.data_locks` / `data_lock_waits` 看实时锁等待；④ 应用层捕获 1213 做有限重试。

### 第 10 层｜怎么预防死锁？
**答**：固定加锁顺序、事务尽量短小、WHERE 走精确索引（缩小锁范围）、减少事务内的用户交互/RPC、热点行用排队/分片/乐观锁、必要时间隙锁降级（RC）或调低隔离级别。没有银弹，主要是"减少锁范围 + 固定顺序"。

### 第 11 层｜乐观锁和悲观锁，你的防重复提交用哪个？
**答**：悲观锁用 `SELECT ... FOR UPDATE` 或分布式锁，适合冲突高的场景；乐观锁用 `version` 字段（`UPDATE ... WHERE id=? AND version=?`），冲突低时性能好。防重复提交我一般三层：前端按钮防抖 + 业务唯一索引（最可靠）+ Redis SETNX 短锁（挡住并发量），数据库唯一索引是最后一道防线。

### 第 12 层（终局）｜InnoDB 源码里加锁和死锁检测怎么走？
**答**：`row_search_mvcc()` 定位记录后调 `lock_rec_lock()`（`lock0lock.cc`）→ `lock_rec_has_to_wait()` 判断冲突 → 冲突则 `lock_add_to_waiting()` 挂入等待队列，并在等待前触发 `Deadlock::check_and_resolve()`；`lock_deadlock_recursive()` 沿 `lock->trx->lock.wait_lock` 等边 DFS 找环，找到后用 `trx_rollback_for_mysql()` 回滚牺牲者并唤醒其他等待者。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 记录锁 | 锁一条索引记录 | 精确到行 | 为什么说"锁索引不锁行" |
| 间隙锁 Gap | 锁两条记录之间的开区间 | 阻止插入、防幻读 | 纯 gap 锁之间兼容 |
| 临键锁 Next-Key | gap + 右侧记录，左开右闭 | RR 的默认加锁单位 | 何时退化成记录锁/间隙锁 |
| 插入意向锁 | 插入前的特殊 gap 锁 | 并发插入互不冲突 | 与 gap lock 冲突 |
| 意向锁 IS/IX | 表级锁，标记行锁意图 | 让表锁判断免于逐行扫描 | 兼容矩阵 |
| MDL | 元数据锁（Server 层） | 保护表结构 | 长事务 + DDL 事故 |
| 共享锁 S / 排他锁 X | 读锁 / 写锁 | 读写并发控制 | `LOCK IN SHARE MODE`（8.0 `FOR SHARE`） |
| 死锁 | 事务互相等待形成环 | 并发加锁的必然产物 | 四个必要条件 |
| wait-for graph | 等待图，边 = 等待关系 | 检测环 | DFS 成本 |
| 牺牲者 | 被回滚的事务 | 打破死锁 | 按 undo 量选最小 |
| `innodb_lock_wait_timeout` | 锁等待超时 | 检测关闭时的兜底 | 默认 50s，别调太小 |

## 代码验证（两个 mysql 客户端 + Java 片段）

```sql
-- ===== 准备 =====
CREATE TABLE t_lock (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,
  KEY idx_user (user_id)
) ENGINE=InnoDB;
INSERT INTO t_lock (user_id, status) VALUES (10,0),(20,0),(30,0);

-- ===== 实验 1：间隙锁阻止插入（RR）=====
-- 会话 A
BEGIN; UPDATE t_lock SET status = 1 WHERE user_id = 25;   -- 25 不存在 → 锁 (20,30) 间隙
-- 会话 B
INSERT INTO t_lock (user_id, status) VALUES (25, 0);      -- 阻塞（等待间隙锁）
-- 会话 A 提交后 B 才会成功；把隔离级别改成 RC 重做，B 不会被阻塞

-- ===== 实验 2：唯一索引等值命中 → 只锁记录 =====
-- 会话 A
BEGIN; SELECT * FROM t_lock WHERE id = 1 FOR UPDATE;
-- 会话 B
UPDATE t_lock SET status = 9 WHERE id = 2;                -- 不阻塞（没锁这条）
UPDATE t_lock SET status = 9 WHERE id = 1;                -- 阻塞（记录锁）

-- ===== 实验 3：复现死锁 =====
-- 会话 A
BEGIN; UPDATE t_lock SET status = 1 WHERE id = 1;
-- 会话 B
BEGIN; UPDATE t_lock SET status = 2 WHERE id = 2;
-- 会话 A
UPDATE t_lock SET status = 3 WHERE id = 2;                -- 等待 B
-- 会话 B
UPDATE t_lock SET status = 4 WHERE id = 1;                -- ERROR 1213 (40001): Deadlock found
SHOW ENGINE INNODB STATUS\G                               -- 看 LATEST DETECTED DEADLOCK

-- ===== 实验 4：实时锁等待（8.0）=====
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

-- ===== 实验 5：MDL 事故复现 =====
-- 会话 A
BEGIN; SELECT * FROM t_lock LIMIT 1;                      -- 不提交，持有 MDL 读锁
-- 会话 B
ALTER TABLE t_lock ADD COLUMN remark VARCHAR(64);         -- 等待 MDL 写锁
-- 会话 C
SELECT * FROM t_lock WHERE id = 1;                        -- 也被堵住（MDL 排队）
```

```java
// 乐观锁：防并发覆盖 + 防重复提交的兜底，捕获 1213 后有限重试
@Transactional
public boolean deduct(Long id, int version) {
    int rows = jdbcTemplate.update(
        "UPDATE t_lock SET status = status + 1, version = version + 1 WHERE id = ? AND version = ?",
        id, version);
    return rows == 1;
}

// 死锁是"可重试异常"，不要包成业务失败
public void deductWithRetry(Long id, int version) {
    for (int i = 0; i < 3; i++) {
        try { if (deduct(id, version)) return; }
        catch (DeadlockLoserDataAccessException e) { /* 随机退避后重试 */ }
    }
    throw new IllegalStateException("deduct failed after retry");
}
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「InnoDB 锁的是行」 | 锁的是索引记录；没索引就锁全表 |
| 「RC 也有间隙锁」 | RC 基本没有间隙锁（外键/唯一性检查例外） |
| 「间隙锁之间会互相阻塞」 | 纯 gap 锁互相兼容，是插入意向锁与 gap 冲突 |
| 「死锁回滚先发起的事务」 | 回滚 undo 记录数最少的事务 |
| 「关掉死锁检测更快」 | 高并发下靠超时会雪崩，不建议关 |
| 「next-key lock 永远是记录锁+间隙锁」 | 唯一索引等值命中会退化成记录锁 |
| 「MDL 和行锁是一回事」 | MDL 在 Server 层管表结构，行锁在引擎层管数据 |
| 「`FOR UPDATE` 不加间隙锁」 | 会加 next-key lock（RR），除非唯一索引等值命中 |
