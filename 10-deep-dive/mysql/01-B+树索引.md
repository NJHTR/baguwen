# B+ 树索引与 InnoDB 页（B+ Tree Index）

> 面试权重：5/5　｜　追问深度：**L5（InnoDB 引擎页结构与源码）**
> 一句话定位：MySQL 的"快"到底从哪来。所有「为什么加了索引就快」「为什么这条 SQL 没走索引」「回表是什么」的追问，终点都在 16KB 页 + B+ 树 + 聚簇索引这三个词上。

## L1 一句话答案（10 秒能说出口）

InnoDB 用 B+ 树组织索引：非叶子节点只存「键 + 子页号」，叶子节点按主键顺序用双向链表相连；聚簇索引的叶子直接存整行数据，二级索引的叶子只存「索引列 + 主键」，所以查非索引列要再回聚簇索引查一次（回表）。一次索引查询的磁盘 IO 次数 = B+ 树高度，通常是 3 次。

## L2 原理层：为什么是 B+ 树、一次查询走哪几步

### 2.1 为什么不用二叉树 / 红黑树 / 哈希 / B 树

| 结构 | 致命问题 | 结论 |
|---|---|---|
| 二叉搜索树 / 红黑树 | 每个节点只存 1 个键，树高 ~log₂N，千万行要 20+ 层，每层一次磁盘 IO | 磁盘 IO 太多 |
| 哈希表 | 只支持等值查询，不支持范围、排序、最左前缀 | 只能做 MEMORY 引擎/自适应哈希的补充 |
| B 树 | 非叶子也存整行 → 一个页能放的键少 → 树更高；范围查询还要中序遍历回溯 | 页利用率低 |
| **B+ 树** | 非叶子只存键+页号，扇出极大（一个 16KB 页存上千个键）；叶子有序链表，范围查询只扫叶子 | 磁盘友好 + 范围友好 |

### 2.2 一次 `WHERE id = 100` 的完整路径

```
① 从根页开始（根页常驻 Buffer Pool，page no 记录在数据字典里）
② 页内二分（Page Directory 稀疏槽位）→ 定位到下一层的子页号
③ 读到子页 → 再二分 → 直到叶子页（树的层数 = 磁盘 IO 次数）
④ 叶子页内二分定位到记录，返回整行（聚簇索引）
```

### 2.3 聚簇索引 vs 二级索引 vs 回表

| 对比 | 聚簇索引（主键索引） | 二级索引（辅助索引） |
|---|---|---|
| 叶子存什么 | **整行数据**（所有列） | 索引列 + **主键值** |
| 一张表有几个 | 1 个（没有主键时用唯一非空索引，再没有就隐式 `DB_ROW_ID`） | N 个 |
| 查非索引列 | 直接拿到 | 要拿主键**回表**再查聚簇索引（随机 IO） |

- **回表代价**：二级索引一次查找 + 聚簇索引一次查找，且主键无序 → 随机 IO。
- **覆盖索引**：`SELECT` 的列全在索引里（含主键），不用回表，`EXPLAIN` 显示 `Using index`。
- **select * 为什么背锅**：几乎必然回表，且把大字段（text/blob）也捞出来。

### 2.4 联合索引的物理排列与最左前缀

`KEY idx_abc (a, b, c)` 在 B+ 树里按 `a → b → c` 依次排序（a 相同才按 b 排）。

- `WHERE a=? AND b=? AND c=?` 正确：全用上
- `WHERE a=?` 正确：用 a
- `WHERE b=?` 错误：用不上（叶子按 a 有序，b 在整个索引里不是全局有序）
- `WHERE a=? AND c=?`：a 能用，c 不能定位，但 5.6+ 的 **ICP** 可以在索引层用 c 过滤掉一部分再回表
- `WHERE a>? AND b=?`：a 用范围，范围之后的 b 无法再用于定位（但可以 ICP 过滤）

### 2.5 索引下推 ICP（Index Condition Pushdown）

没有 ICP：联合索引 `(name, age)` 查 `name like '张%' and age = 20`，引擎只能按 name 回表，Server 层再过滤 age。
有 ICP：把 `age = 20` 下推到引擎，在**索引上**先过滤，再回表。`EXPLAIN` 的 `Extra: Using index condition`。
**注意**：ICP 只能用于二级索引，不能用于聚簇索引；对主键范围查询无效。

## L3 底层层：InnoDB 16KB 页长什么样

### 3.1 页的物理布局（`innodb_page_size` 默认 16384B）

```
┌──────────────────────── File Header (38B) ────────────────────────┐
│ FIL_PAGE_SPACE / OFFSET(页号) / PREV / NEXT / LSN / TYPE ...      │
├──────────────────────── Page Header (56B) ────────────────────────┤
│ PAGE_N_DIR_SLOTS / HEAP_TOP / N_HEAP / FREE / GARBAGE /           │
│ LAST_INSERT / PAGE_LEVEL（树高）/ INDEX_ID / 段指针 ...            │
├──────────── Infimum + Supremum（2 条伪记录，26B）─────────────────┤
├──────────────────── User Records（行记录，变长）─────────────────┤
├──────────────────── Free Space（空闲空间）───────────────────────┤
├──────────────── Page Directory（稀疏槽位，每 6 条记录 1 个槽，2B/槽）┤
├──────────────────── File Trailer (8B) ────────────────────────────┤
│ 旧校验和（4B，与 File Header 的 checksum 对应）+ LSN 低 32 位         │
└───────────────────────────────────────────────────────────────────┘
```

- **File Trailer 的用途**：页面刷盘中途断电时，用尾部 checksum 与头部比对，不一致说明页损坏。
- **Page Header 的 `PAGE_LEVEL`**：记录当前页在 B+ 树中的层级，叶子层为 0，根页 level 最大——所以树高可以现场查出来。
- **Page Directory 是稀疏目录**：不是每条记录一个槽，而是每 6 条记录一个槽、指向组内最大记录；页内查找 = 目录二分 + 组内 `next_record` 顺序扫描（最多 6 条）。
- **行记录（COMPACT/DYNAMIC）额外信息**：变长字段长度列表 + NULL 位图 + 5B 记录头（`delete_mask/min_rec_mask/n_owned/heap_no/record_type/next_record`）+ `DB_TRX_ID(6B)` + `DB_ROLL_PTR(7B)` + 主键/`DB_ROW_ID`。

### 3.2 三层 B+ 树能存多少行？自己算一遍

假设：页 16KB，主键 `bigint` 8B，页号 4B，非叶子一条记录约 `8 + 4 + 5(头) ≈ 17B`（按 14B 估算也常见）：

- 非叶子页可放：`16KB / 14B ≈ 1170` 个键（根页固定常驻内存，不算 IO）
- 三层 = 根 + 中间 + 叶子：`1170 × 1170 ≈ 136.9 万` 个叶子页
- 若每行 1KB → 每叶子页 16 行 → `136.9 万 × 16 ≈ 2190 万行`
- 若每行 200B → 每叶子页约 80 行 → **约 1.1 亿行**

**结论：B+ 树高度通常 2-4 层，千万级表查一行只要 3-4 次 IO**——这就是索引快、也是"为什么不用红黑树"的最好答案。

### 3.3 页分裂、页合并与顺序主键

- **页分裂**：往已满的页插入、且插入位置在中间 → 新开一页并把一半记录挪过去，同时更新父页指针。随机主键（UUID）会造成大量分裂 + 空间碎片。
- **页合并**：删除导致页利用率过低（合并阈值默认 50%）时与相邻页合并。
- 所以**自增主键是性能优化**：永远在最右侧追加，不分裂、页利用率接近 100%。
- **Change Buffer**：非唯一二级索引的写操作先缓存在内存，减少随机读页；唯一索引必须读页校验唯一性，用不上 change buffer（追问点）。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**

### 第 1 层｜MySQL 索引为什么用 B+ 树？
**答**：相比二叉树/红黑树，B+ 树一个页放上千个键，扇出大、树高只有 3-4 层，磁盘 IO 少；相比 B 树，非叶子不存数据、页利用率高、叶子还有序链表，范围查询和排序友好；相比哈希，B+ 树支持范围、排序和最左前缀。

### 第 2 层｜聚簇索引和二级索引有什么区别？
**答**：InnoDB 一定有一个聚簇索引，叶子存整行；二级索引叶子只存索引列 + 主键。查二级索引没覆盖的列必须拿主键回表，所以 `select *` 最贵，`select 主键/索引列` 可能走覆盖索引。

### 第 3 层｜回表是什么？怎么避免？
**答**：二级索引定位到主键后，再去聚簇索引查整行，多一次随机 IO 就是回表。避免方式：把查询列放进联合索引（覆盖索引）、`select` 只查索引列、用主键查询、减少 `select *`。

### 第 4 层｜什么是最左前缀？为什么 `(a,b,c)` 不能只查 b？
**答**：联合索引在 B+ 树里先按 a 排、a 相同按 b 排、b 相同按 c 排。只给 b 时，整个索引里 b 不是全局有序的，无法二分定位。这就是最左前缀。例外是 5.6 的 ICP：a 定位后可以在索引层用 b 过滤，但 b 不能用来减少扫描范围。

### 第 5 层｜为什么 `WHERE a > 1 AND b = 2` 里 b 用不上索引？
**答**：范围条件 `a > 1` 之后，a 已经无法精确匹配，b 在这个范围内虽然有序，但索引已经无法二分定位到 b；只能扫描所有 a>1 的索引项再 ICP 过滤 b。所以**范围条件之后的列会失效**（这是面试高频陷阱，顺序不能反）。

### 第 6 层｜索引失效的真实原因有哪些？
**答**：列上做函数/运算（`where id+1=2`）、隐式类型转换（`varchar 列 = 数字` 会把列转数字）、前导模糊 `like '%x'`、`OR` 里有列没索引、字符集不一致的 join（隐式转换）、区分度极低（优化器判断全表更快）、统计信息过期。注意 `int 列 = '123'` 是常量转换，**仍然走索引**。

### 第 7 层｜为什么字符串列和数字比较会失效，而数字列和字符串比较不会？
**答**：MySQL 比较时"字符串转数字"是隐式转换，把**列**转成数字相当于 `CAST(col AS ...)`，列上做了函数，索引失效；反之数字列与字符串比较时，是把**常量**转成数字，列本身没被动，索引有效。所以建表时字段类型和参数类型必须一致。

### 第 8 层｜索引下推 ICP 是什么？和覆盖索引什么关系？
**答**：ICP 是把 Server 层的 WHERE 条件下推到引擎层、在索引记录上先过滤，减少回表次数，`Extra: Using index condition`。覆盖索引是查询列全部被索引覆盖、完全不用回表，`Extra: Using index`。ICP 是"少回表"，覆盖索引是"不回表"。

### 第 9 层｜一个 16KB 页里到底有什么？
**答**：File Header 38B（页号、前后页、LSN、类型）、Page Header 56B（槽位数、堆顶、`PAGE_LEVEL`、INDEX_ID）、Infimum/Supremum 两条伪记录、User Records 行记录、Free Space、Page Directory 稀疏槽位、File Trailer 8B（checksum + LSN 低 32 位）。页内查找 = Page Directory 二分 + 组内最多 6 条顺序扫。

### 第 10 层｜为什么自增主键比 UUID 好？页分裂怎么发生的？
**答**：B+ 树按主键有序，自增主键永远追加在最右叶子，不触发页分裂；UUID 随机插入会打到中间满页，触发页分裂（挪一半记录、改父页指针），造成随机 IO、碎片和页利用率下降。页分裂还会短暂加锁。

### 第 11 层｜主键用 bigint 自增，为什么建表时还建议 `ORDER BY` 和 `WHERE` 只用索引列？
**答**：索引本身就是有序结构，`ORDER BY 索引列` 可以直接顺着叶子链表读，不需要 `Using filesort`；但一旦 `ORDER BY` 的列顺序/升降序和索引不一致，或者中间隔了别的列，就会退化成排序。这是执行计划优化（见 04 文件）的前置知识。

### 第 12 层（终局）｜InnoDB 源码里一次索引查找怎么走？
**答**：`btr_cur_search_to_nth_level()`（`btr0cur.cc`）负责在 B+ 树里逐层下降：每层调用 `page_cur_search_with_match()`（`page0cur.cc`），它先用 Page Directory 二分缩小到组，再沿 `next_record` 顺序扫组内记录（最多 6 条）。叶子层命中后，聚簇索引直接返回行，二级索引拿主键再走一次同样的流程（`row_search_mvcc`），这就是回表的源码级真相。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 聚簇索引 | 叶子存整行的 B+ 树，主键组织 | 数据即索引，一次查找拿到整行 | 无主键时用谁？`DB_ROW_ID` |
| 二级索引 | 叶子存索引列 + 主键 | 按非主键列加速查询 | 为什么叶子不存行地址？行会移动 |
| 回表 | 拿二级索引的主键回聚簇索引查 | 补充非索引列 | 何时可以避免（覆盖索引） |
| 覆盖索引 | 查询列全在索引中，`Using index` | 免回表、少 IO | 判断是否覆盖的规则 |
| 最左前缀 | 联合索引按定义顺序逐列有序 | 索引只能从头开始定位 | 范围条件后为何失效 |
| ICP 索引下推 | 把 WHERE 下推到索引层过滤 | 减少回表次数 | 与覆盖索引的区别、版本要求 |
| 页分裂 | 满页中间插入时拆页 | 维持 B+ 树有序 | 随机主键为何差、影响写性能 |
| 页合并 | 删除后利用率低时合并页 | 回收空间、防碎片 | 合并阈值、何时发生 |
| Page Directory | 页内稀疏槽位目录 | 页内快速二分 | 为什么是稀疏的（每 6 条一个槽） |
| File Trailer | 页尾 8B checksum + LSN | 检测刷盘中途损坏 | 断电如何校验 |
| Change Buffer | 非唯一二级索引写缓冲 | 减少随机读页 | 唯一索引为何用不上 |
| 自适应哈希 AHI | 对热点页建哈希 | 进一步降低查找成本 | 为什么线上常建议关闭 |
| 基数 cardinality | 索引列不同值数量估计 | 优化器判断索引区分度 | 区分度低为何不选索引 |

## 代码验证（在 MySQL 8.0 从库/本地实例逐条跑，看 EXPLAIN 是否符合预期）

```sql
-- 1. 建表：主键 + 联合索引 + 单列索引
CREATE TABLE t_order (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,
  amount DECIMAL(10,2) NOT NULL,
  created_at DATETIME NOT NULL,
  remark VARCHAR(255) DEFAULT NULL,
  KEY idx_user_status (user_id, status),
  KEY idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO t_order (user_id, status, amount, created_at) VALUES
(1001,0,99.00,'2026-01-01 10:00:00'),(1001,1,199.00,'2026-01-02 10:00:00'),
(1002,0,9.90,'2026-01-03 10:00:00');

-- 2. 覆盖索引：只查索引列 → key=idx_user_status, Extra=Using index
EXPLAIN SELECT user_id, status FROM t_order WHERE user_id = 1001;

-- 3. 需要回表：查 amount → type=ref, Extra=Using where（无 Using index）
EXPLAIN SELECT amount FROM t_order WHERE user_id = 1001;

-- 4. 联合索引两列都用上 → key_len = 8 + 1 = 9
EXPLAIN SELECT * FROM t_order WHERE user_id = 1001 AND status = 1;

-- 5. 违反最左前缀：只查 status → type=ALL, key=NULL（全表扫）
EXPLAIN SELECT * FROM t_order WHERE status = 1;

-- 6. 列上做运算：索引失效 → type=ALL
EXPLAIN SELECT * FROM t_order WHERE user_id + 1 = 1002;

-- 7. 隐式转换的真实案例：user_id 是 BIGINT，传字符串常量仍走索引
EXPLAIN SELECT * FROM t_order WHERE user_id = '1001';

-- 8. 强制走索引做对比（线上排障常见手段，慎用）
EXPLAIN SELECT * FROM t_order FORCE INDEX (idx_user_status) WHERE status = 1;
```

**预期要点**：③ 的 `Extra` 有 `Using index`；④ 的 `key_len=9`；⑤ 出现 `type=ALL`；⑥ 出现 `type=ALL` 且 `key=NULL`。

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「B+ 树非叶子也存数据」 | 非叶子只存键+页号，叶子才存数据/主键 |
| 「加了索引就一定走」 | 优化器按成本选，区分度低/回表多可能不走 |
| 「二级索引叶子存行地址」 | 存的是主键值（行会移动，不能存物理地址） |
| 「`int` 列和字符串比较会失效」 | 常量转换，仍走索引；反过来 varchar 列才会失效 |
| 「范围条件之后的列完全没用」 | 不能定位，但可 ICP 过滤 |
| 「覆盖索引就是联合索引」 | 覆盖是"查询列被索引覆盖"，与索引列数无关 |
| 「一页 16KB 是因为磁盘块 4KB」 | InnoDB 固定页大小可配 4/8/16/32/64KB，默认 16KB 是读写放大与内存的折中 |
