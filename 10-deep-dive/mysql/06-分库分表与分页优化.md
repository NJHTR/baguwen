# 分库分表与分页优化（Sharding & Pagination）

> 面试权重：5/5　｜　追问深度：**L5（InnoDB 页结构与 ShardingSphere 引擎源码）**
> 一句话定位：单表撑不住时，"加索引"救不了，必须拆。拆的代价全在两点：**数据怎么路由**（分片键）和**跨库怎么查**（join、分页、聚合）。只背"分库分表"四个字，必然在这一层被连问穿。

**本文件用法**：从 L1 往下读，每读完一层，合上书自问自答。**停在答不出的那一层，就是你的真实水平线。**
[返回深度追问索引](../00-索引.md)

## L1 一句话答案（10 秒能说出口）

先优化再拆：索引、冷热分离、归档、读写分离都试过，单表逼近 2000 万行或写入打满，才考虑拆分。**垂直拆分**按业务/字段切库表，**水平拆分**按分片键（取模/范围/一致性哈希）切行。全局 ID 用雪花或号段，跨库 join 用冗余/广播表/内存 join/宽表，跨库分页用游标或二次查询，迁移用双写 + 影子表灰度。

## L2 原理层：拆不拆、怎么拆、拆完怎么查

### 2.1 先判断"该不该拆"

| 信号 | 典型表现 | 拆之前的优化 |
|---|---|---|
| 数据量 | 单表 2000 万~5000 万行，B+ 树 4 层 | 归档、冷热分离、分区表 |
| 写压力 | 单库写入 QPS / 连接数打满 | 读写分离、连接池、异步化、缓存 |
| 表宽 | text/blob 拖慢行 | 垂直拆分：大字段单独附表 |

**顺序不能反**：先 SQL 优化（04 文件）→ 索引优化（01 文件）→ 冷热分离/归档 → 最后才分库分表。顺带一句：如果从 PostgreSQL 迁到 MySQL，PG 没有聚簇索引、MVCC 实现也不同，分页与索引策略不能照搬。

### 2.2 垂直拆分 vs 水平拆分

| 对比 | 垂直拆分 | 水平拆分 |
|---|---|---|
| 切分对象 | 业务（库）或字段（表） | 行（按分片键） |
| 优点 | 业务解耦、单表变窄 | 单表数据量下降、写入可扩展 |
| 缺点 | 跨库 join、分布式事务 | 路由复杂、跨库查询/分页/事务、扩容成本 |
| 例子 | user/order/product 分库；大字段拆附表 | `order_0...order_15` 按 `user_id % 16` |

工程上一般**先垂直、再水平**：垂直解决耦合与宽表，水平解决单表行数。

### 2.3 分片键选择（决定 80% 的后续折磨）

三个标准：**高并发查询必须带它**、**数据分布均匀**、**业务上不变**。

| 业务 | 推荐分片键 | 理由 |
|---|---|---|
| C 端订单 | `user_id` | 查询基本都带用户维度 |
| B 端 SaaS | `tenant_id` | 租户隔离、天然可路由 |
| 订单号查询 | 订单号带 `user_id` 基因 | 两种查询都能定位 |
| 日志流水 | 时间范围 | 按时间归档、范围查询友好 |

选错的后果：大量查询不带分片键 → 广播全部库；数据倾斜 → 大客户打爆一个分片；扩容取模变化 → 几乎全量迁移。倾斜解法：大客户单独路由、加盐打散、订单号加基因、时间类按范围切。

### 2.4 全局 ID 五种方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| UUID | 无中心、简单 | 无序导致页分裂；36 字符占空间 |
| DB 自增步长 | 有序、简单 | 扩容改步长；强依赖 DB |
| 号段（Leaf-segment） | 批量取号、不依赖每请求查库 | 切段抖动、DB 挂了取不到新段 |
| 雪花 Snowflake | 趋势递增、本地生成、高吞吐 | 依赖时钟，回拨要处理 |
| Redis INCR | 简单、原子 | 依赖 Redis，多一次网络 RT |

雪花位分配：`1 符号 + 41 毫秒时间戳（约 69 年）+ 10 机器 ID（1024 台）+ 12 序列（4096/毫秒）`。时钟回拨：小回拨等待追平、大回拨抛异常告警、换备用 workerId（Leaf-snowflake 用 ZK 校验）。ID 趋势递增对 InnoDB 友好（顺序写、少页分裂），所以雪花比分表场景的 UUID 更合适。

### 2.5 跨库 join 的四种解法

| 方案 | 做法 | 适用 | 代价 |
|---|---|---|---|
| 字段冗余 | 订单表冗余用户昵称 | 读多写少、字段稳定 | 异步更新的一致性 |
| 广播表 | 字典表每库一份全量 | 小表、低频变更 | 同步机制 |
| 内存 join | 应用层分批查再拼装 | 结果集小 | 内存与多次 RT |
| 宽表/ES | 异步同步成宽表/ES | 报表、复杂检索 | 延迟与运维成本 |


### 2.6 跨库分页（面试高频）

问题：`LIMIT 100000, 10` 在每个分片都要扫 100010 行再内存归并，深分页拖垮内存与 RT。

| 方案 | 做法 | 适用 |
|---|---|---|
| 游标分页 | `WHERE id > last_id ORDER BY id LIMIT 10` | 最优，连续翻页 |
| 延迟关联 | 先按索引查主键再 join 回表 | 单库仍有效 |
| 二次查询 | 两轮查询绕过深偏移 | 必须跳页、按有序字段排 |

**二次查询三步**（n 个分片，偏移 offset，取 limit 条）：

```
① 每个分片 SELECT * FROM t ORDER BY id LIMIT offset/n, limit，取 n 份结果中最小的 id 记为 minId
② 每个分片再查 SELECT * FROM t WHERE id BETWEEN minId AND (该分片第一轮最大 id) ORDER BY id
③ 合并第二轮结果，按 id 排序，跳过 offset % n 条，取 limit 条
```

核心：第一轮只为定位边界 minId，第二轮从 minId 起按范围查，避免每个分片大偏移扫描。

### 2.7 扩容迁移：双写 + 影子表

```
① 建新库表（新分片规则）
② 双写：旧库为准，同步/异步写新库
③ 全量迁移历史数据（DataX），增量用 Canal 追平
④ 全量对账 + 抽样比对，差异回补
⑤ 影子表/影子读：读仍走旧库，新库结果做比对验证
⑥ 按用户/比例灰度切读，再切写；旧库保留只读做回滚
```


### 2.8 ShardingSphere 的路由与归并

```
SQL 解析（ANTLR）→ 路由（标准/广播/笛卡尔）→ 改写（表名/分页/聚合）
→ 多数据源执行 → 归并（流式/内存）
```

- 标准路由：带分片键，定位到单库单表；广播路由：不带分片键（字典表、DDL）；笛卡尔路由：多表 join 都不带分片键，尽量避免。
- 归并：流式归并（有序结果逐条比，适合 order by + limit）、内存归并（全拉回内存排序，深分页风险点）。

## L3 底层层：容量、雪花、ShardingSphere 引擎

### 3.1 单表容量与 B+ 树

2000 万的经验值来自三层 B+ 树：非叶子约 1170 键/页、叶子约 16 行/页（1KB 行）→ 约 2190 万行（推算见 01 文件）。超过后树高变 4 层，每次查询多一次磁盘 IO，DDL/备份/索引维护成本也随数据量线性上升。

### 3.2 雪花与号段的工程细节

- 雪花：时间戳保证趋势递增，机器 ID 保证多实例不重，序列解决同毫秒并发；位运算拼成一个 long，无网络开销。
- 号段（Leaf-segment）：表 `leaf_alloc(biz_tag, max_id, step, version)`，`UPDATE ... SET max_id = max_id + step WHERE biz_tag=? AND max_id=?` 用乐观锁取一段号；双 buffer 在当前段快用完时异步取下一段，避免取号阻塞在 DB。

### 3.3 ShardingSphere 源码入口

`SQLParserEngine`（ANTLR 语法树）→ `ShardingRule`（规则）→ `ShardingRouteEngine`（标准/广播/笛卡尔路由）→ `SQLRewriteEngine`（表名/分页改写）→ `ShardingExecuteEngine`（并发执行）→ `ResultMergeEngine`（`LimitDecoratorMergedResult` 分页归并、`AggregationMergeEngine` 聚合）。深分页内存问题的根源在归并层：内存归并要把各分片结果全拉回。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**
### 第 1 层｜什么时候需要分库分表？
**答**：单表 2000 万~5000 万、写入 QPS 打满单库、DDL/备份时间不可接受时。但先做索引优化、冷热分离、归档、读写分离，都不够再拆。
### 第 2 层｜垂直拆分和水平拆分有什么区别？
**答**：垂直按业务或字段切（用户库/订单库、大字段附表），解决耦合与宽表；水平按分片键切行（order_0~order_15），解决单表行数；一般先垂直再水平。
### 第 3 层｜分片键怎么选？选错会怎样？
**答**：选高并发查询必带、分布均匀、业务不变的字段，C 端用 user_id、SaaS 用 tenant_id。选错会导致查询不带分片键（全库广播）、数据倾斜、扩容几乎全量迁移。
### 第 4 层｜数据倾斜怎么解决？
**答**：大客户/大商户单独库表路由；加盐打散；订单号带分片键基因；时间类数据按范围而不是取模。核心是"让热点可分"。
### 第 5 层｜全局 ID 有哪几种？雪花为什么适合分库分表？
**答**：UUID、DB 自增步长、号段、雪花、Redis INCR。雪花本地生成、趋势递增（对 InnoDB 顺序写友好）、高吞吐，适合分片；但要处理时钟回拨和多实例机器 ID。
### 第 6 层｜跨库 join 怎么办？
**答**：优先字段冗余（读多写少），其次广播表（小字典表每库一份），再次应用层内存 join，复杂查询走宽表/ES。本质是把 join 从查询时前移到写入时或异步链路。
### 第 7 层｜跨库分页怎么实现？二次查询具体步骤？
**答**：游标分页最优。必须跳页时二次查询：第一轮各分片取 `offset/n` 定位边界得 minId；第二轮各分片查 `BETWEEN minId AND 第一轮最大 id`；第三轮合并排序取目标区段，避免每个分片扫大偏移。
### 第 8 层｜2 库扩到 4 库，怎么不停机迁移？
**答**：双写（旧库为准）+ 全量迁移 + binlog 增量追平 + 数据校验回补 + 影子表验证 + 按比例灰度切读 + 切写 + 旧库只读保留回滚。
### 第 9 层｜ShardingSphere 的 SQL 怎么执行？
**答**：解析（ANTLR）→ 路由（标准/广播/笛卡尔）→ 改写（表名、分页、聚合）→ 多数据源执行 → 归并（流式/内存）。深分页和聚合最容易被归并层拖垮。
### 第 10 层｜分表后事务、count、order by 怎么办？
**答**：事务：让同一业务数据落同分片，跨库用 Seata 或本地消息表最终一致。count：各分片相加或维护计数表。order by：流式归并。复杂聚合/报表走宽表或 ES，不在分片库硬算。
### 第 11 层（终局）｜这一层落到源码/结构是什么？
**答**：容量侧看 InnoDB B+ 树页结构与页分裂（`btr0cur.cc`）；路由侧看 ShardingSphere 的 `SQLParserEngine` → `ShardingRouteEngine` → `SQLRewriteEngine` → `ResultMergeEngine`（`LimitDecoratorMergedResult` 做分页归并）；ID 侧看雪花位运算与 Leaf 号段双 buffer。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 分片键 | 决定数据落哪个分片的字段 | 路由与扩展的基础 | 选错、倾斜、扩容 |
| 垂直拆分 | 按业务或字段切 | 解耦、变窄 | 跨库 join、事务 |
| 水平拆分 | 按行切 | 单表行数可控 | 路由、跨库查询 |
| 广播表 | 每库一份的小表 | 避免跨库 join 字典表 | 同步一致性 |
| 雪花 ID | 时间+机器+序列的 64 位 ID | 分布式有序 ID | 时钟回拨 |
| 号段模式 | DB 批量发号区间 | 减少 DB 访问 | 双 buffer、Leaf |
| 游标分页 | 用上一页最后一条定位 | 无偏移、性能稳定 | 不能跳页 |
| 二次查询 | 两轮查询绕过深偏移 | 跨库分页 | 步骤与边界 |
| 影子表 | 新表并行写做验证 | 迁移降风险 | 数据校验 |
| 双写 | 同时写新旧库 | 平滑迁移 | 以谁为准、回滚 |
| ShardingSphere | 客户端分片中间件 | SQL 路由/改写/归并 | 路由类型、归并 |

## 代码验证（MySQL 8.0 可执行 SQL + Java 雪花片段）

```sql
-- 1. 水平分表示例：order_0 ~ order_15，按 user_id % 16 路由
CREATE TABLE order_0 LIKE order_base;   -- order_1..order_15 同理
-- user_id = 10086 → 10086 % 16 = 6 → 查询落在 order_6

-- 2. 游标分页（分片内/单库都适用）
SELECT id, user_id, amount FROM order_6
WHERE user_id = 10086 AND id > 1000000
ORDER BY id LIMIT 10;

-- 3. 二次查询（n=4，offset=100000，limit=10）
SELECT * FROM order_0 ORDER BY id LIMIT 25000, 10;   -- 第一轮：每个分片取 offset/4
SELECT * FROM order_1 ORDER BY id LIMIT 25000, 10;
SELECT * FROM order_2 ORDER BY id LIMIT 25000, 10;
SELECT * FROM order_3 ORDER BY id LIMIT 25000, 10;
SELECT * FROM order_0 WHERE id BETWEEN 500123 AND 500456 ORDER BY id;  -- 第二轮：从 minId 补查
SELECT * FROM order_1 WHERE id BETWEEN 500123 AND 500789 ORDER BY id;

-- 4. 号段模式（Leaf-segment）
CREATE TABLE leaf_alloc (
  biz_tag VARCHAR(64) PRIMARY KEY,
  max_id BIGINT NOT NULL,
  step INT NOT NULL,
  version BIGINT NOT NULL DEFAULT 0,
  update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
INSERT INTO leaf_alloc (biz_tag, max_id, step) VALUES ('order', 100000, 1000);
UPDATE leaf_alloc SET max_id = max_id + step, version = version + 1
WHERE biz_tag = 'order' AND max_id = 100000;   -- 成功即可用 [old_max+1, old_max+step]
```

```java
// 雪花算法（简化版；生产用 Hutool/Leaf，务必处理时钟回拨）
public class SnowflakeId {
    private static final long EPOCH = 1700000000000L, WORKER_BITS = 10L, SEQ_BITS = 12L;
    private final long workerId;
    private long lastTs = -1L, seq = 0L;

    public SnowflakeId(long workerId) { this.workerId = workerId; }

    public synchronized long nextId() {
        long now = System.currentTimeMillis();
        if (now < lastTs) throw new IllegalStateException("clock moved backwards");
        if (now == lastTs) {
            seq = (seq + 1) & ((1L << SEQ_BITS) - 1);
            if (seq == 0) while (now <= lastTs) now = System.currentTimeMillis();  // 序列用尽等下一毫秒
        } else {
            seq = 0L;
        }
        lastTs = now;
        return ((now - EPOCH) << (WORKER_BITS + SEQ_BITS)) | (workerId << SEQ_BITS) | seq;
    }
}
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「分片键随便选，反正有中间件」 | 选错 = 全库广播 + 数据倾斜 |
| 「跨库 join 让中间件处理就行」 | 笛卡尔路由会放大查询，要冗余/广播表/宽表 |
| 「跨库分页加 limit 就行」 | 每分片都要扫 offset，深分页爆内存，要游标/二次查询 |
| 「扩容直接改取模」 | 取模变化几乎全量迁移，要双写/一致性哈希/基因法过渡 |
