# 异步与削峰（线程池隔离 / MQ 削峰 / 背压 / 任务可靠性）

> 面试权重：5/5　｜　追问深度：**L5（ThreadPoolExecutor ctl/Worker / 本地消息表 / Reactive request(n)）**
> 一句话定位：异步与削峰解决**"瞬时流量 > 系统处理能力"**这个根本矛盾：把"同步等待"变成"提交后返回"，把"瞬时高峰"摊平成"可持续速率"。代价是**可靠性、顺序性与可观测性全部变难**——真正的考点不是"会不会用 @Async"，而是"异步之后怎么保证不丢、不重、不乱、可追踪"。

**本文件用法**：先答 L1 的"三个问题"，再按 L4 从线程池 → MQ → 可靠性 → 顺序/背压 → 调度往下走。你的 报告平台 任务系统就是这整套的实战。

## L1 一句话答案（10 秒能说出口）

异步 = 把非关键路径从主链路摘出去，用**有界线程池**或 **MQ** 承接，接口先返回、后台慢慢做；削峰 = 用**消息队列/有界队列**把瞬时高峰缓冲起来，消费者按自己的速率消费（"填谷"）。异步一上就必须回答三个问题：**任务会不会丢？**（落库/本地消息表/事务消息/重试）、**会不会重复？**（幂等键 + 状态机 CAS）、**会不会乱序？**（按 key 单线程/单分区/版本号）。再加**池隔离 + 有界队列 + 拒绝策略 + 上下文传递**，才是一套能上生产的异步体系。

## L2 原理层：线程池、MQ、背压、可靠性

### 2.1 线程池：异步的地基

```java
@Bean("bizExecutor")
public ThreadPoolTaskExecutor bizExecutor() {
    var e = new ThreadPoolTaskExecutor();
    e.setCorePoolSize(8);  e.setMaxPoolSize(16);
    e.setQueueCapacity(200);                 // 重点：有界队列，别用默认无界
    e.setKeepAliveSeconds(60);
    e.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy()); // 背压给调用方
    e.setTaskDecorator(new ContextCopyingDecorator());   // 重点：traceId/MDC 传递
    e.initialize(); return e;
}
```

- **执行顺序**：核心线程 → 队列 → 扩容到 max → 拒绝策略。**队列容量决定 max 是否真的生效**：无界队列下永远只用 core 个线程。
- **拒绝策略**：`AbortPolicy`（抛异常，默认）、`CallerRunsPolicy`（调用方自己执行 → 天然背压，但要小心阻塞 Web 线程）、`Discard*`（静默丢，业务里几乎不能用）。**池大小**：CPU 密集 `core+1`，IO 密集按等待比例，最终压测为准。

### 2.2 `@Async` 的坑（面试高频）

| 坑 | 原因 | 解法 |
|---|---|---|
| `private` / 非 Bean 不生效 | 代理无法覆盖 private、无容器管理 | 改为 public + `@Component` |
| 没自定义 Executor | 默认 `SimpleAsyncTaskExecutor`，每任务新建线程 | `@Async("bizExecutor")` |
| 上下文丢失 / 异常被吞 | ThreadLocal 不跨线程；`void` 返回值异常无人处理 | `TaskDecorator` 复制 MDC，返回 `CompletableFuture` |

### 2.3 线程池隔离与 MQ 削峰

- **隔离维度**：业务重要性、资源类型（CPU/IO）、下游依赖（每个外部服务一个池）。所有池 max 之和 ≤ 机器能承受的线程数。**一个公共池会被慢任务占满，导致核心任务排队超时雪崩。**
- **MQ 削峰收益**：保护 DB/下游、解耦、接口快速返回、可回放；**代价**：**最终一致**（接口返回时任务还没做完）、可靠性成本（生产/消费 ack、重试、死信）、重复消费（要幂等）、延迟增加、积压监控。典型场景：秒杀下单、批量导入、报表、通知。**报告平台 代码沙箱**：提交任务 → 落库 + 发 MQ → worker 起容器执行 → SSE 推进度，就是标准削峰。

### 2.4 背压（Backpressure）

- **问题**：生产者速度 > 消费者速度，无界缓冲最终 OOM 或延迟爆炸。**手段**：有界队列（满了阻塞/拒绝）、**Reactive Streams 的 `request(n)`**（消费者主动声明"我还能处理 n 个"）、`onBackpressureBuffer/Drop/Latest`、MQ 作跨进程缓冲、TCP 滑动窗口。

```java
Flux.range(0, 1_000_000)
    .publishOn(Schedulers.boundedElastic(), 64)   // 预取 64，队列满即反压上游
    .map(this::slowHandler)                       // 慢消费者自动限速
    .subscribe();
```

### 2.5 异步任务的可靠性（不丢）

| 方案 | 做法 | 保证 |
|---|---|---|
| **本地消息表（Outbox）** | 业务事务里同时写业务表和消息表（同库同事务），定时扫未发送消息 → 投递 MQ → 标记已发送；消费端幂等 | 最终一致、不丢 |
| **事务消息** | RocketMQ 半消息 + 本地事务 + 回查；Kafka 用 `transactional.id` | 不丢且与本地事务原子 |
| **任务表 + 补偿扫描** | 任务先落库（PENDING）→ 执行 → 更新状态；定时扫超时/失败任务重试 | 不丢、可重试、可观测 |

**关键原则：先落库，再异步。** 任何"内存里 submit 出去就当成功"的方案都不抗崩溃。

### 2.6 任务状态机、幂等与调度选型

```
PENDING ──► RUNNING ──► SUCCESS
   │            ├────► FAILED ──(重试)──► PENDING
   └──► CANCELED / TIMEOUT
```

- **CAS 状态迁移**：`UPDATE task SET status='RUNNING', worker_id=? WHERE id=? AND status='PENDING'`，影响行数=0 说明已被别人抢到。
- **幂等**：任务 `idempotency_key` + 唯一索引；消费端先查"是否已处理"；MQ 消息用 `(topic, partition, offset)` 或业务键去重。**重试**：有限次数 + 退避 + 死信队列；不可重试的错误（参数错/权限）直接 FAILED。
- **调度选型**：`@Scheduled`（单机）→ **Quartz**（cron + JobStore 持久化 + 集群靠 DB 行锁防重）→ **XXL-JOB**（调度中心 + 执行器、**分片广播**、失败重试、日志告警、可视化，最常用）→ Elastic-Job/PowerJob（大规模编排）。集群防重：调度器保证单次触发只有一个执行器，或执行时抢分布式锁。

## L3 底层层：线程池 ctl 与本地消息表时序

### 3.1 `ThreadPoolExecutor.execute()` 的 JVM 内部

```
execute(task)
 ├── if (workerCount < corePoolSize) → addWorker(task, true)   // 建核心线程直接跑
 ├── else if (workQueue.offer(task)) → 入队，等 Worker 取
 ├── else if (workerCount < maximumPoolSize) → addWorker(task, false)
 └── else → rejectHandler.rejectedExecution(task, this)         // 拒绝
Worker.run()：循环 getTask() → workQueue.poll(keepAlive) / take()
  - take() 阻塞在 AQS Condition → LockSupport.park()（内核 futex 等待），offer 时 unpark 唤醒
  - workerCount 用 AtomicInteger ctl 高 3 位存状态、低 29 位存线程数，CAS 修改
```

**这解释了**：为什么无界队列下 max 永远不生效（`offer` 永远成功）；为什么 `CallerRunsPolicy` 能背压（拒绝时由调用线程执行，Web 线程被拖慢从而降低接收速率）。

### 3.2 本地消息表的时序

```
① 开启 DB 事务：INSERT biz_order ...; INSERT outbox(status='NEW') ...; COMMIT
   ← 业务数据与消息"同时成功或同时失败"
② 定时任务（每 1s）扫 outbox WHERE status='NEW' LIMIT 100 → 投递 MQ → ack 后 UPDATE status='SENT'
③ 消费端幂等处理；失败重试 N 次 → 死信队列 + 告警；成功后回 ack
```

关键点：**消息表与业务表同库同事务**，不依赖 MQ 的事务；MQ 只是"至少一次"投递，重复由消费端幂等兜住。**RocketMQ 事务消息**区别：先发半消息 → 执行本地事务 → commit/rollback → 无响应时 Broker **回查**生产者事务状态；省掉扫表，但强绑定支持事务消息的 MQ。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：第 1-3 层必备，4-6 层拉开差距，7 层以后是加分。

### 第 1 层｜为什么要异步？哪些场景适合？
**答**：把不影响主流程正确性的耗时操作（通知、日志、统计、外部调用、批量计算）从主链路摘出去，缩短接口 RT、提升吞吐，并用队列缓冲瞬时高峰。适合可最终一致、用户不等待结果、可失败重试的操作；**不适合**必须同步拿结果、强一致、金额实时校验。

### 第 2 层｜`@Async` 怎么用？为什么会失效？
**答**：`@EnableAsync` + 自定义 `Executor` Bean + `@Async("bizExecutor")`。失效原因：同类内部调用（未经代理）、方法 private、类不是 Spring Bean、没配线程池（默认每次新建线程）。隐藏坑：`void` 返回异常被吞、ThreadLocal 上下文丢失。

### 第 3 层｜线程池参数怎么设？队列有界还是无界？
**答**：`corePoolSize` 按任务类型（CPU 密集 `core+1`，IO 密集按等待比例）并压测确定；`maxPoolSize` 只在队列满后才生效；**必须用有界队列**（无界会内存膨胀且 max 失效）；`keepAlive` 回收空闲线程。**别用 `Executors.newFixedThreadPool` 的默认无界队列。**

### 第 4 层｜拒绝策略怎么选？`CallerRunsPolicy` 是什么效果？
**答**：默认 `AbortPolicy` 抛 `RejectedExecutionException`，业务要捕获并降级；`CallerRunsPolicy` 让提交任务的线程自己执行——**天然背压**（提交变慢，流量被反向压制），但调用方若是 Tomcat 工作线程会被卡住，要评估；`Discard*` 静默丢任务，只有可丢的埋点类任务能用。

### 第 5 层｜异步线程里怎么传递 traceId / 用户上下文 / 事务？
**答**：ThreadLocal 不会跨线程。① `TaskDecorator` 在提交时捕获 `MDC.getCopyOfContextMap()`/`RequestContextHolder`，线程内设置、finally 清理；② 用 `TransmittableThreadLocal` + `TtlExecutors`（解决线程池复用导致的传递错乱）；③ 事务不要跨线程，异步任务里开自己的新事务（`REQUIRES_NEW` 或干脆不传）。

### 第 6 层｜为什么要线程池隔离？怎么隔离？
**答**：一个池里慢任务（导出/第三方）占满线程，核心任务（下单/回调）排队超时 → 雪崩。按业务重要性/资源类型/下游依赖拆池：核心交易池、通知池、导出台；每个池独立有界队列 + 拒绝策略；核心池拒绝时降级，非核心池拒绝时丢/延后。**还要限制所有池的线程总数。**

### 第 7 层｜MQ 怎么削峰填谷？代价是什么？
**答**：生产端把请求快速写进 MQ 就返回，消费端按自身能力匀速消费，高峰被缓冲、低谷消化积压。代价：**最终一致**（返回时任务未完成）、**可靠性成本**（生产/消费 ack、重试、死信）、**重复消费**、**延迟增加**、**积压监控与扩容**。适合可异步、可最终一致的场景。

### 第 8 层｜异步之后怎么保证任务不丢？
**答**：**先落库再异步**。① 任务表（PENDING）→ 提交执行 → 更新状态，定时扫超时任务重试；② 本地消息表（业务表 + outbox 同事务），定时投递 MQ，发送成功才标记；③ MQ 事务消息（RocketMQ 半消息 + 回查 / Kafka 事务）。**只 submit 到内存线程池、进程崩了就没了，只能用于可丢任务。**

### 第 9 层｜本地消息表和事务消息有什么区别？
**答**：本地消息表把"消息"当业务数据存同库，靠定时扫表投递，**不依赖 MQ 特殊能力**（任何 MQ 都能用），多一次扫表延迟；事务消息由 MQ 提供半消息 + 本地事务 + 回查，**省掉扫表**，但强绑定支持事务消息的 MQ（RocketMQ），实现/排障更复杂。本质都是"业务与消息原子化 + 至少一次投递 + 消费幂等"。

### 第 10 层｜异步任务重复执行怎么办？顺序乱了怎么办？
**答**：**重复**：① 任务级 `idempotency_key` + DB 唯一索引；② 状态机 CAS 抢执行权（影响行数 0 就跳过）；③ 消费端处理记录表或 Redis `SETNX`。**乱序**：先明确是否真需要全局有序（多数只需"同一实体有序"）：按 key 路由同一线程/同一 MQ 分区、状态机/版本号让旧操作失效、单消费者串行；跨实体全局有序基本放弃，用业务状态兜。

### 第 11 层｜背压是什么？Reactive 的 `request(n)` 怎么工作？
**答**：背压 = 消费者告诉生产者"我还能接多少"，避免无限缓冲。订阅时 `Subscription.request(n)` 声明需求，`onNext` 最多推 n 个，消费后继续 `request`；`publishOn`/`flatMap` 有预取参数，队列满就停止向上游请求 → 上游被限速。阻塞队列是"被动背压"（满了阻塞/拒绝），Reactive 是"主动声明需求"；跨进程背压靠 MQ 积压或 TCP 滑动窗口。

### 第 12 层｜分布式任务调度怎么选？XXL-JOB 和 Quartz 区别？
**答**：单机简单定时用 `@Scheduled`；需要 cron + 持久化 + 集群防重、任务量中等用 Quartz（JobStore 存 DB，靠行锁抢触发器）；需要**可视化、分片广播、失败重试、日志告警、动态改 cron** 用 XXL-JOB（调度中心 + 执行器，分片任务按 `index/total` 处理数据分片）。集群下无论哪种，都要"调度器单点触发"或"分布式锁"防重复执行。

### 第 13 层（终局）｜一次 `taskExecutor.execute(task)` 到任务真正跑起来，JVM/内核层面发生了什么？
**答**：`execute` 先 CAS `ctl` 判断线程数：不足 core 就 `addWorker` 新建 `Worker`（`ThreadFactory.newThread` → `Thread.start()`），否则 `workQueue.offer`，队列满且未到 max 继续建线程，再满就拒绝。`Thread.start()` 调 `pthread_create`，新线程在 `Worker.run()` 里循环 `getTask()`：队列空时 `workQueue.take()` 阻塞在 AQS Condition → `LockSupport.park()` → 内核 futex 等待；有任务 `offer` 时 `unpark` 唤醒（futex wake）→ 取任务执行。任务跑完回到 `getTask` 等待，超过 `keepAliveTime` 且线程数 > core 就回收。**线程池的性能点：复用线程避免 `pthread_create`、CAS 管状态避免锁、阻塞队列解耦生产消费；而"异步丢任务"就发生在进程崩溃时内存队列里还没执行的任务——这就是必须先落库的原因。**

## L5 名词拆解表（每个名词都拆开）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| `ThreadPoolExecutor` | JDK 线程池 | 复用线程、控制并发 | 执行顺序、ctl、keepAlive |
| 有界队列 | 固定容量的阻塞队列 | 防内存膨胀 + 触发背压 | 无界队列为何让 max 失效 |
| 拒绝策略 | 队列/线程满时的处理策略 | 保护系统不被打爆 | `CallerRunsPolicy` 的副作用 |
| `@Async` | Spring 异步注解 | 声明式异步 | 失效场景、默认线程池问题 |
| `TaskDecorator` / TTL | 任务提交装饰钩子 / 可继承 ThreadLocal | 跨线程传递上下文 | 线程池复用导致错乱怎么解 |
| 线程池隔离 | 不同业务用独立线程池 | 故障隔离、防雪崩 | 隔离维度、总线程数限制 |
| MQ 削峰 | 用队列缓冲瞬时流量 | 保护下游、平峰 | 代价（最终一致/重复/延迟） |
| 本地消息表 | 业务表 + outbox 同事务 | 保证消息不丢 | 扫表投递、与事务消息区别 |
| 幂等键 / CAS 状态迁移 | 业务唯一标识 / `where status=?` 更新 | 防重复执行、抢占执行权 | 幂等范围怎么定 |
| 背压 / Reactive Streams | 消费端反向限速 / 异步流规范 | 防 OOM、保延迟 | `request(n)`、`publishOn` 预取 |
| XXL-JOB / Quartz | 分布式调度中心 / 老牌调度框架 | 可视化分片 / cron 持久化 | 分片广播、集群防重 |

## 代码验证

```java
// 1) 自定义线程池 + 上下文传递 + 有界队列 + 背压
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {
    @Bean("bizExecutor")
    public ThreadPoolTaskExecutor bizExecutor() {
        ThreadPoolTaskExecutor e = new ThreadPoolTaskExecutor();
        e.setCorePoolSize(8);
        e.setMaxPoolSize(16);
        e.setQueueCapacity(200);
        e.setKeepAliveSeconds(60);
        e.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        e.setTaskDecorator(r -> {
            Map<String, String> mdc = MDC.getCopyOfContextMap();   // 捕获父线程上下文
            return () -> {
                if (mdc != null) MDC.setContextMap(mdc);
                try { r.run(); } finally { MDC.clear(); }
            };
        });
        e.initialize();
        return e;
    }
    @Override
    public Executor getAsyncExecutor() { return bizExecutor(); }
}
```

```java
// 2) 任务状态机：CAS 抢占天然幂等（报告平台 任务）+ 补偿扫描
public boolean start(String taskId) {
    int n = jdbc.update("UPDATE task SET status='RUNNING' WHERE id=? AND status='PENDING'", taskId);
    return n == 1;   // 多 worker 同时抢，只有一个成功
}
// 看门狗：超时任务改 TIMEOUT 交给重试（生产用 @Scheduled 每 30s 扫一次）
```

```java
// 3) 本地消息表：业务与消息同事务 + 定时投递
@Transactional
public void createOrder(Order order) {
    orderMapper.insert(order);
    outboxMapper.insert(new Outbox("order-created", order.getId(), toJson(order), "NEW"));
}   // 事务提交后消息一定在 outbox 表

@Scheduled(fixedDelay = 1000)
public void relay() {
    for (Outbox m : outboxMapper.listNew(100)) {              // status='NEW'
        try {
            kafkaTemplate.send(m.topic(), m.payload()).get(3, TimeUnit.SECONDS);
            outboxMapper.markSent(m.id());                    // 成功才标记
        } catch (Exception e) {                               // 失败重试，超 5 次进死信
            outboxMapper.incrRetry(m.id());
            if (m.retry() > 5) outboxMapper.markDead(m.id());
        }
    }
}
// 调度选型：单机 @Scheduled → Quartz(DB JobStore+行锁) → XXL-JOB(调度中心+分片广播+重试告警)
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「加个 `@Async` 就异步了」 | 同类调用/private 不生效，必须走代理；还要自定义有界线程池 |
| 「线程池队列用无界省事」 | 无界队列导致 max 失效 + 内存膨胀，必须用有界 + 拒绝策略 |
| 「异步了接口就快了」 | 只省了等待时间，任务总耗时没变；还引入一致性/可靠性成本 |
| 「`CallerRunsPolicy` 最安全，直接用它」 | 会让调用线程（可能是 Tomcat 线程）执行任务，可能拖垮 Web 层 |
