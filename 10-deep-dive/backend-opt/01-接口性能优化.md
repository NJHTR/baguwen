# 接口性能优化（连接池 / 批量 / 序列化 / 缓存分层 / 排查）

> 面试权重：5/5　｜　追问深度：**L5（HikariCP 池化本质 / 序列化格式 / 火焰图采样 / 耗时拆解）**
> 一句话定位：接口优化不是"加缓存加机器"，而是**先量化耗时分布，再按成本从低到高动刀**：网络与连接（连接池、keep-alive）→ SQL 与数据量（索引、批量、分页）→ 序列化与体积（字段裁剪、压缩、协议）→ 计算与排队（异步、线程池隔离）→ 架构（缓存分层、BFF、限流降级）。

**本文件用法**：面试问"怎么优化接口"，先答 L1 的口诀 + 耗时拆解，再按 L4 往下。不要一上来就说"加 Redis"。
[返回深度追问索引](../00-索引.md)

## L1 一句话答案（10 秒能说出口）

先看**耗时花在哪**（监控/链路追踪/Arthas/火焰图），再按顺序优化：**① 减少往返**（连接池、keep-alive、接口合并、批量）；**② 减少数据量**（只查需要的字段、分页、压缩、更紧凑的序列化）；**③ 减少计算与排队**（索引、缓存、异步化、线程池隔离）；**④ 兜住流量**（限流、降级、熔断）。**没有度量的优化都是猜。**

## L2 原理层：分层的优化手段

### 2.1 连接池：池化的本质是"复用昂贵资源 + 控制并发"

- **连接为什么贵**：TCP 三次握手 + TLS 握手 + DB 认证 + 会话初始化，一次可能 10-50ms；还占 DB 的 `max_connections` 名额。
- **池化做什么**：启动预建连接、借还复用、校验有效性、控制上限、回收空闲/超时连接。

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20        # 最大连接数
      minimum-idle: 20             # 保活数（生产建议 = max，避免扩容抖动）
      connection-timeout: 3000     # 重点：借连接超时，默认 30s，必须调小（快速失败）
      idle-timeout: 600000         # 空闲回收 10min
      max-lifetime: 1800000        # 最大存活 30min（要小于 DB wait_timeout）
      keepalive-time: 120000       # 定期探活
```

- **最大连接数怎么定**（Hikari 官方公式）：`connections = core_count * 2 + effective_spindle_count`，4 核 + SSD 约 9，取 10-20 足够。**反直觉结论：不是越大越好**——超过 DB 并行处理能力后只是把压力从"应用排队"变成"DB 上下文切换 + 锁竞争"，吞吐反而降。多实例时总连接数 = 单实例池大小 × 实例数，**必须 < DB `max_connections`**。
- `connection-timeout` 默认 30s 是事故放大器：DB 慢时请求全卡 30s、线程池打满 → 雪崩。**调成 2-3s + 快速失败 + 降级**。

### 2.2 N+1 查询与批量（后端最经典的性能坑）

```java
// 错误：N+1：1 次查订单 + N 次查用户
List<Order> orders = orderMapper.list();                    // 1 次
for (Order o : orders) o.setUser(userMapper.selectById(o.getUserId()));  // N 次！

// 正确：方案一：批量 IN + 内存拼装（推荐，可控）
Set<Long> userIds = orders.stream().map(Order::getUserId).collect(toSet());
Map<Long, User> userMap = userMapper.selectByIds(userIds).stream()
        .collect(toMap(User::getId, identity()));           // 1 次
orders.forEach(o -> o.setUser(userMap.get(o.getUserId())));
// 正确：方案二：JOIN 一次查完（注意数据量放大）；方案三：MyBatis <collection> 配批量加载
```

- **批量写**：`ExecutorType.BATCH` 或 `<foreach>` 拼接；MySQL 要开 `rewriteBatchedStatements=true`，否则 JDBC 仍逐条发送。
- **发现 N+1**：开 SQL 日志数一数、MyBatis 插件统计、慢 SQL 里同一条语句高频重复。

### 2.3 索引与 SQL、深分页

- 看 `EXPLAIN`：`type`（const/ref/range/all）、`key`、`rows`、`Extra`（`Using filesort/temporary` 要警惕）。
- 高频招：**覆盖索引**（避免回表）、联合索引最左前缀、**避免函数/隐式转换使索引失效**（`where date(create_time)=...`、字符串列传数字、`like '%x'`）、大事务拆小、批量代替循环单条。
- **深分页**：`limit 100000, 20` 要扫描 10 万行丢弃 → **游标分页**（`where id > lastId order by id limit 20`）或**延迟关联**（先用覆盖索引查 id 再 join 取整行）。`count(*)` 大表也贵，可缓存总数或近似值。

### 2.4 序列化与数据体积

| 格式 | 可读性 | 体积（相对 JSON） | 速度 | schema | 场景 |
|---|---|---|---|---|---|
| JSON（Jackson） | | 1x | 中 | | 对外 API、调试友好 |
| Protobuf | | **约 0.3-0.5x** | 快 2-5x | `.proto` | 内部 RPC、大数据量 |
| Avro | | 约 0.3x | 快 | | 大数据/Kafka 生态 |
| MessagePack | | 约 0.5-0.7x | 快 | | 缓存/内部传输 |
| Hessian/Kryo | | 约 0.5x | 很快 | | RPC/Redis（注意兼容性） |

- **字段裁剪**：DTO 只返回前端需要的字段，别把 Entity 整个扔出去。
- **JSON 优化**：避免深嵌套、`@JsonInclude(NON_NULL)` 省 null、日期用时间戳或固定格式、大列表分页、`ObjectMapper` 复用（线程安全，别每次 new）。
- **HTTP 压缩**：`gzip`/`br`，JSON 一般能压 70-85%；Nginx `gzip on; gzip_min_length 1k; gzip_types application/json;`；**Brotli 比 gzip 再省 15-25%（CPU 更贵）**；已压缩内容（图片/视频/zip）不要再压。

### 2.5 分页与流式响应

- 列表接口必须有分页上限（`size <= 100`），防止 `?size=100000` 拖垮服务。
- 导出/大结果集用**流式**：`StreamingResponseBody` / `Flux` / `SseEmitter` / 游标分批查 + 边查边写，内存恒定；不要 `select *` 全量进内存再写 Excel。
- 响应体大时：压缩、字段裁剪、分页、转后台异步任务（导出 + 进度查询）。

### 2.6 缓存分层（本地 → 分布式 → CDN）

| 层 | 实现 | 命中延迟 | 一致性 | 适合 |
|---|---|---|---|---|
| 本地缓存 | Caffeine / Guava | ~100ns-1μs | 多节点不一致（靠 TTL/广播失效） | 热点字典、配置、超热数据 |
| 分布式缓存 | Redis / Memcached | ~0.5-2ms（网络 RTT） | 统一失效 | 会话、跨实例共享数据 |
| CDN / 浏览器 | CDN + HTTP 缓存头 | ~10-50ms 到边缘 | 靠版本号/短 TTL | 静态资源、图片、公开数据 |

- **Caffeine**：W-TinyLFU 淘汰，命中率高于 LRU；`maximumSize` + `expireAfterWrite`。
- **一致性**：本地缓存用"短 TTL + 主动失效广播（Redis pub/sub）"；更新时 **Cache-Aside：先更新 DB 再删缓存**，别先删缓存再更新 DB。
- **三件套**：穿透（空值缓存/布隆过滤器）、击穿（互斥锁/逻辑过期）、雪崩（随机 TTL/多级缓存/熔断）。

### 2.7 异步化、接口合并、限流降级

- **异步化**：非关键路径（发通知、写日志、更新统计、调外部）用 `@Async`/MQ；注意它缩短的是"接口响应时间"而非"任务总耗时"，线程池要有界 + 拒绝策略 + 上下文传递（见 [异步与削峰](./02-异步与削峰.md)）。
- **接口合并与 BFF**：3 个串行 RTT 的独立查询 → 并行（`CompletableFuture`）或后端聚合一次返回；BFF 为各前端裁剪字段、拼装数据。代价：多一跳网络、聚合层故障影响面大、缓存策略复杂，**只有聚合收益 > 多一跳成本才做**。
- **限流与降级**：令牌桶（允许突发，Guava `RateLimiter`/Sentinel）、漏桶（平滑）、滑动窗口、固定窗口（临界问题）；维度：接口 QPS/用户/IP/租户。降级：兜底值/缓存旧值/关非核心；**熔断**（Resilience4j/Sentinel，错误率或 RT 超阈值自动打开）；**隔离**（线程池/信号量）。原则：**限流保护自己，熔断保护下游，降级保核心。**

### 2.8 慢请求排查工具箱

| 工具 | 看什么 | 用法 |
|---|---|---|
| 链路追踪（SkyWalking/Zipkin） | 哪个 span 慢、调用拓扑 | UI 看 trace 瀑布图 |
| Arthas `trace` | 单次调用里每个子方法耗时 | `trace com.x.Service method '#cost > 100'` |
| Arthas `monitor` | 调用次数/成功率/平均 RT | `monitor -c 5 com.x.Service method` |
| Arthas `profiler` | CPU 火焰图 | `profiler start` → `profiler stop` |
| async-profiler / JFR | 采样 CPU/内存/锁 | `asprof -d 30 -f out.html <pid>` |
| `jstack` | 阻塞/死锁/线程池满 | 连续抓 3 次对比 |
| GC 日志 | 停顿、Full GC | `-Xlog:gc*` |

**火焰图读法**：横轴是调用栈宽度（采样占比 ≈ CPU 时间占比），纵向是调用深度；**找最宽的"平顶"**就是热点；`GC`/`safepoint`/锁 占比高说明不是代码问题。

## L3 底层层：一次请求的耗时拆解

```
客户端 → ① DNS+TCP+TLS（连接复用则近 0）→ ② 网络 RTT（同城 ~0.5ms，跨地域 ~30ms）
  → Nginx/网关 ③ 排队+转发+压缩（keep-alive 复用）
  → 应用（Tomcat）④ 线程池排队（打满则排到超时）→ ⑤ 反序列化/校验/鉴权
     → ⑥ 业务 + 缓存访问（本地 ns / Redis ~1ms）→ ⑦ 借 DB 连接（池满等 connection-timeout）
     → ⑧ SQL 执行（索引命中 ~0.1ms，全表扫 ~100ms+）→ ⑨ 结果映射/序列化/压缩
  → 返回
```

**优化顺序：先砍 ⑧⑨（数据量与 SQL），再并行 ⑥⑦（IO 等待），最后才考虑 ④（加机器/线程池）。**

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：第 1-3 层必备，4-6 层拉开差距，7 层以后是加分。

### 第 1 层｜线上接口 500ms，怎么优化到 100ms？
**答**：先量化：链路追踪/日志打点看耗时分布（DB、Redis、下游、序列化、GC/线程等待各占多少）。再按成本动刀：SQL 加索引/改批量/去 N+1（通常最大头）→ 只查需要的字段 → 加缓存（本地/Redis）→ 并行化独立调用 → 大响应压缩/字段裁剪 → 异步化非关键路径。**不量化就优化 = 瞎猜。**

### 第 2 层｜连接池的作用？最大连接数怎么定？配大会怎样？
**答**：复用昂贵连接（省 TCP/TLS/认证开销）、控制并发保护 DB。Hikari 公式 `core*2 + spindle`，4 核约 10-20；多实例要保证总连接 < DB `max_connections`。**配大反而变慢**：DB 上下文切换、锁竞争、内存占用，表现是 RT 抖动、吞吐下降；且 `connection-timeout` 默认 30s 会让故障时请求全卡住，应调小快速失败。

### 第 3 层｜N+1 查询是什么？怎么发现和解决？
**答**：查 N 条主记录后又逐条查关联（1+N 次 SQL）。发现：SQL 日志里同一条语句高频重复、慢查询统计、链路追踪里 DB span 数量异常。解决：批量 `IN` + 内存 Map 拼装（首选）、JOIN 一次查完、MyBatis `<collection>` 配批量加载、Hibernate `@BatchSize`/`join fetch`；写侧用 `ExecutorType.BATCH` + `rewriteBatchedStatements=true`。

### 第 4 层｜深分页为什么慢？怎么优化？
**答**：`limit 100000, 20` 要扫描并丢弃前 10 万行（还要回表），越翻越慢。优化：**游标/keyset 分页**（`where id > lastId order by id limit 20`，走索引且恒定开销）、**延迟关联**（子查询先用覆盖索引取 id 再 join）、业务上限制最大页数。`count(*)` 大表也很贵，可缓存总数或用近似值。

### 第 5 层｜返回体太大怎么优化？
**答**：① 字段裁剪（DTO 只返回需要的，别透传 Entity）；② 分页（列表接口强制上限）；③ 压缩（gzip/br，JSON 通常压 70%+）；④ 更紧凑的序列化（内部 RPC 用 Protobuf）；⑤ 流式响应（`StreamingResponseBody`/`Flux`，内存恒定）；⑥ 大字段拆到详情接口。

### 第 6 层｜JSON 和 Protobuf 怎么选？
**答**：对外 API/需要可读性和调试 → JSON（Jackson，生态好、浏览器直接解析）；内部高 QPS RPC/大数据量 → Protobuf（二进制、体积约为 JSON 的 1/3-1/2、编解码快 2-5x、有 schema 强类型），代价是要维护 `.proto`、不可读、要生成代码。**别为了"高级"在对外接口上 Protobuf。**

### 第 7 层｜缓存怎么分层？本地缓存和 Redis 的一致性怎么保证？
**答**：Caffeine（热点字典/配置，纳秒级）→ Redis（跨实例共享，毫秒级）→ CDN（静态资源，边缘）。一致性：更新走 **Cache-Aside（先更新 DB 再删缓存）**，本地缓存加**短 TTL + Redis pub/sub 广播失效**；强一致要求高的数据干脆不进本地缓存。注意穿透/击穿/雪崩三件套。

### 第 8 层｜哪些逻辑可以异步化？异步后接口真的更快吗？
**答**：可以异步的是"不影响本次响应正确性"的旁路：通知、日志、统计、外部 webhook、非关键写。异步化缩短的是**接口响应时间**，任务总耗时不变；代价是可靠性（要本地消息表/重试/死信）与可观测性变差。**用有界线程池 + 拒绝策略 + 上下文传递（TTL），别用默认线程池。**

### 第 9 层｜接口合并/BFF 解决什么问题？代价是什么？
**答**：解决"前端一次页面渲染要串行调 5 个接口"的 RTT 叠加与字段冗余；BFF 针对每种前端做聚合、裁剪、协议适配。代价：多一层网络与故障点、聚合逻辑难复用、缓存粒度变粗、发布耦合；收益不明确时优先用 HTTP/2 多路复用 + 前端并行请求。

### 第 10 层｜限流算法有哪些？令牌桶和漏桶区别？
**答**：固定窗口（简单，临界突刺）、滑动窗口（平滑，Sentinel 默认）、**漏桶**（请求入桶、恒定速率流出，绝对平滑但突发被削）、**令牌桶**（按速率发令牌，桶容量允许一定突发，最常用）。令牌桶允许"攒着用"，漏桶强制匀速；实现可用 Guava `RateLimiter`、Sentinel、Redis + Lua 分布式限流。

### 第 11 层（终局）｜把 800ms 的请求拆到每个系统调用/组件，你怎么做？
**答**：用 **traceId + 分段埋点**（网关、应用入口、每个 RPC/DB/Redis 客户端拦截器）拿到 span 树，再对单机用 **async-profiler/JFR 采样**：CPU 火焰图看热点、`wall-clock` 模式把等 IO 的时间也算上、GC 日志看停顿、`strace -c` 看 syscall 次数与耗时（`futex` 多说明锁竞争、`read/write` 多说明 IO 多）、`ss -ti` 看 TCP 重传/RTT。典型拆分：DB 350ms（深分页）+ 序列化 150ms（大对象）+ 下游 HTTP 200ms（串行 3 次）+ 线程排队 50ms + GC 50ms。**优化的顺序就是砍掉最大的那几块，且一次只改一个变量、用压测/A-B 验证。**

## L5 名词拆解表（每个名词都拆开）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 连接池 / HikariCP | 预建复用 DB 连接的容器 | 省握手认证开销、控并发 | 池大小公式、`connection-timeout` 为何要小 |
| N+1 | 1 次主查询 + N 次关联查询 | ORM 懒加载的副作用 | 怎么发现、批量 IN 怎么拼 |
| 覆盖索引 | 查询字段全在索引里 | 避免回表 | `EXPLAIN` 里 `Using index` |
| 深分页 | `limit offset` 大偏移 | 扫描+丢弃大量行 | keyset 分页、延迟关联 |
| `rewriteBatchedStatements` | 驱动把批量改写为多值 insert | 减少网络往返 | 为什么开了才真正批量 |
| gzip / br | HTTP 内容压缩算法 | 省带宽、降传输时间 | 压缩阈值、CPU 代价 |
| Protobuf | 二进制 schema 序列化 | 体积小、编解码快 | 与 JSON 的取舍 |
| Cache-Aside | 先更 DB 再删缓存 | 最常见的缓存一致性模式 | 为什么先更 DB、延迟双删 |
| Caffeine | 本地缓存库（W-TinyLFU） | 纳秒级热点缓存 | 淘汰算法、多节点一致性 |
| 令牌桶 / 漏桶 | 限流算法 | 保护系统容量 | 能否允许突发 |
| 熔断 | 依赖故障时快速失败 | 防雪崩 | 半开状态、错误率阈值 |
| Arthas `trace` / `monitor` | 方法级耗时 / 调用统计 | 定位单次慢调用 | `#cost` 条件、只适合单机 |
| 火焰图 | CPU 采样可视化 | 找热点方法 | 横轴宽度=耗时占比、平顶=热点 |

## 代码验证

```java
// 1) HikariCP 正确配置（快速失败 + 连接寿命小于 DB wait_timeout）
@Bean
public DataSource dataSource() {
    HikariConfig c = new HikariConfig();
    c.setJdbcUrl("jdbc:postgresql://db:5432/appdb");
    c.setUsername("app");
    c.setPassword("***");
    c.setMaximumPoolSize(20);
    c.setConnectionTimeout(3_000);      // 3s 借不到就失败，避免线程堆积
    c.setMaxLifetime(1_800_000);        // 30min < DB wait_timeout
    return new HikariDataSource(c);
}
// 2) 并行化独立调用 + 超时兜底（不要裸线程池）
CompletableFuture<User> userF = CompletableFuture.supplyAsync(
        () -> userClient.get(id), bizExecutor).orTimeout(200, MILLISECONDS);
CompletableFuture<List<Order>> orderF = CompletableFuture.supplyAsync(
        () -> orderClient.list(id), bizExecutor).orTimeout(200, MILLISECONDS);
User user = userF.exceptionally(e -> null).join();          // 失败有兜底
List<Order> orders = orderF.exceptionally(e -> List.of()).join();

// 3) Caffeine + Redis 两级缓存（短 TTL + 失效广播）
Cache<Long, User> local = Caffeine.newBuilder()
        .maximumSize(10_000).expireAfterWrite(Duration.ofSeconds(30)).build();
public User get(Long id) {
    User u = local.getIfPresent(id);
    if (u == null) { u = redis.opsForValue().get("user:" + id); if (u != null) local.put(id, u); }
    return u;
}
// 更新：先 DB 再删 Redis，然后 pub/sub 通知各节点 local.invalidate(id)

// 4) 批量插入：ExecutorType.BATCH + MySQL rewriteBatchedStatements=true
// jdbc:mysql://...?rewriteBatchedStatements=true&useServerPrepStmts=false
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「连接池越大并发越高」 | 超过 DB 处理能力后反而更慢，按公式 + 压测定 |
| 「`connection-timeout` 默认 30s 没问题」 | 故障时会挂住线程造成雪崩，应调 2-3s 快速失败 |
| 「加个 Redis 接口就快了」 | 要分清楚是 DB 慢、序列化慢还是排队，缓存只解热点读 |
| 「`@Async` 加上就异步了」 | 同类调用/private 不生效，且默认线程池不可控 |
| 「gzip 压所有响应」 | 已压缩内容（图片/zip）不压，太小的也浪费 CPU |
