# 线程池（ThreadPoolExecutor）

> 面试权重：5/5　｜　追问深度：**L5（`ctl` 位运算 / Worker 状态机 / 线程复用与回收）**
> 一句话定位：用一组可复用的工作线程 + 一个任务队列承接异步任务，并用 **一个 `AtomicInteger ctl`** 同时编码「线程池状态」和「有效线程数」，靠 CAS 无锁维护。

[返回深度追问索引](../00-索引.md)

## L1 一句话答案（10 秒能说出口）

线程池预先创建并**复用**一批工作线程跑任务：提交任务时按「核心线程 → 阻塞队列 → 非核心线程 → 拒绝策略」四步判断，内部用 `ctl` 高 3 位存运行状态、低 29 位存线程数，空闲线程按 `keepAliveTime` 回收，避免每个任务 `new Thread()` 的创建/销毁开销和无限制膨胀。

## L2 原理层：七大参数 + execute 四步判断

```java
new ThreadPoolExecutor(
    corePoolSize, maximumPoolSize,  // ① 核心线程数（常驻，默认不回收）② 最大线程数（core+临时）
    keepAliveTime, unit,            // ③ 空闲存活时间 ④ 时间单位（默认只作用于超出 core 的线程）
    workQueue,                      // ⑤ 任务队列：核心线程满了之后任务先排队
    threadFactory,                  // ⑥ 线程工厂：自定义线程名，排查问题必须设置
    handler);                       // ⑦ 拒绝策略：队列满且线程数达 max 之后怎么办
```

**`execute()` 四步判断（必须能画出来）**：

```
① workerCount < core                → addWorker(cmd, true)   建核心线程直接跑
② workQueue.offer(cmd) 成功         → 入队 + double-check（STOP? 移除并 reject；
                                      workerCount==0? addWorker(null,false) 补线程）
③ offer 失败（队列满）               → addWorker(cmd, false)  建非核心线程直到 max
④ addWorker 返回 false（已达 max）   → reject(cmd)
```

**反直觉点**：不是先扩到 max 再排队，而是**先排队、队列满了才扩容**。「能进队列」代表任务可接受延迟，没必要为它创建线程；队列都塞不下才说明瞬时过载。想反过来（先扩线程）就把队列换成容量 0 的 `SynchronousQueue`，`offer` 必然失败——这就是 `CachedThreadPool` 的策略。

| 拒绝策略 | 行为 | 适用 |
|---|---|---|
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 必须让调用方感知失败 |
| `CallerRunsPolicy` | 谁提交谁执行（在调用线程跑） | 天然背压不丢任务，但会阻塞上游 Web 线程 |
| `DiscardPolicy` | 静默丢弃 | 可丢的埋点/日志上报 |
| `DiscardOldestPolicy` | 丢队首最老的再试 | 只关心最新值（如状态刷新） |

| 队列 | 边界 | 后果 |
|---|---|---|
| `ArrayBlockingQueue` | 有界 | 生产首选，配拒绝策略形成闭环 |
| `LinkedBlockingQueue` | 默认 `Integer.MAX_VALUE` | 队列永不满 → `max` 形同虚设 → 堆 OOM |
| `SynchronousQueue` | 容量 0 | 必须立刻被线程接走，否则扩容/拒绝 |
| `DelayedWorkQueue` | 无界 | 定时任务（`ScheduledThreadPoolExecutor`） |

## L3 底层层：`ctl` 的位拆分与 Worker 状态机

### 3.1 `ctl`：一个 int 装两样东西

```java
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
private static final int COUNT_BITS = Integer.SIZE - 3;        // 29
private static final int CAPACITY   = (1 << COUNT_BITS) - 1;   // 低 29 位全 1 = 536870911
private static int runStateOf(int c)    { return c & ~CAPACITY; }  // 高 3 位
private static int workerCountOf(int c) { return c &  CAPACITY; }  // 低 29 位
```

```
 bit 31 30 29 | 28 ....................... 0     合并的理由：状态和线程数必须同步变更
 │ runState   │        workerCount          │     （如 STOP 后不许加线程），拆成两个字段
 │  3 bit     │          29 bit             │     就要加锁；合一后可一次 CAS 改两者。
```

| 状态 | 值 | 含义 | 接新任务 | 处理队列 |
|---|---|---|---|---|
| `RUNNING` | `-1 << 29` | 正常 | | |
| `SHUTDOWN` | `0 << 29` | `shutdown()` 后 | | 跑完存量 |
| `STOP` | `1 << 29` | `shutdownNow()` 后 | | 中断在跑线程 |
| `TIDYING` | `2 << 29` | 全部终止，将跑 `terminated()` | | |
| `TERMINATED` | `3 << 29` | `terminated()` 结束 | | |

流转：`RUNNING →shutdown→ SHUTDOWN →(队列空且线程数 0)→ TIDYING → TERMINATED`；`RUNNING →shutdownNow→ STOP → TIDYING → TERMINATED`。注意 `-1 << 29` 是负数，所以源码里状态能直接比大小（`rs >= SHUTDOWN`）。

### 3.2 `Worker` 为什么继承 AQS

```java
private final class Worker extends AbstractQueuedSynchronizer implements Runnable {
    final Thread thread;      // Worker 自己创建的线程
    Runnable firstTask;       // 首个任务，可为 null（补位线程）
    volatile long completedTasks;
}
```

- 它的 **`state` 不表示重入次数，而表示「线程是否正在执行任务/是否可被中断」**：`runWorker` 干活前 `w.lock()`（CAS 0→1），干完 `unlock()`
- `interruptIdleWorkers()` 里 `w.tryLock()` 成功 ⇒ 线程空闲 ⇒ 才 `interrupt()` 让它在 `getTask()` 的 `poll/take` 上醒来；失败 ⇒ 正在跑任务，**不能中断**
- 构造时先 `setState(-1)`，禁止 `start()` 之前被中断；`runWorker` 开头 `unlock()` 放开

### 3.3 线程复用：`runWorker` 的 while 循环

```java
final void runWorker(Worker w) {
    Runnable task = w.firstTask; w.firstTask = null; w.unlock();   // 允许中断（state 归 0）
    while (task != null || (task = getTask()) != null) {           // 重点：复用就发生在这里
        w.lock();                                                  // 标记「忙」
        try { beforeExecute(w, task); task.run(); afterExecute(task, null); }
        finally { task = null; w.completedTasks++; w.unlock(); }
    }
    processWorkerExit(w, false);
}
```

`afterExecute` 默认空实现，子类可在此拿到未捕获异常做统一日志（只对 `execute` 路径有效；`submit` 的异常被 `FutureTask` 吃掉）。

### 3.4 `getTask()`：什么时候返回 `null`（= 线程该死）

```java
boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;      // 是否用「超时版」取任务
Runnable r = timed ? workQueue.poll(keepAliveTime, NANOSECONDS)   // 超时返回 null → 退出循环
                   : workQueue.take();                            // 永久阻塞直到有任务
if (r != null) return r;
if ((wc > maximumPoolSize || (timed && timedOut)) && (wc > 1 || workQueue.isEmpty())
        && compareAndDecrementWorkerCount(ctl)) return null;      // 重点：唯一正常退出路径
```

- **核心线程默认不回收**：`timed=false` 走 `take()` 永久阻塞；`allowCoreThreadTimeOut(true)` 让核心线程也走 `poll(keepAliveTime)`，低峰可缩到 0
- **`timedOut`** 是「上轮 `poll` 已超时」的标记，防抖动；`wc > 1` 保证至少留 1 个线程处理队列

### 3.5 线程池大小估算与「为什么不用 Executors」

`N_threads = N_cpu × U_cpu × (1 + W/C)`，其中 `N_cpu = availableProcessors()`，`U_cpu` 是目标 CPU 利用率，`W/C` 是等待时间/计算时间。**CPU 密集**取 `N_cpu + 1`；**IO 密集**从 `2 × N_cpu` 起步，调 RPC 的池子常见 `4N ~ 8N`。经验值不能抄：先压测，看 CPU 利用率与队列等待时间，线程过多反而上下文切换开销爆炸。**Java 21 虚拟线程**下公式失效——`newVirtualThreadPerTaskExecutor()` 一任务一虚拟线程，瓶颈变成下游连接数（用信号量限流）。

| 工厂方法 | 真实参数 | 事故 |
|---|---|---|
| `newFixedThreadPool` | `LinkedBlockingQueue`（无界） | 任务堆积 → 堆 OOM，`max` 永不生效 |
| `newSingleThreadExecutor` | 同上 | 同上 |
| `newCachedThreadPool` | `max=Integer.MAX_VALUE` + `SynchronousQueue` | 每任务建线程 → 线程爆炸 → `unable to create native thread` |
| `newScheduledThreadPool` | `DelayedWorkQueue`（无界） | 堆积 OOM |

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**

### 第 1 层｜线程池有哪些核心参数？提交一个任务怎么走？
**答**：七个参数（core/max/keepAlive/unit/queue/factory/handler），四步判断：核心没满建核心线程 → 否则入队 → 队列满则建非核心线程到 max → 仍失败走拒绝策略。**钩子**：为什么是这个顺序？

### 第 2 层｜为什么先入队而不是先把线程扩到 max？
**答**：入队成功意味着「任务可以等」，没必要为可等的任务创建实际线程；队列都装不下才说明瞬时过载，扩容才有意义。反过来会丢掉队列这个削峰缓冲。**接着问**：什么场景该反过来？→ `SynchronousQueue` 容量 0，`offer` 必失败，直接走扩容/拒绝。

### 第 3 层｜`ctl` 是什么？为什么合成一个 int？
**答**：`AtomicInteger ctl`，高 3 位状态、低 29 位线程数。合并是为了**一次 CAS 原子地同时改状态与线程数**——状态机不变式（STOP 后不许加线程）跨两个字段就无法无锁保证。取状态 `c & ~CAPACITY`，取线程数 `c & CAPACITY`。**接着问**：为什么不是 2 位状态？

### 第 4 层｜为什么是 3 位状态 + 29 位线程数？
**答**：状态有 5 个值，2 bit 只有 4 个不够，必须 3 bit（8 个值）；剩 29 bit 可表示约 5.36 亿线程，远超实际。另外 `int` 有符号，用高位做状态可借「负数的 RUNNING 比 0 的 SHUTDOWN 小」让状态直接用 `<`、`>=` 比较，源码里到处是 `if (rs >= SHUTDOWN)`。

### 第 5 层｜`shutdown()` 和 `shutdownNow()` 的区别到状态机层？
**答**：`shutdown()` → `advanceRunState(SHUTDOWN)`，只中断**空闲**线程，队列任务继续跑完；`shutdownNow()` → `STOP`，中断**所有**线程并 `drainQueue()` 把队列任务作为返回值吐出。两者最终都流向 `TIDYING → TERMINATED` 并触发 `terminated()` 钩子。**追问**：`shutdown()` 后为什么还能跑完队列？→ `getTask` 判断 `rs < SHUTDOWN` 才拒新任务，但 `take()` 仍取出已有任务。

### 第 6 层｜`Worker` 为什么继承 AQS？`state` 表示什么？
**答**：`state` 表示「是否持有锁」= 线程是否正在执行任务。执行前 `w.lock()`（CAS 0→1），结束 `unlock()`；`interruptIdleWorkers` 用 `tryLock()` 判断——拿得到说明空闲才中断，避免打断正在跑的业务逻辑。**接着问**：为什么构造时先 `setState(-1)`？→ 禁止 `start()` 前被中断，`runWorker` 开头 `unlock` 放开。

### 第 7 层｜线程池怎么「复用」线程？线程什么时候死？
**答**：复用靠 `runWorker` 的 `while (task != null || (task = getTask()) != null)`——线程不退出，继续从队列取下一个任务。退出条件只有 `getTask()` 返回 `null`：`poll` 超时且 `(wc > maximumPoolSize || timedOut) && (wc > 1 || 队列空)`，CAS 扣减线程数成功。异常退出走 `processWorkerExit` 补位。

### 第 8 层｜核心线程怎么回收？`allowCoreThreadTimeOut` 有什么坑？
**答**：`allowCoreThreadTimeOut(true)` 后 `timed = true`，核心线程也 `poll(keepAliveTime)` 超时退出，低峰缩到 0。坑：① 冷启动重新建线程造成延迟尖刺；② `keepAliveTime` 必须 > 0，否则构造即抛 `IllegalArgumentException`；③ 对 `ScheduledThreadPoolExecutor` 语义不同，别混用。

### 第 9 层｜任务里抛异常会怎样？`submit` 和 `execute` 有区别吗？
**答**：`execute` 路径异常从 `task.run()` 冒出，`runWorker` finally 里 `processWorkerExit(w, true)`，**该线程被杀并补新线程**，同时交给 `UncaughtExceptionHandler`；`submit` 路径异常被 `FutureTask.run` 捕获存进 `outcome`，**不打日志也不换线程**，只有 `future.get()` 抛 `ExecutionException`。这是线上「任务静默失败」头号原因。

### 第 10 层｜怎么判断线程池健康？线上监控什么？
**答**：看四个量：`getPoolSize()`、`getActiveCount()`、`getQueue().size()`、`getCompletedTaskCount()`（差分算 TPS）。最关键的是**队列剩余容量**与**拒绝数**：拒绝 > 0 或队列持续满 ⇒ 扩池或限流。注意 `getActiveCount()` 是遍历 workers 估算的，有误差。

### 第 11 层｜线程池没关闭会有什么后果？Spring 里怎么管？
**答**：默认非守护线程，不 `shutdown` 则线程永久 `take()` 阻塞，JVM 无法退出。Spring Boot 自己 `new` 的池要配 `@PreDestroy` 调 `shutdown()`；`ThreadPoolTaskExecutor` 由容器 `destroy()` 管理。`@Async` 必须显式指定执行器名，否则默认 `SimpleAsyncTaskExecutor` 每次新建线程——这才是最大的坑。

### 第 12 层（终局）｜从 `execute(task)` 到任务真正跑起来，机器上发生了什么？
**答**：① CAS 改 `ctl` 争 worker 名额；② 入队或 `addWorker` → `new Worker` → `new Thread(w)` → `t.start()`；③ `start()` → JVM `Thread::start` → native `pthread_create`（Linux 上经 `clone(CLONE_THREAD|CLONE_VM|CLONE_FS|CLONE_FILES)`）分配内核 `task_struct` 与内核栈，进调度队列；④ 新线程 `run()` → `runWorker`，再 `getTask()` 在 `ArrayBlockingQueue.take` 上阻塞，底层是 `ReentrantLock`+`Condition` → `LockSupport.park()` → `futex` 系统调用挂起（**不是自旋**）；⑤ 有任务时 `signal` 唤醒，`task.run()` 在用户态执行；⑥ 超时返回 null、扣减计数、`processWorkerExit`，内核回收 `task_struct`。**分水岭：能说出「park 在 OS 层是 futex」「Linux 创建线程是 clone 不是 fork」。**

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| `ctl` | `AtomicInteger`，高 3 位状态 + 低 29 位线程数 | 一次 CAS 原子维护状态机与线程数 | 拆分公式、为什么不用两个 volatile |
| `CAPACITY` | `(1<<29)-1`，低 29 位掩码 | 位运算取线程数 | `~CAPACITY` 取状态 |
| `runStateOf` / `workerCountOf` | 两个静态位运算方法 | 免去调用方手写掩码 | 手推一遍位运算 |
| `Worker` | 内部类，继承 AQS 且实现 Runnable | 一个对象同时承载线程+任务+忙闲状态 | `state` 语义、为何先 `setState(-1)` |
| `firstTask` | Worker 的首个任务，可为 null | 创建即带任务，省一次入队出队 | 为 null 的场景（补位线程） |
| `getTask` | 取任务的阻塞方法 | 线程复用与超时回收的唯一入口 | 返回 null 的四个条件 |
| `allowCoreThreadTimeOut` | 允许核心线程超时退出 | 低峰缩容到 0 省资源 | 冷启动抖动、必须 `keepAlive>0` |
| `timedOut` | 上一轮 `poll` 是否已超时 | 防止「超时→扣减失败→再进」抖动 | 源码 `timed && timedOut` 语义 |
| `processWorkerExit` | 线程退出后的收尾 | 补足核心线程、检查进 `TIDYING` | 异常退出与正常退出差异 |
| `BlockingQueue` | 任务队列接口 | 削峰 + 排队 | 有界/无界/容量 0 的行为差异 |
| `RejectedExecutionHandler` | 拒绝策略接口 | 过载兜底，不让任务静默消失 | `CallerRunsPolicy` 的背压代价 |
| `pthread_create` / `clone` | OS 层创建线程的系统调用 | 线程最终是内核对象 | Java 线程 = 对象 + `task_struct` |

## 代码验证（`jshell` 逐条跑，Java 17/21 均可）

```java
import java.util.concurrent.*;

// 1) 还原 ctl 位运算：状态能直接比大小
int COUNT_BITS = 29, CAPACITY = (1 << COUNT_BITS) - 1;
int RUNNING = -1 << COUNT_BITS, SHUTDOWN = 0 << COUNT_BITS;
System.out.println(CAPACITY + " " + RUNNING + " " + (RUNNING < SHUTDOWN));  // 536870911 -536870912 true
int ctl = RUNNING | 3;
System.out.println((ctl & ~CAPACITY) + " " + (ctl & CAPACITY));            // -536870912 3

// 2) execute 四步：2 核心 + 2 队列 + 2 临时，第 7 个被拒
ThreadPoolExecutor pool = new ThreadPoolExecutor(2, 4, 60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(2), r -> new Thread(r, "order-pool"));
for (int i = 0; i < 7; i++) {
    final int n = i;
    try {
        pool.execute(() -> { try { Thread.sleep(300); } catch (InterruptedException e) { } });
        System.out.printf("task-%d pool=%d queue=%d%n", n, pool.getPoolSize(), pool.getQueue().size());
    } catch (RejectedExecutionException e) { System.out.println("task-" + n + " 被拒绝"); }
}
pool.shutdown();

// 3) submit 吞异常：只有 get() 才看得到
ExecutorService p2 = Executors.newFixedThreadPool(1);
Future<?> f = p2.submit(() -> { throw new RuntimeException("boom"); });
try { f.get(); } catch (ExecutionException e) { System.out.println("get 才抛: " + e.getCause()); }
p2.shutdown();

// 4) 核心线程回收：开启 allowCoreThreadTimeOut 后能缩到 0
ThreadPoolExecutor p3 = new ThreadPoolExecutor(2, 2, 100, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<>());
p3.execute(() -> System.out.println("run once"));
Thread.sleep(600);
System.out.println("缩容前=" + p3.getPoolSize());   // 核心线程默认不回收
p3.allowCoreThreadTimeOut(true);
Thread.sleep(800);
System.out.println("缩容后=" + p3.getPoolSize());   // 0
p3.shutdown();
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「线程池先扩容到 max，再放队列」 | 核心线程 → 入队 → 队列满才扩到 max → 拒绝 |
| 「`maximumPoolSize` 一定会用到」 | 无界队列下永不触发扩容，`max` 是死参数 |
| 「`Worker` 继承 AQS 是为了重入计数」 | 它的 `state` 表示线程忙/闲，用于安全中断 |
| 「核心线程也会被 keepAliveTime 回收」 | 默认不会；需 `allowCoreThreadTimeOut(true)` |
| 「`shutdown()` 会丢掉队列里的任务」 | 会跑完存量；`shutdownNow()` 才 `drainQueue` |
| 「`submit` 抛异常会被打印出来」 | 被 `FutureTask` 吞掉，只有 `get()` 能看到 |
| 「线程数背 `2N+1` 就行」 | 公式依赖 W/C，必须压测；IO 密集可能 `8N` |
| 「`newFixedThreadPool` 是安全的」 | 无界队列 = OOM 风险，阿里规约禁止 |
