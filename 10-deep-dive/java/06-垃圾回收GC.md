# 垃圾回收（Garbage Collection）

> 面试权重：5/5　｜　追问深度：**L5（三色标记 + 写屏障 + SATB + 着色指针）**
> 一句话定位：GC 的面试题分三层：**怎么判断垃圾（可达性分析）→ 怎么回收（分代 + 三种算法）→ 怎么并发标记还不漏对象（三色标记 + 写屏障）**。第三层是分水岭：能讲清「增量更新」和「原始快照」的差别，才算真的懂 CMS 和 G1。

**本文件用法**：从 L1 往下读，每读完一层合上书自问自答。**停在答不出的那一层，就是你的真实水平线。**

## L1 一句话答案（10 秒能说出口）

JVM 用**可达性分析**从 GC Roots 出发标记活对象，按「对象大多朝生夕死」的分代假说：新生代用**复制算法**（Eden 与两个 Survivor 8:1:1），老年代用**标记-清除/标记-整理**。JDK 9 起默认 **G1**（Region 分区 + 可预测停顿），JDK 17 已经没有 CMS 了（实测 `-XX:+UseConcMarkSweepGC` 直接报 Unrecognized VM option）。

## L2 原理层：判活 + 分代 + 算法 + 收集器

### 2.1 可达性分析

从一组 **GC Roots** 出发沿引用链遍历，能到达的对象存活，不可达的可回收。GC Roots 包括：

- 虚拟机栈/本地方法栈中的局部变量引用（当前方法参数、局部变量）
- 方法区中的静态变量、常量引用（JDK 8 后静态变量随 Class 对象在堆，但仍是根）
- JNI 引用（native 方法持有的全局引用）
- 活动线程对象、被同步锁持有的对象

### 2.2 四种引用强度

| 引用 | 回收时机 | 典型用途 |
|---|---|---|
| 强引用 | 永不回收（除非不可达） | 普通对象 |
| 软引用 `SoftReference` | 内存不足时回收 | 缓存（图片/计算结果） |
| 弱引用 `WeakReference` | 下次 GC 必回收 | `ThreadLocalMap` 的 key、`WeakHashMap` |
| 虚引用 `PhantomReference` | 回收时收到通知 | 清理堆外内存（`Cleaner`） |

### 2.3 分代与算法

| 代 | 特点 | 算法 | 原因 |
|---|---|---|---|
| 新生代（Eden + S0 + S1） | 对象多、存活少 | **复制**（8:1:1，只浪费 10%） | 存活对象少，复制成本低、无碎片 |
| 老年代 | 对象少、存活多 | 标记-清除（有碎片）/ 标记-整理（无碎片） | 存活多时复制不划算 |

### 2.4 收集器演进

| 收集器 | 特点 | 状态 |
|---|---|---|
| Serial / Serial Old | 单线程 STW | 客户端模式/小堆 |
| Parallel / Parallel Old | 多线程，吞吐优先 | JDK 8 默认（现仍是可选） |
| **CMS** | 并发标记清除，低停顿但有碎片 | JDK 9 废弃、**JDK 14 移除** |
| **G1** | Region 分区 + 可预测停顿 | **JDK 9 起的默认收集器**（实测 `UseG1GC=true`） |
| ZGC | 着色指针 + 读屏障，停顿 <1ms | JDK 15 转正，JDK 21 支持分代 |

## L3 底层层：三色标记、写屏障、卡表、Region

### 3.1 三色标记与「漏标」

并发标记时，GC 线程和业务线程同时跑，用三色表示状态：

| 颜色 | 含义 |
|---|---|
| 白 | 还没被访问到（最终会被当作垃圾） |
| 灰 | 自己访问过了，但子引用还没扫完 |
| 黑 | 自己和所有子引用都扫完（不会再扫） |

**漏标的两个必要条件同时成立才会出问题**：

1. 一个**黑色**对象新增了指向**白色**对象的引用（黑色本该扫完了，不会再扫）；
2. 同时，所有从灰对象到该白色对象的引用被**删除**（没有别的路径能再扫到它）。

于是白色对象被当作垃圾回收，程序里却还引用着它 —— 崩溃或数据错乱。两种解法对应两个收集器：

| 方案 | 做法 | 用在哪 |
|---|---|---|
| **增量更新（Incremental Update）** | 记录「黑→白」的**新增**引用，把黑色对象重新变灰、重新扫描 | CMS |
| **原始快照（SATB, Snapshot At The Reference）** | 记录「灰→白」引用**被删除**时的旧值，按「并发标记开始时的快照」为准，把旧值也当活对象 | **G1**、Shenandoah |

SATB 的代价是「浮动垃圾」：快照之后死掉的对象这一轮不会被回收，留到下一轮。

### 3.2 写屏障与卡表

**写屏障（write barrier）** 是 JIT 在「引用赋值」处插入的一小段代码（`oop_store` 的屏障），例如：

```java
// 语义示意：obj.field = value 编译后多一条屏障调用
store(obj.field, value);
if (barrier_needed(obj, value)) {          // 跨代/跨 Region 判断
    card_table[address >> 9] = dirty;      // 卡表标脏（512B 一张卡）
    satb_queue.enqueue(old_value);         // G1：记录删除的旧引用
}
```

- **卡表（Card Table）**：把堆按 512B 切成卡，1 字节标记。YGC 时只需扫「老年代里的脏卡」就能找到跨代引用，**不用扫整个老年代**。
- **RSet（Remembered Set）**：G1 的每个 Region 一份，记录「谁指向我」（来自其他 Region 的卡索引）。YGC/Mixed GC 时用它精确定位外部引用，避免全堆扫描。

### 3.3 G1 的 Region 与停顿预测模型

- 堆被切成约 **2048 个 Region**（每个 1~32MB，必须是 2 的幂），Region 逻辑上扮演 Eden / Survivor / Old；**超过单个 Region 一半大小的对象进 Humongous 区**。
- G1 有两种停顿：**Young GC**（回收所有年轻 Region）和 **Mixed GC**（回收所有年轻 + **部分**老年代，按「回收收益/成本」挑）。
- 停顿预测模型：`-XX:MaxGCPauseMillis`（默认 200ms）是**目标**不是保证。G1 根据历史数据估算「回收某 Region 要多久」，在预算内尽量多收，选出 Collection Set（CSet）。所以 G1 的停顿是「按收益挑出来的」，不是固定值。
- 实测日志格式：`GC(0) Pause Young (Normal) (G1 Evacuation Pause) 14M->2M(32M) 1.479ms`。

### 3.4 GC 日志逐段解读（实测）

```text
[0.052s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 14M->2M(32M) 1.417ms
```

| 片段 | 含义 |
|---|---|
| `[0.052s]` | 启动后 0.052 秒 |
| `GC(0)` | 第 0 次 GC |
| `Pause Young (Normal)` | 停顿类型：年轻代回收 |
| `(G1 Evacuation Pause)` | 触发原因：疏散（复制）式回收 |
| `14M->2M(32M)` | 回收前 14M → 回收后 2M，堆总 32M |
| `1.417ms` | 本次停顿耗时 |

排查接口抖动时看三件事：**停顿时间**（是否 > 目标）、**回收效率**（14M→2M 说明有效）、**频率**（1 秒内 GC 多次说明分配速率过高）。

### 3.5 对象什么时候进老年代

1. 年龄达到 `-XX:MaxTenuringThreshold`（**实测默认 15**，上限也是 15，因为 Mark Word 里 age 只有 4 bit）；
2. **大对象**直接进（G1 里是 Humongous Region）；
3. **动态年龄判断**：Survivor 中某年龄及以下的对象总和超过 Survivor 的一半，该年龄以上的直接晋升；

### 3.6 频繁 Full GC 的排查顺序

① 看日志确认是 Full GC 还是 Mixed/Young（`-Xlog:gc*`）；② 是否**晋升失败**（promotion failed）/ **并发模式失败**（并发收集跟不上分配）；③ 是否有**大对象**（Humongous 分配频繁）；④ 是否**内存泄漏**（dump 后用 MAT 看支配树，重点看集合类和缓存）；⑤ 元空间是否膨胀（反射/动态代理生成类过多）；⑥ 最后才调参（`-Xmx`、`MaxGCPauseMillis`、`InitiatingHeapOccupancyPercent`）。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层拉开差距，第 7 层以后是加分。**

### 第 1 层｜怎么判断对象可以回收？
**答**：可达性分析——从 GC Roots（栈上局部变量、静态变量、常量、JNI 引用、活动线程）出发遍历引用链，不可达的就可以回收。它解决了引用计数的循环引用问题。

### 第 2 层｜为什么不用引用计数？
**答**：① 循环引用永远回收不了（A 引用 B、B 引用 A，计数都不为 0）；② 每次赋值都要维护计数（写屏障开销大）；③ 计数在很多场景下不精确。Python/ObjC 用引用计数+额外机制，Java 直接选了可达性分析。

### 第 3 层｜新生代为什么用复制算法？
**答**：分代假说下新生代对象绝大多数朝生夕死，Minor GC 后存活率通常低于 10%，复制成本极低；而且 Eden 与两个 Survivor 8:1:1 只浪费 10% 空间；复制还顺带整理了内存（无碎片）。如果反过来用标记-清除，存活少反而要扫全代，不划算。

### 第 4 层｜对象什么时候进老年代？
**答**：四条路：年龄到 `MaxTenuringThreshold`（默认 15）、大对象直接进、动态年龄判断（同龄对象总和超 Survivor 一半）、Survivor 放不下。注意年龄上限 15 是硬限制——Mark Word 的 age 只有 4 bit。

### 第 5 层｜三色标记是什么？为什么会漏标？
**答**：白=未访问、灰=自己访问了但子没扫完、黑=自己和子都扫完。并发标记时如果同时满足「黑对象新增指向白对象的引用」和「灰到该白的引用被删除」，这个白对象就再也不会被扫到，被错误回收。解法两条路：增量更新（记新增，把黑重新标灰，CMS）和原始快照（记删除的旧引用，G1）。

### 第 6 层｜写屏障和卡表是干嘛的？
**答**：写屏障是 JIT 插在引用赋值处的代码，用来在赋值发生时记录「需要重新检查」的信息；卡表是它的落地结构，把堆按 512B 分卡、标脏，YGC 只扫老年代的脏卡就能找到跨代引用，避免全堆扫描。G1 还多了每个 Region 的 RSet，记录「谁指向我」，Mixed GC 靠它挑要回收的 Region。

### 第 7 层｜CMS 为什么被废弃？
**答**：三个硬伤：① 标记-清除产生**内存碎片**，大对象分配失败就触发 Full GC；② **Concurrent Mode Failure**——并发清理期间业务又填满老年代，CMS 被迫退化成 Serial Old 单线程 Full GC，停顿可能几秒；③ 无法处理浮动垃圾，且实现复杂。JDK 9 标记废弃（JEP 291），JDK 14 移除（JEP 363）——所以在 JDK 17 上传 `-XX:+UseConcMarkSweepGC` 会直接报 Unrecognized VM option（实测）。

### 第 8 层｜G1 怎么做到「可预测停顿」？
**答**：G1 把堆切成约 2048 个 Region，不再要求连续分代，每次回收只挑一部分 Region 组成 CSet，并用**历史数据估算**每个 Region 的回收成本，在 `MaxGCPauseMillis`（默认 200ms）预算内挑收益最高的那些。所以「可预测」是统计意义上的目标，不是硬保证；Region 小、回收量可控，才让它比 CMS 更容易控停顿。

### 第 9 层｜那 ZGC 凭什么停顿 <1ms？和 G1 差在哪？
**答**：G1 的标记和复制（Evacuation）都需要 STW 或大量写屏障维护 RSet；ZGC 用**着色指针**（指针里 4 个 bit 记录对象状态）+ **读屏障**把「移动对象」这件事和业务线程解耦：标记/移动/重映射全部并发，只有极短的 STW 阶段（初始化标记、再标记）。代价是读屏障带来的吞吐损失和更高内存占用，且需要 64 位地址空间。

### 第 10 层（终局）｜SATB 队列在 CPU 层是怎么落地的？
**答**：G1 的写屏障在 `oop_store` 处插桩，判断若发生「灰→白」的引用覆盖，就把**旧引用**压入线程本地的 `SATBMarkQueue`（`enqueue` 是写内存的原子操作），队列满后由并发标记线程批量 drain 进全局队列。这个屏障在 x86 上体现为 `StoreStore` 语义（确保旧值在覆盖前被记录），而并发标记线程读队列时通过原子/内存屏障保证可见性。**整个过程没有 STW**——这就是「并发标记 + 原始快照」的代价：额外写屏障指令 + 浮动垃圾。再往下就是 CPU 的 store buffer 与内存屏障指令（`mfence`/`lock`），一条 `mov` 之后必须等写完成才能保证别的核看到，这是所有并发 GC 写屏障的物理基础。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| GC Roots | 可达性分析的起点集合 | 判活 | 具体包含哪几类 |
| 复制算法 | 复制存活对象到另一半 | 无碎片、成本与存活量成正比 | 8:1:1 只浪费 10% |
| 三色标记 | 白/灰/黑表示标记进度 | 支持并发标记 | 漏标的两个条件 |
| 增量更新 | 记录黑→白的新增引用 | 防漏标（CMS） | 与 SATB 的差别 |
| 原始快照 SATB | 记录被删除的旧引用 | 防漏标（G1） | 为什么会产生浮动垃圾 |
| 写屏障 | JIT 插在引用赋值处的钩子 | 让并发 GC 感知引用变化 | 与内存屏障不是一回事 |
| 卡表 | 512B 一张卡的脏位数组 | 快速找跨代引用 | 为什么 YGC 不全扫老年代 |
| RSet | G1 每个 Region 的「谁指向我」 | 定位跨 Region 引用 | Mixed GC 依赖它 |
| Region | G1 的堆分区（1~32MB，约 2048 个） | 回收粒度可控、可预测停顿 | Humongous 是什么 |
| Humongous | 超过半个 Region 的大对象区 | 大对象不适合 Region 内复制 | 大对象为什么容易引发 Full GC |
| 着色指针 | 指针高位存对象状态（ZGC） | 并发移动对象 | 读屏障的作用 |

## 代码验证（`GcProbe.java`，JDK 17 编译运行通过）

```java
import java.util.*;

public class GcProbe {
    public static void main(String[] args) {
        System.out.println("maxHeap=" + Runtime.getRuntime().maxMemory() / 1024 / 1024 + "MB");
        List<byte[]> keep = new ArrayList<>();
        for (int i = 0; i < 200_000; i++) {
            keep.add(new byte[512]);                       // 制造大量短命对象
            if (keep.size() > 2048) keep.clear();          // 存活对象很少 → 复制算法最划算
        }
        for (int i = 0; i < 50; i++) {
            keep.add(new byte[1024 * 1024]);               // 大对象：可能进 Humongous/老年代
        }
        System.out.println("done, used=" + (Runtime.getRuntime().totalMemory()
                - Runtime.getRuntime().freeMemory()) / 1024 / 1024 + "MB, keep=" + keep.size());
    }
}
```

```bash
javac -encoding UTF-8 GcProbe.java

# 用 32MB 小堆，强制频繁 Young GC，观察日志（Pause Young / 14M->2M）
java -Xmx32m -Xlog:gc GcProbe

java -Xmx32m -Xlog:gc+heap=debug GcProbe

# 确认默认收集器与 TenuringThreshold
java -XX:+PrintFlagsFinal -version | grep -E 'UseG1GC|UseConcMarkSweepGC|MaxTenuringThreshold|UseStringDeduplication'

# JDK 17 上 CMS 已经没了（会报 Unrecognized VM option）
java -XX:+UseConcMarkSweepGC -version
# JDK 17 可用 ZGC
java -XX:+UseZGC -Xmx64m -version
```

**实测输出（`-Xmx32m -Xlog:gc` 片段）**：

```
[0.006s][info][gc] Using G1
[0.052s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 14M->2M(32M) 1.479ms
[0.079s][info][gc] GC(1) Pause Young (Normal) (G1 Evacuation Pause) 17M->1M(32M) 1.023ms
```

**实测标志**：`UseG1GC = true {ergonomic}`、`MaxTenuringThreshold = 15 {default}`、`UseStringDeduplication = false {default}`；`-XX:+UseConcMarkSweepGC` → `Unrecognized VM option`。

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「JVM 用引用计数判断垃圾」 | 用可达性分析；引用计数解决不了循环引用 |
| 「年轻代和老年代比例 8:1:1」 | 8:1:1 是 Eden:S0:S1；新生代:老年代 默认 1:2 |
| 「写屏障就是内存屏障」 | 写屏障是 JVM 的引用记录钩子；内存屏障是 CPU/编译器的重排约束 |
| 「CMS 还存在于 JDK 17」 | JDK 14 已移除，17 上直接报 Unrecognized VM option |
| 「G1 能精确保证 200ms 停顿」 | `MaxGCPauseMillis` 是目标值，靠 Region 收益估算尽量达成 |
| 「Full GC 一次就调大堆」 | 先看是晋升失败、Humongous、泄漏还是元空间；盲目调大可能更慢 |
