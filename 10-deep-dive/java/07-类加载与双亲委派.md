# 类加载与双亲委派（Class Loading & Parent Delegation）

> 面试权重：4/5　｜　追问深度：**L5（ClassFileParser 验证 + SystemDictionary + 类卸载）**
> 一句话定位：类加载的面试分三层：**五个阶段都干什么（准备阶段赋零值是第一个坑）→ 双亲委派为什么存在、怎么被打破（SPI/Tomcat）→ 两个同名类为什么不等、类什么时候能卸载**。最后一层直接对应「热部署怎么实现」这个工程问题。

**本文件用法**：从 L1 往下读，每读完一层合上书自问自答。**停在答不出的那一层，就是你的真实水平线。**
[返回深度追问索引](../00-索引.md)

## L1 一句话答案（10 秒能说出口）

类加载分**加载 → 验证 → 准备 → 解析 → 初始化**五步：准备阶段只给 static 变量赋**零值**，赋代码里的值发生在初始化（执行 `<clinit>`）。**双亲委派**是加载类时先委派父加载器、父加载不了才自己加载，好处是防止核心类被篡改、避免重复加载；SPI（JDBC）、Tomcat、OSGi 会打破它。

## L2 原理层：五阶段 + 三层加载器

```
                     ┌──────────────────────────┐
   new/反射/静态访问 →│ 加载 Loading              │ 读字节码 → 生成 Class 对象（堆中）
                     ├──────────────────────────┤
                     │ 验证 Verification         │ 文件格式/元数据/字节码/符号引用
                     ├──────────────────────────┤
                     │ 准备 Preparation          │ static 变量赋【零值】；final 常量赋终值
                     ├──────────────────────────┤
                     │ 解析 Resolution           │ 常量池符号引用 → 直接引用
                     ├──────────────────────────┤
                     │ 初始化 Initialization     │ 执行 <clinit>：真正赋代码里的值
                     └──────────────────────────┘
```

| 加载器 | 加载什么 | 实现语言 |
|---|---|---|
| Bootstrap（启动类加载器） | `java.*` 核心库（JAVA_HOME/lib/modules） | C++，非 Java 对象（`cl.getParent()` 返回 null） |
| Platform（平台类加载器，JDK9 前叫 Ext） | `javax.*` 等平台模块 | Java |
| App（系统类加载器） | classpath / 应用类 | Java |
| 自定义 ClassLoader | 从任意位置加载（网络、加密 jar、热部署） | Java |

**实测父链**：`AppClassLoader → PlatformClassLoader → (Bootstrap，返回 null)`；`ClassLoadProbe.class.getClassLoader()` 是 App。

## L3 底层层：验证、初始化、loadClass 源码、卸载

### 3.1 加载：Class 对象在堆，元数据在元空间

- 「加载」做三件事：① 通过类的全限定名拿到二进制字节流（从哪里拿由 ClassLoader 决定）；② 把字节流转成方法区（JDK 8+ 元空间）里的运行时数据结构；③ 在**堆**里生成一个 `java.lang.Class` 对象作为访问入口。
- `defineClass(byte[], off, len)` 是 native 方法，由 JVM 解析字节码并创建 Class；`findClass` 是 ClassLoader 给子类留的扩展点。
- **注意**：`Class` 对象在堆上，所以它也是 GC 可达性分析中的一类根（系统类加载器加载的类通常不会被卸载）。

### 3.2 验证：字节码必须可信

四个阶段（顺序递进）：

1. **文件格式验证**：魔数 `0xCAFEBABE`、主次版本号（不能高于当前 JVM）、常量池索引合法性。
2. **元数据验证**：语义检查（有无父类、是否继承了 final 类、抽象方法是否被实现、字段是否与父类冲突）。
3. **字节码验证**（最复杂）：数据流与控制流分析，保证操作数栈不溢出、跳转不越界、类型转换合法、局部变量表使用正确。JDK 7+ 用 **StackMapTable** 属性做类型检查（省去推导），这也是「高版本编译的 class 低版本 JVM 跑不了」的部分原因。
4. **符号引用验证**：解析时检查引用的类/字段/方法是否真的存在、访问权限是否够（`IllegalAccessError` 就出在这里）。

### 3.3 准备 vs 初始化：第一个坑

```java
public class Demo {
    static int a = 1;                        // 准备阶段：a = 0；初始化阶段：a = 1
    static final int B = 2;                  // 编译期常量 → 准备阶段直接 B = 2（常量折叠）
    static final int C = (int) (Math.random() * 10); // 不是编译期常量 → 初始化才赋值
}
```

**初始化时机（六种，必须背）**：`new`、读/写静态字段或调静态方法、反射、初始化子类前先初始化父类、启动类（含 main）、`MethodHandle` 解析结果指向该类。**以下三种「被动引用」不会触发初始化**：通过子类引用父类的静态字段（只初始化父类）、定义数组 `Demo[] arr = new Demo[10]`、引用编译期常量。

`<clinit>` 是 JVM 层面的构造器，**JVM 保证多线程下只执行一次**（内部加锁 + 状态标记），所以「静态初始化里的单例」天然线程安全——这也是静态内部类单例成立的原因。

### 3.4 双亲委派：`loadClass` 源码（JDK 17 实测）

```java
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {          // 并行加载锁（JDK7+）
        Class<?> c = findLoadedClass(name);             // ① 已加载就直接返回
        if (c == null) {
            long t0 = System.nanoTime();
            try {
                if (parent != null) c = parent.loadClass(name, false);  // ② 委派父加载器
                else c = findBootstrapClassOrNull(name);                // ③ 父为 null 则找 Bootstrap
            } catch (ClassNotFoundException e) { /* 父加载不到，继续 */ }
            if (c == null) {
                c = findClass(name);                    // ④ 自己加载（子类重写 findClass）
            }
        }
        if (resolve) resolveClass(c);
        return c;
    }
}
```

**好处**：① 安全——`java.lang.String` 只会由 Bootstrap 加载，自己伪造一个也没用；② 避免重复加载——同一个类在父加载器加载过后子加载器不会重复定义。

### 3.5 打破双亲委派的四种场景

| 场景 | 谁打破了 | 做法 |
|---|---|---|
| **SPI / JDBC** | `ServiceLoader` | 线程上下文类加载器（TCCL）：父加载器加载的接口，用子加载器加载实现 |
| **Tomcat** | `WebappClassLoader` | 每个 WebApp 一个加载器；**先自己找、找不到再委派父**（除核心类外），实现应用间隔离 + 热部署 |
| **OSGi** | BundleClassLoader | 网状委派，按 bundle 依赖图查找 |
| **Spring Boot fat jar** | `LaunchedClassLoader` | 加载 `BOOT-INF/classes` 与嵌套 jar，不理解「jar 里的 jar」就自己写加载器 |

**SPI 为什么必须用 TCCL**：`DriverManager` 在 `java.base` 里（Bootstrap 加载），而 MySQL 驱动 `com.mysql.cj.jdbc.Driver` 在 classpath（App 加载）。Bootstrap 的父链看不到 App 的类，于是 `ServiceLoader` 用 `Thread.currentThread().getContextClassLoader()`（默认就是 App CL）去加载实现类——**「父加载器要用子加载器的类」正是双亲委派的反方向**。

### 3.6 两个类「相等」的条件与类卸载

- `Class` 相等的条件：**全限定名相同 + 类加载器相同**（`isInstance`/`instanceof`/`equals` 都遵循）。实测：同一份字节码用两个不同的 `MyLoader` 各加载一次，得到两个不相等的 `Class` 对象，互相 `instanceof` 为 false。
- 类卸载条件（三者同时满足）：① 该类的所有实例都不可达；② 该类的 `Class` 对象不可达；③ 加载该类的 ClassLoader 不可达。所以**系统类加载器加载的类永远不会被卸载**——热部署必须用自定义 ClassLoader，并丢掉旧加载器的所有引用。
- 回收的是**元空间**里的类元数据，这就是「Metaspace 能涨也能降」的原因。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层拉开差距，第 7 层以后是加分。**

### 第 1 层｜类加载的过程？
**答**：加载（读字节码、生成 Class 对象）→ 验证（格式/元数据/字节码/符号引用）→ 准备（static 变量赋零值，final 常量赋终值）→ 解析（符号引用转直接引用）→ 初始化（执行 `<clinit>`，真正赋值）。加载、验证、准备、解析、初始化这几步的顺序是确定的，但解析可以在初始化之后才发生（支持动态绑定）。

### 第 2 层｜准备阶段给 static 变量赋什么值？
**答**：赋**零值**（`int` → 0、引用 → null、`boolean` → false）。代码里写的 `static int a = 1` 中的 `1` 是初始化阶段执行 `<clinit>` 时才赋的。唯一例外是 `static final` 编译期常量：它在准备阶段就赋终值（因为常量折叠，值已经在常量池里）。

### 第 3 层｜双亲委派是什么？有什么好处？
**答**：加载类时先让父加载器加载，父加载不了才自己加载。好处两个：安全（核心类只能由 Bootstrap 加载，防止 `java.lang.String` 被伪造替换）和避免重复加载。实现就在 `ClassLoader.loadClass` 里：`findLoadedClass` → `parent.loadClass` → `findClass`。

### 第 4 层｜我自己写一个 `java.lang.String` 能加载吗？为什么？
**答**：不能。`loadClass` 会先委派给父加载器，最终委派到 Bootstrap，它发现 `java.lang.String` 已经加载过（在核心库里）就直接返回那个 Class，你写的类根本没有被定义的机会。而且即使绕过（比如用自定义加载器直接 `defineClass`），JVM 也会抛 `SecurityException: Prohibited package name: java.lang`。

### 第 5 层｜SPI 为什么要用线程上下文类加载器？
**答**：因为「接口在父加载器、实现在子加载器」。以 JDBC 为例：`DriverManager` 在 `java.base` 由 Bootstrap 加载，驱动实现在 classpath 由 AppClassLoader 加载；Bootstrap 的父链上根本看不到 App 的类，靠双亲委派加载不到实现。于是 `ServiceLoader` 用 `Thread.currentThread().getContextClassLoader()` 反方向去找子加载器的类——这就是「打破双亲委派」。Spring/MyBatis 的 SPI、`ServiceLoader` 都这么干。

### 第 6 层｜两个类相等的条件是什么？
**答**：全限定名相同 **且** 类加载器相同。所以同一份字节码被两个 ClassLoader 各加载一次，会得到两个互不相等的 Class，`instanceof` 为 false、强转报 `ClassCastException`。这也解释了 Tomcat 为什么每个应用一个加载器——同名类在不同应用里互不干扰；以及热部署为什么会「旧对象还在、新类已加载」导致类型不匹配。

### 第 7 层｜`Class.forName` 和 `ClassLoader.loadClass` 有什么区别？
**答**：`loadClass` 只做「加载」（不初始化，静态块不执行）；`Class.forName(name)` 默认 `initialize=true`，会走完初始化（执行 `<clinit>`）。实测：`loadClass` 不打印静态块，`forName` 会打印。JDBC 老代码用 `Class.forName("com.mysql.jdbc.Driver")` 就是因为「要触发驱动类的静态块去注册自己」；JDK 6+ 其实靠 SPI 自动注册，那一行只是兼容写法。

### 第 8 层｜类什么时候能被卸载？热部署怎么实现？
**答**：必须三者同时满足：该类的所有实例不可达、它的 `Class` 对象不可达、加载它的 ClassLoader 不可达。系统类加载器永远可达，所以它加载的类永远不卸载。热部署的做法：每次部署 `new` 一个自定义 ClassLoader 加载类，重新部署时丢掉旧加载器（切断所有引用，包括线程、缓存、注册表里持有的对象），触发 GC 后旧类元数据被回收，再用新加载器加载同名类。

### 第 9 层｜Tomcat 的类加载器为什么要打破双亲委派？
**答**：Tomcat 里每个 WebApp 有独立的 `WebappClassLoader`，加载顺序是「先看自己（`WEB-INF/classes`、`WEB-INF/lib`）→ 再委派父」。这样做的目的是**隔离**：两个应用依赖不同版本的同一个 jar 互不干扰，且应用自己优先（除 `java.*` 等核心类仍强制委派）。代价是内存占用高（每个应用一套类）、以及跨应用共享对象要走特定机制。

### 第 10 层（终局）｜HotSpot 里一次 `loadClass` 最后落在哪些数据结构上？
**答**：Java 层的 `loadClass` 只是委派策略，真正的定义在 native 的 `ClassLoader.defineClass1` → `JVM_DefineClassWithSource` → `ClassFileParser::parseClassFile`（HotSpot，`src/hotspot/share/classfile/classFileParser.cpp`）完成魔数/版本/常量池/字段方法/StackMapTable 的解析与验证；然后 `SystemDictionary::resolve_or_fail` 查表——这张表就是「类加载器 + 类名 → InstanceKlass」的全局字典，键里包含加载器，所以**同名不同加载器是两个条目**；类的元数据挂在 `ClassLoaderData`（CLD）下，`ClassLoaderDataGraph` 管理所有 CLD，卸载时销毁 CLD 并回收元空间。这也解释了为什么「加载器可达 → 类不可卸载」：CLD 的生命周期绑定在加载器上。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 加载 Loading | 读字节流 → Class 对象 | 把磁盘/网络的字节变成 JVM 可用的类 | Class 对象在堆还是元空间 |
| 验证 Verification | 检查字节码合法性 | 防止恶意/损坏的 class 破坏 JVM | 四阶段分别查什么 |
| 准备 Preparation | static 变量赋零值 | 保证字段有确定初始状态 | 为什么不是赋代码里的值 |
| 解析 Resolution | 符号引用 → 直接引用 | 把「名字」变成「地址」 | 为什么可以推迟到初始化后 |
| 初始化 Initialization | 执行 `<clinit>` | 真正执行静态初始化代码 | 六种触发 + 三种被动引用 |
| `<clinit>` | 类初始化方法 | 承载静态块与静态赋值 | 线程安全由谁保证（JVM 加锁） |
| 双亲委派 | 父优先加载策略 | 安全 + 避免重复加载 | 源码在哪（loadClass） |
| TCCL | 线程上下文类加载器 | 让父加载器能加载子加载器的类 | SPI/JDBC 为什么需要它 |
| `defineClass` | native，生成 Class | 真正「定义」一个类 | 和 `loadClass` 的区别 |
| `findClass` | 给子类重写的查找钩子 | 自定义来源加载 | 重写它还是重写 loadClass |
| SystemDictionary | HotSpot 的类字典（含加载器） | 全局唯一化的 Class | 同名不同加载器为何不等 |
| ClassLoaderData | 加载器关联的元数据容器 | 类卸载时统一释放 | 卸载三个条件 |
| LaunchedClassLoader | Spring Boot 加载 fat jar 的加载器 | 处理 jar in jar | 为什么需要自定义加载器 |
| 被动引用 | 不触发初始化的引用方式 | 明确初始化时机 | 数组/父类字段/编译期常量 |

## 代码验证（`ClassLoadProbe.java`，JDK 17 编译运行通过）

```java
import java.io.IOException;
import java.nio.file.*;
import java.lang.reflect.*;

public class ClassLoadProbe {
    static class InitMarker {                                  // 观察初始化时机
        static { System.out.println("        >> InitMarker.<clinit> 执行了"); }
        static int X = 42;
    }
    static class MyLoader extends ClassLoader {                // 自定义加载器
        private final Path dir;
        MyLoader(Path dir) { super(ClassLoadProbe.class.getClassLoader()); this.dir = dir; }
        @Override protected Class<?> findClass(String name) throws ClassNotFoundException {
            try {
                byte[] b = Files.readAllBytes(dir.resolve(name.replace('.', '/') + ".class"));
                return defineClass(name, b, 0, b.length);
            } catch (IOException e) { throw new ClassNotFoundException(name, e); }
        }
    }
    public static void main(String[] args) throws Exception {
        System.out.println("[1] 父加载器链：");
        for (ClassLoader c = ClassLoadProbe.class.getClassLoader(); c != null; c = c.getParent())
            System.out.println("        " + c);

        System.out.println("[2] loadClass 不初始化：");
        Class<?> c1 = ClassLoadProbe.class.getClassLoader().loadClass("ClassLoadProbe$InitMarker");
        System.out.println("        loaded=" + c1.getSimpleName());   // 不打印 clinit
        System.out.println("[3] Class.forName 会初始化：");
        Class.forName("ClassLoadProbe$InitMarker");                   // 打印 clinit

        Path out = Paths.get("plugin-out");                            // 放一份编译好的 plugin/Plugin.class
        Class<?> p1 = new MyLoader(out).loadClass("plugin.Plugin");
        Class<?> p2 = new MyLoader(out).loadClass("plugin.Plugin");
        System.out.println("[4] 同一份字节码、两个加载器：p1==p2 ? " + (p1 == p2));   // false
        Object obj = p1.getDeclaredConstructor().newInstance();
        System.out.println("        invoke = " + p1.getMethod("hello").invoke(obj));
    }
}
```

```bash
# 先准备一份不在 classpath 上的类，验证自定义加载器
mkdir -p plugin-src/plugin plugin-out
cat > plugin-src/plugin/Plugin.java <<'EOF'
package plugin;
public class Plugin { public String hello() { return "hello from " + getClass().getClassLoader(); } }
EOF
javac -encoding UTF-8 -d plugin-out plugin-src/plugin/Plugin.java

javac -encoding UTF-8 ClassLoadProbe.java
java ClassLoadProbe
```

**实测输出**：父链 `AppClassLoader → PlatformClassLoader`；`loadClass` 不打印 `<clinit>`、`forName` 打印；`p1 == p2 ? false`，`invoke = hello from ClassLoadProbe$MyLoader@...`。

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「准备阶段就给 static 变量赋值」 | 准备阶段赋零值，赋值在初始化阶段 |
| 「Bootstrap 是 Java 实现的，`getParent()` 能拿到」 | 它是 C++ 实现，`getParent()` 返回 null |
| 「双亲委派保证类只被加载一次」 | 保证「同一个加载器链上」不重复；不同加载器可各加载一份 |
| 「`Class.forName` 和 `loadClass` 一样」 | 前者初始化（跑 `clinit`），后者只加载 |
| 「自定义加载器必须重写 loadClass」 | 一般只重写 `findClass`，保留双亲委派逻辑 |
| 「类加载后永远不会卸载」 | 满足三条件可卸载；系统类加载器加载的确实永不卸载 |
| 「Tomcat 也完全遵守双亲委派」 | 它先自己找再委派父，属于打破场景 |
