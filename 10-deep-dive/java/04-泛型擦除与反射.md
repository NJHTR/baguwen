# 泛型擦除与反射（Type Erasure & Reflection）

> 面试权重：4/5　｜　追问深度：**L5（字节码 Signature 属性 + `Method.invoke` 的 inflation）**
> 一句话定位：泛型是**编译期幻觉**，反射是**运行期特权**——两者正好是一对：泛型把类型信息删掉、反射靠元数据把它找回来。面试从「擦除后怎么还能拿到 `List<String>`」一路追到「`Method.invoke` 为什么前 15 次慢、之后变快」，答得出这层就是「读过字节码和 JDK 源码」的水平。

**本文件用法**：从 L1 往下读，每读完一层合上书自问自答。**停在答不出的那一层，就是你的真实水平线。**
[返回深度追问索引](../00-索引.md)

## L1 一句话答案（10 秒能说出口）

Java 泛型在编译期检查、编译后**擦除**为 `Object` 或上界，所以运行时 `List<String>` 和 `List<Integer>` 是同一个类；泛型信息只保留在 class 文件的 `Signature` 属性里，反射能读到但没法用它做运行时类型检查。反射则是运行时通过 `Class` 对象拿构造器/方法/字段并调用，框架（Spring、MyBatis、Jackson）全靠它。

## L2 原理层：擦除的三条规则 + 反射的三条路径

### 2.1 擦除规则

| 声明 | 擦除后 | 说明 |
|---|---|---|
| `T` | `Object` | 无界类型参数 |
| `T extends Number` | `Number` | 有上界，擦成第一个上界 |
| `List<String>` | `List` | 类型实参整个消失 |

**由此产生的限制**：不能 `new T()`、不能 `T.class`、不能 `new T[10]`、不能 `instanceof List<String>`、类的静态成员不能用类级泛型参数（静态上下文拿不到 `T`）。

### 2.2 反射三条获取 `Class` 的路径

```java
Class<?> c1 = User.class;                      // 字面量，编译期确定，最安全
Class<?> c2 = user.getClass();                 // 运行时对象反查
Class<?> c3 = Class.forName("com.x.User");     // 字符串加载，会触发类初始化
```

### 2.3 通配符 PECS（Producer Extends, Consumer Super）

| 写法 | 能读 | 能写 | 直觉 |
|---|---|---|---|
| `List<? extends Number>` | 读到 `Number` | **不能写**（除 null） | 生产者：我只从里面拿 |
| `List<? super Integer>` | 只能读到 `Object` | 能写 `Integer` | 消费者：我只往里放 |
| `List<Number>` | 读到 `Number` | 能写 `Number` | 不变（invariant） |

原因还是擦除：`? extends Number` 的运行时类型未知（可能是 `List<Integer>` 也可能是 `List<Double>`），编译器不敢让你写入。

## L3 底层层：Signature 属性、桥接方法、invoke 的 inflation

### 3.1 擦除的证据：descriptor 被擦、Signature 保留

`javap -v` 看一个泛型方法 `List<String> names()` 的 class 文件：

```
descriptor: ()Ljava/util/List;                          ← 方法描述符：擦除后的真实签名
Signature: #39  // ()Ljava/util/List<Ljava/lang/String;>;  ← 泛型信息存在这里
```

- **descriptor** 是 JVM 链接/调用时唯一认的东西，已经被擦除。
- **Signature** 是给反射/编译器看的「附加属性」，JDK 5 引入，老 JVM 直接忽略。
- 所以 `Method.getReturnType()` 返回 `interface java.util.List`，而 `Method.getGenericReturnType()` 返回 `java.util.List<java.lang.String>`（实测）。

泛型的真实类型还能从**父类的泛型声明**里捞：`new TypeReference<List<User>>(){}` 创建匿名子类后，`getClass().getGenericSuperclass()` 能拿到 `ParameterizedType`，进而取出 `User`——Jackson、Spring 的 `ResolvableType` 都这么干。**这也是为什么泛型反序列化必须写成匿名子类，不能直接传 `List<User>.class`。**

### 3.2 桥接方法：擦除的补丁

```java
class Box implements Comparable<Box> {
    public int compareTo(Box o) { return 0; }   // 我们写的
}
```

擦除后接口里的方法签名是 `compareTo(Object)`，而我们只实现了 `compareTo(Box)`。为了让多态调用（通过 `Comparable` 接口引用调用）能落到我们的方法上，编译器**自动生成**一个桥接方法：

```
public int compareTo(java.lang.Object);        ← 编译器生成
    descriptor: (Ljava/lang/Object;)I
    flags: ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
```

**实测** `getDeclaredMethods()` 会看到**两个** `compareTo`：`compareTo(Box)`（bridge=false）和 `compareTo(Object)`（bridge=true, synthetic=true）。桥接方法内部做一次 `checkcast Box` 再转调真正的实现。

这个知识点在 Spring AOP、CGLIB 代理里会反复出现：**反射遍历方法时会把桥接方法也遍历出来**，Spring 的 `BridgeMethodResolver` 就是为了解决这个。

### 3.3 `Method.invoke` 的真实调用链与 inflation

```
Method.invoke(obj, args) → DelegatingMethodAccessorImpl
  └─ NativeMethodAccessorImpl        ← 前 15 次：JNI，慢
     if (++numInvocations > inflationThreshold) generateAccessor()
        └─ 字节码版 accessor → setDelegate(...)   ← 之后快
```

- `NativeMethodAccessorImpl`：用 JNI 调 `Method.invoke0`，省去字节码生成成本，适合「只调用几次」的场景。
- 调用次数超过阈值后 **inflation（膨胀）**：用 `MethodAccessorGenerator` 动态生成一个类（内部类名类似 `GeneratedMethodAccessor1`），直接执行 `checkcast` + `invokevirtual`，把反射调用降级成接近直接调用。
- **阈值默认 15**：`ReflectionFactory` 里 `private static int inflationThreshold = 15;`（JDK 17 源码实测），可用 `-Dsun.reflect.inflationThreshold=N` 改；`-Dsun.reflect.noInflation=true` 则从一开始就用字节码版。
- 注意：这个生成过程要创建类，所以**会占用 Metaspace**；大量不同的 `Method` 各生成一个类也是元空间 OOM 的常见来源之一（框架应缓存 `Method`）。

> JDK 18 的 **JEP 416** 把整条 accessor 链换成了 `MethodHandle`（`DirectMethodHandleAccessor`），inflation 机制被移除。你是 Java 21，可以说「21 里已经没有 NativeMethodAccessor 那套了，但思想——先解释执行、热了再优化——没变」。

### 3.4 反射为什么慢：查找、调用、包装

1. **查找**：`getDeclaredMethods()` 每次都要解析、复制数组、校验，成本极高（所以框架都缓存 `Method`/`Field`）。
2. **调用**：前 15 次走 JNI，之后走生成的字节码（仍比直接调用多一次 `checkcast` + 数组拷贝参数）。
3. **包装**：`invoke(Object, Object...)` 要装箱/拆箱、创建 `Object[]` 参数数组；`setAccessible(true)` 跳过访问检查能再省一点（但模块化后不一定允许）。

**结论**：反射不是「慢一个量级」，调用点热了之后大约是直接调用的 2-3 倍；真正的性能杀手是「每次都查找」和「参数装箱」，而不是 `invoke` 本身。

### 3.5 模块化之后：`setAccessible` 的边界

JDK 9 起 `java.base` 的私有成员默认不开放反射：`Field.setAccessible(true)` 会抛 `InaccessibleObjectException`，除非：

- 启动参数 `--add-opens java.base/java.lang=ALL-UNNAMED`（实测：不加就报 `module java.base does not "opens java.lang"`）；
- 或者模块 `module-info.java` 里 `opens` 该包。

这也解释了为什么 Spring Boot 3 / 高版本 JDK 上老代码经常报 `InaccessibleObjectException`——**不是 Spring 的问题，是模块系统的边界**。

### 3.6 框架里的反射落点（面试举例用）

| 框架 | 用反射做什么 | 关键 API |
|---|---|---|
| Spring IoC | 扫注解 → 反射实例化 Bean、注入字段/构造器 | `Class.newInstance`/`Constructor.newInstance`、`Field.set` |
| Spring MVC | 参数绑定、`@Valid` 校验、返回值序列化 | `Method.getParameters`、`getGenericParameterTypes` |
| MyBatis | 把 `ResultSet` 映射成实体，读泛型 Mapper 方法返回类型 | `setAccessible` + `ResultSet.getObject` |
| Jackson | 序列化/反序列化字段，泛型靠 `TypeReference` | `getGenericSuperclass`、`ParameterizedType` |

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层拉开差距，第 7 层以后是加分。**

### 第 1 层｜什么是类型擦除？
**答**：Java 泛型只在编译期做类型检查，编译后 `List<String>` 变成 `List`，`T` 擦成 `Object` 或它的第一个上界，运行时没有类型实参信息。所以 `List<String>` 和 `List<Integer>` 的 `getClass()` 相等。

### 第 2 层｜为什么要擦除？不擦行不行？
**答**：为了**向后兼容**。JDK 5 引入泛型时，已经存在大量用 `List`（元素是 Object）的老代码和第三方库；擦除让 `List<String>` 和老 `List` 是同一个运行时类，新老代码能在同一个 JVM 里混跑，也不需要改 JVM 的类格式。代价就是运行时拿不到泛型信息、不能 `new T()`。C# 是「具化泛型」，运行时保留类型参数，但无法和旧的非泛型集合二进制兼容。

### 第 3 层｜擦除后，`List<User>` 的类型还能拿到吗？怎么拿？
**答**：能，但只限于**声明处**。泛型信息保存在 class 文件的 `Signature` 属性里，反射通过 `getGenericReturnType()` / `getGenericParameterTypes()` / `getGenericSuperclass()` 读到 `ParameterizedType` 再取 `getActualTypeArguments()`。关键限制是**拿不到局部变量的泛型**（`List<User> list = ...` 没有 Signature），所以 Jackson 要你写 `new TypeReference<List<User>>(){}` —— 用匿名子类的父类泛型声明来保存类型。

### 第 4 层｜桥接方法是什么？为什么会出现？
**答**：擦除会让子类的 `compareTo(Box)` 和接口擦除后的 `compareTo(Object)` 签名不一致，编译器就自动生成一个 `compareTo(Object)` 的桥接方法做 `checkcast` 后转调，保证多态分派正确。它带 `ACC_BRIDGE|ACC_SYNTHETIC` 标记，`getDeclaredMethods()` 会把它也列出来（实测一个类里出现两个 `compareTo`）。Spring 解析方法时必须过滤桥接方法，否则会把一个方法认成两个。

### 第 5 层｜不能 `new T()`、不能 `T[].class`，框架怎么绕过去？
**答**：把 `Class<T>` 显式传进来：`<T> T create(Class<T> type) { return type.newInstance(); }`；Spring 的 `BeanFactory.getBean(Class<T>)`、Jackson 的 `readValue(json, User.class)` 都是这个套路。数组用 `Array.newInstance(clazz, len)`（它的运行时类型是 `T[]` 而不是 `Object[]`）。再进一步是用 `Supplier<T>` / 工厂接口。**核心思路：擦除抹掉的是「推不出来的类型」，那就让调用方显式给。**

### 第 6 层｜PECS 为什么 `extends` 只能读、`super` 只能写？
**答**：`List<? extends Number>` 的运行时可能是 `List<Integer>`、`List<Double>`——编译器不知道是哪个，所以 `add(1)` 不合法（万一实际是 `List<Double>`），但读取一定能得到一个 `Number`（上界）。`List<? super Integer>` 反之，写入 `Integer` 一定合法（实际类型是 `List<Integer>` 或 `List<Number>` 或 `List<Object>`），但读出来只能是 `Object`。一句话：**写用下界、读用上界**。

### 第 7 层｜`Class.forName`、`User.class`、`getClass()` 有什么区别？
**答**：`User.class` 是编译期字面量，不触发初始化；`obj.getClass()` 是运行时反查，对象已存在所以类已初始化；`Class.forName(name)` 会**加载 + 链接 + 初始化**（执行 `<clinit>`），常用于 JDBC 驱动加载；`ClassLoader.loadClass(name)` 只加载不初始化（实测：`loadClass` 不打印静态块，`forName` 会打印）。

### 第 8 层｜反射慢在哪？为什么「前 15 次慢、之后快」？
**答**：慢有三层：查找（每次 `getDeclaredMethod` 都很贵，框架会缓存）、调用（JNI vs 字节码）、包装（装箱和参数数组）。「前 15 次慢」是 `NativeMethodAccessorImpl` 用 JNI 实现 `invoke`，调用够 15 次（`ReflectionFactory.inflationThreshold` 默认 15）后触发 **inflation**，用 `MethodAccessorGenerator` 生成字节码 accessor 替换掉 JNI 版本，之后每次调用就是一次普通虚方法调用 + 类型检查。所以「反射慢」主要是「没缓存 Method」导致的**查找**开销。

### 第 9 层｜反射能调私有方法，模块化之后还有什么限制？
**答**：JDK 9+ 下访问 `java.base` 的非导出/未开放成员会抛 `InaccessibleObjectException`，需要 `--add-opens` 或模块 `opens` 声明（实测：不加参数反射 `String.coder` 直接抛）。另外 `SecurityManager`（已废弃）和 JIT 对反射调用的内联限制也有影响。边界感可以这么讲：**反射的能力 = 语言给的 + 模块系统允许的**。

### 第 10 层（终局）｜字节码与 HotSpot 层：inflation 到底生成了什么？
**答**：`MethodAccessorGenerator.generateMethod` 用 `ByteVector` 手工拼出一个类（命名如 `GeneratedMethodAccessor1`），字节码大致是：`aload_0` 取目标对象 → `checkcast 目标类` → `aload_1` 取参数数组 → 逐个 `checkcast`/拆箱 → `invokevirtual 真实方法` → 按返回类型装箱 → `areturn`。随后通过 `Unsafe.defineAnonymousClass` / `defineClass` 定义并注入，`DelegatingMethodAccessorImpl.setDelegate(新accessor)`。所以第 15 次之后的「反射调用」已经不是反射了，是**一段为这个方法量身生成的直接调用代码**——这也是 JIT 能把 `invokevirtual` 内联掉、反射开销接近零的原因。JDK 18 的 JEP 416 把这一套换成 `DirectMethodHandleAccessor`（直接用 `MethodHandle`），机制不同、目标相同。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 类型擦除 | 编译后丢掉类型实参 | 兼容 JDK5 前的二进制 | 擦成什么（Object/上界） |
| `descriptor` | 方法描述符，擦除后的签名 | JVM 链接与调用的唯一依据 | 为什么它不含泛型 |
| `Signature` 属性 | class 文件里的泛型签名 | 让反射/编译器还原泛型 | 只能从声明处拿到 |
| `ParameterizedType` | 带类型参数的 `Type` 子接口 | 反射读取 `List<String>` | `getActualTypeArguments` |
| `TypeReference` | Jackson 的泛型载体（匿名子类） | 绕过「拿不到局部变量泛型」 | 为什么必须匿名子类 |
| 桥接方法 | 编译器生成的签名适配方法 | 让擦除后的多态分派正确 | `ACC_BRIDGE`/`ACC_SYNTHETIC` |
| `setAccessible(true)` | 关闭访问检查 | 访问私有成员 | 模块化后可能抛异常 |
| `MethodAccessor` | 真正执行 invoke 的对象 | 分离「入口」与「实现」 | 见 inflation |
| `inflation` | 调用 15 次后生成字节码 accessor | 兼顾「少量调用」与「热调用」 | 阈值默认 15、可配置 |
| `MethodAccessorGenerator` | 生成 accessor 字节码的生成器 | 把反射降级为直接调用 | 生成类会占 Metaspace |
| PECS | Producer Extends / Consumer Super | 通配符读写规则 | 为什么 extends 不能写 |

## 代码验证（`ReflectProbe.java`，JDK 17 编译运行通过）

```java
import java.lang.reflect.*;
import java.util.*;

public class ReflectProbe {
    static class Box implements Comparable<Box> {
        final int v;
        Box(int v) { this.v = v; }
        public int compareTo(Box o) { return Integer.compare(v, o.v); }   // 真实实现
        public List<String> names() { return List.of("box"); }           // 泛型返回值
    }
    public static void main(String[] a) throws Exception {
        // ① 桥接方法：一个 compareTo 变两个
        for (Method m : Box.class.getDeclaredMethods()) {
            System.out.println(m.getName() + " params=" + Arrays.toString(m.getParameterTypes())
                    + " bridge=" + m.isBridge() + " synthetic=" + m.isSynthetic());
        }
        // ② 擦除 vs Signature：raw 与 generic 的差别
        Method names = Box.class.getMethod("names");
        System.out.println("raw return     = " + names.getReturnType());        // interface java.util.List
        System.out.println("generic return = " + names.getGenericReturnType()); // List<java.lang.String>

        // ③ 反射调用桥接方法（多态分派经桥接 → 真实实现）
        Method cmp = Box.class.getMethod("compareTo", Object.class);
        System.out.println("bridge target = " + cmp.getDeclaringClass().getSimpleName()
                + ", result = " + cmp.invoke(new Box(1), new Box(2)));

        // ④ inflation 阈值：默认没设系统属性，源码里是 15
        System.out.println("inflationThreshold prop = " + System.getProperty("sun.reflect.inflationThreshold"));
    }
}
```
```bash
javac -encoding UTF-8 ReflectProbe.java
java --add-opens java.base/java.lang=ALL-UNNAMED ReflectProbe

# 关键证据都在 javap -v 里：descriptor（擦除后）/ Signature（泛型）/ ACC_BRIDGE
javap -v -p 'ReflectProbe$Box.class' | grep -E 'Signature|ACC_BRIDGE|descriptor'
# PowerShell 下把 grep 换成 Select-String
```

**预期输出**：`compareTo params=[class java.lang.Object] bridge=true synthetic=true`、`compareTo params=[class ReflectProbe$Box] bridge=false synthetic=false`、`raw return = interface java.util.List`、`generic return = java.util.List<java.lang.String>`、`inflationThreshold prop = null`（null 表示用源码默认 15）。

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「泛型运行时还能做类型检查」→ 能判断 `List<String>` | 擦除了，`instanceof List<String>` 编译不过，只能判断 `List` |
| 「`getDeclaredMethods` 返回的就是我写的方法」 | 还会含编译器生成的桥接/合成方法，要过滤 `isBridge()` |
| 「反射很慢，能用就不用」 | 调用热了接近直接调用；真正的坑是不缓存 `Method` |
| 「`setAccessible` 能访问任何私有成员」 | JDK 9+ 模块化后受限，需要 `--add-opens` |
| 「泛型返回类型反射拿不到」 | `getGenericReturnType()` 能拿到，信息在 `Signature` 属性 |
| 「擦除是因为 JVM 不支持泛型」 | 是为了跟 JDK5 之前的老代码二进制兼容 |
