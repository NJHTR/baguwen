# 前端性能优化（Performance）

> 面试权重：4/5　｜　追问深度：**L5（渲染管线 + 打包产物 + HTTP 缓存分层）**
> 一句话定位：性能优化不是背技巧，而是沿着「网络 → 解析 → 执行 → 渲染 → 交互」这条关键路径找瓶颈、用指标量化收益。

**本文件用法**：先记住五个核心指标和一条关键路径，再按 L2 的四层优化往下展开。**面试官最烦"我用了懒加载"这种没有数据的回答，L3 的测量方法必须会。**
[返回深度追问索引](../00-索引.md)

---

## L1 一句话答案（10 秒能说出口）

性能优化 = 缩短关键路径 + 减少主线程阻塞：网络层减请求/压体积/用缓存，解析层减少阻塞资源，执行层拆分长任务，渲染层减少布局绘制，交互层降低 INP；用 FCP、LCP、INP、CLS 量化，而不是凭感觉。

## L2 原理层：四层优化清单

### 2.1 先定指标（Core Web Vitals）

| 指标 | 含义 | 良好阈值 |
|---|---|---|
| TTFB | 首字节时间（网络 + 服务端） | < 800ms |
| FCP | 首次内容绘制 | < 1.8s |
| LCP | 最大内容绘制（首屏主内容） | < 2.5s |
| INP | 交互到下次绘制（替代 FID） | < 200ms |
| CLS | 累计布局偏移 | < 0.1 |

### 2.2 网络层

- CDN + HTTP/2/3：就近接入、多路复用；静态资源长缓存 + 内容哈希。
- 压缩：gzip/brotli、图片 WebP/AVIF、`srcset` 响应式图片、`loading="lazy"`。
- 资源提示：`preconnect`（提前建连）、`dns-prefetch`、`preload`（当前页关键资源）、`prefetch`（下一页可能用）。

### 2.3 资源层（打包）

- 代码分割：路由级 `import()`、组件级懒加载；`manualChunks` 拆 vendor。
- Tree-shaking：ESM 静态结构 + sideEffects 标记；按需引入组件库/图标。
- 压缩与降级：esbuild/terser minify、移除无用 polyfill（按 browserslist）、sourcemap 单独上传。

### 2.4 渲染与交互层

- 减少重排重绘：读写分离、`DocumentFragment`、`transform/opacity` 做动画、虚拟列表。
- 减少主线程长任务：大计算放 Web Worker、`requestIdleCallback`、时间切片。
- 感知优化：骨架屏、SSR/预渲染、`content-visibility: auto`。

## L3 底层层：渲染管线、Vite 产物、缓存分层

### 3.1 关键渲染路径与帧预算

```
HTML 流式下载 → preload scanner 提前发现资源
→ 解析 HTML 构建 DOM（普通 script 阻塞解析）
→ 解析 CSS 构建 CSSOM（CSS 阻塞渲染）
→ DOM + CSSOM = Render Tree
→ Layout（几何）→ Paint（绘制指令）→ Composite（GPU 合成）
```

- 60Hz 一帧 **16.6ms**；主线程任务超过 **50ms** 记为 Long Task；INP 超过 200ms 算差。
- 一次布局/绘制没做完就掉帧；布局抖动（读写交替）会让主线程反复重排。

### 3.2 Vite 的 dev 与 build 差异（项目常问）

| 阶段 | 机制 | 性能特征 |
|---|---|---|
| dev | 原生 ESM 按需编译 + esbuild 预构建依赖 | 启动快，冷启动只编译当前路由 |
| build | Rollup 打包 + esbuild minify + chunk 分割 | 产物小、可 tree-shaking、带 content hash |

- 拆包不是越细越好：HTTP/2 下多请求成本低，但小 chunk 太多会增加请求与解析开销；**按缓存更新频率拆**（vendor、业务、路由）更实用。
- `modulepreload` 让浏览器提前加载入口依赖；生产用 hash 文件名实现"内容变才失效"。

### 3.3 HTTP 缓存分层（性能与发布的结合点）

```
CDN 边缘节点（s-maxage）
  → 浏览器强缓存（Cache-Control: max-age，Memory/Disk Cache）
    → 协商缓存（ETag/Last-Modified → 304）
      → Service Worker（离线与缓存策略）
```

- 发布策略：`index.html` 必须 `no-cache`；`/assets/*.[hash].js` 设 `max-age=31536000, immutable`。
- 发版白屏排查顺序：HTML 缓存 → 资源 hash → Service Worker 旧版本 → CDN 未刷新。

### 3.4 怎么量：Performance API

`PerformanceObserver` 能监听 `largest-contentful-paint`、`longtask`、`layout-shift`、`event`（INP）等；DevTools 的 Performance 面板看火焰图与长任务；Lighthouse 给评分与优化建议。**能用数据说话，比背 20 条技巧更有说服力。**

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层必备，第 4-6 层拉开差距，第 7 层以后加分。**

### 第 1 层｜性能优化从哪些维度入手？
**答**：网络（请求数、体积、缓存、CDN）、解析（阻塞资源、preload）、执行（长任务、拆包）、渲染（重排重绘、合成）、交互（INP）五个维度。

### 第 2 层｜首屏时间怎么拆？
**答**：DNS + TCP + TLS（TTFB 前）+ 服务端处理（TTFB）+ HTML 下载 + 关键 CSS/JS 下载执行 + 首次渲染到 LCP；每一段用 Navigation Timing 量出来，再决定优化哪段。

### 第 3 层｜为什么 CSS 阻塞渲染、JS 阻塞解析？defer/async 怎么选？
**答**：CSSOM 不完整就无法构建渲染树，所以 CSS 阻塞渲染且阻塞其后 JS；JS 可能修改 DOM，所以阻塞解析。`defer` 解析完按序执行、不阻塞解析，适合业务入口；`async` 下载完立即执行、顺序不定，适合独立统计脚本。

### 第 4 层｜preload、prefetch、preconnect 的区别？
**答**：`preconnect` 提前建连（DNS+TCP+TLS）；`preload` 告诉浏览器当前页马上要用某资源、提高优先级；`prefetch` 是空闲时预取下一页可能用的资源，优先级低。

### 第 5 层｜打包体积怎么降？
**答**：tree-shaking + 按需引入（组件库/图标）、路由级代码分割、剔除无用 polyfill、压缩图片/字体、`manualChunks` 拆分公共依赖并利用长缓存。

### 第 6 层｜Vite 为什么 dev 快？build 为什么也可能慢？
**答**：dev 不打包，按需编译 + 依赖预构建（esbuild）；build 要 Rollup 完整打包、压缩、生成 sourcemap，大项目/大依赖（monaco、echarts）会慢，用 `manualChunks`、按需引入和构建缓存优化。

### 第 7 层｜大表格/长列表怎么优化？
**答**：虚拟列表（只渲染可视区 + 缓冲）、分页/懒加载、行高固定、避免每行重复计算；计算密集用 Web Worker；报告平台导出/聚合放服务端更合适。

### 第 8 层｜动画为什么用 `transform/opacity`？
**答**：它们只触发合成，不触发布局和绘制；`width/top` 会触发重排，`background-color` 触发重绘。合成层在 GPU 上做，主线程压力小；配合 `will-change` 提前分层，但别滥用。

### 第 9 层｜怎么定位性能瓶颈？INP 怎么优化？
**答**：Performance 面板看火焰图和长任务、Lighthouse 跑分、PerformanceObserver 采集真实用户数据。INP 高通常是长任务或事件处理过重：拆任务（时间切片/Worker）、减少不必要渲染、事件委托、`passive` 监听、避免同步布局。

### 第 10 层（终局）｜一帧里 Blink 到底怎么调度，打包和缓存怎么配合？
**答**：Blink 的调度器在收到 BeginMainFrame 后执行输入处理 → rAF → 样式 → 布局 → 绘制 → 合成，总预算 16.6ms；超时的任务会推迟到下一帧，连续超时表现为掉帧（LoAF/Long Animation Frame 会记录）。打包产物层面，content hash 让"内容变→文件名变"，配合 `index.html no-cache + assets immutable`，既拿到最长强缓存，又能发布即生效；CDN 层用 `s-maxage` 与刷新接口兜底。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| TTFB | 首字节时间 | 衡量网络+服务端 | 怎么优化 |
| FCP | 首次内容绘制 | 衡量"看到东西" | 与 LCP 区别 |
| LCP | 最大内容绘制 | 衡量首屏主内容 | 元素选取规则 |
| INP | 交互到下次绘制 | 衡量响应性 | 与 FID 区别 |
| CLS | 累计布局偏移 | 衡量视觉稳定 | 常见来源（图片/字体） |
| 关键渲染路径 | DOM→CSSOM→渲染树→布局→绘制 | 首屏瓶颈定位 | 哪些资源阻塞 |
| preload scanner | 解析 HTML 时并行扫资源的机制 | 提前发现外链资源 | 与 JS 执行的关系 |
| Long Task | 超 50ms 的主线程任务 | 卡顿的度量口径 | 用 PerformanceObserver 测 |
| 16.6ms 帧预算 | 60Hz 一帧的时间 | 渲染流畅的硬约束 | 掉帧根因 |
| Code Splitting | 按需加载代码块 | 减小首包、并行下载 | 与 HTTP/2 权衡 |
| Tree-shaking | 删除未引用导出 | 减小产物体积 | 为什么依赖 ESM |
| `modulepreload` | 提前加载模块依赖 | 减少瀑布 | 与 preload 区别 |
| `immutable` | 强缓存指令 | 资源指纹下永不复验 | 与 `no-cache` 配合 |
| Service Worker | 浏览器后台脚本 | 离线与缓存编排 | 旧版本接管导致白屏 |

## 代码验证（打开浏览器控制台逐条跑，验证理解）

```js
// 1. 首屏耗时拆解（Navigation Timing）
const nav = performance.getEntriesByType('navigation')[0]
if (nav) {
  console.table({
    DNS: Math.round(nav.domainLookupEnd - nav.domainLookupStart),
    TCP: Math.round(nav.connectEnd - nav.connectStart),
    TTFB: Math.round(nav.responseStart - nav.requestStart),
    'HTML 下载': Math.round(nav.responseEnd - nav.responseStart),
    'DOM 解析': Math.round(nav.domContentLoadedEventEnd - nav.responseEnd),
  })
}

// 2. 监听 LCP（刷新页面后看最新一次）
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('LCP', Math.round(entry.startTime), 'ms', entry.element?.tagName)
  }
}).observe({ type: 'largest-contentful-paint', buffered: true })

// 3. 监听 Long Task，并人为制造一个 80ms 长任务
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) console.log('Long Task', Math.round(entry.duration), 'ms')
}).observe({ type: 'longtask', buffered: true })
const t = performance.now()
while (performance.now() - t < 80) {} // 预期：控制台出现 Long Task ~80ms

// 4. 布局抖动：读写交替 vs 批量读写
const box = document.createElement('div')
box.style.cssText = 'width:100px;height:10px;background:#ccc'
document.body.appendChild(box)
const t1 = performance.now()
for (let i = 0; i < 200; i++) box.style.width = box.offsetWidth + 1 + 'px'
const cost1 = performance.now() - t1
const t2 = performance.now()
let width = box.offsetWidth
for (let i = 0; i < 200; i++) width += 1
box.style.width = width + 'px'
const cost2 = performance.now() - t2
console.log('读写交替', cost1.toFixed(2), 'ms；批量改写', cost2.toFixed(2), 'ms')
box.remove()
// 预期：第一种明显更慢（每次循环都强制同步布局）
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「减少 DOM 操作就等于性能优化」 | 先看是否触发布局/绘制，以及是否在主线程 |
| 「HTTP/2 之后不用拆包了」 | 仍要按缓存粒度和首屏拆，只是请求成本降低 |
| 「图片懒加载一定更快」 | 首屏关键图不能懒加载，会拖慢 LCP |
| 「`will-change` 加得越多越流畅」 | 占 GPU 内存，滥用反而更慢 |
| 「Lighthouse 100 分就是快」 | 实验室数据，还要看真实用户指标（RUM） |
| 「Vite 快是因为打包算法好」 | dev 快是因为不打包、原生 ESM 按需编译 |
