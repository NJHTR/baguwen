# 事件循环（Event Loop）

> 面试权重：5/5　｜　追问深度：**L5（浏览器渲染管线 + V8 微任务队列）**
> 一句话定位：JS 单线程的调度中枢。所有「为什么这段先执行」「为什么 Promise 比 setTimeout 快」的问题，答案都在这条循环里。

## L1 一句话答案（10 秒能说出口）

事件循环不断取任务执行：同步代码在调用栈跑完 → 清空**所有**微任务 → 浏览器找机会渲染 → 再取一个宏任务。微任务（`Promise` 回调、`await` 之后、`queueMicrotask`、`MutationObserver`）永远优先于下一个宏任务和渲染。

## L2 原理层：宏任务、微任务与一轮循环

| 类别 | 典型来源 | 执行时机 |
|---|---|---|
| 微任务 | `Promise.then/catch/finally`、`await` 之后的代码、`queueMicrotask`、`MutationObserver` | 每个宏任务执行完立即清空 |
| 宏任务 | 整个 `<script>`、`setTimeout/setInterval`、UI 事件回调、I/O、`MessageChannel` | 一轮只取一个 |
| 渲染 | `requestAnimationFrame` → 样式计算 → 布局 → 绘制 → 合成 | 微任务清空后、下一个宏任务前 |

```text
while (true) {
  task = 从宏任务队列取一个（按 task source 先进先出）
  执行 task（期间可能产生新的微任务）
  while (微任务队列非空) 执行微任务
  if (这一轮需要渲染) 执行渲染步骤
}
```

**必须记住的 4 条规则**：
1. 微任务一次清到底，清空过程中新加的微任务也在本轮执行完。
2. 微任务为空才算完成一次 microtask checkpoint，之后才可能渲染。
3. 渲染不是每轮必做：页面没变化、后台标签页可能跳过。
4. Node 与浏览器不同：Node 分 timers/poll/check 等阶段，且 `process.nextTick` 优先于 Promise。

```js
console.log('1')
setTimeout(() => console.log('2'), 0)
Promise.resolve().then(() => console.log('3'))
queueMicrotask(() => console.log('4'))
console.log('5')
// 输出：1 5 3 4 2
```

## L3 底层层：HTML 规范模型 + V8 微任务队列 + 渲染帧预算

### 3.1 规范里的一轮循环（HTML Standard: event loop processing model）

1. 从**某个 task queue** 取最老的 task（浏览器按 task source 分成多个队列：DOM 操作、用户交互、网络、定时器）。
2. 执行 task，同步代码入栈、出栈。
3. **microtask checkpoint**：从微任务队列循环取任务直到空。
4. 判断是否需要渲染：需要则执行 `update the rendering`（rAF → 样式 → 布局 → 绘制 → 合成）。
5. 回到 1。

> 关键认知：**宏任务由浏览器调度，不是 V8 管的**。V8 只负责执行 JS，以及维护自己的微任务队列。

### 3.2 V8 的 `MicrotaskQueue`

- 每个 `v8::Isolate` 有微任务队列（Blink 使用 `v8::MicrotaskQueue`），`PerformCheckpoint` 在调用栈为空时驱动执行。
- `Promise` reaction、`queueMicrotask`、`MutationObserver` 回调最终都进这个队列，本质是同一个东西。
- V8 内部是 `MicrotaskQueue` 对象 + `Microtask` 链表；压入/清空是 O(1) 操作。
- `await` 之后的代码不是"另起一个函数"，而是被编译器拆成一个 continuation 注册成微任务（详见 [async/await](./03-async-await.md)）。

### 3.3 渲染管线与 16.6ms 帧预算

```
一帧（60Hz = 16.6ms）
input 事件 → requestAnimationFrame 回调 → 样式计算 → 布局(layout) → 绘制(paint) → 合成(composite)
```

- 渲染只在「需要」时发生；一轮 task + 微任务超预算就掉帧（jank）。
- Long Task 定义为**超过 50ms 的主线程任务**，会阻塞输入响应。
- 后台标签页的 `setTimeout` 被节流到 1s 甚至 1min，rAF 暂停。
- `requestIdleCallback` 在主线程空闲时执行低优先级任务（浏览器支持度要注意）。

### 3.4 Node.js 的事件循环

| 阶段 | 处理内容 |
|---|---|
| timers | `setTimeout/setInterval` 到期回调 |
| pending callbacks | 系统级回调（如 TCP 错误） |
| poll | 等待 I/O，执行 I/O 回调 |
| check | `setImmediate` |
| close | `close` 事件回调 |

每个阶段之间清空微任务；`process.nextTick` 队列优先于 Promise 微任务。Node 11+ 后 `setTimeout` 与 `setImmediate` 的顺序不再"随机"。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层拉开差距，第 7 层以后是加分。**

### 第 1 层｜宏任务和微任务分别有哪些？
**答**：微任务是 `then/catch/finally`、`await` 后代码、`queueMicrotask`、`MutationObserver`；宏任务是 `script` 整体、`setTimeout/setInterval`、UI 事件、I/O、`MessageChannel`。

### 第 2 层｜`Promise` 和 `setTimeout(0)` 谁先？
**答**：`Promise`。微任务在每轮宏任务后清空，`setTimeout` 要排到下一个宏任务；即使设为 0ms，也要等当前同步代码和全部微任务结束。

### 第 3 层｜微任务什么时候执行完？微任务里再产生微任务呢？
**答**：一直执行到队列为空，包括清空过程中新增的微任务。所以微任务可以"无限套娃"，只要不断递归产生就会饿死后续渲染。

### 第 4 层｜为什么必须先清空微任务再渲染？
**答**：保证同一轮里数据一致性：如果渲染插在微任务之间，会画出"只更新一半"的中间态。规范把 checkpoint 放在渲染前，框架（如 Vue 的 `nextTick`）正是利用这一点在 DOM 更新后、渲染前统一 flush。

### 第 5 层｜`requestAnimationFrame` 在循环哪个位置？和微任务谁先？
**答**：微任务先。rAF 属于渲染步骤，在微任务 checkpoint 之后、样式计算之前执行；同一帧内的 rAF 回调按注册顺序执行。用 rAF 改样式可以避免一帧内多次布局。

### 第 6 层｜`setTimeout(fn, 0)` 为什么不是 0ms 执行？4ms 是怎么回事？
**答**：它只能保证"至少延迟 0ms"，实际要排队到下一轮，且浏览器有最小延迟；嵌套超过 5 层的定时器最小延迟约 4ms。另外被同步长任务阻塞时，实际延迟可能几百毫秒。

### 第 7 层｜浏览器和 Node 的事件循环有什么不同？
**答**：浏览器是「宏任务队列 + 微任务 + 渲染」模型；Node 是分阶段的 libuv 循环（timers → poll → check…），每阶段后清微任务，`process.nextTick` 独立且优先于 Promise。所以同样代码在两端输出可能不同。

### 第 8 层｜微任务死循环会发生什么？
**答**：页面完全卡死：主线程始终在清微任务，渲染步骤永远排不上，输入事件也无法处理；Chrome 最终可能弹"页面无响应"。这是微任务比宏任务更危险的地方。

### 第 9 层｜UI 事件回调是宏任务吗？`MutationObserver` 为什么设计成微任务？
**答**：UI 事件是宏任务（task source 为 user interaction）。`MutationObserver` 设计成微任务，是为了在 DOM 变更后、渲染前批量回调，保证观察者在页面重绘之前看到所有变更，而不用等下一帧。

### 第 10 层（终局）｜V8 微任务队列和浏览器渲染是怎么衔接的？
**答**：Blink 的 task runner 取出一个 task 交给 V8 执行；返回后调用 `MicrotaskQueue::PerformCheckpoint` 清空微任务；随后调度器判断是否进入 `BeginMainFrame`，在渲染更新里执行 rAF、样式、布局、绘制、合成。V8 只提供微任务机制，**"什么时候渲染"由 Blink 的调度器（如 `FrameScheduler`）决定**，并且可以被后台状态、可见性、帧预算节流。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 宏任务（task） | 浏览器调度的执行单元 | 把 JS 与 I/O、事件、定时器统一排队 | 哪些是宏任务；task source 有几种 |
| 微任务（microtask） | 当前任务结束后立即执行的高优队列 | 保证同一轮内状态一致、Promise 及时回调 | 为什么 Promise 是微任务 |
| 任务队列 | 按 task source 分开的多个 FIFO 队列 | 避免不同类型任务互相插队 | 不是"一个队列" |
| task source | 任务来源分类（DOM/网络/定时器…） | 同源任务保序、不同源可调度均衡 | 用户输入优先于定时器 |
| microtask checkpoint | 清空微任务队列的时机 | 规范定义的状态同步点 | 什么时候触发 |
| 调用栈 | JS 函数执行栈 | 同步执行与上下文的载体 | 栈溢出、调用栈为空才 checkpoint |
| rAF | 渲染前回调 | 让动画与渲染帧对齐 | 与微任务/定时器顺序 |
| 渲染帧 | 一次 style→layout→paint→composite | 60Hz 下 16.6ms 一帧 | 掉帧、jank |
| 帧预算 | 一帧可用的主线程时间 | 约束每帧工作量 | Long Task 50ms |
| Long Task | 超 50ms 的主线程任务 | 性能指标与告警口径 | 用 PerformanceObserver 测 |
| `nextTick` | Node 的高优先队列 | 在微任务前执行，兼容历史 API | 与 Promise 顺序 |
| `MutationObserver` | DOM 变更观察器 | 微任务批量回调，先于渲染 | 与渲染时机的关系 |

## 代码验证（打开浏览器控制台逐条跑，验证理解）

```js
// 注意 以下每段单独粘贴运行；一起跑时所有同步代码先执行完，微任务输出会交错
// 1. 基础顺序：同步 → 微任务 → 宏任务
console.log('A')
setTimeout(() => console.log('B'), 0)
Promise.resolve().then(() => console.log('C'))
queueMicrotask(() => console.log('D'))
console.log('E')
// 输出：A E C D B

// 2. async/await 的微任务拆分
async function f() {
  console.log('f1')
  await null
  console.log('f2')
}
console.log('start')
f()
Promise.resolve().then(() => console.log('then'))
console.log('end')
// 输出：start f1 end f2 then
// 原因：f() 内部的 await 续体先入微任务队列，所以 f2 排在 then 前面

// 3. 同步阻塞会推迟定时器
const t0 = performance.now()
setTimeout(() => console.log('timer 实际延迟约', Math.round(performance.now() - t0), 'ms'), 0)
while (performance.now() - t0 < 100) {} // 同步忙等 100ms
// 预期：timer 实际延迟约 100ms，因为宏任务要等同步代码结束

// 4. 微任务饿死渲染（200ms 后自行结束，不会真的卡死）
const start = performance.now()
let n = 0
function spin() {
  n++
  if (performance.now() - start < 200) {
    Promise.resolve().then(spin) // 微任务套微任务，渲染排不上
  } else {
    console.log('微任务链结束，迭代次数', n)
  }
}
spin()
// 预期：页面在这 200ms 内无法响应渲染/输入
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「宏任务先执行，微任务后执行」 | 每个宏任务后立即清空微任务 |
| 「`setTimeout(0)` 会立即插队」 | 排到下一轮宏任务，且受 4ms/阻塞影响 |
| 「`new Promise` 里的 executor 是异步的」 | executor 同步执行，只有回调进微任务 |
| 「rAF 是宏任务」 | 属于渲染步骤，在微任务后、样式计算前 |
| 「Node 和浏览器事件循环一样」 | Node 分阶段且 `nextTick` 优先，顺序可能不同 |
| 「每个宏任务后一定渲染」 | 只有需要时才渲染，可能被跳过 |
