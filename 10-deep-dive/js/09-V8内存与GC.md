# V8 内存与垃圾回收（Memory & GC）

> 面试权重：4/5　｜　追问深度：**L5（分代回收 / 三色标记 / Orinoco 并发回收）**
> 一句话定位：V8 用「可达性」判断对象死活，用分代 + 标记清除/整理回收内存；所有「内存泄漏」最终都落在一条可达性链上。

**本文件用法**：L2 建立内存地图，L3 记分代算法，L4 练连续追问。**面试能答到"三色标记 + 写屏障 + 增量并发"就明显高于平均线。**

## L1 一句话答案（10 秒能说出口）

V8 把堆分成新生代和老生代，从根对象出发做可达性分析：Scavenge 复制算法回收新生代，标记-清除/标记-整理回收老生代，并用增量标记、并发回收降低停顿；**内存泄漏 = 对象不再需要但仍然可达**。

---

## L2 原理层：内存地图与回收判据

### 2.1 V8 堆的分区

| 区域 | 存什么 | 特点 |
|---|---|---|
| 调用栈 | 栈帧、局部原始值、对象指针 | 函数返回即弹出，不归 GC 管 |
| 新生代（new space） | 新创建的小对象 | 分 from/to 两个半空间，回收频繁 |
| 老生代（old space） | 存活久/晋升的对象 | 大，回收次数少，停顿较长 |
| 大对象空间（large object space） | 超大对象（如大数组/大字符串） | 不复制，单独管理 |
| 代码空间 / Map 空间 | JIT 代码、隐藏类元数据 | 引擎内部使用 |
| 只读空间 | 内置对象/字符串 | 进程内共享，不回收 |

### 2.2 分配与判据

- 分配用**指针碰撞**（bump pointer）+ **TLAB**（线程本地分配缓冲），几乎零成本；大对象直接进大对象空间。
- 回收判据是**可达性**：从根（全局对象、调用栈、活动句柄、寄存器）出发遍历，遍历不到的就是垃圾。V8 不用引用计数。
- 一个对象是否泄漏，取决于**是否还有路径从根到它**——闭包、定时器、全局缓存、DOM 监听都可能成为那条路径。

### 2.3 常见泄漏来源

| 来源 | 为什么可达 |
|---|---|
| 意外全局变量 | `window` 是根 |
| 未清理的定时器 / 监听 | 浏览器全局持有回调 |
| 闭包持有大对象 | 函数对象 → Context → 变量 |
| 无上限缓存（Map） | 模块作用域永久可达 |
| 游离 DOM | JS 变量仍引用已移除节点 |
| 未取消的请求/流 | 回调与闭包挂在网络层 |

## L3 底层层：Scavenge、标记清除、Orinoco

### 3.1 新生代：Scavenge（Cheney 复制算法）

1. 新生代分 from/to 两个半空间，新对象分配在 from；
2. GC 时从根出发，把 from 中的**存活对象复制到 to**（复制即整理，无碎片）；
3. 复制完成的存活对象**年龄 +1**，达到阈值（或 to 空间占用超限）**晋升到老生代**；
4. from/to 角色翻转，整个 from 空间一次性回收。

特点：存活对象少时极快（只复制活的）；缺点是复制成本和空间浪费（一半空间闲置）。

### 3.2 老生代：Mark-Sweep 与 Mark-Compact

- **标记-清除**：三色标记找出所有存活对象，把未标记的（白色）内存加回空闲列表；不移动对象，但会产生碎片。
- **标记-整理**：标记后把存活对象向一端移动，消除碎片，代价是移动和更新指针。
- **三色标记**：白（未访问）、灰（已发现但子引用未处理）、黑（处理完）。GC 从根开始把对象置灰，逐个处理灰色对象、把引用标灰，最后仍为白色的就是垃圾。
- **写屏障**：增量/并发标记时，应用线程还在改引用，可能把黑对象指向白对象导致漏标。写屏障（Dijkstra/Steele）在赋值时把新引用记录到标记队列或染灰，保证不漏。
- **记忆集（remembered set）**：记录「老生代对象 → 新生代对象」的跨代引用，回收新生代时不用扫描整个老生代。

### 3.3 停顿与 Orinoco

- 传统 GC 是 stop-the-world：暂停 JS 执行，停顿随堆大小增长。V8 的 **Orinoco** 回收器把工作拆开：
  - **并行标记**：多个 GC 线程同时标记；
  - **并发标记**：标记与 JS 执行同时进行（靠写屏障）；
  - **增量标记**：把标记切成小步，在 JS 执行的间隙推进；
  - **并发清除/整理**、**空闲时间 GC**（利用浏览器 idle 时间）。
- 目标：把单次停顿压到毫秒级，避免主线程卡顿。
- **Blink 的 Oilpan**：DOM 节点等由 Blink 自己的 GC 管理，同样基于可达性，并与 V8 堆协作（跨堆引用需要写屏障）。

### 3.4 弱引用

`WeakMap/WeakSet` 的键、`WeakRef`、`FinalizationRegistry` 不阻止回收：对象只被弱引用时仍可被回收。适合做缓存与元数据，不适合需要稳定存活的场景。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层必备，第 4-6 层拉开差距，第 7 层以后加分。**

### 第 1 层｜JS 的内存什么时候回收？
**答**：由引擎自动决定，业务代码无法主动触发；GC 在分配压力或空闲时运行，判断标准是对象是否从根可达。

### 第 2 层｜什么是可达性？根有哪些？
**答**：从根出发沿引用链能否访问到对象。根包括全局对象、当前调用栈、活动句柄、寄存器；闭包、定时器、DOM 监听都能让对象保持可达。

### 第 3 层｜为什么要分新生代和老生代？
**答**：大多数对象朝生夕死（弱代假说）。新生代小、回收频繁且快（复制算法）；老生代大、存活久，用标记清除/整理，减少整体回收次数。

### 第 4 层｜Scavenge 具体怎么复制？什么时候晋升？
**答**：from 空间存活对象复制到 to，复制后年龄 +1；年龄达阈值、对象较大或 to 空间占用超过约 25% 时晋升到老生代；然后 from/to 翻转。

### 第 5 层｜标记-清除和标记-整理的区别？
**答**：清除只回收未标记内存、不移动对象，快但产生碎片；整理会把存活对象移动到一起、更新指针，消除碎片但更慢，适合碎片严重时。

### 第 6 层｜三色标记为什么需要写屏障？
**答**：增量/并发标记期间应用线程仍在改引用，可能出现「黑对象指向白对象」导致白对象被漏标。写屏障在赋值时记录或染灰，保证标记完整性。

### 第 7 层｜为什么要增量/并发回收？停世界是什么？
**答**：全量 GC 要暂停 JS（stop-the-world），堆越大停顿越久，用户会感知卡顿。增量把标记切碎插入执行间隙，并发让 GC 线程与主线程同时工作，从而缩短单次停顿。

### 第 8 层｜哪些对象容易晋升？大对象去哪？
**答**：存活超过一两轮 Scavenge 的对象会晋升；超大对象/大数组直接分配到 large object space，避免复制开销。

### 第 9 层｜内存泄漏怎么排查？为什么 WeakMap 能防泄漏？
**答**：DevTools Memory 面板拍两次 heap snapshot 对比、看 Allocation 时间线、Performance Monitor；WeakMap 的键是弱引用，不构成可达路径，键对象被回收时条目自动清除。

### 第 10 层（终局）｜V8 一次完整 GC 在引擎里怎么发生？
**答**：分配触发 GC（或空闲时间 GC）→ 新生代用 Scavenge 并行复制、存活对象晋升 → 老生代在 Orinoco 下做增量/并发标记（三色 + 写屏障 + 记忆集处理跨代引用）→ 并发清除或整理 → 更新空闲列表/压缩堆。整个过程与 JS 执行交错，靠写屏障保证正确性，目标是毫秒级停顿。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 分代回收 | 按对象年龄分区域回收 | 弱代假说，提升效率 | 为什么新生代回收更频繁 |
| 新生代 | 存放新对象的小空间 | 快速回收朝生夕死的对象 | from/to 结构 |
| 老生代 | 存放晋升对象的大空间 | 降低回收次数 | 标记清除/整理 |
| Scavenge | 新生代复制算法 | 无碎片、只复制存活 | 晋升条件 |
| Cheney 算法 | Scavenge 的实现方式 | 广度优先复制、无需递归栈 | from/to 翻转 |
| Mark-Sweep | 标记后清除未标记内存 | 不移动对象、快 | 碎片问题 |
| Mark-Compact | 标记后移动压缩 | 消除碎片 | 更新指针成本 |
| 三色标记 | 白/灰/黑标记状态 | 增量标记的正确性基础 | 漏标条件 |
| 写屏障 | 赋值时插入的检查代码 | 并发标记时不漏标 | Dijkstra/Steele |
| 记忆集 | 老→新跨代引用记录 | 新生代回收不扫老生代 | 跨代引用 |
| 晋升（promotion） | 新生代对象移到老生代 | 长期存活对象集中管理 | 触发条件 |
| Orinoco | V8 的并发/增量 GC 体系 | 降低停顿 | 并行 vs 并发 vs 增量 |
| stop-the-world | GC 暂停所有 JS 执行 | 保证一致性 | 停顿时间优化 |
| TLAB | 线程本地分配缓冲 | 加速对象分配 | 指针碰撞 |
| 可达性 | 从根能否访问到对象 | GC 判据 | WeakRef 的影响 |

## 代码验证（打开浏览器控制台逐条跑，验证理解）

```js
// 1. 看当前堆使用（Chrome/Edge 支持 performance.memory）
if (performance.memory) {
  console.log('已用堆', (performance.memory.usedJSHeapSize / 1048576).toFixed(2), 'MB')
}

// 2. 制造增长：持有大数组不释放（注意：这只是演示，别在真实页面常驻）
const before = performance.memory ? performance.memory.usedJSHeapSize : 0
let leaked = []
for (let i = 0; i < 10; i++) leaked.push(new Array(1e5).fill(i))
const after = performance.memory ? performance.memory.usedJSHeapSize : 0
console.log('增长约', ((after - before) / 1048576).toFixed(1), 'MB') // 约 8-10MB
leaked = null // 断开引用后，等下一次 GC 才会回收

// 3. WeakRef：不阻止回收（需要在 DevTools Memory 面板手动点 Collect garbage 验证）
let target = { big: new Array(1e6).fill(0) }
const ref = new WeakRef(target)
console.log('弱引用可读到', ref.deref() !== undefined) // true
target = null
// 未触发 GC 时仍可能读到对象；在 DevTools 的 Memory 面板点「Collect garbage」后应变为 undefined
setTimeout(() => console.log('GC 后弱引用为', ref.deref()), 3000) // 可能打印 undefined

// 4. 观察闭包持有大对象的可达链
function createLeak() {
  const big = new Array(1e6).fill('x')
  return () => big.length // 闭包 → Context → big
}
const leak = createLeak()
console.log(leak()) // 1000000
// 只要 leak 仍可达，big 就不会被回收；leak = null 后才断开

// 5. FinalizationRegistry：对象被回收后的回调（非确定性，仅演示）
const registry = new FinalizationRegistry((label) => console.log('已回收', label))
let temp = { name: 'temp' }
registry.register(temp, 'temp 对象')
temp = null // 触发 GC 后（手动或等待）可能打印「已回收 temp 对象」
```

> 排查泄漏的实操：DevTools → Memory → Heap snapshot 连续拍两次，用 Comparison 对比新增对象；或 Performance 面板勾选 Memory 看内存曲线是否只涨不跌。

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「V8 用引用计数回收」 | 用可达性分析（标记清除系） |
| 「垃圾回收可以手动触发」 | 业务代码无法强制 GC，只能断开引用 |
| 「闭包变量一定在堆上」 | 被内层函数引用的才提升到 Context |
| 「内存泄漏是内存没被回收」 | 是对象仍可达、但业务上已不需要 |
| 「新生代用标记清除」 | 新生代用 Scavenge 复制，老生代才标记清除/整理 |
| 「标记阶段完全暂停 JS」 | Orinoco 支持增量/并发标记，停顿被切碎 |
