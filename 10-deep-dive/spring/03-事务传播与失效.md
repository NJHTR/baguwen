# 事务传播与失效

> 面试权重：5/5　｜　追问深度：**L5（连接 ThreadLocal 绑定 / `doBegin` / savepoint / 隔离与传播边界）**
> 一句话定位：`@Transactional` 就是 AOP + `TransactionInterceptor`；事务管理器在方法前后管连接，连接通过 **`TransactionSynchronizationManager` 的 ThreadLocal** 绑定到线程，所以「同一个线程 + 同一个 DataSource」才能共享一个事务——跨线程、跨代理边界都失效。

[返回深度追问索引](../00-索引.md)

## L1 一句话答案（10 秒能说出口）

`@Transactional` 由 AOP 代理拦截，`TransactionInterceptor` 调 `PlatformTransactionManager.getTransaction()` 开事务（`DataSourceTransactionManager` 里就是 `setAutoCommit(false)` + 把连接绑到 `ThreadLocal`），方法正常返回则 `commit`，抛 `RuntimeException/Error` 则 `rollback`（受检异常默认不回滚）。传播行为决定「当前已存在事务时怎么办」，其中 `REQUIRES_NEW` 挂起外层、`NESTED` 用 savepoint。

## L2 原理层：拦截链 + 七种传播行为

```
调用方（拿到的是代理）
 └─ TransactionInterceptor.invoke
     └─ TransactionAspectSupport.invokeWithinTransaction
         ├─ createTransactionIfNecessary → tm.getTransaction(txAttr)   ← 开启/加入事务
         ├─ invocation.proceedWithInvocation()                          ← 业务方法（Controller→Service→DAO）
         ├─ commitTransactionAfterReturning → tm.commit(status)
         └─ catch Throwable → completeTransactionAfterThrowing → rollbackOn(ex) ? rollback : commit
```

```java
// DataSourceTransactionManager（AbstractPlatformTransactionManager 模板方法调子类）
protected void doBegin(Object transaction, TransactionDefinition definition) {
    DataSourceTransactionObject txObject = (DataSourceTransactionObject) transaction;
    Connection con = obtainDataSource().getConnection();
    txObject.setConnectionHolder(new ConnectionHolder(con));
    con.setAutoCommit(false);                                     // 重点：真正的「开启事务」
    con.setTransactionIsolation(...); con.setReadOnly(...);       // 按定义设置
    TransactionSynchronizationManager.bindResource(getDataSource(), txObject.getConnectionHolder()); // 重点：绑定到线程
}
protected void doCommit(DefaultTransactionStatus status) { status.getTransaction().getConnectionHolder().getConnection().commit(); }
protected void doRollback(...) { con.rollback(); }
// 事务结束后：unbindResource + 恢复 autoCommit + 归还连接池
```

**七种传播行为（必须逐条说清）**：

| 传播 | 外层有事务 | 外层无事务 | 本质 |
|---|---|---|---|
| `REQUIRED`（默认） | **加入**同一个事务 | 新建事务 | 最常用；内层失败会拖垮外层 |
| `REQUIRES_NEW` | **挂起外层**，新建独立事务 | 新建事务 | 内层失败不影响外层，但**两个连接**，可能死锁；日志/审计常用 |
| `SUPPORTS` | 加入 | 以非事务方式执行 | 跟着调用方 |
| `NOT_SUPPORTED` | 挂起外层，非事务执行 | 非事务执行 | 跑不想被事务包住的操作 |
| `MANDATORY` | 加入 | **抛异常** | 强制要求调用方开事务 |
| `NEVER` | **抛异常** | 非事务执行 | 严禁在事务内调用 |
| `NESTED` | **创建 savepoint**（子事务） | 新建事务 | 内层回滚到 savepoint，外层可继续；仅 `DataSourceTransactionManager` 等支持 |

**失效的 10 种场景**（面试最爱问「为什么我加了注解没回滚」）：

| # | 场景 | 原因 |
|---|---|---|
| 1 | 同类方法自调用 `this.b()` | 不走代理（同 AOP 失效根因） |
| 2 | 方法 `private` / `final` / `static` | 代理无法覆写/拦截；`private` 直接不可见 |
| 3 | 非 `public` | JDK 代理只代理接口方法；Spring 6 起 CGLIB 对 protected/包可见放宽，但仍不保证 |
| 4 | 异常类型不匹配 | 默认只回滚 `RuntimeException`/`Error`，受检异常必须 `rollbackFor` |
| 5 | 异常被 `catch` 吞掉 | 拦截器看不到异常 ⇒ 认为成功 ⇒ 提交 |
| 6 | 多线程 / 新线程里执行 | 连接绑定在 ThreadLocal，新线程是另一个事务（或没有） |
| 7 | 对象不是 Spring 管理的 | `new` 出来的对象没代理；`@Bean` 内部 `new` 的依赖也不行 |
| 8 | 数据库引擎不支持 | MySQL `MyISAM` 不支持事务，改了不报错但不回滚 |
| 9 | 传播设成 `NOT_SUPPORTED`/`NEVER` | 主动声明不要事务 |
| 10 | 类没被扫描到 / 代理未生效 | 不在容器里，`@Transactional` 只是注释 |

## L3 底层层：ThreadLocal 资源绑定与挂起/恢复

```java
public abstract class TransactionSynchronizationManager {
    private static final ThreadLocal<Map<Object, Object>> resources = new NamedThreadLocal<>("Transactional resources");
    private static final ThreadLocal<Set<TransactionSynchronization>> synchronizations = ...;
    private static final ThreadLocal<String> currentTransactionName = ...;
    private static final ThreadLocal<Boolean> actualTransactionActive = ...;
    public static void bindResource(Object key, Object value)      // key = DataSource
    public static Object getResource(Object key)                   // DataSourceUtils.getConnection 走这里
    public static Object unbindResource(Object key)                // 事务结束时解绑
}
```

- `DataSourceUtils.getConnection(dataSource)` 先查 ThreadLocal 有没有绑定，有就复用（**同一个事务内所有 DAO 拿的是同一个 Connection**），没有才从连接池取新连接
- `REQUIRES_NEW` 的挂起：`AbstractPlatformTransactionManager.suspend()` 把当前 `ConnectionHolder` 从 ThreadLocal **解绑**并放进 `SuspendedResourcesHolder`，新事务再绑定新连接；外层恢复时 `resume()` 再绑回去
- `NESTED` 的 savepoint：`doBegin` 时不新建连接，而是 `con.setSavepoint()` 生成 `Savepoint`；内层回滚 `con.rollback(savepoint)`，外层仍可提交。JDBC 3.0 的 `Savepoint` 是数据库能力，Redis/Mongo 之类没有，所以 NESTED 不是通用能力
- 提交时机：`commit` 发生在**业务方法返回之后、代理返回之前**；所以在事务方法里发 MQ 或 P99 远程调用，消息可能先于提交被消费 ⇒ 用 `TransactionSynchronization.afterCommit()` 或事务消息
- `readOnly=true`：`Connection.setReadOnly(true)`，让驱动/数据库走只读优化（MySQL 可路由到只读库，某些场景减少 undo）；**不是强制**，写操作仍可能成功
- `timeout`：`DataSourceTransactionManager` 会 `Statement.setQueryTimeout()`，是**语句级**而非硬性事务级中断

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**

### 第 1 层｜`@Transactional` 的原理？
**答**：AOP 代理 + `TransactionInterceptor`。拦截器在方法前 `getTransaction`（开或加入事务），正常返回 `commit`，抛异常按 `rollbackOn` 决定回滚还是提交。

### 第 2 层｜事务管理器具体做了什么？
**答**：`DataSourceTransactionManager` 的 `doBegin`：从连接池取连接 → `setAutoCommit(false)` → 按定义设隔离级别/只读 → 把 `ConnectionHolder` 绑定到 `TransactionSynchronizationManager` 的 ThreadLocal；`doCommit/doRollback` 调 `Connection.commit/rollback`；结束时解绑、恢复 `autoCommit`、还连接。

### 第 3 层｜一个事务里多个 DAO 怎么共用同一个连接？
**答**：`DataSourceUtils.getConnection` 先查 `TransactionSynchronizationManager.getResource(dataSource)`，有绑定就复用。所以同一线程、同一 `DataSource` 的多个 Mapper 拿到同一个连接，这才有「一起提交/回滚」。

### 第 4 层｜七种传播行为，`REQUIRED` 和 `REQUIRES_NEW` 的区别？
**答**：`REQUIRED` 外层有事务就**加入**，内外共用一个事务和连接，内层抛异常外层也回滚；`REQUIRES_NEW` **挂起**外层、新建独立事务和连接，内层回滚不影响外层（外层回滚也不影响已提交的内层）。代价是占两个连接，高并发下有连接池耗尽和死锁风险。

### 第 5 层｜`NESTED` 和 `REQUIRES_NEW` 差在哪？savepoint 怎么实现？
**答**：`NESTED` 只有**一个连接、一个物理事务**，靠 JDBC `Savepoint`：进入内层 `conn.setSavepoint()`，内层异常 `conn.rollback(savepoint)` 回到保存点，外层可继续；`REQUIRES_NEW` 是**两个独立物理事务**。注意 JDBC savepoint 是数据库能力，不是所有数据源都支持。

### 第 6 层｜为什么同类自调用事务会失效？
**答**：`this.b()` 用的是目标对象，不经过代理，`TransactionInterceptor` 没机会执行。解决：注入自身代理（`@Lazy`）、`AopContext.currentProxy()`、拆到另一个 Bean，或改用 `TransactionTemplate` 显式编程式事务。

### 第 7 层｜哪些异常默认会回滚？`rollbackFor` 怎么生效？
**答**：默认只回滚 `RuntimeException` 和 `Error`（`DefaultTransactionAttribute.rollbackOn` 判断）；受检异常（如 `IOException`）默认**回滚不了**，要 `@Transactional(rollbackFor = Exception.class)`。反过来也可以用 `noRollbackFor` 指定不回滚。

### 第 8 层｜多线程里为什么事务失效？
**答**：事务的 `ConnectionHolder` 绑在**发起线程**的 ThreadLocal 上；新线程的 ThreadLocal 是空的，`DataSourceUtils.getConnection` 会新取一个连接（如果没手动传递），等于另一个独立事务，外层回滚管不到它。异步任务里要传播事务必须显式传 `TransactionStatus`/连接或用事务消息。

### 第 9 层｜事务方法里发 MQ / 调远程接口有什么风险？
**答**：提交发生在方法返回后。如果在方法内发消息，消费者可能先看到消息、后看到数据提交 ⇒ 读不到数据（脏读/空查）。解法：`TransactionSynchronization.afterCommit()` 里发、事务消息（RocketMQ 半消息）、本地消息表 + 补偿。

### 第 10 层｜`readOnly` 和 `timeout` 真的有用吗？
**答**：`readOnly` 是给驱动/数据库的**提示**：`Connection.setReadOnly(true)`，MySQL 可据此路由只读库或减少 undo，但**不阻止写**；`timeout` 最终是 `Statement.setQueryTimeout`，只能中断慢 SQL，不能强杀事务，长事务风险仍要靠业务和 `innodb_lock_wait_timeout` 控制。

### 第 11 层｜一个 `@Transactional` 方法里调用另一个 Bean 的 `@Transactional(REQUIRES_NEW)`，连接怎么切？
**答**：外层事务的 `ConnectionHolder` 从 ThreadLocal 解绑放进 `SuspendedResourcesHolder`（不还池，等外层恢复）；内层从连接池**另取**一个连接绑定；内层提交/回滚后解绑、还池；外层 `resume()` 把原 holder 绑回。所以同一时刻这个线程占用两个连接。

### 第 12 层（终局）｜从代理进方法到事务提交，完整链路？
**答**：代理 `invoke` → `TransactionInterceptor.invoke` → `invokeWithinTransaction`：解析 `@Transactional` 属性 → `createTransactionIfNecessary` → `tm.getTransaction`（`doGetTransaction` 判断是否已有 ConnectionHolder；`propagationBehavior` 决定新建/加入/挂起）→ `doBegin`（取连接、`autoCommit=false`、绑定 ThreadLocal）→ `proceedWithInvocation` 执行业务 → 正常返回 `commit`（`doCommit` + `triggerAfterCommit` + 解绑 + 恢复 autoCommit + 还连接）→ 异常则 `rollback`。**分水岭：能说出「提交在方法返回后」「绑定 key 是 DataSource」「挂起不还连接」。**

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| `PlatformTransactionManager` | 事务管理器顶层接口（commit/rollback/getTransaction） | 屏蔽 JDBC/JTA/Redis 等不同事务实现 | 与 `TransactionTemplate` 关系 |
| `DataSourceTransactionManager` | JDBC 单数据源实现 | 用 `Connection` 做本地事务 | `doBegin/doCommit/doRollback` |
| `TransactionInterceptor` | AOP 的 `MethodInterceptor` | 把「事务」做成横切关注点 | 与 `@Transactional` 的绑定 |
| `TransactionSynchronizationManager` | 事务资源的 ThreadLocal 管家 | 让同一线程内共享连接/同步回调 | `bindResource` 的 key 是什么 |
| `ConnectionHolder` | 连接持有者 | 标记连接已被事务占用、记录隔离级 | 与 `DataSourceUtils` 配合 |
| `TransactionStatus` | 事务运行状态（是否新事务、savepoint） | 控制提交/回滚/嵌套 | `isNewTransaction` 用途 |
| 传播行为 | 7 种「有/无外层事务」策略 | 精确控制事务边界 | REQUIRED/REQUIRES_NEW/NESTED 差异 |
| `SuspendedResourcesHolder` | 被挂起事务的资源快照 | `REQUIRES_NEW` 时暂存外层连接 | 挂起时连接不归还池 |
| Savepoint | JDBC 保存点 | 支持 NESTED 的「部分回滚」 | 数据库能力限制 |
| `rollbackOn` | 判断异常是否回滚 | 默认只回滚运行时异常 | `rollbackFor`/`noRollbackFor` |
| `TransactionSynchronization` | 事务回调（before/afterCommit） | 提交后再做副作用（发消息） | `afterCommit` 的典型用途 |
| `readOnly` / `timeout` | 事务属性 | 只读优化 / 限制慢查询 | 都只是提示，不保证 |
| 自调用失效 | 内部调用绕过代理 | 所有注解式 AOP 的通病 | 4 种解法 |

## 代码验证（JDK 单文件可跑：用 ThreadLocal 模拟连接的绑定与传播）

```java
// 保存为 TxDemo.java：javac TxDemo.java && java TxDemo
import java.util.*;

public class TxDemo {
    static final ThreadLocal<String> RESOURCE = new ThreadLocal<>();   // 模拟 ConnectionHolder 绑定
    static int beginCount = 0;                                        // 模拟 doBegin 次数

    static void begin(String name) { beginCount++; RESOURCE.set(name); System.out.println("  开启事务 " + name); }
    static void commit() { System.out.println("  提交 " + RESOURCE.get()); RESOURCE.remove(); }
    static void suspend() { System.out.println("  挂起 " + RESOURCE.get()); RESOURCE.remove(); }  // 注意：不还连接

    static void required(String name) {                 // REQUIRED：有事务就加入
        boolean isNew = RESOURCE.get() == null;
        if (isNew) begin(name);
        System.out.println("    " + name + " 执行（isNew=" + isNew + "，当前连接=" + RESOURCE.get() + "）");
        if (isNew) commit();
    }
    static void requiresNew(String name) {              // REQUIRES_NEW：挂起外层再新建
        String outer = RESOURCE.get();
        if (outer != null) suspend();
        begin(name);
        System.out.println("    " + name + " 执行（独立连接=" + RESOURCE.get() + "）");
        commit();
        if (outer != null) { RESOURCE.set(outer); System.out.println("  恢复 " + outer); }
    }
    public static void main(String[] args) {
        System.out.println("① 外层 REQUIRED，内层 REQUIRED（应只有 1 次 doBegin）:");
        begin("TX-outer");
        required("inner-required");
        commit();
        System.out.println("   doBegin 次数 = " + beginCount);
        beginCount = 0;
        System.out.println("② 外层 REQUIRED，内层 REQUIRES_NEW（应有 2 次 doBegin）:");
        begin("TX-outer2");
        requiresNew("inner-new");
        commit();
        System.out.println("   doBegin 次数 = " + beginCount);   // 2
    }
}
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「加了 `@Transactional` 就一定回滚」 | 受检异常默认不回滚，要 `rollbackFor` |
| 「同类调用也能生效」 | 自调用不走代理，必须走代理或 `TransactionTemplate` |
| 「`REQUIRES_NEW` 和 `NESTED` 一样」 | 前者两个物理事务，后者一个事务 + savepoint |
| 「连接池里的连接是事务的一部分」 | 连接靠 ThreadLocal 绑定，跨线程就断 |
| 「事务提交在方法内」 | 提交在方法返回后、代理返回前 |
| 「`readOnly=true` 就不能写」 | 只是提示，写仍可能成功 |
| 「事务超时能强杀事务」 | 是 `setQueryTimeout`，语句级 |
| 「`private` 方法加注解也行」 | 代理无法拦截（Spring 6 对 CGLIB 放宽但仍有限制） |
