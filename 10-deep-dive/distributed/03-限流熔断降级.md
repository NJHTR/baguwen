# 限流、熔断与降级

> 面试权重：4/5　｜　追问深度：**L5（滑动窗口实现 / Sentinel 熔断状态机 / Redis+Lua 分布式限流）**
> 一句话定位：限流是**保护自己**（入口按 QPS/并发截流）、熔断是**保护调用方**（下游持续失败就快速失败一段时间）、降级是**给用户一个还能接受的兜底**；三者串起来才是完整的「过载保护」体系。

[返回深度追问索引](../00-索引.md)

## L1 一句话答案（10 秒能说出口）

限流：固定窗口有「临界双倍流量」问题，所以用**滑动窗口**（Sentinel 的 `LeapArray`）或**令牌桶**（允许突发）/漏桶（恒定速率）。熔断：统计一段时间内的失败率/慢调用比例，超过阈值把断路器的 `CLOSED` 推到 `OPEN`，所有请求快速失败；时间窗过后进入 `HALF_OPEN` 放少量请求试探。隔离用线程池或信号量，降级返回兜底数据；分布式场景用 Redis + Lua 或网关层限流。

## L2 原理层：四种限流算法 + 熔断状态机

| 算法 | 原理 | 优点 | 缺陷 |
|---|---|---|---|
| 固定窗口计数器 | 每 1s 计数，超阈值拒绝 | 实现最简单 | **临界问题**：窗口交界处可放两倍流量 |
| 滑动窗口 | 把窗口切成 N 个小桶，按时间滚动统计 | 平滑、精度可控 | 需要存储桶，实现稍复杂 |
| 漏桶 | 请求进桶，**固定速率**流出 | 输出绝对平滑 | 无法应对突发（突发也被排队/丢弃） |
| 令牌桶 | 按固定速率加令牌，请求取令牌 | **允许一定突发** | 参数（速率/桶容量）要调 |

```
固定窗口临界问题：                     滑动窗口（1s 切成 2 个 500ms 桶）：
  0.9s 来 100 个（窗口 A 内）            统计「当前桶 + 前一桶按比例折算」，
  1.1s 又来 100 个（窗口 B 内）          所以 1.1s 时仍能看到 0.9s 的 100 个，
  窗口 A 与 B 都没超 100/s，             不会出现双倍流量。
  但 0.2s 内实际过了 200 个。
```

**Sentinel 核心设计**：每个资源对应一个 `Slot Chain`（责任链）：`NodeSelectorSlot`（构建调用树）→ `ClusterBuilderSlot`（统计来源）→ `StatisticSlot`（统计 pass/block/rt）→ `FlowSlot`（限流规则）→ `DegradeSlot`（熔断规则）→ `SystemSlot`（系统自适应保护）。所有规则都是「先统计、后判断」。

**熔断状态机**（Sentinel `DegradeRule`）：

```
        失败率/慢调用比例超阈值
CLOSED ---------------------------> OPEN（所有请求快速失败，不再调用下游）
  ^                                    |
  |  试探成功（达到阈值次数）             | 经过 timeWindow
  +----------- HALF_OPEN <-------------+
                 |  试探失败
                 +------> OPEN
```

三种熔断策略：慢调用比例（`SLOW_REQUEST_RATIO`，rt 超过 `slowRatioThreshold` 的比例）、异常比例（`ERROR_RATIO`）、异常数（`ERROR_COUNT`），都配合 `minRequestAmount`（最小请求数）与 `statIntervalMs`（统计窗口）。

**隔离策略**：

| | 线程池隔离 | 信号量隔离 |
|---|---|---|
| 原理 | 每个依赖独立线程池，异步调用 | 计数器限制并发数，同线程执行 |
| 开销 | 线程切换、上下文开销大 | 极低 |
| 能否超时中断 | 能（Future 超时） | 不能（只能等） |
| 适用 | 下游慢、需要超时保护 | 高并发、调用本身很快（如 Redis） |

## L3 底层层：LeapArray 环形窗口 / 熔断器实现 / Redis+Lua

### 3.1 Sentinel 的滑动窗口：`LeapArray`

```java
// 简化后的核心结构
public abstract class LeapArray<T> {
    protected int windowLengthInMs;   // 每个桶的长度 = interval / sampleCount
    protected int sampleCount;        // 桶数量（默认 2，可配 10 等）
    protected AtomicReferenceArray<WindowWrap<T>> array;   // 环形数组，长度 = sampleCount

    public WindowWrap<T> currentWindow(long timeMillis) {
        long timeId = timeMillis / windowLengthInMs;       // 用整除定位桶
        int idx = (int) (timeId % array.length());         // 环形索引
        // 桶的 startTime 过期则重置（CAS 复用），否则直接用
    }
}
```

- 默认 `interval=1000ms`、`sampleCount=2` ，即 每桶 500ms；统计时取当前桶 + 上一个桶（窗口是滚动的）
- 桶复用靠**比较 `windowStart`**：`timeId` 变了就 RESET 重算，避免频繁建对象
- 统计值存在 `MetricBucket`（`LongAdder`）：`pass/block/complete/exception/rt`，保证高并发下计数不成为瓶颈
- 集群限流时，`ClusterNode` 的统计会由 token server 汇总，规则判断在 server 侧完成

### 3.2 熔断器实现要点

- 熔断判断在 `DegradeSlot`，每个资源一个 `CircuitBreaker`，状态用 `AtomicReference<State>` CAS 切换
- `OPEN` 期间所有请求直接抛 `DegradeException`（不执行下游），同时用一个「下次允许探测时间」控制何时进 `HALF_OPEN`
- `HALF_OPEN` 只放 **1 个**请求（有的实现是计数），成功则 `CLOSED` 并清空统计，失败则重新 `OPEN` 并重新计时
- `minRequestAmount` 防止「只有 1 个请求失败就算 100% 失败率」的误判

### 3.3 Redis + Lua 分布式限流

| 方案 | Lua 核心操作 | 特点 |
|---|---|---|
| 固定窗口 | `INCR key`，第一次 `EXPIRE 1` | 简单，但有临界问题 |
| 滑动窗口 | `ZADD key now now` + `ZREMRANGEBYSCORE key 0 (now-1000)` + `ZCARD` | 精确，内存与请求数成正比 |
| 令牌桶 | `GET tokens,lastRefill` → 按时间差补令牌 → `SET` 回去 | 允许突发，需处理时钟 |

Lua 脚本在 Redis 单线程内原子执行，所以「读-算-写」不会被并发打断——这是分布式限流不超卖的关键。Spring Cloud Gateway 的 `RedisRateLimiter` 就是令牌桶 Lua 实现，参数 `replenishRate`（每秒令牌）、`burstCapacity`（桶容量）、`requestedTokens`。

> 网关层限流和业务层限流分工：网关做**粗粒度**（按 IP/路由/用户），挡住绝大部分恶意与突发流量；业务层做**细粒度**（按用户/租户/接口的业务配额），因为网关看不到业务语义。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**

### 第 1 层｜限流、熔断、降级分别是什么？
**答**：限流是入口按阈值截流（保护自己）；熔断是下游持续失败时快速失败一段时间（保护调用方、给下游恢复时间）；降级是失败时返回兜底值/缓存/默认页（保用户体验）。

### 第 2 层｜固定窗口计数器的临界问题是什么？
**答**：窗口边界处会放行双倍流量。例如限制 100 QPS，0.9s 来了 100 个（属于窗口 A），1.1s 又来 100 个（属于窗口 B），两个窗口都没超，但 0.2 秒内实际过了 200 个。

### 第 3 层｜滑动窗口怎么解决？Sentinel 怎么实现的？
**答**：把 1 秒切成 N 个桶，统计时按时间滚动地累加「当前桶 + 之前的桶」。Sentinel 用 `LeapArray`：环形数组 + `windowStart` 判断桶是否过期，默认 1s 切 2 个 500ms 桶，取值时合并当前桶与上一桶，用 `LongAdder` 统计。

### 第 4 层｜漏桶和令牌桶的区别？分别适合什么场景？
**答**：漏桶以恒定速率流出，进桶的请求多出来就排队/丢弃，输出绝对平滑，适合「保护下游不被突发打崩」；令牌桶按速率生成令牌、桶里可攒令牌，请求拿不到才拒绝，允许一定突发，适合「允许短时突发但平均速率受限」的 API 限流。

### 第 5 层｜Sentinel 的熔断状态机是怎样的？
**答**：`CLOSED` 正常统计；失败率/慢调用比例/异常数超阈值且请求数达到 `minRequestAmount` 就转 `OPEN`，期间所有请求直接快速失败；经过 `timeWindow` 后转 `HALF_OPEN`，放少量请求试探，成功回 `CLOSED` 并清统计，失败回 `OPEN` 重新计时。

### 第 6 层｜线程池隔离和信号量隔离怎么选？
**答**：线程池隔离给每个依赖独立线程池，能超时中断、保护调用方，但线程切换开销大、线程数难估；信号量隔离只是计数并发，开销极低但不能超时中断。下游慢（HTTP/RPC）用线程池，高频短调用（Redis/本地缓存）用信号量。

### 第 7 层｜降级有哪些兜底方式？
**答**：返回默认值/空列表、读缓存里的旧数据、返回排队中提示、快速失败给友好文案、切到备用服务/降级开关。关键是把「降级逻辑」和业务主流程解耦，并且降级本身要幂等、不能引发二次故障。

### 第 8 层｜分布式限流为什么必须用 Lua？
**答**：限流是「读取当前计数 → 判断 → 写回」的复合操作，Redis 多命令之间可能被其他请求插入，导致超限。Lua 脚本在 Redis 中**原子执行**，且能减少网络往返（一次 RTT 完成全部判断），所以是分布式限流的标准做法。

### 第 9 层｜Redis 滑动窗口用 ZSET 怎么实现？有什么问题？
**答**：每次请求 `ZADD key now now`，再 `ZREMRANGEBYSCORE` 删掉 1 秒前的成员，`ZCARD` 判断是否超限。问题是内存与请求量成正比（每个请求一条成员），高 QPS 下需要设过期时间、或用固定窗口/令牌桶替代。

### 第 10 层｜网关限流和业务限流分别放什么规则？
**答**：网关做粗粒度：按 IP、路由、用户维度做 QPS/并发限制，防刷防突发，返回 429；业务层做细粒度：按租户配额、接口业务规则（如下单每人每秒 1 次），因为业务语义只有业务层知道。

### 第 11 层｜限流触发后返回什么？客户端怎么配合？
**答**：HTTP 429 Too Many Requests，带 `Retry-After` 告知重试时间；RPC 返回特定错误码。客户端要配合指数退避 + 随机抖动重试，写操作重试必须幂等（唯一键/去重表），否则重试会放大问题。

### 第 12 层（终局）｜一次请求在 Sentinel 责任链里到底发生了什么？
**答**：`SphU.entry(resource)` → 取该资源的 `ProcessorSlotChain`（每种资源一条）→ `NodeSelectorSlot` 建调用树节点 → `ClusterBuilderSlot` 绑定 ClusterNode → `StatisticSlot` 先放行并统计（等于先执行后续 slot 再记账）→ `FlowSlot` 按 `FlowRule` 判断 QPS/并发是否超限，超限抛 `FlowException` → `DegradeSlot` 判断熔断状态，`OPEN` 时抛 `DegradeException` → `SystemSlot` 做系统级保护（load/rt/线程数）→ 通过后执行真正的业务。**分水岭：能说出「先统计后判断」和「桶按时间窗口滚动复用」。**

## L5 名词拆解表（每个名词都拆开）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| QPS / 并发数 | 每秒请求数 / 同时处理数 | 两种不同的限流维度 | QPS 限制入口、并发限制资源 |
| 固定窗口 | 每周期一个计数器 | 实现最简单 | 临界双倍流量 |
| 滑动窗口 | 多个小桶滚动统计 | 平滑限流 | 桶数量与精度的权衡 |
| 漏桶 | 恒定速率流出 | 输出绝对平滑 | 与令牌桶区别 |
| 令牌桶 | 按速率发令牌、可攒 | 允许突发 | 容量参数怎么定 |
| `LeapArray` / `WindowWrap` | Sentinel 的环形窗口结构 | 高性能滑动统计 | 桶复用、环形索引 |
| `MetricBucket` | 一个窗口内的统计值 | 用 `LongAdder` 高并发计数 | pass/block/rt 各表示什么 |
| `SlotChain` | 资源对应的责任链 | 把统计、限流、熔断、系统保护串起来 | 各 Slot 顺序与职责 |
| 熔断器 | 三态开关（CLOSED/OPEN/HALF_OPEN） | 下游故障时快速失败 | 三态转换条件、探测请求数 |
| 慢调用比例 | rt 超过阈值的请求占比 | 比失败率更早发现劣化 | `slowRatioThreshold` 含义 |
| `minRequestAmount` | 触发熔断的最小请求数 | 防止小样本误判 | 与统计窗口配合 |
| 线程池隔离 / 信号量隔离 | 两种隔离资源的方式 | 防止单个依赖拖垮整体 | 能否超时中断 |
| 降级 | 兜底返回 | 保可用性与体验 | 兜底数据来源、幂等 |
| 分布式限流 | 多实例共享配额 | 单机限流总量会翻倍 | Redis+Lua、网关、集群限流 |
| 429 / `Retry-After` | 限流的标准响应 | 让客户端知道何时重试 | 与退避、幂等的关系 |

## 代码验证（JDK 单文件可跑：固定窗口临界 vs 滑动窗口 vs 令牌桶）

```java
// 保存为 RateLimitDemo.java：javac RateLimitDemo.java && java RateLimitDemo
import java.util.*;
import java.util.concurrent.*;

public class RateLimitDemo {
    // 1) 固定窗口：每 1000ms 一个窗口，阈值 5
    static class FixedWindow {
        long windowStart = 0; int count = 0; final int limit;
        FixedWindow(int limit) { this.limit = limit; }
        synchronized boolean tryAcquire(long now) {
            if (now - windowStart >= 1000) { windowStart = now; count = 0; }
            if (count < limit) { count++; return true; }
            return false;
        }
    }
    // 2) 滑动窗口：3 个桶（每桶 333ms），统计最近 1000ms
    static class SlidingWindow {
        final int[] buckets; final long[] starts; final int limit;
        SlidingWindow(int n, int limit) { buckets = new int[n]; starts = new long[n]; this.limit = limit; Arrays.fill(starts, -1); }
        synchronized boolean tryAcquire(long now) {
            int idx = (int) ((now / 333) % buckets.length);
            long start = (now / 333) * 333;
            if (starts[idx] != start) { starts[idx] = start; buckets[idx] = 0; }
            int total = 0;
            for (int i = 0; i < buckets.length; i++) if (starts[i] >= 0 && now - starts[i] < 1000) total += buckets[i];
            if (total < limit) { buckets[idx]++; return true; }
            return false;
        }
    }
    // 3) 令牌桶：每秒 5 个令牌，容量 5
    static class TokenBucket {
        double tokens = 5; long last = System.currentTimeMillis(); final double rate = 5; final double cap = 5;
        synchronized boolean tryAcquire(long now) {
            tokens = Math.min(cap, tokens + (now - last) / 1000.0 * rate); last = now;
            if (tokens >= 1) { tokens -= 1; return true; }
            return false;
        }
    }
    public static void main(String[] args) throws Exception {
        FixedWindow fixed = new FixedWindow(5);
        System.out.println("固定窗口：900ms 连发 5 个 -> " + tryN(fixed::tryAcquire, 900, 5) + "，1100ms 再发 5 个 -> " + tryN(fixed::tryAcquire, 1100, 5));
        SlidingWindow sliding = new SlidingWindow(3, 5);
        System.out.println("滑动窗口：900ms 连发 5 个 -> " + tryN(sliding::tryAcquire, 900, 5) + "，1100ms 再发 5 个 -> " + tryN(sliding::tryAcquire, 1100, 5));
        TokenBucket bucket = new TokenBucket();
        long t0 = System.currentTimeMillis();
        System.out.println("令牌桶：连发 7 个 -> " + tryN(bucket::tryAcquire, t0, 7) + "（容量 5，前 5 个通过）");
        Thread.sleep(400);
        System.out.println("令牌桶：400ms 后再发 3 个 -> " + tryN(bucket::tryAcquire, System.currentTimeMillis(), 3) + "（约补 2 个令牌）");
    }
    interface Limiter { boolean tryAcquire(long now); }
    static int tryN(Limiter l, long now, int n) { int ok = 0; for (int i = 0; i < n; i++) if (l.tryAcquire(now)) ok++; return ok; }
}
```

```lua
-- Redis 滑动窗口限流（原子）：每 1 秒最多 limit 次
local key, now, limit, window = KEYS[1], ARGV[1], tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)     -- 清掉窗口外的
local count = redis.call('ZCARD', key)
if count < limit then
  redis.call('ZADD', key, now, now .. '-' .. math.random(1000000))
  redis.call('PEXPIRE', key, window)
  return 1
end
return 0
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「固定窗口限流就够了」 | 有临界双倍流量问题，高要求场景要用滑动窗口/令牌桶 |
| 「漏桶和令牌桶等价」 | 漏桶输出恒定、不容突发；令牌桶允许攒令牌、可突发 |
| 「限流是限总请求数」 | 是限「单位时间的速率」或「并发数」，两种维度不同 |
| 「熔断等于限流」 | 熔断针对下游持续失败，快速失败；限流针对自身容量，提前截流 |
| 「熔断打开后永远不再调用」 | `timeWindow` 后进 `HALF_OPEN` 试探，成功就恢复 |
| 「线程池隔离一定比信号量好」 | 线程池能超时但开销大，高频短调用适合信号量 |
| 「Redis INCR 就能做分布式限流」 | 复合操作要原子，必须用 Lua；否则并发下会超限 |
| 「网关限流能覆盖所有限流」 | 网关看不到业务语义，细粒度配额要在业务层做 |
