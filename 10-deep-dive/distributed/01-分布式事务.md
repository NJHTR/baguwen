# 分布式事务

> 面试权重：5/5　｜　追问深度：**L5（2PC 协议状态 / TCC 异常场景 / Seata AT 的 undo_log 与全局锁）**
> 一句话定位：分布式事务不是「把本地事务放大」，而是在**没有全局锁的前提下**用协议或业务补偿来保证多数据源的一致性：要么两阶段提交（强一致、阻塞、性能差），要么 TCC/Saga/消息（最终一致、要处理补偿与幂等）。

## L1 一句话答案（10 秒能说出口）

单库靠数据库 ACID 就够了，跨服务/跨库没有全局锁，只能选：2PC/3PC（协调者两阶段提交，强一致但同步阻塞、协调者单点）、TCC（Try 预留、Confirm 提交、Cancel 回滚，业务补偿换性能，要处理空回滚/悬挂/幂等）、Saga（长事务拆本地事务 + 反向补偿）、本地消息表/RocketMQ 事务消息（最终一致），以及 Seata AT（一阶段本地提交 + `undo_log`，二阶段用 `undo_log` 做自动反向补偿，配合全局锁保证写隔离）。

## L2 原理层：五种主流方案对比与流程

| 方案 | 一致性 | 性能 | 侵入性 | 典型场景 |
|---|---|---|---|---|
| 2PC / XA | 强一致 | 低（同步阻塞） | 低（数据库/中间件支持） | 传统金融、银行内部跨库 |
| 3PC | 强一致（仍有边界问题） | 略好于 2PC | 低 | 已较少使用 |
| TCC | 最终一致 | 高 | 高（要写三个接口） | 订单 + 库存 + 支付、资金类 |
| Saga | 最终一致 | 高 | 中（要写补偿） | 长流程、跨多服务编排 |
| 本地消息表 | 最终一致 | 高 | 中 | 单库业务 + MQ 通知 |
| 事务消息 | 最终一致 | 高 | 低（MQ 保障） | 下单后通知库存/积分 |
| Seata AT | 最终一致（读未提交） | 中 | 低（加注解即可） | 国内互联网最常见的落地 |

**2PC（两阶段提交）**：

```
协调者(TM)                    参与者(RM) x N
  |-- prepare 请求 ----------->|  执行本地事务、锁资源、写 undo/redo、不提交
  |<-- yes / no --------------|
  |  全部 yes：-- commit ----->|  提交并释放锁
  |  任一 no ：-- rollback --->|  回滚
```

缺陷：**同步阻塞**（prepare 阶段资源全程锁定，长事务拖死整个集群）、**协调者单点**（挂了参与者一直锁着）、**数据不一致**（commit 阶段部分参与者失败）、**过于保守**（任一失败全回滚）。3PC 把 prepare 拆成 `canCommit` + `preCommit`，并给参与者加超时，缓解阻塞但仍有「preCommit 后网络分区」的不一致角落。

**TCC 三阶段（业务层两阶段）**：

| 阶段 | 做什么 | 要求 |
|---|---|---|
| Try | 检查并**预留**资源（冻结库存、预扣金额） | 幂等；资源不足直接拒绝 |
| Confirm | 确认使用预留资源（真正扣减） | 幂等；只要 Try 成功必须能成功 |
| Cancel | 释放预留资源 | 幂等；空回滚要能容错 |

三大经典问题：**空回滚**（Try 没到达，Cancel 先到，不能把别人的资源退了）、**悬挂**（Cancel 先执行，迟到的 Try 再预留资源，资源永久冻结）、**幂等**（Confirm/Cancel 重试多次）。解法：事务控制表记录状态（`try`/`confirm`/`cancel` + 防重键），Cancel 时若查不到 Try 记录就标记「已空回滚」，后续 Try 看到该标记直接拒绝（防悬挂）。

**Seata AT（Automatic Transaction）**：

```
TM 开启全局事务 -> TC 生成 XID 并下发
RM（每个数据源）一阶段：
  拦截业务 SQL -> 解析出 beforeImage / afterImage
  -> 执行业务 SQL（本地已提交）
  -> 写 undo_log（rollback_info 里存前后镜像）
  -> 向 TC 注册分支、申请全局锁（lock_table）
TC 收到全部一阶段完成：
  二阶段-提交：异步删除 undo_log（极快）
  二阶段-回滚：按 undo_log 生成反向 SQL，校验 afterImage 未被改过（脏写检查），执行回滚
```

## L3 底层层：undo_log 结构 / 全局锁 / 事务消息回查

### 3.1 `undo_log` 与 `lock_table`

```sql
-- undo_log：每个业务库一张，一阶段写、二阶段用于回滚或清理
CREATE TABLE undo_log (
  branch_id     BIGINT,      -- 分支事务 id
  xid           VARCHAR(128),-- 全局事务 id
  context       VARCHAR(128),-- 序列化方式
  rollback_info LONGBLOB,    -- beforeImage + afterImage（JSON）
  log_status    INT,         -- 0 正常 / 1 已回滚
  log_created   DATETIME,
  log_modified  DATETIME,
  UNIQUE KEY ux_undo_log (xid, branch_id)
);

-- lock_table：TC 侧的全局锁表（写隔离）
-- 主键 (xid, table_name, pk)，一行代表某条记录被某个全局事务锁住
```

**写隔离**的完整链：本地事务先拿**数据库行锁** → 业务 SQL 执行 → 注册分支时再拿**全局锁**（在 TC 的 `lock_table` 里插一行）→ 本地提交时释放行锁但**全局锁保留到二阶段结束**。别的全局事务想改同一行，本地 SQL 能执行（拿到行锁），但注册分支时申请全局锁失败 → 重试/回滚。这样避免了「A 已提交、B 在二阶段回滚时把 A 的修改覆盖掉」的脏写。

**读隔离**：AT 默认是**读未提交**（因为一阶段就本地提交了），要读已提交必须 `@GlobalLock + SELECT ... FOR UPDATE`（或 `@Transactional` 里的 `select for update`），代价是锁竞争。

### 3.2 RocketMQ 事务消息（半消息 + 回查）

```
生产者 send half message（对消费者不可见）
  -> 执行本地事务（写订单表）
  -> 返回 commit / rollback
  -> commit：消息对消费者可见；rollback：丢弃
如果生产者挂掉没返回：Broker 定时回查（checkLocalTransaction，默认最多 15 次，间隔递增）
  -> 应用根据本地事务表/订单状态回答 commit 或 rollback
```

它解决的是「本地事务 + 发消息」的原子性：消息不会先于本地事务生效，也不会本地成功消息丢失。注意消费者端仍要**幂等**（消息可能重复）。

### 3.3 本地消息表 vs 事务消息

| | 本地消息表 | RocketMQ 事务消息 |
|---|---|---|
| 实现 | 业务库一张 `message` 表，和业务同事务写入，定时任务扫表投递 | MQ 的半消息 + 回查 |
| 依赖 | 只需数据库 + 一个定时任务 | 依赖支持事务消息的 MQ |
| 可靠性 | 靠扫表重试，最终一致 | 靠 Broker 回查 + 重试 |
| 适用 | 不想引入 MQ 事务能力、异构系统 | 已用 RocketMQ、追求低侵入 |

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**

### 第 1 层｜为什么需要分布式事务？
**答**：单机事务靠数据库的 undo/redo 和行锁保证 ACID；一旦一个业务动作跨了两个数据库或两个服务（下单扣库存 + 扣余额），本地事务管不到另一边，就需要「要么都成功、要么都回滚」的跨资源机制。

### 第 2 层｜2PC 的两个阶段？有什么问题？
**答**：协调者先向所有参与者发 prepare，参与者执行但不提交、锁住资源并回 yes/no；全 yes 再发 commit，否则 rollback。问题：同步阻塞（资源锁定时间长）、协调者单点、commit 阶段部分失败导致不一致、任一参与者失败就整体回滚过于保守。

### 第 3 层｜3PC 比 2PC 多了什么？为什么没普及？
**答**：把 prepare 拆成 `canCommit` 和 `preCommit`，并在参与者侧加超时，减少阻塞时间；但 preCommit 之后网络分区仍可能让部分节点提交、部分回滚，一致性并没有真正解决，复杂度却上去了，所以工业界更常用 TCC / 消息 / Seata。

### 第 4 层｜TCC 的空回滚、悬挂、幂等分别怎么防？
**答**：用一张事务控制表：Try 先写记录（状态 TRYING），Cancel 时查不到记录说明是空回滚，插入一条 CANCELED 记录并直接返回成功；如果 Cancel 先到（CANCELED 存在），后到的 Try 直接拒绝，防止悬挂；Confirm/Cancel 每次执行前查状态、执行后落状态，保证幂等。

### 第 5 层｜Saga 和 TCC 的区别？
**答**：TCC 是「先预留再确认」，资源在 Try 阶段就被锁定，隔离性好、实现重；Saga 是「一串本地事务顺序执行，失败就反向调用补偿」，没有预留、并发高，但**中间状态对外可见**（例如订单已创建、库存未扣），且补偿操作必须幂等、可重试，还可能补偿失败需要人工介入。

### 第 6 层｜本地消息表怎么保证「业务成功则消息一定发出去」？
**答**：把「写业务表」和「写消息表」放在**同一个本地事务**里，保证原子性；之后由定时任务扫未发送的消息去投递，投递成功才标记已发送。这样即使 MQ 暂时不可用，消息也不会丢，最坏是延迟。

### 第 7 层｜RocketMQ 事务消息的回查是什么？为什么要回查？
**答**：生产者发半消息后执行本地事务，如果还没来得及返回 commit/rollback 就宕机，Broker 会定时回调生产者的 `checkLocalTransaction` 询问「这个事务到底成没成」，应用根据本地事务状态表回答。没有回查，消息就会永远处于「半消息」不可见状态。

### 第 8 层｜Seata AT 一阶段做了什么？为什么说它是「自动补偿」？
**答**：RM 拦截业务 SQL，解析出 `beforeImage`/`afterImage`，执行业务 SQL 并**本地提交**，同时写 `undo_log`、向 TC 注册分支、申请全局锁。二阶段回滚时按 `undo_log` 生成反向 SQL 执行，所以业务代码不用写补偿逻辑——补偿是框架从镜像里算出来的。

### 第 9 层｜AT 的全局锁解决什么问题？为什么一阶段已经提交了还需要锁？
**答**：一阶段本地提交后行锁就释放了，如果没有全局锁，另一个全局事务可能改掉同一行；当第一个事务二阶段回滚时，会把别人已提交的修改覆盖掉（脏写）。全局锁把「这条记录的写权」保留到二阶段结束，保证回滚安全。

### 第 10 层｜AT 默认读未提交，怎么做到读已提交？
**答**：AT 一阶段就提交了本地事务，所以其他事务能读到中间状态（读未提交）。要读已提交，需要在读取时加 `@GlobalLock` 并对目标行 `SELECT ... FOR UPDATE`，这样会去 TC 检查全局锁，若被别的全局事务持有则等待——本质是用锁换隔离级别。

### 第 11 层｜订单状态流转这种业务，你选哪种分布式事务？
**答**：看一致性要求。订单 + 库存 + 积分的「下单」链路，我会用 **RocketMQ 事务消息 / 本地消息表 + TCC 或 AT** 的组合：主交易用 AT（低侵入、能回滚），下游通知用事务消息保证最终一致；如果涉及资金，则用 TCC 明确预留与确认。核心原则是「强一致尽量缩小范围，跨服务一律最终一致 + 幂等」。

### 第 12 层（终局）｜一次 Seata AT 的跨服务调用，从 SQL 到回滚到底发生了什么？
**答**：TM 向 TC 开启全局事务拿 XID（通过 RPC 透传）→ 服务 A 的 RM 拦截 SQL：查前镜像 → 执行 SQL → 查后镜像 → 写 `undo_log` → 本地提交 → 向 TC 注册分支并申请全局锁 → 调服务 B（XID 透传）→ B 重复同样动作 → 任一分支失败，TC 通知所有分支回滚 → 各 RM 按 `undo_log` 校验 `afterImage`（脏写检查）后生成反向 SQL 回滚 → 删除 `undo_log`。**分水岭：能说出「一阶段已提交、二阶段靠 undo_log 反做」和「全局锁保留到二阶段」。**

## L5 名词拆解表（每个名词都拆开）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 2PC / XA | 两阶段提交协议 / XA 接口 | 数据库层面支持跨库强一致 | prepare 阻塞、协调者单点 |
| 3PC | 三段式提交 | 缓解 2PC 阻塞 | 网络分区下仍不一致 |
| TCC | Try-Confirm-Cancel 业务补偿 | 用业务预留替代数据库锁 | 空回滚、悬挂、幂等 |
| Saga | 长事务拆本地事务 + 反向补偿 | 适合长流程、高并发 | 中间状态可见、补偿失败 |
| 本地消息表 | 业务库里的待投递消息表 | 业务与消息同事务，保证不丢 | 扫表重试、幂等消费 |
| 事务消息 | MQ 的半消息 + 回查机制 | 让「本地事务 + 发消息」原子 | half message、checkLocalTransaction |
| Seata TC/TM/RM | 事务协调者 / 管理器 / 资源管理器 | 把分布式事务做成中间件 | 三者职责、XID 透传 |
| `undo_log` | 业务库里的镜像日志表 | 二阶段回滚的依据 | beforeImage/afterImage、脏写检查 |
| `lock_table` | TC 侧全局锁表 | 保证写隔离、防脏写 | 全局锁保留到二阶段 |
| 全局锁 | 跨库记录级写锁 | 一阶段提交后仍能安全回滚 | 与数据库行锁的关系 |
| 脏写检查 | 回滚前比对 afterImage | 防止覆盖别人已提交的修改 | 校验失败怎么处理 |
| 空回滚 | Try 未执行但 Cancel 到达 | 网络超时导致 | 事务控制表标记 |
| 悬挂 | Cancel 先于 Try 执行 | 重试乱序 | Try 看到 CANCELED 直接拒绝 |
| 幂等 | 同一操作执行多次结果一致 | 所有重试/补偿的前提 | 唯一键、状态机、防重表 |
| 最大努力通知 | 反复重试 + 对账兜底 | 弱一致场景的兜底 | 与最终一致的边界 |

## 代码验证（JDK 单文件可跑：TCC 的空回滚、防悬挂与幂等）

```java
// 保存为 TccDemo.java：javac TccDemo.java && java TccDemo
import java.util.*;

public class TccDemo {
    enum Status { TRYING, CONFIRMED, CANCELED }
    // 事务控制表：txId -> 状态（真实场景落库并加唯一索引）
    static final Map<String, Status> TX = new HashMap<>();
    static final Map<String, Integer> RESERVED = new HashMap<>(); // txId -> 预留数量
    static int frozenStock = 0;                                  // 预留（冻结）库存

    static boolean tryPhase(String txId, int qty) {              // Try：预留资源
        Status s = TX.get(txId);
        if (s == Status.CANCELED) { System.out.println("Try 拒绝：已 Cancel，防悬挂"); return false; }
        if (s == Status.TRYING || s == Status.CONFIRMED) { System.out.println("Try 幂等：已存在"); return true; }
        TX.put(txId, Status.TRYING); RESERVED.put(txId, qty); frozenStock += qty;
        System.out.println("Try 成功，冻结库存=" + frozenStock);
        return true;
    }
    static void confirm(String txId) {                            // Confirm：确认扣减（幂等）
        if (TX.get(txId) == Status.CONFIRMED) { System.out.println("Confirm 幂等：已确认"); return; }
        if (TX.get(txId) != Status.TRYING) { System.out.println("Confirm 忽略：没有 Try 记录"); return; }
        TX.put(txId, Status.CONFIRMED);
        frozenStock -= RESERVED.getOrDefault(txId, 0);             // 预留转为真实扣减
        System.out.println("Confirm 成功，扣减预留，冻结库存=" + frozenStock);
    }
    static void cancel(String txId) {                             // Cancel：释放预留（防空回滚 + 幂等）
        Status s = TX.get(txId);
        if (s == Status.CANCELED) { System.out.println("Cancel 幂等：已取消"); return; }
        if (s == null) { TX.put(txId, Status.CANCELED); System.out.println("空回滚：没有 Try 记录，标记 CANCELED 防止悬挂"); return; }
        TX.put(txId, Status.CANCELED);
        frozenStock -= RESERVED.getOrDefault(txId, 0);             // 释放预留
        System.out.println("Cancel 成功，释放后冻结库存=" + frozenStock);
    }
    public static void main(String[] args) {
        System.out.println("场景1 正常：Try -> Confirm");
        tryPhase("tx1", 10); confirm("tx1"); confirm("tx1");
        System.out.println("场景2 空回滚：Cancel 先到，迟到的 Try 被拒（防悬挂）");
        cancel("tx2"); tryPhase("tx2", 10);
        System.out.println("场景3 失败回滚：Try -> Cancel -> Cancel 重试");
        tryPhase("tx3", 10); cancel("tx3"); cancel("tx3");
        System.out.println("最终冻结库存=" + frozenStock);
    }
}
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「2PC 性能差是因为网络慢」 | 主要是 prepare 阶段资源全程锁定，同步阻塞 |
| 「TCC 的 Cancel 一定能回滚」 | Try 可能没执行（空回滚），也可能 Cancel 先到（悬挂），必须用状态表兜住 |
| 「Seata AT 是两阶段锁」 | 一阶段本地提交并释放行锁，靠 `undo_log` + 全局锁在二阶段补偿 |
| 「AT 默认读已提交」 | 默认读未提交，要读已提交需 `@GlobalLock + for update` |
| 「事务消息能保证消费不重复」 | 只保证生产者侧原子性，消费端必须幂等 |
| 「Saga 不需要幂等」 | 补偿操作重试时必须幂等，否则会重复扣减 |
| 「本地消息表不需要定时任务」 | 必须扫表投递 + 重试，否则消息永远发不出去 |
| 「分布式事务可以做到高性能强一致」 | CAP 下强一致必然牺牲可用性或性能，工程上多用最终一致 |

## 自测标准

- 能对比 2PC/3PC/TCC/Saga/消息/Seata AT 五类方案的一致性、性能与侵入性
- 能讲清 TCC 三大异常（空回滚/悬挂/幂等）的成因与防护
- 能画出 Seata AT 一阶段与二阶段的完整流程，并解释 `undo_log` 与全局锁
- 能讲清 RocketMQ 事务消息的半消息与回查机制
- 能针对「订单 + 扣库存 + 积分」给出选型与幂等设计
- L4 讲到第 8 层（AT 一阶段）算及格；讲到第 12 层（SQL 到回滚全链路）算优秀
