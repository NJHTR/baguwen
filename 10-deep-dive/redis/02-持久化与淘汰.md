# 持久化与过期淘汰（RDB / AOF / Eviction）

> 面试权重：5/5　｜　追问深度：**L5（Redis 持久化与淘汰源码 + 内核 COW）**
> 一句话定位：Redis 是内存数据库，但必须回答两个问题：「重启后数据还在吗」（持久化）和「内存满了怎么办」（淘汰）。所有 fork、COW、AOF 重写、八种淘汰策略的追问，都是为了这两件事。

**本文件用法**：从 L1 往下读，每读完一层，合上书自问自答。**停在答不出的那一层，就是你的真实水平线。**

## L1 一句话答案（10 秒能说出口）

RDB 是「定时 fork 子进程把内存快照写成二进制文件」，恢复快但可能丢最后一次快照后的数据；AOF 是「把每条写命令追加到日志」，按 `appendfsync` 策略决定丢多少数据，4.0 起支持 RDB+AOF 混合持久化。过期键用「惰性删除 + 定期删除」两种策略，内存达到 `maxmemory` 时按 `maxmemory-policy` 的 8 种策略淘汰。

## L2 原理层：RDB、AOF、过期、淘汰四件事

### 2.1 RDB 与 AOF 对比（必背表）

| 维度 | RDB | AOF |
|---|---|---|
| 存什么 | 内存数据的二进制快照 | 写命令日志（RESP 协议） |
| 文件大小 | 小、紧凑、可压缩（LZF） | 大（命令冗余，重写后变小） |
| 恢复速度 | 快（直接加载） | 慢（重放命令） |
| 数据安全 | 差（两次快照之间的数据全丢） | 好（`everysec` 最多丢 1s） |
| 对性能影响 | fork 阻塞 + COW 内存放大 | fsync 磁盘 IO（everysec 影响小） |
| 适用 | 备份、主从全量同步 | 对数据安全要求高的场景 |
| 混合模式 | `aof-use-rdb-preamble yes`，重写时前半段 RDB + 后半段增量命令 | 4.0+ |

### 2.2 RDB 的 fork + COW（面试重灾区）

```
父进程 ──fork()──► 子进程
  │                  │
  │  页表被复制，物理页共享（只读）
  │                  │
  ├─ 收到写命令 ──► 触发"写时复制"：内核复制这一页，父进程写新页
  │                  │
  └─ 子进程遍历自己的页（旧数据）写 RDB 文件
```

- `fork()` 本身会阻塞主线程（复制页表，内存越大越慢；几十 GB 实例可能几百 ms）。
- 父进程写越频繁 → COW 复制的页越多 → 内存可能接近翻倍；`INFO memory` 的 `rdb_last_cow_size` 可以看上次 fork 的 COW 量。
- 所以：**大内存实例做 RDB 要错峰、控制写流量**，避免内存打满触发 OOM。

**触发时机**：`SAVE`（阻塞）、`BGSAVE`（fork 子进程）、`save 900 1 / 300 10 / 60 10000`（自动）、`SHUTDOWN`、主从全量同步。

### 2.3 AOF 的三步与 fsync 策略

```
写命令 → 追加到 aof_buf（内存缓冲）→ write() 到文件 → fsync() 刷盘
```

| `appendfsync` | 行为 | 最多丢多少 | 性能 |
|---|---|---|---|
| `always` | 每条命令都 fsync | 0（几乎不丢） | 最差（每条一次磁盘 IO） |
| `everysec`（默认） | 后台每秒 fsync 一次 | 1 秒 | 好（推荐） |
| `no` | 交给操作系统刷盘 | 不确定（内核 page cache 决定） | 最好 |

**AOF 重写**：AOF 越来越大（同一条 key 被改 100 次就有 100 条命令），重写就是「用当前内存数据生成最小命令集」。流程：

```
父进程 fork 子进程 → 子进程遍历内存写新 AOF 文件
父进程同时把新写命令写入「AOF 重写缓冲区」（不能丢）
子进程写完 → 父进程把重写缓冲区追加到新 AOF 尾部 → 原子替换旧文件
```

**混合持久化**：重写时新 AOF 文件的前半段用 RDB 格式（加载快），后半段是增量命令（保证完整），`aof-use-rdb-preamble yes`（7.0 默认开启）。

### 2.4 过期键删除：惰性 + 定期

| 策略 | 做法 | 优缺点 |
|---|---|---|
| 惰性删除 | 访问 key 时检查 `expireIfNeeded`，过期就删并返回 nil | 省 CPU，但没人访问的 key 永远占内存 |
| 定期删除 | `serverCron` 每 100ms 调 `activeExpireCycle`，随机抽样检查 | 折中：默认每轮抽 20 个 key，过期比例 > 25% 就继续抽（限时） |
| 定时器（不用） | 每个 key 一个 timer | 内存/CPU 开销太大，Redis 不用 |

**从节点**：从节点不主动删过期 key（等主节点删完发 DEL 同步）；从节点读过期 key 时返回 nil（逻辑过期），保证主从一致。

### 2.5 内存淘汰：8 种 `maxmemory-policy`

| 策略 | 淘汰范围 | 淘汰规则 | 适用 |
|---|---|---|---|
| `noeviction`（默认） | 不淘汰 | 写命令返回 OOM 错误 | 不能丢数据的场景 |
| `allkeys-lru` | 所有 key | 近似 LRU | 纯缓存，最常用 |
| `allkeys-lfu` | 所有 key | 最不经常使用 | 有热点数据（推荐 4.0+） |
| `allkeys-random` | 所有 key | 随机 | 访问均匀 |
| `volatile-lru` | 设了 TTL 的 key | 近似 LRU | 缓存 + 持久数据混存 |
| `volatile-lfu` | 设了 TTL 的 key | LFU | 同上 |
| `volatile-random` | 设了 TTL 的 key | 随机 | 同上 |
| `volatile-ttl` | 设了 TTL 的 key | 剩余 TTL 最短优先 | 优先清即将过期的 |

- **近似 LRU**：Redis 不维护全局 LRU 链表（太贵），而是每个 key 存 24bit 时钟，淘汰时**随机采样 `maxmemory-samples`（默认 5）个 key，挑最久没用的**。样本越大越接近精确 LRU。
- **LFU**：复用 key 的 24bit lru 字段（8bit 计数 + 16bit 衰减时间，单位分钟），按 `lfu-log-factor` 增长、`lfu-decay-time`（分钟）衰减，解决"偶发访问把老热点顶掉"的问题。

## L3 底层层：RDB 文件、AOF 实现、COW 内核

### 3.1 RDB 文件长什么样

```
"REDIS" 魔数 + 版本号
+ 每个 db 的 SELECTDB + 键值对（类型 + key + value，字符串可 LZF 压缩）
+ EOF 标记 + CRC64 校验和
```

- 加载时直接按格式反序列化建对象，比 AOF 重放命令快得多。
- 主从**全量同步**就是把 RDB 文件发给从节点（`diskless` 模式直接走 socket 不落盘）。

### 3.2 AOF 在 Redis 7 的变化

- Redis 7.0 引入**多部分 AOF（Multi Part AOF）**：`manifest` 文件记录 base AOF（RDB 或旧 AOF）和 incr AOF 列表，重写时不用"重写缓冲区"那套单文件逻辑，改由子进程写 base、父进程继续写 incr，最后更新 manifest 原子切换。
- `aof_buf` → `write()` → `fsync()` 的流程不变；`everysec` 下由后台线程（bio）执行 fsync，主线程不阻塞。
- AOF 重写期间如果父进程收到写命令，会同时写「旧 AOF」和「重写缓冲区」，保证不丢。

### 3.3 COW 的内核细节

- `fork()` 复制父进程的页表，所有物理页标记为**只读共享**；任一进程写入 → 触发缺页异常（page fault）→ 内核复制该页 → 各自持有副本。
- Redis 的 RDB 子进程**只读不写**，所以 COW 只发生在父进程写的时候；父进程写越猛，复制页越多，`rdb_last_cow_size` 越大。
- `THP（透明大页）` 会把 4KB 页合并成 2MB，一次 COW 复制 2MB，放大内存与延迟——大内存 Redis 常建议关闭 THP。

### 3.4 淘汰在源码里的入口

- `performEvictions()`（`evict.c`）：每次处理命令前检查 `maxmemory`，超了就按策略从 eviction pool 弹 key 删除，删到低于阈值或超时。
- LRU 时钟在 `robj->lru`（24bit），LFU 复用同一字段（16bit 计数 + 8bit 时间）。
- `activeExpireCycle()`（`expire.c`）：定时删除；`expireIfNeeded()` 惰性删除。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**

### 第 1 层｜RDB 和 AOF 有什么区别？线上怎么选？
**答**：RDB 是二进制快照，文件小、恢复快，但会丢两次快照之间的数据；AOF 是命令日志，按 fsync 策略最多丢 1 秒，但文件大、恢复慢。生产一般「RDB 做备份/主从同步 + AOF everysec 保证数据安全」，4.0+ 开混合持久化兼得两者。

### 第 2 层｜fork 为什么能快速做快照？COW 具体怎么发生？
**答**：fork 只复制页表、物理页共享且只读，子进程能立刻看到父进程的一致性数据；父进程之后写某页时触发缺页异常，内核复制该页给父进程，子进程继续读旧页。所以子进程拿到的是 fork 那一刻的快照。

### 第 3 层｜fork 有什么风险？
**答**：① fork 本身阻塞主线程（复制页表，内存越大越慢）；② 父进程写多时 COW 复制大量页，内存可能接近翻倍，触发 OOM 或 swap；③ 大 key 多、写流量大时风险更高，所以要在低峰做 BGSAVE、控制写流量、关 THP。

### 第 4 层｜AOF 三种 fsync 怎么选？为什么默认 everysec？
**答**：`always` 每条命令刷盘，最安全但性能最差；`everysec` 每秒刷一次，最多丢 1 秒，性能和安全折中，是默认值；`no` 交给 OS，最快但丢数据不可控。金融级要 always 或依赖主从/集群冗余。

### 第 5 层｜AOF 重写为什么不会阻塞主线程？重写期间的新命令怎么办？
**答**：重写是 fork 子进程做的，子进程遍历内存写新文件，主线程继续处理命令。父进程把重写期间的新命令写入「AOF 重写缓冲区」（7.0 是 incr AOF），子进程写完 base 后由父进程把增量追加进去，原子替换。fork 那一刻仍会短暂阻塞。

### 第 6 层｜混合持久化是什么？
**答**：AOF 重写时，新文件前半段直接写 RDB 格式的快照（加载快），后半段写重写期间的增量命令（不丢数据）。恢复时先加载 RDB 再重放增量。`aof-use-rdb-preamble yes` 开启（7.0 默认）。

### 第 7 层｜Redis 怎么删除过期 key？为什么不用定时器？
**答**：惰性删除（访问时检查）+ 定期删除（每 100ms 抽样检查）。不用定时器是因为每个 key 维护一个 timer 的内存和 CPU 成本太高，而且 Redis 是单线程，定时器会打散处理。

### 第 8 层｜定期删除具体怎么采样？
**答**：`activeExpireCycle` 每轮从过期字典随机抽 20 个 key，删除其中过期的；如果过期比例超过 25%，说明过期 key 还很多，继续抽下一轮（受时间上限 `timelimit` 约束，避免阻塞主线程）。

### 第 9 层｜8 种淘汰策略怎么选？
**答**：纯缓存用 `allkeys-lru`/`allkeys-lfu`（有热点用 lfu）；缓存与持久数据混存用 `volatile-*`（只淘汰带 TTL 的）；绝对不能丢用 `noeviction`（写会报错，靠监控兜底）；想优先清快过期的用 `volatile-ttl`。

### 第 10 层｜LRU 是精确的吗？LFU 怎么实现？
**答**：不是，Redis 是近似 LRU：每个 key 存 24bit 时钟，淘汰时随机采样 `maxmemory-samples` 个挑最久未用的，采样越多越准。LFU 用 16bit（8bit 计数 + 8bit 衰减时间），计数随访问增长（对数曲线），按 `lfu-decay-time` 衰减，避免偶发访问污染。

### 第 11 层｜主从/集群下过期 key 怎么处理？内存满了从节点怎么办？
**答**：从节点不主动删过期 key，等主节点删后发 DEL 命令同步；从节点读到过期 key 返回 nil。集群下各节点只管自己槽位里的 key，淘汰也是各节点独立按策略做，可能出现各节点内存不均。

### 第 12 层（终局）｜这些逻辑在 Redis 源码哪里？
**答**：`rdb.c` 的 `rdbSaveBackground()`（fork 子进程）与 `rdbSaveRio()`（写文件）；`aof.c` 的 `flushAppendOnlyFile()`（write+fsync）、`rewriteAppendOnlyFileBackground()`；`evict.c` 的 `performEvictions()`；`expire.c` 的 `activeExpireCycle()` / `expireIfNeeded()`；`bio.c` 的后台线程负责 fsync。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| RDB | 内存二进制快照 | 备份、快速恢复、主从同步 | fork 与数据丢失窗口 |
| AOF | 写命令追加日志 | 更高数据安全性 | fsync 策略与重写 |
| fork | 创建子进程 | 不阻塞地做快照/重写 | 页表复制阻塞、大内存风险 |
| COW | 写时复制 | 父子共享物理页，按需复制 | 内存放大、THP |
| `appendfsync` | AOF 刷盘策略 | 安全与性能折中 | always/everysec/no |
| AOF 重写 | 用最小命令集重写日志 | 控制 AOF 体积 | 重写缓冲区、混合持久化 |
| 混合持久化 | RDB 前半 + AOF 增量 | 恢复快且不丢数据 | 4.0+、配置项 |
| 惰性删除 | 访问时才删过期 key | 省 CPU | 内存泄漏风险 |
| 定期删除 | 定时抽样删过期 key | 兜底回收内存 | 采样比例、时间上限 |
| `maxmemory-policy` | 内存满时的淘汰策略 | 防止 OOM | 8 种策略的适用场景 |
| 近似 LRU | 采样估计最久未用 | 省内存、够用 | 为什么不做精确 LRU |
| LFU | 按访问频率淘汰 | 抗偶发访问 | 计数增长与衰减 |

## 代码验证（redis-cli 观察配置与运行状态）

```bash
# 1. 持久化配置
redis-cli CONFIG GET appendonly            # no（默认）/yes
redis-cli CONFIG GET appendfsync           # everysec
redis-cli CONFIG GET save                  # 900 1 300 10 60 10000
redis-cli CONFIG GET aof-use-rdb-preamble  # yes

# 2. 手动触发并观察
redis-cli BGSAVE            # Background saving started
redis-cli BGREWRITEAOF      # Background append only file rewriting started
redis-cli INFO persistence  # 看 rdb_last_bgsave_status / aof_last_rewrite_time_sec

# 3. 内存淘汰配置
redis-cli CONFIG GET maxmemory          # 0 表示不限制
redis-cli CONFIG SET maxmemory 100mb
redis-cli CONFIG SET maxmemory-policy allkeys-lfu
redis-cli CONFIG GET maxmemory-samples  # 5
redis-cli INFO memory                   # used_memory / maxmemory / mem_fragmentation_ratio
redis-cli INFO stats | grep evicted_keys

# 4. 过期键验证
redis-cli SET k1 v1 EX 2
redis-cli TTL k1
sleep 3 && redis-cli GET k1    # nil（惰性删除/过期）
redis-cli INFO keyspace        # 过期 key 不计数

# 5. 观察 COW 内存放大（大实例上）
redis-cli INFO memory | grep rdb_last_cow_size
```

```java
// Jedis 读取持久化状态做监控
try (Jedis jedis = new Jedis("127.0.0.1", 6379)) {
    jedis.info("persistence").lines()
        .filter(l -> l.startsWith("rdb_last_bgsave_status") || l.startsWith("aof_last_bgrewrite_status"))
        .forEach(System.out::println);
    jedis.info("memory").lines()
        .filter(l -> l.startsWith("used_memory_human") || l.startsWith("mem_fragmentation_ratio"))
        .forEach(System.out::println);
}
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「RDB 不丢数据」 | 两次快照之间的数据会丢 |
| 「AOF everysec 丢 0 数据」 | 最多丢 1 秒 |
| 「fork 会复制全部内存」 | 只复制页表，物理页 COW 共享 |
| 「AOF 重写会阻塞主线程」 | 子进程做重写，fork 瞬间短暂阻塞 |
| 「LRU 是精确的」 | 采样近似 LRU |
| 「noeviction 会删数据」 | 不淘汰，写命令直接报 OOM |
| 「RDB 和 AOF 只能二选一」 | 4.0+ 可混合持久化，也可同时开 |
