# 分布式锁与 Redis 高可用（Distributed Lock & HA）

> 面试权重：5/5　｜　追问深度：**L5（Redisson 源码 / 哨兵协议 / Cluster 源码）**
> 一句话定位：分布式锁的面试就是一条"缺陷链"：SETNX 会死锁 → 加过期不原子 → 原子了会误删 → 误删防住会超时 → 超时续期解决了又怕主从切换 → Redlock 想解决又被 Kleppmann 质疑。高可用则分两步：主从 + 哨兵撑住单点故障，Cluster 撑住容量。

## L1 一句话答案（10 秒能说出口）

分布式锁要同时满足互斥、防死锁、防误删。演进链：`SETNX` → `SETNX + EXPIRE`（不原子）→ `SET key value NX EX`（原子加锁）→ Lua 校验 value 再删（防误删）→ 看门狗续期（防业务超时）→ Redisson 封装可重入 → Redlock 多实例多数派（仍有争议）。**生产上：Redisson 单实例锁 + 业务幂等兜底；高可用：主从 + 哨兵，容量不够上 Cluster。**

## L2 原理层：从 SETNX 到 Redlock 的完整缺陷链

### 2.1 一把合格的分布式锁要满足什么

1. **互斥**：同一时刻只有一个客户端持有
2. **防死锁**：持有者崩溃后锁能自动释放（过期时间）
3. **防误删**：只能删自己加的锁（value 校验）
4. **可重入**（可选但常见）：同一线程可重复加锁
5. **高可用**：加锁节点故障不能导致永久不可用（哨兵/Cluster）

### 2.2 缺陷链演进（面试就按这个顺序讲）

| 代 | 实现 | 问题 |
|---|---|---|
| ① | `SETNX lock 1` | 加锁后进程崩了 → 锁永不过期，死锁 |
| ② | `SETNX` + `EXPIRE` 两条命令 | 两条命令之间宕机 → 还是死锁（不原子） |
| ③ | `SET lock uuid NX EX 30` | 原子加锁 正确，但删除时不校验持有者 → 可能删别人的锁 |
| ④ | 删除前 GET 校验 uuid，再 DEL | GET 和 DEL 之间锁可能过期被抢 → 仍需 Lua 原子执行 |
| ⑤ | Lua：`if GET==uuid then DEL` | 删除原子 正确，但业务执行超过 30s → 锁提前释放，别人进来了 |
| ⑥ | 看门狗定时续期（Redisson） | 续期解决超时 正确，但主从切换时锁可能丢 |
| ⑦ | Redlock：N 个独立 master 多数派 | 时钟漂移/GC 停顿下仍不严格安全（Kleppmann 质疑） |
| ⑧ | fencing token：锁服务发单调递增 token，下游校验 | 真正解决"锁失效后的旧请求"，但要下游配合 |

### 2.3 SET NX EX 为什么是原子的

Redis 2.6.12+ 的 `SET` 支持 `NX/XX/EX/PX` 选项，一条命令里同时完成「不存在才设置」和「设置过期」，不会出现中间态。这是分布式锁能用 Redis 的基础。

```bash
SET lock:order:1001 "uuid-abc" NX EX 30   # 成功返回 OK，失败返回 nil
```

### 2.4 释放锁的 Lua（必须能默写）

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

Redis 单线程执行 Lua，脚本执行期间不会穿插其他命令，所以"判断 + 删除"是原子的。

### 2.5 看门狗（watchdog）

- Redisson 加锁时如果不指定 `leaseTime`，默认用 `lockWatchdogTimeout=30s`，并启动一个定时任务**每 10s（1/3 周期）续期一次**，业务没结束就一直续。
- 指定了 `leaseTime` 就不续期（到点自动释放），所以**不确定业务耗时就不要传 leaseTime**。
- 续期由 Redisson 内部的 `TimerTask` 完成，客户端崩溃后续期停止，锁在 30s 内自动过期——防死锁和防超时的折中。

### 2.6 主从切换为什么会丢锁

```
① 客户端 A 在 master 上加锁成功
② master 还没把这条写命令同步给 slave，宕机
③ 哨兵把 slave 提升为新 master（它没有这把锁）
④ 客户端 B 在新 master 上加锁成功 → 两个客户端同时持锁
```

Redis 主从是**异步复制**，这个窗口无法消除。所以：**Redis 锁适合"效率型"场景（防重复提交、防缓存击穿），不适合"正确性型"场景（转账扣款）**。正确性场景要 fencing token、数据库唯一约束或 ZooKeeper/etcd。

### 2.7 Redlock 与争议

**算法**：部署 N（通常 5）个**互相独立**的 Redis master；客户端依次向每个节点 `SET NX EX`，加锁总耗时必须小于锁过期时间；超过 `N/2+1` 个成功才算拿到锁；失败要向所有节点发解锁。

**Kleppmann 的质疑（2016）**：
1. **时钟漂移**：节点时钟跳变会让锁提前过期；
2. **GC/网络停顿**：客户端拿到锁后长时间停顿，醒来时锁已过期，但业务还在跑；
3. **无法感知锁失效**：Redlock 不提供 fencing，旧持有者的写可能覆盖新持有者。
**Antirez 的回应**：Redlock 面向效率而非正确性，且有 `min validity time` 等防护。**结论：要正确性必须配 fencing token。**

### 2.8 哨兵与 Cluster

**哨兵（Sentinel）**：监控 + 自动故障转移。

```
① 主观下线 SDOWN：单个哨兵 PING 超时
② 客观下线 ODOWN：收集到 quorum 个哨兵的 SDOWN 后判定
③ 选举 leader：哨兵之间 Raft 式投票（每个 epoch 一票，需 majority）
④ 选新 master：优先级 > 复制 offset > run_id
⑤ 其余 slave 指向新 master，旧 master 恢复后降为 slave
```

客户端不直连 master，而是连哨兵问 `get-master-addr-by-name`，失败自动切换。

**Cluster**：数据分片 + 高可用。

- 共 **16384 个槽**，key 用 `CRC16(key) % 16384` 定位；每个 master 负责一部分槽，从节点复制。
- `MOVED`：槽不在当前节点且迁移已完成 → 客户端更新路由；
- `ASK`：槽正在迁移中，先到目标节点继续 → 客户端**不更新**路由。
- 为什么是 16384：心跳包用位图携带槽信息，16384 bit = 2KB（若 65536 则 8KB，gossip 消息过大）；同时 16384 足够分给 1000 个节点。
- 脑裂风险：主节点被分区但未死，客户端写旧主 → 数据丢失。用 `min-replicas-to-write` 限制"没有足够从节点就不接受写"。

## L3 底层层：SET 源码、哨兵协议、Cluster 心跳

### 3.1 SET 命令怎么保证 NX/EX 原子

`t_string.c` 的 `setGenericCommand()`：解析 `OBJ_SET_NX/XX/EX/PX` 标志，先做存在性检查，再 `setKey()` 写值，最后 `setExpire()` 设过期——**全在一条命令的单线程执行内完成**，没有中间态。

### 3.2 主从复制与部分重同步

- `PSYNC <runid> <offset>`：从节点上报主节点 runid 和复制偏移量。
- 主节点维护 `repl-backlog` 环形缓冲区（默认 1MB），若从节点要的 offset 还在缓冲区内 → 部分重同步（只发增量）；否则全量同步（RDB + 增量）。
- 主从复制是异步的：主节点写完就返回客户端，不等从节点确认——这是丢锁/丢数据的根源。

### 3.3 哨兵与 Cluster 的源码入口

- `sentinel.c`：`sentinelIsMasterDownByAddr()`（SDOWN）、`sentinelCheckObjectivelyDown()`（ODOWN）、`sentinelFailoverStateMachine()`（故障转移状态机）、`sentinelSendSlaveOf()`。
- `cluster.c`：`clusterProcessGossipSection()`（gossip）、`clusterUpdateState()`、`clusterHandleConfigEpochCollision()`、`clusterSendFailoverAuthIfNeeded()`（从节点拉票）。
- 槽迁移：`CLUSTER SETSLOT`、`MIGRATE`、ASKING 命令背后的 `clusterRedirectClient()`。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**

### 第 1 层｜为什么要用分布式锁？和本地锁有什么区别？
**答**：本地锁（synchronized/ReentrantLock）只在单 JVM 内有效；多实例部署时，同一份资源（订单、库存）会被多个实例同时改，需要跨进程的锁。分布式锁用 Redis/ZK/etcd 做统一仲裁。

### 第 2 层｜为什么不能直接用 SETNX？
**答**：SETNX 没有过期时间，客户端加锁后崩溃，锁永远不释放，其他实例全部阻塞。必须加过期时间，而且加锁和设过期要原子。

### 第 3 层｜SETNX + EXPIRE 为什么不行？正确写法是什么？
**答**：两条命令之间如果宕机，锁没有过期时间 → 死锁。正确写法是一条命令：`SET key value NX EX 30`（Redis 2.6.12+），把"不存在才设"和"过期"原子完成。

### 第 4 层｜拿到锁的客户端怎么安全释放？为什么要 Lua？
**答**：释放前要 GET 比较 value（防止删了别人续期后的锁），但 GET 和 DEL 之间锁可能过期被抢，所以用 Lua 脚本把"比较 + 删除"原子化。value 一般用 `UUID + 线程 ID`。

### 第 5 层｜业务执行时间超过锁的过期时间怎么办？
**答**：看门狗续期。Redisson 不传 leaseTime 时默认 30s，每 10s 续期一次，业务结束才释放；客户端崩溃则停止续期，锁自动过期。也可以把业务做成幂等，锁只是"效率优化"。

### 第 6 层｜主从切换时锁会丢吗？怎么办？
**答**：会。主节点加锁后未同步就宕机，从节点升主后没有这把锁，另一个客户端能加锁成功 → 双持有。缓解：Redlock、等主从同步（`WAIT` 命令）、fencing token、或换 ZooKeeper/etcd（基于共识，切换不丢）。

### 第 7 层｜Redlock 是怎么做的？为什么有争议？
**答**：N 个独立 master，依次 `SET NX EX`，多数派成功且总耗时小于过期时间才算成功。争议（Kleppmann）：时钟漂移导致锁提前过期、GC/网络停顿让持有者"以为还持锁"、没有 fencing 机制防止旧请求覆盖新持有者。所以 Redlock 适合效率锁，不适合正确性锁。

### 第 8 层｜fencing token 是什么？怎么用？
**答**：锁服务每次加锁返回一个**单调递增**的 token，客户端把 token 带到下游（数据库/存储）写请求里，下游只接受"token 大于已见过的最大值"的写。这样即使旧持有者锁过期后还在写，也会被拒绝。

### 第 9 层｜Redisson 的可重入锁怎么实现？
**答**：用 Hash 结构存 `{锁名: {uuid:threadId -> 重入次数}}`，加锁时 Lua 判断是不是自己、是则计数 +1；释放时计数 -1，减到 0 才真正删 key。同时配看门狗续期，和 Java 的 `ReentrantLock` 心智一致但跨进程。

### 第 10 层｜Redis 锁、ZooKeeper 锁、etcd 锁怎么选？
**答**：Redis 性能高、部署简单，但主从异步复制可能丢锁，适合防重复提交/缓存重建这类效率场景；ZooKeeper/etcd 基于共识协议，锁不会因切换丢失，适合正确性要求高的场景，但性能和运维成本更高。选型看"锁失效的业务代价"。

### 第 11 层｜你的"防重复提交"具体怎么做的？
**答**：三层：① 前端按钮防抖/置灰（挡误操作）；② Redis `SET NX EX` 短锁（如 5s，key 用用户+接口+参数），挡住并发重复请求；③ 数据库唯一索引（最可靠，最终兜底）。分布式锁只是第二层，最终正确性靠唯一约束。

### 第 12 层｜哨兵是怎么选主的？脑裂怎么办？
**答**：哨兵先通过 PING 判定主观下线，quorum 个哨兵确认后客观下线；然后哨兵之间 Raft 式投票选出 leader，leader 按优先级 → 复制 offset → run_id 选新 master，通知其余从节点切换。脑裂（旧 master 未死但被分区）时，用 `min-replicas-to-write` 让旧 master 拒绝写，减少数据丢失。

### 第 13 层｜Cluster 的槽为什么是 16384？MOVED 和 ASK 区别？
**答**：槽数决定路由位图大小：16384 bit = 2KB，gossip 心跳能接受；65536 bit 就是 8KB，心跳包太大。MOVED 表示槽已迁走、客户端要更新路由缓存；ASK 表示槽正在迁移、这次请求去目标节点但**不更新**路由。两者都是重定向，语义不同。

### 第 14 层（终局）｜这些在源码里在哪？
**答**：锁：`t_string.c` 的 `setGenericCommand()`（NX/EX 原子）、`scripting.c` 的 Lua 执行；Redisson 的 `RedissonLock.tryLockInnerAsync()`（Lua 加锁）和 `scheduleExpirationRenewal()`（看门狗）。高可用：`sentinel.c` 的故障转移状态机、`cluster.c` 的 gossip 与 `clusterRedirectClient()`、`replication.c` 的 `PSYNC`。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| `SET NX EX` | 一条命令完成加锁+过期 | 避免非原子导致的死锁 | 版本要求、返回 nil |
| Lua 脚本 | Redis 内原子执行的脚本 | "比较+删除"必须原子 | 单线程、Cluster 同槽 |
| 看门狗 | 定时续期锁过期时间 | 业务耗时不确定 | 30s/10s、指定 leaseTime 不续 |
| Redlock | 多独立 master 多数派加锁 | 抗单点故障 | 时钟漂移、GC 停顿争议 |
| fencing token | 单调递增的锁凭证 | 防止旧持有者写覆盖 | 下游如何校验 |
| 可重入锁 | 同一线程可重复加锁 | 避免自己锁死自己 | Hash + 计数 |
| 哨兵 | 监控 + 自动故障转移 | 单点故障自动恢复 | SDOWN/ODOWN/选举 |
| 脑裂 | 网络分区导致双主 | 分布式系统的经典故障 | min-replicas-to-write |
| Cluster | 16384 槽分片 + 主从 | 容量与高可用 | MOVED/ASK、槽数原因 |
| MOVED / ASK | 集群重定向 | 路由错误/迁移中 | 是否更新客户端路由 |
| `min-replicas-to-write` | 从节点不足时拒写 | 减少脑裂数据丢失 | 与 `min-replicas-max-lag` 配合 |

## 代码验证（redis-cli + Java Redisson/Jedis + 哨兵/集群命令）

```bash
# 1. 原子加锁 / 释放（Lua）
redis-cli SET lock:order:1001 uuid-abc NX EX 30     # OK 表示拿到锁
redis-cli SET lock:order:1001 uuid-def NX EX 30     # nil 表示已被占用
redis-cli EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 lock:order:1001 uuid-abc
# 返回 1 表示删除成功；用错误 uuid 执行返回 0（防误删验证）

# 3. 哨兵：查当前 master 与状态
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
# 手动触发故障转移（测试环境）
redis-cli -p 26379 SENTINEL failover mymaster

# 4. Cluster：槽与节点
redis-cli -c -p 7000 CLUSTER INFO
redis-cli -c -p 7000 CLUSTER KEYSLOT user:1
redis-cli -c -p 7000 SET user:1 tom      # 自动 MOVED 重定向
redis-cli -c -p 7000 GET user:1
```

```java
// Redisson 标准用法：不传 leaseTime → 看门狗续期；finally 释放
Config config = new Config();
config.useSingleServer().setAddress("redis://127.0.0.1:6379");
RedissonClient redisson = Redisson.create(config);
RLock lock = redisson.getLock("lock:order:1001");
if (!lock.tryLock(3, TimeUnit.SECONDS)) throw new IllegalStateException("获取锁失败"); // 不传 leaseTime → 看门狗续期
try { /* 业务：扣库存 / 防重复提交 */ }
finally { if (lock.isHeldByCurrentThread()) lock.unlock(); }

// 纯 Jedis 版：加锁 + Lua 释放（无自动续期，生产更推荐 Redisson）
String uuid = UUID.randomUUID().toString();
String ok = jedis.set("lock:order:1001", uuid, new SetParams().nx().ex(30));
if ("OK".equals(ok)) {
    try { /* 业务 */ }
    finally { jedis.eval(LUA_UNLOCK, List.of("lock:order:1001"), List.of(uuid)); }
}
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「SETNX 就够用了」 | 没过期时间，宕机就死锁 |
| 「先 SETNX 再 EXPIRE 就行」 | 不原子，中间宕机仍死锁 |
| 「Redis 锁能保证强一致」 | 主从异步复制，切换会丢锁 |
| 「Redlock 是完美方案」 | 有时钟漂移/GC 停顿争议，正确性要 fencing |
| 「释放锁直接 DEL 就行」 | 必须校验 value，否则可能删别人的锁 |
| 「哨兵能保证零丢数据」 | 只能自动切换，异步复制窗口仍可能丢 |
