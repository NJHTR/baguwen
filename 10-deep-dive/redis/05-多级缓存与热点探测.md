# 多级缓存与热点探测（Multi-level Cache & Hotkey）

> 面试权重：4/5　｜　追问深度：**L5（Caffeine 淘汰算法 / hotkey 探测 / 一致性哈希）**
> 一句话定位：Redis 再快也有网络 RT 和单分片上限。多级缓存 = 本地缓存（Caffeine）扛热点 + Redis 做共享层；真正拉开差距的是三件事：**本地缓存怎么保持一致**、**热点 key 怎么发现并本地化**、**Redis 挂了怎么降级**。

**本文件用法**：从 L1 往下读，每读完一层，合上书自问自答。**停在答不出的那一层，就是你的真实水平线。**

## L1 一句话答案（10 秒能说出口）

多级缓存是「本地缓存（Caffeine，纳秒级）+ Redis（毫秒级共享）+ DB」三层。本地缓存用 W-TinyLFU 抗扫描污染，一致性靠广播失效/版本号/短 TTL；热点 key 用滑动窗口统计探测出来后主动本地化；大 key 定期扫描治理；Redis 故障时按「本地缓存 → 静态兜底 → 限流」降级；客户端分片用一致性哈希减少扩容迁移。

## L2 原理层：为什么分层、怎么保持一致、热点怎么处理

### 2.1 为什么不能只用 Redis

| 层次 | 典型延迟 | 容量 | 问题 |
|---|---|---|---|
| 本地缓存（堆内 Caffeine） | 约 100 纳秒 | 受 JVM 内存限制 | 多实例不一致、GC 压力 |
| Redis | 约 0.5~1 毫秒 | 单机几十 GB | 网络 RT、单分片 QPS/带宽上限、热点集中 |
| DB | 几毫秒~几十毫秒 | 大 | 并发能力最弱 |

一个热点 key 打到 Redis 单分片，几十万 QPS 就能打满单核/带宽；放到本地缓存只花内存。多级缓存的核心收益：热点扛在本地、共享数据放 Redis、兜底靠 DB。

### 2.2 两级缓存架构与读写路径

```
读：L1 Caffeine 命中即返回
    → 未命中查 L2 Redis（命中回填 L1 返回）
    → 未命中查 DB（回填 L2 + L1）

写：更新 DB → 删除 L2 Redis → 广播失效所有实例的 L1
```


### 2.3 Caffeine 与 W-TinyLFU

- Caffeine 是 Java 本地缓存主流选择，淘汰策略 **W-TinyLFU**（Window + TinyLFU + SLRU），比纯 LRU 抗"扫描污染"：一次全表扫描不会把热数据全冲掉。
- 配置：`maximumSize`、`expireAfterWrite`、`refreshAfterWrite`（异步刷新，先返回旧值）、`recordStats()`（命中率）。
- 对比：Guava Cache 是 LRU 分段锁，高并发和命中率弱于 Caffeine。

### 2.4 本地缓存一致性五种手段

| 手段 | 做法 | 可靠性 | 适用 |
|---|---|---|---|
| 短 TTL | L1 只缓存 1~5 秒 | 最终一致，有窗口 | 容忍短暂旧数据 |
| Redis Pub/Sub 广播 | 更新后 publish 失效消息，各实例订阅删 L1 | 断连会丢消息 | 一般场景 |
| MQ 广播 | 发 MQ，所有实例消费失效 | 可靠（可重试/持久化） | 一致性要求较高 |
| 版本号 | L1 带版本，读时与 Redis 版本比对 | 可靠但多一次读 | 配置/商品等关键数据 |

工程组合：Pub/Sub 广播 + 短 TTL 兜底；强一点用 MQ + 版本号。本地缓存没有强一致，只能把窗口压到秒级。

### 2.5 热点 key 探测（京东 hotkey 思路）

```
业务代码/SDK 本地用滑动窗口统计每个 key 的访问次数
    → 定时上报（key 的 hash 决定上报到哪个 worker）
    → 聚合 worker 汇总全局 QPS，超阈值判定热点
    → 推送各客户端，把热点 key 主动加载到本地缓存
```

- 按 key hash 上报：同一 key 的统计必须落到同一个 worker，才能做全局计数。
- 客户端用环形数组按秒分桶实现滑动窗口，O(1) 更新。
- 简化版：本地计数每 5 秒上报 Redis，超阈值告警并手动加本地缓存；或用 `redis-cli --hotkeys`（LFU 策略下）排查。

### 2.6 热点 key 的四种治理手段

1. **本地化**：探测到后放入 L1，最有效；
2. **打散**：key 加随机后缀拆成 N 份（读随机取一份，写写 N 份），摊开单分片压力；
3. **多副本**：读多写少的热点在多个 Redis 实例冗余，客户端随机读。

### 2.7 大 key 治理

- 定义（经验）：string 值 > 10KB，或集合元素 > 5000 个。
- 危害：单线程下 `DEL`/`HGETALL`/`SMEMBERS` 阻塞主线程；带宽打满；集群槽倾斜；迁移变慢。
- 发现：`redis-cli --bigkeys`（抽样）、`MEMORY USAGE key`、`SCAN` 采样 + 埋点。
- 治理：拆 key（hash 分桶）、`UNLINK` 异步删、控制 value 大小、压缩、设 TTL、读用 `HSCAN` 分批。

### 2.8 缓存预热与降级兜底链路

- 预热：启动/大促前把热点数据（首页、登录用户、活动商品）批量加载进 L2/L1；预热要限流，避免启动瞬间打挂 DB。
- 雪崩分层保护 / 降级链路：本地 L1 挡一层 → Redis L2 挡一层 → DB 前限流 → Redis 挂时 L1 兜底 → 静态兜底（默认值/兜底页）→ 限流返回。

### 2.9 一致性哈希与客户端分片

- Redis Cluster 的槽位固定 16384，扩缩容要迁移槽；如果要自己控制分片（单机 Redis + 客户端分片），用一致性哈希。
- 做法：`hash(key)` 映射到 2^32 的环，节点也映射到环上（每个物理节点 100~200 个虚拟节点防倾斜），key 顺时针找第一个节点。
- 优势：扩容只迁移 `1/(n+1)` 的数据；取模方案扩容几乎全量迁移。代价：要自己维护节点变更、故障转移、数据迁移，所以生产更常用 Cluster 或代理（Codis/Twemproxy）。

## L3 底层层：W-TinyLFU、滑动窗口与哈希环

### 3.1 Caffeine 的 W-TinyLFU 结构

```
全部缓存空间
├── Window Cache：约 1%，新数据先进窗口（LRU）
└── Main Cache：约 99%
    ├── Probation（考察区）：约 20%
    └── Protected（保护区）：约 80%
```

- 新条目先进 Window；Window 淘汰时，候选与 Main 的 Probation 区 victim 比较**频率**（TinyLFU 准入），频率高者留下。
- 频率用 **Count-Min Sketch**（4-bit 计数器，sampleSize 默认约 `10 * maximumSize`），省内存近似统计；超过样本时整体频率减半（reset），近似"近期频率"。
- 这就是 Caffeine 不怕扫表的原因：一次性访问的 key 频率低，进不了 Main。

### 3.2 热点统计的滑动窗口

```
时间轴：[桶0][桶1]...[桶9] 环形复用，每桶=1 秒访问计数
窗口 QPS = 最近 N 个桶之和
```

O(1) 更新、O(N) 统计；窗口内访问量超阈值（如 5000 次/秒）即判定热点，上报并本地化。

### 3.3 一致性哈希环

环大小 2^32，节点与 key 都 hash 到环上，key 顺时针取第一个节点；虚拟节点 100~200 个/物理节点解决分布不均；扩容只接管逆时针到上一节点的区间，平均迁移 `1/(n+1)`；节点故障需要迁移该区间数据，所以生产用 Cluster（槽位 + 主从）或代理。

### 3.4 源码入口

- Caffeine：`BoundedLocalCache.evictEntries()`（Window/Probation/Protected 晋升与淘汰）、`FrequencySketch`（Count-Min Sketch）。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**
### 第 1 层｜为什么需要多级缓存？只用 Redis 不行吗？
**答**：Redis 有网络 RT（约 0.5ms）和单分片上限，热点 key 几十万 QPS 就能打满单节点；本地缓存约 100ns 且不占网络，能扛热点。Redis 负责多实例共享，本地负责极致性能和削峰。
### 第 2 层｜本地缓存选 Caffeine 还是 Guava？
**答**：Caffeine 用 W-TinyLFU，抗扫描污染、命中率高；Guava 是 LRU 分段锁，高并发与命中率都弱一些，新项目基本选 Caffeine。
### 第 3 层｜W-TinyLFU 怎么淘汰？为什么比 LRU 好？
**答**：新数据进 Window（约 1%），Window 淘汰的候选与 Main 的 Probation 区 victim 比频率，高的留下。LRU 遇到全表扫描会把热数据全冲掉，TinyLFU 用频率门槛挡住只访问一次的冷数据。
### 第 4 层｜本地缓存怎么和多实例保持一致？
**答**：没有强一致，只能压窗口：写 DB 后删 Redis，再 Pub/Sub 或 MQ 广播让所有实例删本地缓存，加短 TTL 兜底，重要数据用版本号比对。
### 第 5 层｜Pub/Sub 广播失效有什么问题？怎么兜底？
**答**：Pub/Sub 即发即忘，订阅方断连期间的消息会丢，某些实例本地缓存永久不更新。兜底：短 TTL、MQ 持久化广播、版本号比对、定时全量刷新。
### 第 6 层｜热点 key 怎么发现？
**答**：客户端滑动窗口统计访问量，按 key hash 上报聚合 worker，超阈值的 key 判定热点并推送。简化方案是本地计数定时上报，或用 Redis LFU 的 `--hotkeys`。核心是"分片统计再聚合"。
### 第 7 层｜发现热点 key 之后怎么处理？
**答**：本地化（进 L1）、key 打散（加后缀拆 N 份）、接口限流、多副本随机读。首选本地化，它同时解决性能和 Redis 单分片压力。
### 第 8 层｜大 key 怎么发现、有什么危害、怎么治理？
**答**：`--bigkeys`、`MEMORY USAGE`、SCAN 采样发现；危害是阻塞主线程、带宽打满、槽倾斜；治理是拆分、`UNLINK` 异步删、限制 value 大小、压缩、HSCAN 分批读。
### 第 9 层｜缓存预热怎么做？要注意什么？
**答**：启动或大促前批量把热点数据加载进 L2/L1，避免冷启动打穿 DB。注意限流（预热本身别打满 DB）、只预热确定的热点、预热失败要降级、预热完成再放流量。
### 第 10 层｜Redis 挂了，接口怎么不崩？
**答**：降级链路：本地缓存兜底 → 静态默认值/兜底页 → 限流/熔断返回。Redis 客户端超时要短，配线程池隔离和熔断器（Sentinel/Resilience4j），避免 Redis 抖动拖垮整个接口。
### 第 11 层（终局）｜这一层落到源码是什么？
**答**：Caffeine 的 `BoundedLocalCache.evictEntries()` 决定 Window/Probation/Protected 的晋升与淘汰，`FrequencySketch` 用 Count-Min Sketch 做频率统计；hotkey 用环形桶滑动窗口做客户端统计、worker 聚合推送；一致性哈希用虚拟节点把数据均匀映射到 2^32 环上。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 多级缓存 | 本地 + Redis + DB 分层 | 性能与容量折中 | 各层职责与一致性 |
| Caffeine | Java 本地缓存库 | 高命中率、高并发 | W-TinyLFU 结构 |
| W-TinyLFU | Window + TinyLFU + SLRU | 抗扫描污染 | 准入策略 |
| 本地缓存一致性 | 多实例 L1 同步 | 避免脏数据 | 广播/版本号/TTL |
| Pub/Sub 广播 | Redis 发布订阅失效 | 实时通知 | 丢消息风险 |
| 版本号 | 缓存带版本比对 | 可靠一致性 | 多一次读的代价 |
| 热点 key | 访问极度集中的 key | 单分片压力 | 探测与本地化 |
| 大 key | 值过大/元素过多的 key | 阻塞与倾斜 | 发现与 UNLINK |
| 缓存预热 | 提前加载热点 | 防冷启动击穿 | 限流与失败降级 |
| 一致性哈希 | 按环分配数据 | 减少扩容迁移 | 虚拟节点、1/(n+1) |

## 代码验证（Java + redis-cli）

```java
// 1. Caffeine 本地缓存（一级）+ L1 -> L2 -> DB 两级读
Cache<String, String> local = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(Duration.ofSeconds(3))     // 短 TTL 兜底一致性
        .recordStats()
        .build();

public String getUserName(long userId) {
    String key = "user:name:" + userId;
    String v = local.getIfPresent(key);
    if (v != null) return v;                          // L1
    v = redis.get(key);                               // L2
    if (v == null) {
        v = userMapper.selectNameById(userId);        // DB 回填
        if (v != null) redis.set(key, v, SetParams.setParams().ex(1800));
    }
    local.put(key, v);
    return v;
}

// 2. 写路径：更新 DB -> 删 L2 -> 广播失效 L1
public void updateUserName(long userId, String name) {
    userMapper.updateName(userId, name);
    String key = "user:name:" + userId;
    redis.del(key);
    redis.publish("cache:invalidate", key);           // 各实例订阅后 local.invalidate(key)
}
```

```java
// 3. 简化版热点探测：环形桶滑动窗口（每 5 秒上报聚合）
class HotkeyCounter {
    private final long[] buckets = new long[10];   // 10 秒窗口
    private int cursor = 0;
    private long lastSecond = System.currentTimeMillis() / 1000;
    synchronized void hit() {
        long now = System.currentTimeMillis() / 1000;
        if (now != lastSecond) { cursor = (int) (now % buckets.length); buckets[cursor] = 0; lastSecond = now; }
        buckets[cursor]++;
    }
    synchronized long qps() { long s = 0; for (long b : buckets) s += b; return s / buckets.length; }
}
```

```bash
# 命中率与内存（多级缓存上线前后对比指标）
redis-cli INFO stats | grep -E 'keyspace_hits|keyspace_misses'
redis-cli INFO memory | grep -E 'used_memory_human|mem_fragmentation_ratio'

# 热点与大 key 排查（LFU 策略下 --hotkeys 才有效）
redis-cli CONFIG GET maxmemory-policy
redis-cli --hotkeys
redis-cli --bigkeys
redis-cli MEMORY USAGE user:name:1001
redis-cli OBJECT FREQ user:name:1001      # LFU 计数，超阈值即可疑热点

```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「本地缓存设长 TTL 就行」 | 多实例会长期不一致，长 TTL 必须配广播/版本号 |
| 「Pub/Sub 一定不会丢消息」 | 即发即忘，断连会丢，要用 MQ/版本号兜底 |
| 「热点 key 加 Redis 副本就够」 | 副本也要参与路由，有效的是本地化 + 打散 |
| 「大 key 用 DEL 直接删」 | 用 `UNLINK` 异步删，`DEL` 会阻塞主线程 |
| 「一致性哈希扩容还是全量迁移」 | 只迁移 1/(n+1)，但节点变更要自己处理 |
| 「预热就是把所有数据加载一遍」 | 只预热确定的热点，并限流，否则启动就打挂 DB |
