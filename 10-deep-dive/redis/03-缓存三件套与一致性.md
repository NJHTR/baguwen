# 缓存三件套与一致性（穿透 / 击穿 / 雪崩 / 双写）

> 面试权重：5/5　｜　追问深度：**L5（缓存模式 + binlog 链路 + 源码时机）**
> 一句话定位：缓存问题面试就三句话：**穿透**是查不存在、**击穿**是热点 key 过期、**雪崩**是大量 key 同时失效或 Redis 宕机；一致性问题就一句话：先更新 DB 再删缓存，异步兜底，接受最终一致。

**本文件用法**：从 L1 往下读，每读完一层，合上书自问自答。**停在答不出的那一层，就是你的真实水平线。**

## L1 一句话答案（10 秒能说出口）

**穿透**：查一个 DB 里也没有的数据，缓存永远不命中 → 空值缓存 + 布隆过滤器。**击穿**：某个热点 key 过期瞬间，大量请求同时打到 DB → 互斥锁重建或逻辑过期。**雪崩**：大量 key 同时过期或 Redis 整体不可用 → TTL 加随机、多级缓存、限流降级。**一致性**：Cache Aside，先更新 DB 再删缓存，配合延迟双删或 binlog 订阅做最终一致。

## L2 原理层：三件套对比 + 四种缓存模式

### 2.1 三件套一表分清（面试必背）

| 问题 | 根本原因 | 典型现象 | 解法 | 代价 |
|---|---|---|---|---|
| 缓存穿透 | 查**不存在**的数据，缓存不命中 | 恶意请求 `id=-1` 打满 DB | 空值缓存（短 TTL）、布隆过滤器、参数校验、限流 | 空值占内存、布隆有假阳性 |
| 缓存击穿 | **热点 key 过期**瞬间并发打 DB | 秒杀商品详情缓存失效，DB QPS 暴涨 | 互斥锁重建、逻辑过期（不设 TTL）、热点 key 永不过期 | 锁竞争、短暂旧数据 |
| 缓存雪崩 | **大量 key 同时过期**或 Redis 宕机 | 凌晨统一过期，DB 瞬间被打挂 | TTL 加随机、多级缓存、Redis 高可用、限流降级、预热 | 架构复杂度 |

**记忆法**：穿透=数据不存在；击穿=一个热点 key 挂了；雪崩=一大片 key 挂了。

### 2.2 四种缓存读写模式

| 模式 | 读 | 写 | 说明 |
|---|---|---|---|
| **Cache Aside**（最常用） | 先读缓存，miss 读 DB 并回填 | 先更新 DB，再删缓存 | 业务代码自己控制 |
| Read Through | 缓存层代理读，miss 由缓存去 DB 加载 | — | 需要缓存中间件支持 |
| Write Through | — | 写缓存，缓存同步写 DB | 写性能差 |
| Write Behind | — | 写缓存后异步批量刷 DB | 性能好，可能丢数据 |

**为什么是"删缓存"而不是"更新缓存"**：更新缓存有并发覆盖问题（A、B 同时更新，后写的可能更旧），而且很多缓存值需要多表计算，更新成本高，所以删掉让下次读按需重建更简单。

### 2.3 先删缓存 vs 先更新 DB（一致性的核心）

| 顺序 | 并发问题 | 脏数据概率 |
|---|---|---|
| 先删缓存，再更新 DB | A 删缓存 → B 读 miss 读到**旧值**并回填 → A 更新 DB | 高（窗口大） |
| 先更新 DB，再删缓存 | A 读 miss 读到旧值 → B 更新 DB 并删缓存 → A 把旧值回填 | 低（要求 A 读 DB 比 B 更新慢，概率小） |
| 先更新 DB，再更新缓存 | 两个事务并发更新，缓存被覆盖成中间态 | 中 |

**结论：先更新 DB，再删缓存**（Cache Aside 标准做法）。它仍然不是强一致，只是把不一致窗口压到最小。

### 2.4 延迟双删

```
① 更新 DB
② 删除缓存
③ sleep 一段时间（如 500ms~1s）
④ 再次删除缓存（把 ②~③ 期间被旧值回填的缓存删掉）
```

- 延迟时间估算：**读请求耗时 + 主从复制延迟**（从库回填旧值、主库已更新）。
- 本质是"补救"，不是强一致；sleep 会占线程（用异步线程/延时队列）。
- 更彻底：**订阅 binlog（canal）**，DB 变更后异步删缓存，天然有序、可重试，业务代码零侵入。

### 2.5 布隆过滤器

- 位数组 + k 个哈希函数：插入时把 k 个位置置 1；查询时 k 个位置全为 1 才"可能存在"。
- **只有假阳性，没有假阴性**：说不在一定不在，说在不一定在——正好用来挡穿透。
- 缺陷：不支持删除（位共享，删一个可能影响别的）、误判率随元素增加上升（需预估容量）、需要 RedisBloom 模块或 Guava 本地版。

### 2.6 逻辑过期 vs 互斥锁

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 互斥锁重建 | cache miss → `SETNX` 拿锁 → 只有一个线程查 DB 回填，其他线程自旋/等待 | 数据较新 | 等待延迟、锁风险 |
| 逻辑过期 | value 里存 `expireAt`，不设 Redis TTL；发现逻辑过期就**异步重建**，当前请求先返回旧值 | 不阻塞、高可用 | 短暂返回旧数据，需要额外线程池 |

## L3 底层层：时间窗口与链路细节

### 3.1 击穿的时间窗口从哪来

Redis 的过期删除是「惰性 + 定期抽样」：key 到期后不会立刻从内存消失，而是等访问（`expireIfNeeded`）或定期抽样（每 100ms）才删。所以**热点 key 过期后的几十毫秒到几百毫秒内，所有请求都会 miss**——这就是击穿窗口。互斥锁/逻辑过期就是用来把这段时间的 DB 请求收敛成一次。

### 3.2 穿透的极端场景：布隆过滤器容量估算

- 误判率 `p` 与位数组大小 `m`、元素个数 `n`、哈希函数个数 `k` 的关系：`m ≈ -n·ln(p) / (ln2)²`，`k = m/n·ln2`。
- 例：1000 万数据、误判率 1% → 约 9580 万 bit ≈ **11.4MB**；误判率 0.1% → 约 1.44 亿 bit ≈ 18MB。
- 布隆过滤器放 Redis（RedisBloom `BF.ADD/BF.EXISTS`），本地 Guava 版有容量上限、重启丢失。

### 3.3 一致性链路：DB → 缓存的时间线

```
T0 用户请求 → 缓存 miss
T1 读 DB 得到 v1
T2 另一个线程更新 DB 为 v2，删缓存
T3 T0 的线程把 v1 写回缓存   ← 脏数据，直到下次过期/删除
```

- 窗口大小 = T3 - T2（读 DB + 回填缓存的耗时）。
- 缓解：① 回填前再查一次缓存（双重检查）；② 延迟双删；③ binlog 订阅强制删；④ 短 TTL 兜底。
- **强一致做不到**（跨两个存储、无分布式事务），工程上只承诺最终一致 + 短窗口。

### 3.4 多级缓存的一致性

本地缓存（Caffeine）+ Redis 两级：本地缓存 TTL 短（如 3s）、Redis 变更后通过消息广播（Redis Pub/Sub / MQ）通知各实例清本地缓存；或者接受短 TTL 的最终一致。**不要给本地缓存设长 TTL**，否则多实例数据长期不一致。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：从上往下问。**第 1-3 层是应届生必备，第 4-6 层是拉开差距，第 7 层以后是"能答出来就是加分"。**

### 第 1 层｜缓存穿透、击穿、雪崩分别是什么？怎么解决？
**答**：穿透是查不存在的数据，缓存永不命中，用空值缓存/布隆过滤器/参数校验；击穿是热点 key 过期瞬间并发打 DB，用互斥锁重建或逻辑过期；雪崩是大量 key 同时过期或 Redis 宕机，用 TTL 随机化、多级缓存、限流降级和高可用架构。

### 第 2 层｜空值缓存有什么坑？
**答**：如果攻击者每次用不同的不存在 key，空值缓存会占满内存（缓存污染）。要控制：空值 TTL 设短（30-60s）、key 加前缀白名单/参数格式校验、配合布隆过滤器在入口拦截，或者直接限流。

### 第 3 层｜布隆过滤器为什么能挡穿透？有什么缺陷？
**答**：位数组 + k 个哈希，查不存在的数据时至少一个位是 0，直接拒绝，不会打到 DB。缺陷：有假阳性（可能放少量不存在的 key 过去）、不支持删除、容量要预估（超了误判率飙升），所以还要配合空值缓存。

### 第 4 层｜互斥锁重建具体怎么写？要注意什么？
**答**：缓存 miss 后 `SET lock NX EX` 抢锁，抢到的查 DB 回填缓存再释放锁，没抢到的短暂 sleep 后重试读缓存。注意：锁要设过期时间防死锁、释放时用 Lua 校验持有者、抢锁失败的线程要有重试上限（防止雪崩时全部卡住）、可以做双重检查（拿到锁后再查一次缓存）。

### 第 5 层｜逻辑过期和互斥锁怎么选？
**答**：一致性优先、允许少量等待用互斥锁；高可用优先、能容忍短暂旧数据用逻辑过期（比如商品详情、榜单）。逻辑过期实现是 value 里带 `expireAt`，Redis 不设 TTL，发现过期就异步线程池重建，当前请求返回旧值。

### 第 6 层｜为什么推荐先更新 DB 再删缓存，而不是先删缓存？
**答**：先删缓存的话，删完到更新 DB 之间，其他请求读 miss 会把旧值回填，脏数据窗口大；先更新 DB 再删缓存，脏数据需要"读请求比更新慢"才会发生，概率小得多。两种都不是强一致，只是窗口大小不同。

### 第 7 层｜为什么是删缓存而不是更新缓存？
**答**：更新缓存并发时可能被旧值覆盖（后写的未必更新），而且缓存值经常是多表聚合算出来的，更新成本高、容易漏。删掉让读请求按需重建，逻辑简单、最终一致。

### 第 8 层｜延迟双删延迟多久？为什么还不是强一致？
**答**：延迟 = 读请求耗时 + 主从复制延迟（常见 500ms~1s）。它只是把"删缓存后又被旧值回填"的那次删掉，但延迟期间读到的仍是旧值；如果第二次删失败、或者读请求比 sleep 还慢，仍会脏。所以是最终一致。

### 第 9 层｜删除缓存失败了怎么办？
**答**：三种兜底：① 操作放进消息队列/重试表，失败重试并告警；② 订阅 binlog（canal）异步删，天然可重试且不依赖业务代码；③ 缓存设短 TTL 让它自然过期。生产上常用 ②+③。

### 第 10 层｜主从延迟下 Cache Aside 会读到旧值吗？
**答**：会。更新主库并删缓存后，如果读请求被路由到从库，从库还没同步到新数据，就会读到旧值并回填缓存。缓解：关键读走主库、延迟双删把从库延迟算进去、或用 binlog 方案。这也是"读写分离 + 缓存"经常被追问的点。

### 第 11 层｜多级缓存怎么保证一致性？
**答**：本地缓存 TTL 设很短（秒级）+ Redis 变更后广播失效消息（Pub/Sub 或 MQ），各实例收到后删本地缓存。强一致做不到，工程上接受秒级最终一致；热点数据可以本地缓存 + 定期刷新。

### 第 12 层（终局）｜这条链路在源码/组件里怎么走？
**答**：缓存侧：`expire.c` 的 `activeExpireCycle`（定期抽样）和 `expireIfNeeded`（惰性删除）决定击穿窗口；DB 侧：canal 伪装成 MySQL 从库，解析 binlog 的 ROW 事件，投递到 MQ，消费者按顺序删缓存/更新缓存，失败重试 + 死信告警。强一致只能靠分布式事务/锁，缓存方案本质是最终一致。

## L5 名词拆解表（"每个名词都拆开"）

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 缓存穿透 | 查不存在的数据绕过缓存 | 恶意/异常请求打 DB | 空值缓存与布隆的取舍 |
| 布隆过滤器 | 位数组 + k 哈希的概率结构 | O(1) 判断"可能存在" | 假阳性、不支持删除 |
| 缓存击穿 | 热点 key 过期瞬间并发 | 单点热点打 DB | 互斥锁 vs 逻辑过期 |
| 逻辑过期 | value 带过期时间、不设 TTL | 不阻塞读、高可用 | 旧数据窗口 |
| 缓存雪崩 | 大面积 key 同时失效 | DB 被打挂 | TTL 随机、多级缓存 |
| Cache Aside | 读缓存、写 DB+删缓存 | 业务可控、最常用 | 先删还是后删 |
| 延迟双删 | 更新后延迟再删一次 | 清掉并发回填的旧值 | 延迟怎么估 |
| binlog 订阅 | 监听 DB 变更异步删缓存 | 业务零侵入、可重试 | canal 原理、顺序性 |
| 互斥重建 | SETNX 锁 + 双重检查 | 收敛击穿时的 DB 请求 | 锁超时、重试 |
| 多级缓存 | 本地 + Redis | 抗热点、降延迟 | 一致性怎么保 |
| 热点 key | 访问极度集中的 key | 单分片/单节点压力 | 探测与打散 |
| 最终一致 | 允许短暂不一致 | 跨存储无法强一致 | 窗口多大、怎么兜底 |

## 代码验证（Java + redis-cli，Cache Aside + 击穿保护）

```java
// 1. Cache Aside：先更新 DB，再删缓存（失败重试）
@Transactional
public void updateUser(User user) {
    userMapper.updateById(user);
    int retry = 0;
    while (retry++ < 3) {
        try { redis.del("user:" + user.getId()); return; }
        catch (Exception e) { sleep(50L * retry); }
    }
    log.error("del cache failed, userId={}", user.getId());
}

// 2. 击穿保护：互斥锁重建 + 双重检查 + 超时
public User getUser(Long id) {
    String key = "user:" + id;
    String cached = redis.get(key);
    if (cached != null) return JSON.parseObject(cached, User.class);

    String lockKey = "lock:user:" + id;
    if (redis.set(lockKey, "1", SetParams.setParams().nx().ex(10))) {
        try {
            cached = redis.get(key);              // 双重检查：可能别人刚回填
            if (cached != null) return JSON.parseObject(cached, User.class);
            User user = userMapper.selectById(id); // 只有拿到锁的线程查 DB
            if (user == null) {
                redis.set(key, "", SetParams.setParams().ex(60)); // 空值缓存 60s，防穿透
                return null;
            }
            redis.set(key, JSON.toJSONString(user), SetParams.setParams().ex(1800));
            return user;
        } finally {
            redis.del(lockKey);                   // 生产用 Lua 校验 value 再删（见 04 文件）
        }
    }
    sleep(50);                                    // 没抢到锁：短暂重试读缓存
    return getUser(id);
}

// 3. 逻辑过期版（高可用优先）：value 里带 expireAt，异步重建
public User getUserWithLogicExpire(Long id) {
    String json = redis.get("user:" + id);
    if (json == null) return loadAndSet(id);
    UserWrapper w = JSON.parseObject(json, UserWrapper.class);
    if (w.getExpireAt() < System.currentTimeMillis()) {
        asyncExecutor.execute(() -> loadAndSet(id)); // 异步重建，不阻塞当前请求
    }
    return w.getUser();
}
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「先删缓存再更新 DB 更好」 | 标准是**先更新 DB 再删缓存**，脏窗口更小 |
| 「延迟双删能保证强一致」 | 只是缩小窗口，仍最终一致 |
| 「布隆过滤器能删除」 | 普通布隆不支持删除（计数布隆/布谷鸟才行） |
| 「逻辑过期就是设长 TTL」 | 逻辑过期不设 Redis TTL，过期标记在 value 里 |
| 「击穿 = 雪崩」 | 击穿是单个热点 key，雪崩是大量 key |
| 「空值缓存可以设很长」 | 设短 TTL，否则内存被污染 |
| 「缓存一致性能做到实时」 | 跨存储只能最终一致，靠重试/binlog 兜底 |
