# 可观测性（日志 / 指标 / 链路追踪 / SLO）

> 面试权重：5/5　｜　追问深度：**L5（traceparent 协议 / OTel Collector 链路 / Prometheus 存储与分位数）**
> 一句话定位：可观测性是用**系统外部输出推断内部状态**的能力，三大支柱各司其职：**指标（Metrics）**看趋势与告警、**日志（Logs）**看具体发生了什么、**链路追踪（Traces）**看一次请求卡在哪一跳。三者靠 **traceId** 串起来，最终落到 **SLI/SLO/错误预算**上衡量"系统到底好不好"。

**本文件用法**：先背 L2 的三大支柱分工与信号传递，再逐层追问。答不出"histogram 分位数的坑""traceparent 长什么样"，说明只背了概念。
[返回深度追问索引](../00-索引.md)

---

## L1 一句话答案（10 秒能说出口）

可观测性 = **指标 + 日志 + 链路追踪 + 统一上下文**。指标用 Prometheus 的 Counter/Gauge/Histogram 做趋势与告警；日志结构化输出并带上 traceId/spanId；链路追踪用 W3C `traceparent` 把一次请求的每一跳（HTTP、DB、Redis、MQ）记成父子 Span，经 OpenTelemetry SDK/Collector 上报。再往上用 SLI（成功率/延迟分位）定义 SLO（如 99.9%），用**错误预算**决定发布节奏，用**多窗口燃烧率**做告警降噪。

## L2 原理层：三大支柱与 SLO

### 2.1 三大支柱的分工

| 支柱 | 回答的问题 | 成本 | 典型工具 |
|---|---|---|---|
| 指标 Metrics | 系统整体是否健康、趋势与容量 | 低（聚合数值） | Prometheus + Grafana |
| 日志 Logs | 这一次请求/这个错误到底发生了什么 | 高（体积大） | Loki / ES / ClickHouse |
| 链路 Traces | 一次请求慢在哪个服务、哪一跳 | 中（采样后可控） | Jaeger / Tempo / SkyWalking |

**只有指标会告警**（便宜、可聚合）；日志和链路用来**定位**。三者用同一个 `traceId` 串联：告警 → 点进面板 → 按 traceId 查日志与链路。

### 2.2 结构化日志与 traceId

- **结构化**：输出 JSON（`timestamp/level/service/traceId/spanId/userId/msg/错误栈/耗时`），而不是拼字符串；便于采集、检索、聚合，字段固定才能建索引。
- **级别**：`ERROR`（需要人处理）、`WARN`（可自愈/降级）、`INFO`（关键状态变更，生产默认）、`DEBUG/TRACE`（排障临时开）。**错误日志必须带上下文**（参数、traceId、下游返回），否则等于没打。
- **采样**：高 QPS 场景全量 INFO 日志会打爆磁盘与 IO。做法：只采错误/慢请求（tail sampling）、按比例采样（1%-10%）、按接口/租户动态采样；异步 appender + 有界队列 + 丢弃策略（宁可丢日志不能阻塞业务）。
- **traceId 注入**：入口过滤器从请求头取 `traceparent`（没有就生成），放进 MDC，日志模板统一带 `%X{traceId}`；响应头回传 traceId 方便用户报障。

### 2.3 Prometheus 四种指标类型

| 类型 | 语义 | 典型用法 | 注意 |
|---|---|---|---|
| Counter | 只增不减的累计值 | 请求总数、错误总数（配 `rate()`/`increase()`） | 不能直接看绝对值，要算速率 |
| Gauge | 可增可减的瞬时值 | 当前连接数、队列长度、内存占用 | 直接看值或 `avg_over_time` |
| Histogram | 按 bucket 累计计数（+`_sum`/`_count`） | 请求延迟分布、P99 | 分位数由 `histogram_quantile()` 在查询端估算 |
| Summary | 客户端算好的分位数（+`_sum`/`_count`） | 单实例延迟分位 | **分位数不能跨实例聚合**，慎用 |

**直方图分位数陷阱**：
1. 分位数是**桶边界内线性插值估算**的，bucket 设计不合理（比如只配了 100ms/1s/10s）会导致 P99 误差很大；
2. `histogram_quantile(0.99, sum by (le) (rate(http_duration_bucket[5m])))` 可以聚合**桶**后再算分位，但**不能把各实例的 P99 求平均**（平均分位不是分位）；
3. 平均值（`rate(_sum)/rate(_count)`）会掩盖长尾，SLO 要看 P95/P99；Summary 的分位在客户端算好、**跨实例无法合并**，大规模场景优先 Histogram。

### 2.4 链路追踪：TraceID / Span / 上下文

```
TraceID：一次请求的全局唯一 ID（全链路一致）
  └── Span：一个工作单元（一次 RPC、一次 SQL、一次 Redis 调用），有 spanId + parentSpanId
        ├── Span A（网关入口，root）
        ├── Span B（订单服务 HTTP handler，parent=A）
        │     ├── Span C（DB 查询，parent=B）
        │     └── Span D（Redis GET，parent=B）
        └── Span E（支付服务调用，parent=A）
```

- **采样**：head-based（入口决定采不采，成本低但可能漏掉慢请求）、tail-based（在 Collector 里按"慢/错"决定保留，质量高但要在后端缓存整条链路）。
- **W3C `traceparent` 格式**（跨服务传递的标准）：

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
              version(2) - trace-id(32 hex) - parent-id(16 hex) - trace-flags(2, 01=sampled)
加上 tracestate: 厂商自定义状态（key=value 列表）
```

- **上下文传播**：HTTP 用 header（traceparent/b3）、gRPC 用 metadata、MQ 用消息头、线程池用上下文包装、Reactor 用 `Context`；LangChain/AI Agent 这类调用链同样要透传，否则链路断成两段。

### 2.5 OpenTelemetry 采集链路

```
应用（OTel SDK / Java Agent 自动埋点）
  └── OTLP exporter（gRPC:4317 / HTTP:4318，protobuf）
        └── OTel Collector（receiver → processor(batch/retry/memory_limiter) → exporter）
              ├── traces → Jaeger / Tempo
              ├── metrics → Prometheus / Mimir
              └── logs → Loki / ES
```

- 标准统一：一套 SDK + 一套协议（OTLP）把 trace/metric/log 都收上来，后端可换（避免被 APM 厂商锁定）。
- 自动埋点：Java Agent 对 Spring MVC、JDBC、Redis、Kafka、OkHttp 等插件化织入，业务代码零改动；需要手动埋点时用 `Tracer.spanBuilder()`。
- **eBPF 无侵入观测**：内核层抓 HTTP/gRPC/DB 的请求与耗时，适合老服务/无法改代码的场景，但语义（业务字段）不如 SDK 丰富。

### 2.6 黄金四指标与 SLI/SLO/错误预算

- **黄金四指标（Google SRE）**：**延迟（Latency）**、**流量（Traffic）**、**错误（Errors）**、**饱和度（Saturation）**。对应到接口：P99 延迟、QPS、5xx/业务错误率、连接池/线程池使用率。
- **SLI / SLO**：SLI 是可测量的指标（如"HTTP 成功率"= 2xx/总数、"延迟 SLI"= P99 < 300ms 的请求占比）；SLO 是对 SLI 的目标（如"30 天内成功率 >= 99.9%"），对应**错误预算 = 1 - SLO = 0.1%**（一个月约 43 分钟不可用）。
- **错误预算的用途**：预算充足可以激进发布/做实验；预算烧光冻结发布、优先修稳定性——**它把"稳定 vs 迭代"从吵架变成数字。**
- **燃烧率（burn rate）**：实际错误率 / 预算允许错误率。1 小时烧掉 14.4 倍 = 一天烧光月预算。**多窗口多燃烧率告警**（如 5m+1h 同时超阈值才告警）能显著降噪。

### 2.7 告警降噪

1. **按症状告警**（用户可感知：错误率、P99、可用性），不按原因告警（CPU 高、某中间件慢）；
2. **分级**：P0（页面/电话）、P1（IM）、P2（工单）；每级有响应时限；
3. **分组 + 抑制**：同一根因的告警合并（Alertmanager `group_by`），上游故障时抑制下游告警（inhibition）；
4. **静默 + 持续判定**：发布/维护窗口用 `silence`，`for: 5m` 等状态持续才触发，恢复时发 resolved；
5. **每条告警必须带 runbook**（怎么查、找谁、能否降级），否则值班只会转发。

### 2.8 项目落点

- **报告平台 任务系统**：提交任务（HTTP）→ 落库 → MQ → Docker 沙箱执行 → SSE 推进度，整条链路用同一个 traceId；指标看任务成功率/排队时长/沙箱执行耗时，日志带 taskId 便于按任务追踪。
- **数字人 WebSocket 流式**：会话建立、每轮 ASR/TTS 的耗时用 span 记录，指标看并发会话数、首字延迟、音频帧处理延迟；容器/沙箱的 CPU/内存/执行时长（cgroup 指标）进 Prometheus，OOM（`memory.events`）触发告警；WS 没有 HTTP header 天然传上下文，要在握手参数或首帧里带 traceId。

## L3 底层层：数据在 wire 与存储里的样子

### 3.1 Prometheus 的拉取与存储

- **Pull 模型**：Prometheus 按 `scrape_interval` 主动 GET 目标 `/metrics`（文本格式 `metric{label="v"} value timestamp`）；服务发现（K8s SD/文件）决定抓谁；`relabel` 做标签改写。
- **存储与 PromQL**：TSDB 按 2 小时一个 block 落盘，内存 head + WAL；标签是索引维度，**高基数标签（userId、traceId）会撑爆内存**；`rate(counter[5m])` 要至少两个样本，`histogram_quantile(0.99, sum by (le) (rate(latency_bucket[5m])))` 是分位标准写法。

### 3.2 OTLP 与 Collector

- OTLP 是 protobuf 编码（gRPC 4317 / HTTP 4318），一次请求携带一批 span/metric/log；Collector 的 `batch`（攒批）、`retry`（后端抖动重试）、`memory_limiter`（自保护）、`tail_sampling`（按错误/延迟采样）是生产必备 processor。
- **tail sampling 的代价**：要在 Collector 内存里保留整条 trace 直到判定，采集器要水平扩展并保证同一 trace 落到同一实例（按 traceId 负载均衡）。

### 3.3 日志采集

Filebeat/Fluent Bit 从容器 stdout 或文件采集 → 缓冲（Kafka）→ ES/Loki/ClickHouse；**Loki 只索引标签不索引全文**，成本低，适合按 traceId 检索；ES 全文索引贵但检索强。日志量控制靠级别、采样、清理周期。

## L4 追问树（面试官一路往下问，你能撑到第几层？）

> 规则：第 1-3 层必备，4-6 层拉开差距，7 层以后是加分。

### 第 1 层｜三大支柱分别解决什么问题？为什么三个都要？
**答**：指标回答"系统整体是否健康、趋势如何"，便宜可聚合，用来告警；日志回答"这一次到底发生了什么"，信息最全但贵；链路追踪回答"一次请求慢在哪一跳"，把跨服务调用串起来。只有指标会告警，日志和链路负责定位，靠 traceId 串起来，缺一个就会在排障时断链。

### 第 2 层｜结构化日志怎么设计？traceId 怎么串起来？
**答**：输出 JSON，固定字段：timestamp、level、service、traceId、spanId、msg、耗时、错误栈、业务键（taskId/orderId）；入口过滤器从 `traceparent` 取或生成 traceId 注入 MDC，日志模板统一输出 `%X{traceId}`，响应头回传；下游调用把它放进 HTTP 头/MQ 头继续传。**字段固定才能检索与聚合，traceId 一致才能把一条请求的日志串起来。**

### 第 3 层｜日志级别与采样怎么定？日志写多了会怎样？
**答**：生产默认 INFO，ERROR 必须带上下文，DEBUG/TRACE 临时开；高 QPS 下按比例采样或只保留错误/慢请求（tail sampling），用异步 appender + 有界队列 + 丢弃策略。写多了会：磁盘打满、IO 争抢拖慢业务、采集链路（Filebeat→Kafka→ES）堆积、检索变慢、成本飙升。

### 第 4 层｜Prometheus 四种指标类型区别？Histogram 和 Summary 怎么选？
**答**：Counter 只增（请求数/错误数，配 rate）、Gauge 可增可减（连接数/队列长度）、Histogram 按 bucket 累计并在查询端算分位、Summary 在客户端算好分位。选择：**需要跨实例聚合/看分布 → Histogram**（分位可合并）；单实例、不想指定 bucket、对精度要求高 → Summary（但分位不可合并，扩缩容/多副本时失真）。

### 第 5 层｜直方图分位数有哪些坑？为什么不能对分位数再平均？
**答**：① 分位数是 bucket 内线性插值估算，bucket 边界不合理误差大；② `histogram_quantile` 必须对 `le` 聚合后再算，不能把各实例的 P99 求平均（P99 的平均不是 P99）；③ 平均值会掩盖长尾，SLO 看 P95/P99；④ Summary 的分位无法跨实例合并。正确写法：`histogram_quantile(0.99, sum by (le) (rate(http_duration_seconds_bucket[5m])))`。

### 第 6 层｜TraceID/Span 的父子关系怎么建立？跨服务怎么传？
**答**：每个 Span 有 spanId 和 parentSpanId，服务入口创建 root span（没有父），内部每次 RPC/DB/Redis 调用创建子 span，形成树。跨服务用 W3C `traceparent` 头（version-traceId-parentId-flags）由客户端注入、服务端提取后作为新 span 的 parent；gRPC 用 metadata、MQ 用消息属性、WebSocket 在首帧/握手参数里传。

### 第 7 层｜跨线程池、消息队列怎么传 trace 上下文？
**答**：ThreadLocal（OTel Context/MDC）不会自动跨线程。线程池用 `TaskDecorator` 复制上下文或用 OTel 的 `Context.current()` 包装 Runnable；Reactor 用 `contextWrite` 与 `Hooks.enableAutomaticContextPropagation`；MQ 生产端把 traceparent 写进消息头，消费端提取后继续建子 span；定时任务/异步回调要显式传递，否则链路断成两段。

### 第 8 层｜OpenTelemetry 的采集链路长什么样？
**答**：应用内 OTel SDK（Java Agent 自动埋点或手动埋点）产生 trace/metric/log → OTLP exporter（gRPC 4317/HTTP 4318，protobuf）→ Collector（receiver 接收、processor 批处理/重试/内存限制/尾部采样、exporter 导出）→ Jaeger/Tempo 存 trace、Prometheus/Mimir 存指标、Loki/ES 存日志。标准化的价值是不锁定厂商、三类信号统一上下文。

### 第 9 层｜黄金四指标怎么用？和 SLI/SLO 什么关系？
**答**：黄金四指标是"看什么"的框架：延迟、流量、错误、饱和度，分别对应 dashboard 的 P99、QPS、错误率、资源使用率。SLI 是把其中可度量的部分定义成指标（成功率、延迟达标率），SLO 是对 SLI 设目标（99.9%/30 天），错误预算 = 100% - SLO。**四指标是观测面，SLI/SLO 是承诺面。**

### 第 10 层｜SLI/SLO/错误预算怎么落地？燃烧率告警是什么？
**答**：先选 1-2 个用户可感知的 SLI（成功率、P99 延迟、可用性），定 SLO 与统计窗口，错误预算 = 1 - SLO（99.9% → 每月 43 分钟）。发布策略与预算挂钩：预算充足可快发，预算耗尽冻结发布。告警用**燃烧率**（实际错误率 / 允许错误率）多窗口组合（如 5m 烧 14.4x 且 1h 烧 6x），比"错误率 > 1%"既及时又少误报。

### 第 11 层｜告警太多怎么降噪？
**答**：① 按症状（用户可感知）而非原因告警；② 分级 P0/P1/P2，不同通道与时限；③ Alertmanager 分组、抑制（上游故障抑制下游）、静默（发布窗口）；④ `for: 5m` 持续判定 + 恢复通知；⑤ 多窗口燃烧率替代固定阈值；⑥ 每条告警配 runbook；⑦ 定期复盘"无效告警"并删除。

### 第 12 层（终局）｜一次请求从入口到上报，trace/指标/日志在 wire 上分别长什么样？
**答**：请求带 `traceparent: 00-<32hex traceId>-<16hex parentId>-01` 到网关，网关生成 root span 并把同样的 header 透传给下游；每个服务入口提取 header，创建子 span，调 DB/Redis 时在客户端埋点里再建子 span；最后 SDK 把整条 trace 的 span 列表用 **OTLP protobuf**（gRPC 4317）批量发到 Collector，Collector `batch` 后导出到 Jaeger/Tempo，存储按 traceId 建索引。指标是服务内 `/metrics` 文本（或 OTLP metrics）被 Prometheus 每 15s 拉一次，样本存 TSDB。日志是 stdout 的 JSON 行，被 Fluent Bit/Filebeat 采集后（可经 Kafka 缓冲）进 Loki/ES，索引里带 traceId 方便反查。**三条线共用同一个 traceId，这就是"可观测"的闭环。**

| 名词 | 是什么 | 为什么存在 | 面试追问点 |
|---|---|---|---|
| 结构化日志 | JSON 字段化输出 | 可检索、可聚合、可关联 | 字段设计、traceId 注入 |

| 黄金四指标 | 延迟/流量/错误/饱和度 | 统一的健康观测框架 | 各对应哪些指标 |
| SLI / SLO / 错误预算 | 指标定义 / 目标承诺 / 允许失败额度 | 把"稳定性"量化并指导发布 | 99.9% 对应多少 downtime、燃烧率 |

```java
// 2) 入口过滤器：从 traceparent 提取 traceId 注入 MDC（无则生成）
String tp = request.getHeader("traceparent");
String traceId = (tp != null && tp.length() >= 55) ? tp.split("-")[1] : UUID.randomUUID().toString().replace("-", "");
MDC.put("traceId", traceId);
try { chain.doFilter(request, response); } finally { MDC.remove("traceId"); }
// 异步/线程池：用 TaskDecorator 把 MDC 复制到子线程，或 TtlExecutors 包装

// 3) Micrometer 打点：Counter + Histogram（SLO 用）
Counter.builder("http_server_errors_total").tag("uri", "/api/tasks").register(registry).increment();
Timer.builder("http_server_duration_seconds").tag("uri", "/api/tasks")
     .publishPercentileHistogram().register(registry).record(duration);   // 产生 _bucket 可算 P99
```

```promql
# 4) 延迟 P99（对桶聚合后再算分位，标准写法）
histogram_quantile(0.99,
  sum by (le, uri) (rate(http_server_duration_seconds_bucket[5m])))

# 5) 错误率与 SLO 燃烧率：burn rate = 错误率 / (1 - 0.999)
sum(rate(http_server_errors_total[5m])) / sum(rate(http_server_requests_total[5m]))
```

## 高频错误（面试官最爱抓的）

| 错误说法 | 正确说法 |
|---|---|
| 「日志级别全开 DEBUG 方便排查」 | 高 QPS 会打爆磁盘与 IO，生产用 INFO + 按需/采样开 DEBUG |
| 「平均响应时间能代表用户体验」 | 均值掩盖长尾，要看 P95/P99 分位 |
| 「P99 的平均还是 P99」 | 分位数不可平均，要用 `histogram_quantile` 对桶聚合后再算 |
| 「Summary 和 Histogram 随便选」 | Summary 分位不可跨实例合并，多副本场景优先 Histogram |
| 「traceId 用 userId 做 label 更细」 | 高基数 label 会撑爆 Prometheus TSDB，标签只放低基数维度 |
| 「链路追踪全量采集最准」 | 全量成本极高，要 head/tail 采样，至少保留错误与慢请求 |
