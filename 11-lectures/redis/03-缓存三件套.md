# 缓存三件套：穿透、击穿、雪崩到底怎么区分？

> 精讲层级：从「零基础能看懂」到「源码级」，每个名词都拆开
> 阅读时间：约 30 分钟

---

## 0. 一句话先讲明白

三者都表现为「请求打到数据库」，区别只在**谁出了问题**：

- **穿透**：查的数据**根本不存在**，缓存永远不可能命中，每次都打数据库；
- **击穿**：**一个热点 key 刚好过期**，瞬间大量请求同时回源；
- **雪崩**：**大量 key 同时过期**，或者**缓存层整体不可用**，请求大面积回源。

对应的解法也正好三组：布隆过滤器/空值缓存对付「不存在」，互斥锁/逻辑过期对付「单个热点过期」，随机 TTL/多级缓存/限流熔断对付「大面积失效」。

---

## 1. 它解决什么问题：数据库挡不住流量

### 1.1 缓存存在的意义

数据库（如 MySQL）单机每秒能承受的查询量通常在几千量级；而一个热门接口的 QPS 可能是十万级。缓存把「读多写少」的数据放在内存里，挡住绝大部分读请求。

**数字化推导一：缓存到底挡了多少**

```text
接口 QPS = 100,000
缓存命中率 = 99%
→ 打到数据库 = 100,000 × 1% = 1,000 QPS（数据库轻松承受）

如果缓存整体失效：
→ 100,000 QPS 全部打到数据库
→ 数据库容量假设 5,000 QPS，超载 20 倍，连接池瞬间打满
→ 数据库响应变慢 → 请求堆积 → 应用线程被拖死 → 整条链路雪崩
```

所以「缓存三件套」的本质不是缓存本身的问题，而是**缓存失效瞬间如何保护数据库**。

### 1.2 三个概念为什么容易混

因为它们的结果看起来一样：数据库压力突然升高。区分的抓手是三个问题：

| 问题 | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 数据存在吗？ | 不存在 | 存在 | 存在 |
| 缓存里有吗？ | 永远没有 | 有过，刚过期 | 大量 key 同时没有 |
| 影响范围？ | 单个不存在的 key（可重复） | 单个热点 key | 大量 key / 整个缓存层 |
| 持续时间？ | 取决于攻击量 | 毫秒~秒级 | 数秒~数分钟 |
| 主要解法 | 布隆过滤器、空值缓存 | 互斥锁、逻辑过期 | 随机 TTL、多级缓存、限流熔断 |

## 2. 一步步拆开

### 2.1 先解释名词

| 名词 | 是什么 |
|---|---|
| 缓存命中（hit） | 请求的数据在缓存里找到了，直接返回 |
| 缓存未命中（miss） | 缓存里没有，需要回源查数据库 |
| 回源 | 缓存未命中时去数据库/下游服务取数据，再写回缓存 |
| 热点 key | 被极高频访问的 key，如首页商品、爆款库存 |
| TTL | Time To Live，缓存键的存活时间，到期自动删除 |
| 布隆过滤器 | 用位数组 + 多个哈希函数判断「元素可能存在/一定不存在」的概率数据结构 |
| 互斥锁 | 保证同一时刻只有一个请求回源的锁（本地锁或分布式锁） |
| 逻辑过期 | value 中记录逻辑过期时间，由应用判断是否过期，Redis 不设物理 TTL |
| 降级 | 依赖不可用时返回兜底数据（默认值、旧数据、空列表） |

### 2.2 穿透：查一个不存在的数据

典型场景：攻击者用 `id=-1`、`id=999999999` 这类不存在的 ID 请求；或业务上大量无效查询（爬虫、脏链接）。

问题链条：缓存没有 → 查数据库 → 数据库也没有 → **不写缓存** → 下次还查数据库。因为「没有数据」这件事没有被缓存，每个请求都会穿透。

**解法一：空值缓存**

查数据库为空时，仍往缓存写一个特殊值（如 `"NULL"`），TTL 设短（30~120 秒）。后续请求命中空值，直接返回。

风险：
- 数据后来被创建了，要**主动删除这个空值缓存**，否则用户会看到「不存在」直到 TTL 到期；
- 攻击者用海量不同的不存在 key，每个都写空值 → 内存占用。用短 TTL + 限流控制。

**解法二：布隆过滤器前置**

在缓存前加一层布隆过滤器：所有存在的 ID 提前放进去。查询时先问：

- 「一定不存在」→ 直接返回空，不查缓存也不查库；
- 「可能存在」→ 继续查缓存/数据库（可能是误判）。

```text
位数组 m 位（初始全 0），k 个哈希函数
插入 x：k 个位置全部置 1
查询 y：k 个位置只要有一个是 0 → 一定不存在
        全是 1 → 可能存在（别的元素也可能把这些位置置 1）
```

三个关键性质：
1. **没有假阴性**：真正存在的元素一定判为「可能存在」；
2. **有假阳性**：不存在的元素可能被误判，概率可计算、可控制；
3. **标准布隆不支持删除**：把位置 0 会影响其他元素；需要删除时用计数布隆或布谷鸟过滤器。

生产实现：RedisBloom 模块（`BF.RESERVE`/`BF.ADD`/`BF.EXISTS`），或 Guava `BloomFilter`（单机）。数据新增要同步写入过滤器。

**解法三：参数校验与限流**：`id <= 0` 直接拒绝；单 IP/单用户限频；异常 ID 直接返回空。

### 2.3 击穿：一个热点 key 过期

某个爆款商品的缓存 TTL 到期，恰好在这一瞬间有几千个请求同时到达。它们都 miss，同时查数据库 → 数据库瞬时被打出尖峰。

击穿的前提：数据**存在且是热点**，只是缓存过期了；影响**单个 key**，但若该 key 承担大部分流量，后果可能和雪崩一样严重。

**解法一：互斥锁（只让一个请求回源）**

```text
请求 A：缓存 miss → 拿锁成功 → 查 DB → 写缓存 → 释放锁
请求 B/C/D：缓存 miss → 拿锁失败 → 短暂等待后重试读缓存 → 命中
```

细节：
1. **二次检查**：拿到锁后再查一次缓存，避免前一个请求已写好、自己又查一次库；
2. **锁超时**：锁必须带过期时间，防止持锁进程崩溃导致死锁；
3. **等待策略**：短间隔自旋重试或直接返回兜底值，不能让大量请求无限挂起（线程池会被占满）；
4. **锁粒度**：按 key 加锁（`lock:goods:{id}`），不要全局一把锁。

**解法二：逻辑过期（不设物理 TTL，异步重建）**

value 存 `{ data, expireAt }`，Redis 不设 TTL。读取时判断：

- 未过期：直接返回；
- 已过期：尝试拿重建锁，拿到锁的线程**异步**查库并更新缓存；其他线程**直接返回旧数据**。

优点：请求永不阻塞，可用性高；缺点：短时间读到旧数据（最终一致），重建逻辑要幂等。

**解法三：热点 key 永不过期 + 后台刷新**：极热数据用后台任务定时刷新，刷新失败继续用旧值。

### 2.4 雪崩：大面积失效

两种触发：

1. **大量 key 同时过期**：凌晨批量预热 1000 个 key、TTL 都设 30 分钟，30 分钟后同时失效；
2. **缓存层整体不可用**：Redis 宕机、主从切换、网络分区、集群分片故障。

结果：请求同时打向数据库，数据库被打挂后，依赖它的其他接口也挂，故障扩散。

**解法一：随机 TTL**：基础 TTL 加随机抖动，避免同一秒集体失效（定量分析见第 6 节）。

**解法二：多级缓存**：本地缓存（Caffeine 等）+ Redis；极热数据放本地，扛住 Redis 抖动；本地缓存 TTL 短（秒级~分钟级），配失效广播。

**解法三：熔断、限流、降级**：限流把打库 QPS 限制在数据库容量内；熔断在错误率升高时快速失败；降级返回兜底数据（默认推荐、缓存快照、静态页）。

**解法四：缓存高可用**：主从 + 哨兵/集群、持久化、故障转移、容量监控、预热。缓存层要按「会挂」来设计。

## 3. 完整推导

### 3.1 布隆过滤器误判率公式与算例

设位数组长度 m、插入元素个数 n、哈希函数个数 k。

推导：
1. 一次哈希把某一位设为 1 的概率是 `1/m`，不设的概率是 `1 - 1/m`；
2. 插入 n 个元素、每个 k 次哈希，共 kn 次：某一位仍为 0 的概率约 `(1 - 1/m)^{kn} ≈ e^{-kn/m}`；
3. 查询不存在的元素时，k 个位置都为 1 才误判：

```text
p ≈ (1 - e^{-kn/m})^k
```

**完整代入算例**：m = 1000 万位（约 1.19 MiB），n = 100 万 key，k = 7：

```text
kn/m = 7 × 1,000,000 / 10,000,000 = 0.7
e^{-0.7} ≈ 0.4966
p ≈ (1 - 0.4966)^7 = 0.5034^7 ≈ 0.0082 = 0.82%
```

也就是说：100 万个 key 只占约 1.19 MiB，就能把 99.18% 的不存在请求挡在数据库之外；剩下 0.82% 的误判由空值缓存兜底。

**为什么 k 有最优值**：固定 m/n = 10，把 k 从 4 试到 9：

| k | e^{-kn/m} | p = (1 - e^{-kn/m})^k |
|---|---|---|
| 4 | 0.6703 | 0.0118 |
| 5 | 0.6065 | 0.0094 |
| 6 | 0.5488 | 0.0084 |
| 7 | 0.4966 | 0.0082（最小） |
| 8 | 0.4493 | 0.0085 |
| 9 | 0.4066 | 0.0090 |

k 太小，k 个位置全被占满的概率高；k 太大，每个位被置 1 的概率上升，误判率反而回升。对 `ln p(k)` 求导并令导数为 0：

```text
ln p = k · ln(1 - e^{-kn/m})
令 a = e^{-kn/m}，k·n/m = -ln a，求导并整理：
ln(1 - a) - a·ln(a)/(1 - a) = 0
解得 a = 1/2 → kn/m = ln2 → k = (m/n)·ln2
```

所以最优 k ≈ (m/n)·ln2。在本例中 (m/n)·ln2 = 10 × 0.693 ≈ 6.93，取整为 7，和表格最小值一致。
给定目标误判率 p，所需位数 `m ≈ -1.44·n·log2(p)`；100 万元素、p=1% 约需 958 万位（1.14 MiB），p=0.1% 约需 1435 万位（1.71 MiB）。

### 3.2 数字化推导三：雪崩峰值差多少

1000 个 key 的 TTL 都是 30 分钟，且在同一时刻写入：

```text
无随机：30 分钟后 1000 个 key 在同一秒过期
        假设每个 key 每秒被访问 10 次 → 瞬时回源 10,000 QPS
加随机：TTL 在 [25min, 35min] 均匀分布
        过期分散在 600 秒内，平均每秒过期 1000/600 ≈ 1.7 个 key
        瞬时回源 ≈ 1.7 × 10 ≈ 17 QPS
峰值降低约 600 倍
```

### 3.3 数字化推导四：空值缓存的内存开销

假设有人用 100 万个不同的不存在 ID 每天扫描一次（约 11.6 QPS）：

```text
空值缓存 TTL = 60 秒
同时存活的空值 key 上限 ≈ 11.6 × 60 ≈ 700 个
每个 key（ID + "NULL" + Redis 对象开销）按 100 字节估算 ≈ 70KB
```

内存完全可接受。真正需要担心的是高 QPS 攻击（如 1 万 QPS 打不同 ID），此时靠限流/黑名单，而不是无限写空值。

### 3.4 数字化推导五：击穿时锁等待的代价

热点 key 过期，1000 个请求同时到达，回源耗时 50ms：

```text
互斥锁：1 个请求查库（50ms），其余 999 个等待
  50ms 后重试命中缓存 → 总耗时约 50~60ms，数据库只承受 1 次查询
  但 999 个请求各自占着线程等待 → 线程池压力大
逻辑过期：所有请求立即返回旧值，后台异步重建 → 数据库 0 次即时查询
```

结论：互斥锁保护了数据库，但把压力转移到应用线程；QPS 极高时用「逻辑过期/异步重建」或「本地锁 + 短等待」。

## 4. 极简模型：3 个 key、其中 1 个不存在

设定三个 key：

| key | 状态 | 对应问题 | 请求到来时会发生什么 |
|---|---|---|---|
| A | 存在、热点，缓存**刚过期** | 击穿 | 大量并发请求同时 miss，同时回源 |
| B | 存在、普通，和 A **同一秒过期** | 雪崩（最小缩影：真实雪崩是大量 key 同时失效） | 同样 miss 回源，和 A 一起放大数据库压力 |
| C | **不存在** | 穿透 | 永远 miss，每个请求都查一次库且查不到 |

用 3 个客户端 c1/c2/c3 同时请求，对照三者的处理：

| 场景 | 无防护 | 有防护 |
|---|---|---|
| c1/c2/c3 同时查 C | 3 次 miss → 3 次查库（都查不到） | 布隆判「不存在」→ 0 次查库；或空值缓存：1 次查库 + 后两次命中 `NULL` |
| c1/c2/c3 同时查 A（刚过期） | 3 次同时回源 | 互斥锁：1 次回源，另 2 次等缓存写好后命中；逻辑过期：3 次都立即返回旧值，后台重建 1 次 |
| 到点后 A、B 同一秒过期 | 2 个 key × 3 个客户端 = 6 次回源，随 key 数量线性放大 | 随机 TTL 让 A、B 的过期时间错开，峰值被摊平 |

这个最小模型说明：**穿透看「是否存在」，击穿看「单个 key 是否过期」，雪崩看「多少 key 同时失效」**；三者的解法也可以在这一张表里一一对应。

## 5. 为什么这样设计：被否决的方案

### 5.1 被否决方案一：穿透不处理，让数据库硬扛

**做法**：查不到就查不到，靠数据库连接池和 InnoDB buffer pool。
**否决理由**：攻击流量无上限，数据库容量有限；一次扫描就能把连接池打满，影响所有业务。穿透必须拦在数据库之前。

### 5.2 被否决方案二：所有不存在的 key 都永久缓存

**做法**：查不到就写缓存，永不设置 TTL。
**否决理由**：攻击者可用海量随机 key 把内存打爆；数据后来创建后用户会一直看到「不存在」。空值缓存必须短 TTL，并在数据创建时主动删除。

### 5.3 被否决方案三：任何 miss 都加分布式锁

**做法**：只要缓存 miss 就加锁，只让一个请求回源。
**否决理由**：非热点 key 的 miss 也排队，吞吐下降；锁竞争、锁超时、等待线程占内存；数据库偶发抖动会被锁放大。正确做法是只对**热点 key**做互斥/逻辑过期。

### 5.4 被否决方案四：热点 key 永不设置 TTL

**做法**：热点数据写入后不设过期，靠业务主动更新。
**否决理由**：一旦更新逻辑漏掉，缓存永远陈旧；内存也无法自动回收。更好的是「逻辑过期 + 异步刷新」或「永不过期 + 可靠的消息驱动更新」。

### 5.5 被否决方案五：雪崩只靠数据库扩容

**做法**：缓存挂了就加从库/升配。
**否决理由**：扩容速度赶不上流量尖峰（分钟级 vs 秒级），成本高且治标不治本。必须组合「随机 TTL（预防）+ 多级缓存（缓冲）+ 限流熔断（兜底）」。

## 6. 关键参数为什么是这个值

### 6.1 空值缓存 TTL：30~120 秒

- 太短：防不住高频重复查询；
- 太长：数据创建后用户长时间看到「不存在」；
- 折中：30~120 秒，并在写入数据时主动删除空值 key；
- 攻击场景配合限流，恶意 key 不写空值（直接拒绝）。

### 6.2 布隆过滤器误判率与容量：1% 起步

- 1% 约需 9.6 位/元素；0.1% 约需 14.4 位/元素；
- 误判的代价只是多查一次数据库（有空值缓存兜底），不必追求极低；
- 容量 n 要按峰值预估：实际元素远超容量时误判率快速上升；
- RedisBloom 用 `BF.RESERVE key error_rate capacity` 创建，容量不能后期随意扩。

### 6.3 随机 TTL 的取值范围：基础值的 10%~20%，最少 5 分钟

以「基础 30 分钟 ± 5 分钟」为例：

```text
过期窗口 = 600 秒
1000 个 key 均匀分布 → 平均每秒过期 1000/600 ≈ 1.7 个
不抖动时同一秒过期 1000 个 → 瞬时压力相差约 600 倍
```

「同时失效概率」的粗略估计：若抖动幅度为 ±ΔT，同批 key 数 N，则任意一秒内到期的期望个数约为 `N/(2ΔT)`；取 ΔT=300 秒、N=1000，即每秒约 1.7 个。若一个 key 的 TTL 只有几十秒，抖动至少给到 5~10 秒，否则等于没打散。

为什么幅度不能太大：抖动过大会降低命中率、让 TTL 语义混乱、内存占用波动；10%~20% 是「打散尖峰」与「保留缓存意义」的折中。

### 6.4 互斥锁的超时、重试次数与间隔

- 锁 TTL：大于回源 P99 的 2~3 倍，例如回源 P99 200ms，锁 TTL 设 3~5 秒；
- 等待重试：**3~5 次，间隔 50~100ms**（总等待 150~500ms），超过就降级返回兜底值；
- 不要 0 间隔自旋：那等于把「等锁」变成新的流量洪峰；
- 二次检查：拿到锁后先查缓存，再决定是否回源。

### 6.5 雪崩限流阈值：数据库容量的 60%~70%

留 30%~40% 余量给突发流量和故障转移；熔断错误率阈值常见 50%（连续失败达到比例后打开断路器）。

## 7. 版本演进

### 7.1 Redis

| 版本 | 与缓存三件套相关的变化 |
|---|---|
| 4.0（2017） | 模块系统上线，RedisBloom 以模块形式提供布隆过滤器；引入 LFU 淘汰策略 |
| 6.0（2020） | 多线程网络 IO（命令执行仍单线程）、ACL；高并发下缓存层吞吐提升 |
| 6.2 | `GETDEL`/`GETEX` 等命令，方便「取出并删除」类缓存操作 |
| 7.0（2022） | Functions、多部分 AOF、更细的淘汰与内存统计 |
| 7.x 后续与 8.x（2025 起） | 部分模块能力（含 Bloom 类数据结构）逐步并入发行版，具体以官方版本说明为准 |

### 7.2 Java 生态

- **Guava BloomFilter**：单机、简单，不支持删除，容量与误判率在创建时固定。
- **Caffeine**：本地缓存事实标准，W-TinyLFU 淘汰算法，适合做多级缓存的 L1。
- **Spring Cache**：`@Cacheable/@CacheEvict` 抽象，底层可接 Redis/Caffeine。
- **Redisson**：分布式锁/限流器等组件，互斥锁方案可直接使用其 `RLock`。
- **Sentinel / Resilience4j**：限流、熔断、降级，是雪崩兜底的主力。
- **布谷鸟过滤器**：RedisBloom 的 CF 类型或部分 Java 库支持，解决标准布隆不能删除的问题。

## 8. 亲手验证

> 说明：以下 Redis 命令需要本地 Redis；当前环境无 Redis，输出为预期输出。布隆模拟为 Python，本环境无 Python，数值按公式推导，实测会在 1% 附近波动。

### 8.1 普通缓存与空值缓存

```bash
redis-cli SET goods:1 '{"name":"机械键盘"}' EX 1800
# 预期：OK
redis-cli TTL goods:1
# 预期：1800（或略小）

# 空值缓存：查不到的数据也写一个短 TTL 的特殊值
redis-cli SETEX empty:999999 60 'NULL'
# 预期：OK
redis-cli GET empty:999999
# 预期："NULL"
redis-cli TTL empty:999999
# 预期：60
```

### 8.2 互斥锁（击穿场景）

```bash
# 只让一个请求回源：NX 不存在才设置，PX 3000 表示 3 秒自动过期
redis-cli SET lock:goods:1 uuid-a NX PX 3000
# 预期：OK（第一个请求抢到锁）
redis-cli SET lock:goods:1 uuid-b NX PX 3000
# 预期：(nil)（第二个请求抢锁失败，应等待后重试读缓存）

# 释放锁必须比较 value，防止误删别人的锁（Lua 保证原子）
redis-cli EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:goods:1 uuid-a
# 预期：1
redis-cli EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:goods:1 uuid-b
# 预期：0（uuid 不匹配，不会误删）
```

### 8.3 布隆过滤器（RedisBloom 模块）

```bash
redis-cli BF.RESERVE bf:user 0.01 1000000
# 预期：OK（误判率 1%，容量 100 万）
redis-cli BF.ADD bf:user user:1
# 预期：1（添加成功）
redis-cli BF.EXISTS bf:user user:1
# 预期：1（可能存在）
redis-cli BF.EXISTS bf:user user:999999999
# 预期：0（一定不存在；偶发 1 属于误判）
```

没有 RedisBloom 时可用 `SETBIT`/`GETBIT` 手写：m=9,585,059 位 ≈ 1.14MiB，k=7 个哈希位置。

### 8.4 布隆过滤器误判率模拟（Python）

```python
import hashlib, math
class Bloom:
    def __init__(self, n, p):
        self.m = math.ceil(-n * math.log(p) / (math.log(2) ** 2))
        self.k = max(1, round(self.m / n * math.log(2)))
        self.bits = bytearray((self.m + 7) // 8)
    def _idx(self, s):
        h1 = int.from_bytes(hashlib.md5(s.encode()).digest()[:8], "big")
        h2 = int.from_bytes(hashlib.sha1(s.encode()).digest()[:8], "big") | 1
        return ((h1 + i * h2) % self.m for i in range(self.k))
    def add(self, s):
        for i in self._idx(s): self.bits[i >> 3] |= 1 << (i & 7)
    def contains(self, s):
        return all(self.bits[i >> 3] & (1 << (i & 7)) for i in self._idx(s))

n, p = 10000, 0.01
bf = Bloom(n, p)
for i in range(n): bf.add(f"user:{i}")
fp = sum(bf.contains(f"absent:{i}") for i in range(100000))
print(f"m={bf.m} bits ({bf.m/8/1024:.2f} KiB), k={bf.k}, 实测误判率={fp/100000:.4f}")
```

预期输出：

```text
m=95851 bits (11.70 KiB), k=7, 实测误判率=0.0100 左右
```

把 n 改成 1,000,000，m 会变成 9,585,059 位（约 1.14 MiB），误判率仍接近 1%——这正是 `m ≈ -1.44 n log2(p)` 的含义。

### 8.5 统计缓存命中率

```bash
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses"
# 预期：keyspace_hits:1234567
#       keyspace_misses:12345
# 命中率 = hits / (hits + misses) ≈ 99.0%
```

命中率骤降通常意味着批量过期、热点迁移或 key 设计问题，是排查三件套的第一现场。

## 9. 常见误区

| 错误说法 | 正确说法 |
|---|---|
| 「穿透、击穿、雪崩是同一件事」 | 穿透是数据不存在，击穿是单个热点 key 过期，雪崩是大量 key 同时失效或缓存整体不可用 |
| 「布隆过滤器能 100% 判断数据存在」 | 只能说「一定不存在」或「可能存在」，存在判断有误判率 |
| 「布隆过滤器可以随便删除元素」 | 标准布隆不支持删除（会清掉其他元素共享的位），要用计数布隆或布谷鸟过滤器 |
| 「布隆过滤器容量写小了也没关系」 | 实际元素远超容量时误判率飙升，等于形同虚设 |
| 「加了互斥锁就万事大吉」 | 锁超时、等待线程耗尽、二次检查缺失都会让锁失效或把应用拖死 |
| 「逻辑过期不会返回脏数据」 | 重建完成前返回的就是旧值，属于最终一致，只是把延迟藏在后台 |
| 「随机 TTL 幅度越大越好」 | 幅度过大会降低命中率、TTL 语义混乱；10%~20% 或至少几分钟即可 |
| 「雪崩只可能是 key 同时过期」 | 缓存层宕机、主从切换、网络分区、集群分片故障都会造成雪崩 |
| 「缓存命中率高就没问题」 | 命中率高但热点集中，仍有击穿与单点风险；要看命中率与热点分布 |

## 10. 连续追问 Q&A

### Q1：用三句话区分穿透、击穿、雪崩。

**答**：穿透是「数据根本不存在」，缓存永远命中不了；击穿是「一个热点 key 刚过期」，瞬时并发回源；雪崩是「大量 key 同时过期」或「缓存层整体不可用」，请求大面积回源。

### Q2：空值缓存和布隆过滤器都能防穿透，怎么选？

**答**：空值缓存实现简单、能兜住重复查询，但占内存且数据新增后要删 key；布隆过滤器内存效率高、能挡随机 ID 攻击，但有误判、需要维护数据同步。常见组合是「布隆做前置拦截 + 空值缓存做兜底」，再加参数校验与限流。

### Q3：布隆过滤器为什么会有误判？为什么不能删除？

**答**：多个元素共享同一批 bit 位，某个不存在的元素查询时，k 个位置可能恰好都被别的元素置 1，于是被误判为「可能存在」；删除时把某位置 0 会影响共享该位的其他元素，所以标准布隆不支持删除。

### Q4：布隆过滤器的参数怎么定？

**答**：先估元素数 n 和目标误判率 p：位数 `m = -1.44 n log2(p)`，哈希个数 `k = (m/n) ln2`。例如 100 万元素、1% 误判约需 958 万位（1.14MiB）、k=7；容量要按峰值预估，不能明显小于实际元素数。

### Q5：互斥锁方案有哪些坑？

**答**：锁超时（业务没做完锁就释放）、死锁（忘了设过期）、误删（A 删了 B 的锁，要 value 校验 + Lua）、等待线程堆积（大量请求阻塞占线程池）、锁粒度过大（全局一把锁）。要二次检查缓存、设置合理等待与降级策略、按 key 加锁。

### Q6：逻辑过期和互斥锁怎么选？

**答**：互斥锁强一致、实现简单，但会让请求等待，高并发下可能打满线程；逻辑过期不阻塞、可用性高，但返回旧值、有一致性延迟，且重建逻辑要幂等。热点极热、可接受短暂陈旧选逻辑过期；一致性要求高、并发不极端选互斥锁。

### Q7：缓存击穿时用分布式锁，锁本身会不会成为瓶颈？

**答**：会。热点 key 过期瞬间，锁的获取/释放、等待重试都集中在一个 key 上，高 QPS 下线程大量阻塞。改进方向：逻辑过期 + 异步重建、本地锁 + 短等待、热点 key 永久缓存 + 主动更新、预热避免过期。

### Q8：随机 TTL 具体怎么加？

**答**：`TTL = base + random(0, base*0.1~0.2)`，并保证同一批预热的 key 落在不同时刻；必须整批失效的场景（如配置缓存）用「版本号 key」或主动失效，而不是靠 TTL。

### Q9：缓存雪崩时，除了随机 TTL 还能做什么？

**答**：多级缓存（本地缓存挡住 Redis 故障）、限流（保护数据库）、熔断降级（快速失败 + 兜底数据）、缓存高可用（哨兵/集群 + 持久化 + 故障转移）、监控告警、预热与容量规划。随机 TTL 只解决「同时过期」这一类雪崩。

### Q10：为什么缓存要设置「空值缓存」而不是直接返回空？

**答**：直接返回空不会写缓存，下一次同样的请求还会查数据库；空值缓存把「不存在」这个结果也缓存下来，把重复穿透变成缓存命中。关键是短 TTL + 数据创建时删除该空值 key。

### Q11：缓存预热怎么做？

**答**：在流量低峰（如凌晨）或服务启动时，把可预测的热数据批量写入 Redis；预热脚本要按 key 规模分批、控制速率，避免压垮数据库和 Redis；预热后还要验证命中率与数据一致性。对突发热点，预热解决不了，要靠热点探测与自动缓存。

### Q12：怎么发现热点 key？

**答**：监控（按 key 维度统计访问量）、代理层统计、Redis 的 `hotkeys`/`--hotkeys` 采样、业务侧埋点；发现后做本地缓存、拆分 key、限流保护。热点 key 是击穿 + 雪崩的高危对象，要重点保护。

### Q13：本地缓存和 Redis 要不要都加？

**答**：取决于访问规模与一致性要求。本地缓存扛极热与 Redis 抖动，但多实例可能不一致、容量受限；Redis 做共享层。常见组合是「本地短 TTL + Redis + 失效广播」，并接受秒级不一致；一致性要求极高时不要加本地缓存，或强制走 Redis。

### Q14：缓存和数据库的一致性怎么保证？和这三件套什么关系？

**答**：常用「先更新数据库，再删除缓存」，配合延迟双删、binlog 订阅异步补偿，本质是最终一致。三件套解决「缓存失效时的数据库保护」，一致性解决「缓存与库数据对不上」，两者要一起设计。

## 11. 一张图总结

```text
请求
  │
  ├─ 参数校验 / 限流（挡明显恶意请求）
  ├─ 布隆过滤器（穿透第一道防线）── 不存在 ──► 直接返回空
  ▼（可能存在）
本地缓存（L1）── 命中 ──► 返回
  │ 未命中
  ▼
Redis（共享缓存）── 命中 ──► 返回（命中率是核心指标）
  │ 未命中
  ├─ 穿透：空值缓存（短 TTL）+ 布隆
  ├─ 击穿：互斥锁（只放一个回源）或逻辑过期（异步重建）
  └─ 雪崩：随机 TTL 预防 + 熔断/限流/降级兜底
                    │
                    ▼
             数据库（最后防线，必须被保护）
```

## 12. 一句话复盘

> 三件套的区别在「谁出了问题」：穿透是数据不存在，用布隆过滤器和空值缓存拦截；击穿是单个热点 key 过期，用互斥锁或逻辑过期保证只有一个重建者；雪崩是大量 key 同时失效或缓存整体挂掉，用随机 TTL 预防、多级缓存缓冲、限流熔断兜底。所有方案的共同目标只有一个：**缓存失效时，数据库不能被瞬间打垮。**

## 13. 自测题（先自己答，再看答案）

**1. 攻击者用 100 万个不存在的 ID 持续请求，属于哪种问题？两种防护手段分别拦在哪一步？**
答案：穿透。布隆过滤器拦在缓存之前（判定「一定不存在」直接返回）；空值缓存拦在第一次查库之后（把空结果缓存短 TTL），后续相同 ID 命中缓存。

**2. 1000 个 key 同时过期和 1 个热点 key 过期，本质区别是什么？**
答案：影响范围与并发度。单个热点 key 过期是「一个 key 的并发回源」（击穿）；大量 key 同时过期是「大量 key 同时回源」（雪崩）。前者靠锁/逻辑过期让一个请求重建，后者必须把过期时间打散并做整体保护。

**3. 布隆过滤器说「不存在」，能不能直接返回？为什么？**
答案：能。布隆没有假阴性，真正存在的元素一定不会被判为不存在；只有「可能存在」可能是误判，需要继续查缓存/数据库。

**4. 互斥锁方案里，为什么拿到锁后还要再查一次缓存？**
答案：二次检查。等锁期间前一个持锁请求可能已把数据写回缓存；再查一次避免重复回源。

**5. 逻辑过期方案为什么能做到请求不阻塞？代价是什么？**
答案：value 中带逻辑过期时间，过期后仍直接返回旧数据，同时由一个线程异步重建缓存并加锁。代价是重建期间数据陈旧，属于最终一致。

**6. 随机 TTL 的抖动幅度为什么不能太大？**
答案：太大会降低缓存命中率、TTL 语义混乱、内存占用波动，且对「必须尽快失效」的数据不友好。通常取 base 的 10%~20% 或至少几分钟。

**7. 如果 Redis 整个集群挂了，随机 TTL 还有用吗？**
答案：没用。随机 TTL 只解决「key 同时过期」；集群整体故障属于另一类雪崩，需要多级缓存、限流熔断降级、缓存高可用与容灾兜底。
