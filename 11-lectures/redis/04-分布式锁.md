## 0. 一句话先讲明白

分布式锁要同时满足五件事：**互斥、不死锁、防误删、可重入（可选）、高可用**。
它的演进史就是一条**缺陷链**：`SETNX` 会死锁 → 加过期时间但不原子 → `SET NX EX` 原子了但会误删 → 唯一 value + Lua 校验防住误删但业务超时会丢锁 → 看门狗续期但客户端停顿仍会丢 → Redlock 多节点防主从丢锁但有时钟/无 fencing 的争议 → **fencing token** 把「锁对不对」的责任移交到存储层，才是最终正确性。
每一步都在解决上一步的问题，又留下一个新问题——这就是面试官想听的主线。

---

## 1. 它解决什么问题：单机锁出了 JVM 就不管用

### 1.1 单机锁的边界

`synchronized`、`ReentrantLock` 的互斥范围是**一个 JVM 进程**。服务一旦多实例部署：

```text
3 个实例同时收到「扣库存 1 件」的请求
实例 A 的锁只能拦住 A 自己的线程
实例 B、C 的线程完全不受影响
→ 库存从 100 被扣成 -2
```

这就是分布式锁要解决的问题：**跨进程的互斥**。

### 1.2 真实场景与量化损失

| 场景 | 不加锁的后果 |
|---|---|
| 库存扣减 | 超卖（库存扣成负数）或少卖（读改写丢失） |
| 定时任务防重 | 3 个实例各跑一遍，一天多执行 2 次，数据重复 |
| 幂等/防重复提交 | 同一请求执行多次，产生重复订单 |
| 选主/单点任务 | 多个节点同时认为自己是主，脑裂 |

**数字化推导一：定时任务重复执行的代价**

```text
3 个实例，定时任务每 5 分钟执行一次
一天执行次数 = 24 × 60 / 5 = 288 次/实例
无锁：3 × 288 = 864 次（其中 576 次是重复执行）
有锁：288 次
若每次任务要扫 100 万条订单、耗时 4 分钟：
  无锁时 3 个实例同时扫同一批数据 → 数据库 CPU 三倍，且可能重复发券
```

### 1.3 一把合格的分布式锁要满足什么

| 要求 | 说明 |
|---|---|
| 互斥 | 同一时刻只有一个客户端能持有锁 |
| 不死锁 | 持有者崩溃后，锁最终能自动释放 |
| 防误删 | A 的锁不能被 B 删掉 |
| 可重入（可选） | 同一客户端可重复获取，避免自己把自己锁死 |
| 阻塞/非阻塞 | 能选择等待或立即失败 |
| 高可用 | 锁服务本身不能是单点，故障时不能出现两个持有者 |
| 性能 | 加锁/释放的开销要远小于业务本身 |

后面整篇文章，就是「为了同时满足这几条，每一代方案补了哪个洞、又漏了哪个洞」。

## 2. 一步步拆开：七代方案的缺陷链

### 2.1 第一代：`SETNX lock 1`

`SETNX`（SET if Not eXists，Redis 2.6 之前就有）在 key 不存在时设置成功、存在时失败：

```bash
redis-cli SETNX lock 1     # 返回 1：抢到
redis-cli SETNX lock 1     # 返回 0：已被占用
```

**解决的问题**：互斥。
**留下的洞**：持有者崩溃或忘记删除，key 永远存在 → **死锁**。

### 2.2 第二代：`SETNX` + `EXPIRE`

```bash
redis-cli SETNX lock 1     # 成功
redis-cli EXPIRE lock 30   # 再设置 30 秒过期
```

**解决的问题**：崩溃后锁能自动过期，不再永久死锁。
**留下的洞**：两个命令**不原子**。如果进程在 `SETNX` 成功之后、`EXPIRE` 执行之前崩溃（或被 kill、机器断电），key 没有过期时间 → 仍然死锁。这个窗口很小，但在生产上会发生。

**被否决方案**：有人用「`SETNX` 失败就 `EXPIRE` 兜底」补丁，逻辑更复杂且仍有竞态。

### 2.3 第三代：`SET key value NX EX 30`（原子）

Redis 2.6.12 起，`SET` 支持 `NX`/`XX`、`EX`/`PX` 选项，一条命令同时完成「不存在才设置 + 设置过期」：

```bash
redis-cli SET lock uuid-a NX EX 30    # 返回 OK：抢到
redis-cli SET lock uuid-b NX EX 30    # 返回 nil：抢不到
```

**解决的问题**：加锁与过期原子化，不再有「设了锁没设过期」的窗口。
**留下的洞 1：业务超时**。锁 30 秒过期，但业务执行了 40 秒 → 第 31 秒锁已释放，另一个客户端拿到锁，**两个客户端同时执行**。
**留下的洞 2：误删**。A 的业务超时、锁过期，B 拿到锁；A 执行完 `DEL lock` 删除的是 **B 的锁**，于是 B 的互斥被破坏，后续请求又能加锁 → 三个客户端同时跑。

### 2.4 第四代：唯一 value + Lua 校验删除

给锁的 value 一个唯一标识（如 `UUID + 线程 ID`），释放时**先比较再删除**，且比较与删除必须原子：

```bash
# 加锁：value 是本次请求的唯一 ID
SET lock uuid-a NX EX 30

# 释放：Lua 脚本内 GET + 比较 + DEL，Redis 单线程执行保证原子
EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock uuid-a
```

**解决的问题**：只有 value 匹配才删除，A 删不掉 B 的锁。
**留下的洞**：业务超时问题还在。锁过期后 B 拿到锁，A 虽然删不掉锁，但 A **仍然在继续执行业务**（写数据库、改库存）——互斥已经被破坏，Lua 只能防「误删」，防不了「过期后继续操作」。

### 2.5 第五代：看门狗（watchdog）续期

思路：业务没执行完之前，后台定时把锁的过期时间延长。

- Redisson 的 `lockWatchdogTimeout` 默认 **30 秒**，续期间隔是它的 **1/3（10 秒）**；
- 只要客户端存活，锁就会一直被续期；客户端崩溃后不再续期，锁在 30 秒后释放；
- 注意：如果显式指定了 `leaseTime`（如 `lock.lock(10, TimeUnit.SECONDS)`），Redisson **不会**启动看门狗，到期就释放。

**解决的问题**：业务耗时不可预测时，锁不会提前过期。
**留下的洞**：续期依赖客户端存活。如果客户端发生长 GC（Stop-The-World 几十秒）、线程被饿死、网络分区导致续期命令没到 Redis，锁仍会过期；而客户端醒来后**以为自己还持有锁**，继续写数据。看门狗能降低概率，不能消除「过期后继续操作」的问题。

### 2.6 第六代：Redlock（多节点）

单节点 Redis 还有一个更根本的问题：**主从架构下 Redis 是异步复制的**。

```text
客户端在 master 上 SET lock 成功
master 还没把这条命令同步到 slave，突然宕机
sentinel 把 slave 提升为新 master —— 新 master 上根本没有这把锁
另一个客户端在新 master 上 SETNX 成功
→ 两个客户端同时持有锁
```

**Redlock 的方案**（Redis 作者 antirez 提出）：准备 N 个**相互独立**的 Redis master（常用 N=5，不共享数据、不组成集群），客户端依次向每个节点加锁（同样的 key、value、TTL）：

- 在**大多数节点**（N/2+1，5 个节点即 3 个）上加锁成功；
- 且整个加锁过程耗时小于锁的 TTL；
- 才算加锁成功，否则向所有节点释放。

**解决的问题**：不再依赖单个 master 的复制，单点故障不会直接导致丢锁。
**留下的争议**：见第 3、5 节——时钟漂移、客户端长时间停顿、以及**没有 fencing token** 时，Redlock 仍无法保证「旧持有者不会在锁过期后写数据」。

### 2.7 第七代：fencing token（最终正确性）

核心思想：**不要相信锁的持有者，让被保护资源自己拒绝过期请求**。

锁服务每次成功加锁时返回一个**单调递增**的 token（编号）。客户端带着 token 去写资源；资源（数据库/存储）记住「已见过的最大 token」，拒绝更小的 token：

```text
客户端 A 拿到 token = 33，随后发生长时间 GC（锁过期）
客户端 B 拿到 token = 34，写入资源，资源记录 last_token = 34
A 醒来，带着 token = 33 写入 → 资源发现 33 < 34，拒绝
```

**解决的问题**：即使锁失效、旧持有者延迟写，资源层也能阻止破坏。**这是唯一不依赖「锁一定正确」的方案**。

### 2.8 其他维度：可重入、公平、阻塞

- **可重入**：Hash 存 `{uuid:threadId -> 重入次数}`，加锁 +1、释放 -1，减到 0 才删 key；Redisson 默认支持。
- **公平/阻塞**：ZK 临时顺序节点天然先来先得；Redis 需自建队列，常用自旋或订阅通知实现等待。

### 2.9 五种实现横向对比

| 实现 | 互斥 | 不死锁 | 防误删 | 主从/容灾 | 性能 | 适用 |
|---|---|---|---|---|---|---|
| Redis `SET NX PX` + Lua | 是 | 靠 TTL | 是 | 主从切换可能丢锁 | 高 | 大多数业务、可容忍极端情况 |
| Redisson（单节点） | 是 | TTL + 看门狗 | 是（Lua） | 同上 | 高 | 业务简单、部署简单 |
| Redlock（多节点） | 是 | TTL | 是 | 多节点容错 | 中 | 强调锁可用性、但仍有争议 |
| ZooKeeper 临时顺序节点 | 是 | 会话断开自动删 | 是（节点唯一） | CP，强一致 | 中低 | 强一致、公平锁 |
| etcd（lease + revision） | 是 | lease 到期 | 是 | CP，Raft | 中 | 强一致 + 天然 fencing（revision） |
| 数据库唯一索引/行锁 | 是 | 事务回滚 | 是 | 依赖 DB | 低 | 低频、简单场景 |

## 3. 完整推导

### 3.1 数字化推导二：锁 TTL 应该设多大

设业务执行耗时：P50 = 20ms，P99 = 200ms，P999 = 800ms。

```text
方案 A：TTL = 1 秒 → 0.1% 请求超过 800ms 仍可能超时；每天 100 万次加锁约 1000 次提前过期
方案 B：TTL = 3 秒 → 是 P999 的 3.75 倍，多数慢请求可覆盖；更长任务靠看门狗续期
方案 C：TTL = 30 秒 + 看门狗 → 正常业务无需续期；崩溃后最多 30 秒释放
```

结论：**TTL 至少取业务 P999 的 2~3 倍**；业务时长不可控时用看门狗，而不是把 TTL 设成几分钟。

### 3.2 数字化推导三：看门狗失效的窗口

Redisson 默认：TTL = 30 秒，每 10 秒续一次。如果客户端发生 45 秒的 Stop-The-World GC：

```text
t=0    加锁成功，TTL 30s
t=10   续期成功，过期时间延到 40s
t=20   GC 开始，客户端完全暂停（续期线程也暂停）
t=40   锁到期，Redis 删除锁
t=45   GC 结束，客户端恢复，但仍以为自己持有锁
       → 另一个客户端在 t=40 之后已拿到锁，两个客户端并发
```

看门狗不是万能的：**它依赖「客户端能按时执行续期」**。GC 停顿、CPU 饥饿、容器 CPU 被限流都可能导致续期失败。

### 3.3 数字化推导四：主从切换的丢锁窗口

```text
t=0.000s  客户端 A 在 master 执行 SET lock NX 成功
t=0.001s  master 尚未把命令复制到 slave（复制延迟约 0.1~1ms）
t=0.002s  master 宕机
t=0.003s  slave 数据里没有这把锁
t=15s     sentinel 完成故障转移，slave 升为新 master
t=15s     客户端 B 向新 master 加锁成功
→ t=0.003 ~ t=15s 之间，A 和 B 都可能认为自己持有锁
```

即使复制延迟只有 1ms，只要宕机正好发生在「写成功、未同步」的窗口内，锁就丢了。这是单节点/主从 Redis 锁的固有限制，不是配置能完全消除的。

### 3.4 数字化推导五：fencing token 如何拒绝陈旧写

| 时刻 | 客户端 A（token=33） | 客户端 B（token=34） | 资源层 last_token |
|---|---|---|---|
| t1 | 拿到锁，token=33 | 等待 | 32 |
| t2 | 发生 40 秒 GC | 锁过期，拿到 token=34 | 32 |
| t3 | 仍在 GC | 写入，token=34 | 34 |
| t4 | 恢复，写入 token=33 | — | 34，拒绝 33 |

关键点：token **单调递增**且由锁服务（etcd revision、ZK zxid 等）保证；资源层做「只接受更大 token」的校验。**锁只负责下发号码，正确性由资源层兜底**。

## 4. 极简模型：3 个客户端、1 把锁、1 个资源

设定：锁 key = `lock:stock`，资源是一行库存记录（初始 100 件）。

**场景一：没有锁**

```text
A/B/C 同时读到库存 100
各自计算 100 - 1 = 99，各自写回 99
→ 卖出去 3 件，库存只减了 1（少卖）
```

**场景二：有锁但会误删（第三代方案）**

```text
t0  A 加锁成功（TTL 3s），开始处理（实际要 5s）
t3  锁过期
t3  B 加锁成功，开始处理
t5  A 处理完，执行 DEL lock → 删掉了 B 的锁
t5  C 加锁成功 → B、C 同时处理
```

**场景三：唯一 value + Lua（第四代）**

```text
t5  A 执行完，Lua 比较 value：锁的 value 是 uuid-b，不是 uuid-a
    → 返回 0，A 删不掉 B 的锁；但 A 对库存的修改已经发生
→ 误删防住了，但 A 在 t3 之后仍然操作了资源（超卖/少卖仍可能）
```

**场景四：fencing token**

```text
A 的 token=7，B 的 token=8
B 先写成功，资源 last_token=8
A 恢复后带 token=7 写 → 被资源拒绝
→ 即使 A 在锁过期后继续执行，也不会破坏数据
```

这个极简模型把整条链讲完整了：**锁解决「同一时刻谁进」，TTL 解决「进程崩了怎么办」，Lua 解决「删错锁」，看门狗解决「业务超时」，Redlock 解决「锁服务单点」，fencing 解决「过期后的陈旧写」。**

## 5. 为什么这样设计：被否决的方案

### 5.1 被否决方案一：只用 `SETNX`，不设过期

**否决理由**：持有者崩溃后锁永远不会释放，所有后续请求被永久阻塞，业务直接不可用。任何锁都必须有「自动释放」的兜底。

### 5.2 被否决方案二：`SETNX` + 单独 `EXPIRE`

**否决理由**：两条命令非原子，中间崩溃就回到了「永不释放」。正确做法是 `SET NX EX` 一条命令原子完成。

### 5.3 被否决方案三：`GET` 后 `DEL` 释放

**否决理由**：`GET` 和 `DEL` 之间可能发生「锁过期 + 另一客户端加锁」，导致删掉别人的锁。必须用 Lua 把「比较 + 删除」变成原子操作，或只允许持有者用唯一 value 删除。

### 5.4 被否决方案四：只加锁不做 fencing

**否决理由**：锁有失效的可能（GC、网络分区、主从丢锁），旧持有者可能在锁过期后继续写资源。只要业务对正确性有严格要求，就必须在资源层用 fencing token 或幂等/版本号校验兜底。

## 6. 关键参数为什么是这个值

### 6.1 锁 TTL：业务 P999 的 2~3 倍

- 太小：业务没执行完锁就释放，出现并发；
- 太大：客户端崩溃后锁释放慢，影响可用性；
- 默认值：Redisson 看门狗 30 秒；显式 `leaseTime` 时按业务定；
- 秒杀/短任务常用 3~10 秒，长任务用看门狗。

### 6.2 看门狗 30 秒、续期 10 秒

- 续期周期取 TTL 的 1/3：即使一次续期失败，还有两次机会；
- TTL 30 秒：客户端崩溃后最多 30 秒自动释放，业务恢复不至于等太久；
- 如果显式设置 `leaseTime`，Redisson 不续期——这是最常见的「锁到期了业务还没完」的原因。

### 6.3 重试与等待：3~5 次，间隔 50~100ms

- 立即失败适合「拿不到就降级」的场景；
- 阻塞等待要设上限（`tryLock(waitTime, leaseTime, unit)`），避免线程无限挂起；
- 0 间隔自旋会把锁竞争变成网络/CPU 压力；建议随机退避，避免惊群。

### 6.4 Redlock 的 N=5、quorum=3

- N 取奇数：5 个节点允许挂 2 个，仍有 3 个（大多数）；
- 有效时间：`validity = TTL - 加锁耗时 - 时钟漂移`；
- 时钟漂移按 TTL 的 1%~5% 预留（保守取 5%），例如 TTL=10s、耗时 100ms、漂移 500ms，有效时间约 9.4s；
- 释放时向所有节点发删除（即使没加成功的节点也要发，避免残留）。

### 6.5 Redlock 节点为什么要独立

Redlock 要求节点之间**没有数据复制、没有共享故障域**。如果直接用 Redis Cluster 或主从集群，节点间存在复制与依赖，就退化成「一个逻辑 Redis」，Redlock 的多数派保证失效。

### 6.6 fencing token 从哪来

- etcd：事务 + revision（全局单调递增）；
- ZooKeeper：顺序节点的 zxid/序号；
- Redis：需要自己维护一个单调递增计数器（`INCR`），但**不要用随机 value**——随机数没有可比性，无法防陈旧写；
- 资源侧：数据库加 `version`/`last_token` 列，`UPDATE ... WHERE token > last_token`，不满足则拒绝。

## 7. 版本演进

### 7.1 Redis

| 版本 | 与分布式锁相关的变化 |
|---|---|
| 2.6.12（2012） | `SET` 支持 `NX`/`XX`、`EX`/`PX` 选项，加锁与过期可以一条命令原子完成，取代 `SETNX + EXPIRE` |
| 2.6 起 | Lua 脚本（`EVAL`）可用，Redis 单线程执行脚本保证「比较 + 删除」原子 |
| 3.0（2015） | Cluster 分片；但分布式锁通常仍部署单点/主从，或 Redlock 使用独立节点 |
| 6.0（2020） | ACL、多线程网络 IO；锁命令本身没有本质变化 |
| 7.0（2022） | Functions（可把 Lua 逻辑封装成函数）、多部分 AOF、ACL 细化 |
| 7.x / 8.x | 锁相关命令语义稳定；生产更多依赖客户端库（Redisson）实现看门狗/可重入 |

### 7.2 客户端与生态

- **Redisson**：Java 生态最常用的 Redis 锁实现，提供可重入 `RLock`、看门狗续期、`tryLock` 等待、RedLock 实现；不同 3.x 小版本在续期细节上有差异，升级要回归验证。
- **Curator**：ZooKeeper 的锁封装（`InterProcessMutex`），临时顺序节点 + watcher，天然公平、可重入。
- **jetcd**：etcd 的 Java 客户端，用 lease 维持会话、用事务 + revision 实现锁与 fencing。

### 7.3 业界争议事件

2016 年前后，分布式系统领域出现过一轮公开争论：一方指出 Redlock 依赖时钟与进程不暂停的假设，且在缺少 fencing token 时无法保证正确性；另一方回应称 Redlock 的设计已考虑有界时钟漂移，并强调它在「效率型锁」场景的可用性。
这场争论没有改变 Redis 的命令语义，但让「**锁不等于正确性，资源层必须能拒绝陈旧写**」成为共识，也推动了 etcd/ZooKeeper 这类带 revision/顺序号的方案在强一致场景的使用。

### 8.2 Redisson 的加锁/续期/释放（Java，预期日志）

```java
import org.redisson.Redisson;
import org.redisson.api.*;
import org.redisson.config.Config;
import java.util.concurrent.TimeUnit;

public class LockDemo {
    public static void main(String[] args) throws Exception {
        Config config = new Config();
        config.useSingleServer().setAddress("redis://127.0.0.1:6379");
        RedissonClient client = Redisson.create(config);
        RLock lock = client.getLock("lock:order:1");
        // 不传 leaseTime：启用看门狗（30s TTL，每 10s 续期）
        if (lock.tryLock(3, TimeUnit.SECONDS)) {
            try {
                System.out.println("拿到锁，开始执行");
                Thread.sleep(45_000);
                System.out.println("业务执行完成");
            } finally {
                if (lock.isHeldByCurrentThread()) lock.unlock();
            }
        } else {
            System.out.println("等待 3 秒仍未拿到锁，降级");
        }
        client.shutdown();
    }
}
```

预期输出（看门狗生效时）：

```text
拿到锁，开始执行
（45 秒后）业务执行完成
```

如果把 `tryLock(3, TimeUnit.SECONDS)` 改成 `lock.lock(10, TimeUnit.SECONDS)`（显式 leaseTime），Redisson 不再续期：10 秒后锁自动释放，45 秒的业务会与后续加锁者并发——这正是「锁超时」的经典事故。

### 8.3 fencing token 在资源层拒绝陈旧写（SQL）

```sql
CREATE TABLE stock (
  id INT PRIMARY KEY,
  amount INT NOT NULL,
  last_token BIGINT NOT NULL DEFAULT 0
);
INSERT INTO stock (id, amount, last_token) VALUES (1, 100, 0);

-- 客户端 B，持有 token = 34
UPDATE stock SET amount = amount - 1, last_token = 34
WHERE id = 1 AND last_token < 34;
-- 预期：1 行受影响

-- 客户端 A 醒来，仍持有陈旧 token = 33
UPDATE stock SET amount = amount - 1, last_token = 33
WHERE id = 1 AND last_token < 33;
-- 预期：0 行受影响（被资源层拒绝）
```

关键：token 必须**单调递增**，且资源层的判断与写入在同一个事务/原子语句里完成。

### 8.4 Redlock 的五节点加锁过程（伪代码，预期结果）

```text
节点：redis-1 ~ redis-5，各自独立；key = lock:order:1，TTL = 10s
1. 记录开始时间 t0
2. 向 5 个节点执行 SET lock:order:1 uuid-a NX PX 10000
   结果：4 个 OK、1 个超时
3. 耗时 80ms，4 > 5/2（=2.5），且 80ms < 10s → 加锁成功
4. 成功数 ≤ 2 或耗时 ≥ TTL → 向所有节点释放，视为失败
```

注意第 3 步的判定：**大多数节点成功 + 耗时小于 TTL**，两个条件缺一不可；单节点成功但总耗时超过 TTL 也要放弃。

## 9. 常见误区

| 错误说法 | 正确说法 |
|---|---|
| 「SETNX 就能实现分布式锁」 | 没有过期会死锁，必须配合 TTL；且 TTL 与加锁要原子 |
| 「加了过期时间就安全了」 | 业务超时后锁会提前释放，仍可能并发；需要看门狗或 fencing |
| 「释放锁直接 DEL 就行」 | 必须比较唯一 value 再删，且用 Lua 保证原子，否则会误删别人的锁 |
| 「看门狗能保证锁一定不丢」 | 客户端长 GC/网络分区时续期失败，锁仍会过期，只是概率降低 |
| 「Redlock 解决了主从丢锁，就万无一失」 | 仍有时钟漂移、客户端停顿、无 fencing 的问题；对正确性要求高的场景要 fencing |
| 「锁过期就代表没人操作资源」 | 旧持有者可能在锁过期后继续写，资源层必须能拒绝 |
| 「分布式锁能替代幂等设计」 | 锁解决并发互斥，重复请求/重试/消息重投仍要靠幂等与唯一约束 |
| 「ZooKeeper/etcd 一定比 Redis 好」 | 它们更强一致但吞吐低、运维重；按业务对正确性和性能的要求选择 |

## 10. 连续追问 Q&A

### Q1：为什么单机锁不够用？

**答**：`synchronized`/`ReentrantLock` 只在单个 JVM 内互斥；多实例部署时，不同 JVM 的线程互不可见，同一时刻仍可能同时修改共享资源。分布式锁是跨进程的互斥机制。

### Q2：`SETNX` 有什么问题？

**答**：只保证「不存在才设置」，没有过期时间。持有者崩溃后 key 永久存在，后续所有请求都拿不到锁，形成死锁。必须配合自动过期。

### Q3：为什么 `SETNX + EXPIRE` 也不行？

**答**：两条命令不是原子的。`SETNX` 成功后、`EXPIRE` 执行前进程崩溃，key 就没有过期时间，仍会死锁。`SET key value NX EX 30` 一条命令同时完成，才是正确做法。

### Q4：为什么锁的 value 要唯一？为什么释放要用 Lua？

**答**：唯一 value 用来标识持有者，避免 A 删除 B 的锁；Lua 把「比较 value + 删除」变成原子操作，防止比较后、删除前锁过期并被别人重新加锁的竞态。

### Q5：业务执行时间超过锁 TTL 怎么办？

**答**：优先用看门狗续期（Redisson 默认 30s，每 10s 续一次）；但客户端 GC/网络分区时续期可能失败，所以还要靠幂等 + fencing token/版本号兜底。不要简单把 TTL 调得很大，否则崩溃后锁释放太慢。

### Q6：Redis 主从切换为什么会丢锁？

**答**：主从是异步复制。客户端在 master 加锁成功后、命令还没同步到 slave 时 master 宕机，slave 升主后没有这把锁，另一个客户端就能加锁成功，出现两个持有者。这是 AP 系统的固有限制。

### Q7：Redlock 的原理是什么？

**答**：准备 N 个独立 Redis 节点，客户端依次加锁；当在大多数节点（N/2+1）加锁成功且总耗时小于 TTL 时，认为加锁成功；否则向所有节点释放。它降低了对单个主节点的依赖。

### Q8：Redlock 有哪三点质疑？

**答**：第一，依赖时钟：TTL 过期和有效性计算都基于时间，NTP 跳变、时钟回拨可能让锁提前失效；第二，进程停顿：客户端长 GC 或网络延迟可能导致它在锁过期后才执行写操作，锁本身无法阻止；第三，缺少 fencing：Redlock 返回的 value 是随机串，不是单调递增编号，资源层无法拒绝陈旧写。因此对正确性要求高的系统，应使用带 fencing 的锁服务或在资源层做版本校验。

### Q9：fencing token 具体怎么落地？

**答**：锁服务每次成功加锁返回单调递增的 token（etcd 的 revision、ZK 的顺序号，或 Redis 自增计数器）；客户端带 token 写资源；资源表加 `last_token` 列，写入语句带 `WHERE token > last_token`，不满足就拒绝。这样即使旧持有者延迟写，也不会破坏数据。

### Q10：Redis 锁和 ZooKeeper/etcd 锁怎么选？

**答**：Redis 性能高、实现简单、适合「效率型」锁（防重复、降低并发），但极端故障下可能丢锁；ZK/etcd 是 CP 系统，强一致、可带 fencing，适合「正确性型」场景（资金、库存），但吞吐低、运维重。也可以两者结合：Redis 做前置快速互斥，数据库唯一约束/版本号做最终兜底。

### Q11：Redis 可重入锁怎么实现？

**答**：用 Hash 结构存 `{客户端唯一标识: 重入次数}`：加锁时如果 field 已存在则次数 +1，否则写入 1；释放时 -1，减到 0 才删除 key。整个判断与增减用 Lua 保证原子。Redisson 的 `RLock` 默认就是可重入实现。

### Q12：锁的等待与重试应该怎么设计？

**答**：优先有限等待（如 `tryLock` 等 3 秒），超时后降级而不是无限阻塞；重试间隔用随机退避（如 50~100ms），避免同一时刻大量客户端同时抢锁（惊群）；高并发场景可以用订阅通知代替轮询。

## 11. 一张图总结

```text
SETNX                 → 互斥，但崩溃死锁
  │ 加过期
SETNX + EXPIRE        → 不死锁，但两条命令非原子
  │ 合成一条
SET NX EX             → 原子，但会误删、业务超时会丢锁
  │ value 唯一 + Lua
SET NX EX + Lua 校验   → 防误删，但过期后旧持有者仍在写
  │ 看门狗续期
Redisson watchdog     → 降低超时丢锁概率，但 GC/网络分区仍失效
  │ 多节点
Redlock（N=5, quorum=3）→ 防单点/主从丢锁，但时钟、停顿、无 fencing
  │ 资源层校验
fencing token         → 最终正确性：资源拒绝陈旧写

锁只负责「尽量互斥」；正确性 = 锁 + 幂等 + 资源层版本号/token 校验。
```

## 12. 一句话复盘

> 分布式锁的演进是一条缺陷链：`SETNX` 解决互斥但会死锁；`SET NX EX` 把加锁与过期变成原子；唯一 value + Lua 防误删；看门狗解决业务超时但依赖客户端存活；Redlock 用多节点降低主从丢锁概率，但仍有时钟漂移、GC 停顿、无 fencing 三个问题。真正可靠的方案是「锁只负责下发单调递增的 token，资源层用版本号拒绝陈旧写」——锁可以失效，数据不能错。

## 13. 自测题（先自己答，再看答案）

**1. 为什么 `SETNX` 单独用会导致死锁？**
答案：它只设置 key，不设置过期时间；持有者崩溃或忘记释放后，key 永久存在，其他客户端永远拿不到锁。必须用 `SET NX EX` 同时设置过期。

**2. `SET NX EX` 解决了什么问题？又留下什么问题？**
答案：解决了加锁与设置过期不原子的问题；留下两个问题：业务执行超过 TTL 时锁会提前释放（并发），以及旧持有者可能删掉新持有者的锁（误删）。

**3. 释放锁为什么必须用 Lua？**
答案：`GET` 比较 value 和 `DEL` 是两步，中间可能锁过期、别人重新加锁，导致删错；Lua 在 Redis 中单线程原子执行，保证比较与删除不可分割。

**4. 看门狗续期一定能避免锁过期吗？**
答案：不能。续期依赖客户端存活且能按时执行命令；长时间 GC、CPU 饥饿、网络分区都会让续期失败，锁仍会过期，旧持有者可能继续写。

**5. Redlock 加锁成功的两个条件是什么？**
答案：在大多数节点（N/2+1）上加锁成功，且整个加锁过程耗时小于锁的 TTL；两个条件缺一不可，否则向所有节点释放并视为失败。

**6. Redlock 的三点质疑分别是什么？**
答案：依赖时钟（时钟回拨/漂移影响有效期）、进程停顿（GC/网络延迟导致锁过期后继续写）、缺少 fencing token（随机 value 无法让资源拒绝陈旧写）。

**7. fencing token 为什么能解决「锁过期后旧持有者写数据」？**
答案：token 单调递增，资源层记录已见的最大 token，写入时要求 token 更大；旧持有者的 token 更小，写入被拒绝，因此即使锁失效也不会破坏数据。
