## 0. 一句话先讲明白

InnoDB 有三套日志，各管一摊：
**redo log（重做日志）** 是物理日志，记录「哪个页的哪些字节改成了什么」，用「先写日志、后刷数据页」的方式（WAL）把随机写变成顺序写，崩溃后能把数据页恢复出来；
**undo log（回滚日志）** 是逻辑日志，记录旧值，负责回滚和 MVCC 的版本链；
**binlog（归档日志）** 是 Server 层的逻辑日志，记录 SQL 或行变更，负责主从复制和数据归档。
redo 与 binlog 必须保持一致，靠的是**两阶段提交**：redo 先 prepare → 写 binlog → redo commit；崩溃恢复时按「binlog 是否完整」决定提交还是回滚。

---

## 1. 痛点背景：一条 UPDATE 到底要写多少地方

### 1.1 正常的一条 UPDATE 背后

```sql
UPDATE t SET balance = 200 WHERE id = 1;
```

看起来一行，实际至少涉及：

1. 在 Buffer Pool 里找到 id=1 所在的页；
2. 把旧值写进 undo log（为了能回滚、也为了 MVCC）；
3. 修改 Buffer Pool 里的页（此时页是「脏页」，和磁盘不一致）；
4. 写 redo log（记录这次页修改）；
5. 事务提交时写 binlog（归档 + 主从复制）；
6. 后台线程择机把脏页刷回磁盘。

问题来了：**第 4 步的 redo 和第 5 步的 binlog 是两个独立系统，如果其中一个写了、另一个没写就断电，会怎样？**

### 1.2 为什么不能每次直接刷数据页

- 数据页是随机的：id=1 可能在第 5 页，id=9999 在第 2000 页，每次 UPDATE 都要随机写一个 16KB 页。
- 机械盘随机写大约 100 次/秒，每次 16KB → `100 × 16KB = 1.6MB/s`，慢得离谱；顺序写能到 200MB/s，相差 **100 倍以上**。
- 而且一次事务可能改多个页，逐个刷盘没法保证「一组修改要么全成功、要么全失败」。

### 1.3 数字推导：redo 为什么能把写入放大压下来

- 一次 UPDATE 改 1 个页：直接刷盘 = 写 16KB。
- 如果只写 redo：页里改了 100B，redo 大约只记录「页号 + 偏移 + 新值」，假设 200B。
- 写入量从 16KB 降到 200B，**约 80 倍**；而且 redo 是追加写（顺序 IO），不是随机写。

这就是 WAL（Write-Ahead Logging，预写日志）的核心：**先顺序写日志（小、快），把随机刷页推迟到后台批量做。**

## 2. 逐步拆解：三种日志、环形结构、两阶段提交

### 2.1 三种日志的分工表

| 维度 | redo log | undo log | binlog |
|---|---|---|---|
| 归属 | InnoDB 引擎层 | InnoDB 引擎层 | Server 层 |
| 类型 | 物理日志（页 + 字节修改） | 逻辑日志（旧值） | 逻辑日志（SQL 或行镜像） |
| 写法 | 环形写、循环覆盖 | 追加写，按事务/回滚段管理 | 追加写，文件滚动 |
| 解决的问题 | 崩溃恢复（已提交不丢） | 回滚 + MVCC | 主从复制、归档、恢复 |
| 刷盘参数 | `innodb_flush_log_at_trx_commit` | 无 | `sync_binlog` |

### 2.2 redo 的环形结构与三个 LSN

redo 不是无限增长的，而是一组固定大小的文件循环使用（5.7 叫 `ib_logfile0/1`，8.0 改成 `#innodb_redo` 目录下多个文件）：

```
       checkpoint pos（可覆盖起点）
            ↓
  ┌───────────────────────────────┐
  │ 已经刷过盘的旧日志（可覆盖）    │  ← 环形
  │ ─────────────────────────────  │
  │ 还没刷盘的日志（不可覆盖）      │
  │                         ↑      │
  └─────────────────────────│──────┘
                       write pos（写入位置）
```

三个关键 LSN（Log Sequence Number，日志序列号，单调递增的字节偏移）：

| LSN | 含义 |
|---|---|
| `log_sys->lsn` | 已经写入 redo 的总量（写到哪了） |
| `flushed_to_disk_lsn` | 已经 fsync 落盘的位置 |
| `checkpoint_lsn` | 对应脏页已经刷盘、可以覆盖的起点 |

**写满了会怎样**：`write pos` 追上 `checkpoint pos` 时，必须推进 checkpoint（把对应脏页刷盘）。如果刷盘速度跟不上写入，写入会**阻塞等待**——所以 redo 太小会导致「日志写满卡业务」。

**数字感受**：8.0 的 `innodb_redo_log_capacity` 默认 100MB；一个简单事务的 redo 约几百字节，能装几十万个事务。5.7 默认 `innodb_log_file_size = 48MB`、2 个文件，共 96MB。

### 2.3 WAL 的完整链路

```
事务提交
  → 写 redo 到 log buffer（内存）
  → 按 innodb_flush_log_at_trx_commit 策略 write/fsync 到 redo 文件
  → 返回客户端「提交成功」
  → 后台线程（page cleaner）择机把脏页刷盘
  → checkpoint 推进，旧 redo 可覆盖
```

### 2.4 undo 与 MVCC 的关系

- undo log 记录旧值，事务回滚时反向执行；
- 同时，聚簇索引行上的 `DB_ROLL_PTR` 指向 undo 中的旧版本，形成版本链，供 MVCC 使用；
- `insert undo` 提交后即可删除，`update undo` 要等 purge 线程确认没有快照需要它。

（版本链与 ReadView 的细节见 [MVCC 与 ReadView](02-MVCC与ReadView.md)。）

### 2.5 binlog 的三种格式

| 格式 | 记录什么 | 优点 | 缺点 |
|---|---|---|---|
| STATEMENT | SQL 原文 | 日志小 | `NOW()`、`RAND()`、`UUID()`、无 `ORDER BY` 的 `LIMIT` 会导致主从不一致 |
| ROW（8.0 默认） | 每行的 before/after 镜像 | 最准确、可回放 | 批量更新日志放大 |
| MIXED | 自动切换 | 折中 | 不确定性仍在，排查困难 |

**数字化**：`UPDATE t SET status = 1` 影响 10 万行，ROW 格式下每行记录约 200B（before + after + 元信息），binlog 大约 `10 万 × 200B = 20MB`；STATEMENT 格式只有一条 SQL（几百字节）。这是「批量任务要控制批大小」的重要原因之一。

### 2.6 两阶段提交的完整时序

```
        InnoDB（redo）                    Server（binlog）
时间轴
  │
  ├─ ① 写 redo，标记 prepare          （记录 XID）
  │      ↓ fsync（按双一参数）
  │
  ├─ ②                               写 binlog（事件 + XID）
  │                                      ↓ fsync（sync_binlog）
  │
  ├─ ③ redo 标记 commit
  │
  └─ ④ 返回客户端「提交成功」
```

关键点：**binlog 写完之前，redo 一直是 prepare 状态**。崩溃恢复时，InnoDB 重放 redo 到 prepare 事务，就去 binlog 里查这个 XID：

- binlog 里**有完整事务**（提交标记在）→ 提交；
- binlog 里**没有或不完整** → 回滚。

## 3. 完整推导：崩溃恢复的两条规则

### 3.1 把崩溃点分成四类

一个事务从开始到提交，中间有若干个可能崩溃的点：

| 崩溃时机 | redo 状态 | binlog 状态 | 恢复动作 |
|---|---|---|---|
| 写 redo 之前 | 无 | 无 | 回滚（相当于没发生过） |
| redo 写完（prepare）后、binlog 写完前 | prepare | 无/不完整 | **回滚** |
| binlog 写完（含提交标记）后、redo commit 前 | prepare | 完整 | **提交**（补 commit） |
| redo commit 之后 | commit | 完整 | 正常提交 |

### 3.2 两条规则（背下来）

> **规则一**：redo 里是 prepare，且 binlog 里存在对应的完整事务 → **提交**。
> **规则二**：redo 里是 prepare，但 binlog 里不存在或不完整 → **回滚**。

### 3.3 为什么规则必须这样定

核心判据是「binlog 是否完整」，因为：

- binlog 决定从库和备份里有没有这条数据；如果 binlog 完整而主库回滚，主从就不一致；
- 如果 binlog 不完整而主库提交，从库永远缺这条数据；
- 所以「binlog 完整」就必须提交，「binlog 不完整」就必须回滚。redo 只是执行者，binlog 是裁决者。

### 3.4 恢复时的重放过程

1. 从 redo 文件里找到 checkpoint LSN，从那里开始重放；
2. 重放每个页修改时比较页头的 page LSN：页里已经包含的修改跳过（保证幂等）；
3. 重放完成后，用 undo 回滚所有未提交事务；
4. 对 prepare 事务执行上面的两条规则。

## 4. 极简模型：一行数据、一次事务、一个崩溃点

### 4.1 设定

表 `t` 只有一行：`id = 1, balance = 0`。

事务 T1（XID = 100）：`UPDATE t SET balance = 100 WHERE id = 1`。

### 4.2 正常提交的内存/磁盘状态

```
① redo（prepare）：页 5 偏移 100，balance 0 → 100；XID = 100
② binlog：Table_map + Update_rows(before 0, after 100) + XID 事件
③ redo（commit）
```

### 4.3 崩溃点 A：binlog 刚写完、redo commit 还没写

重启后：

- redo 里 T1 是 prepare；
- binlog 里 T1 完整（有 XID 事件）；
- 按规则一：**提交**（补写 redo commit 标记），余额 100。

### 4.4 崩溃点 B：redo prepare 写完、binlog 还没写

重启后：

- redo 里 T1 是 prepare；
- binlog 里查不到 XID = 100；
- 按规则二：**回滚**（用 undo 恢复旧值），余额 0。

**两个崩溃点只差几毫秒，但结果分别是「提交」和「回滚」——这就是两阶段提交存在的意义。**

### 4.5 再小一号：只考虑 redo

如果系统里根本没有 binlog（比如纯单机、无复制需求），那崩溃恢复只需要：redo 里 commit 的提交、prepare 的用 undo 回滚。binlog 的存在，让 prepare 状态多了一层「查 binlog」的裁决。

## 5. 为什么这样设计：四个被否决的方案

### 5.1 否决方案一：只要 redo，不要 binlog

- redo 是物理日志，只记录「页怎么改」，**没法给从库重放**（从库的页号/页结构与主库不同，物理日志不可移植）；
- 也没法做时间点恢复（PITR）和归档；
- 所以 binlog 必须存在。

### 5.2 否决方案二：只要 binlog，不要 redo

- binlog 是逻辑日志，只记录「改了什么」，崩溃后要重新执行 SQL/行事件才能恢复数据页，速度和正确性都不如物理重放；
- binlog 在 Server 层，InnoDB 崩溃恢复太晚才拿到它，无法保证「已提交不丢」；
- 所以 redo 必须存在。

### 5.3 否决方案三：两个日志各写各的，不做两阶段提交

这就是文章开头的问题：会出现「主库有、从库没有」或「从库有、主库回滚」的不一致。两阶段提交是**用 prepare 状态做标记，让崩溃恢复有据可依**。

### 5.4 否决方案四：每条事务单独 fsync，不做组提交

单事务单 fsync 的开销：假设磁盘 fsync 1ms，单线程提交 QPS 上限约 1000。组提交把 N 个事务合并成一次 fsync，N=20 时理论 QPS 提升 20 倍。所以 binlog 组提交是「`sync_binlog=1` 还能跑到几万 QPS」的关键。

## 6. 关键参数为什么是这个值

### 6.1 `innodb_flush_log_at_trx_commit` 三档

| 值 | 提交时行为 | 崩溃丢数据 | 性能 |
|---|---|---|---|
| 0 | 每秒后台刷 redo，提交不刷 | MySQL/OS 崩溃丢约 1 秒 | 最高 |
| 1（默认） | 每次提交 fsync | 不丢 | 最低，金融级必选 |
| 2 | 提交时 write 到 OS cache，每秒 fsync | MySQL 进程崩溃不丢；OS/断电丢约 1 秒 | 折中 |

**为什么默认是 1**：数据库的底线是「提交成功 = 数据持久化」，默认必须保证这一点；性能不足用组提交、SSD、批量事务解决，而不是降低默认安全性。

### 6.2 `sync_binlog`

- 0：由操作系统决定何时刷盘，最快，可能丢；
- 1：每次提交 fsync binlog，最安全；
- N：每 N 次提交 fsync 一次。

金融级配置是「双一」：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`。互联网很多业务用 `sync_binlog=0/100` 换吞吐，代价是可能丢少量 binlog。

### 6.3 redo 容量多大合适（数字推导）

- 8.0 默认 `innodb_redo_log_capacity = 100MB`；
- redo 太小：写满就阻塞刷脏页，出现「日志写满卡业务」；
- redo 太大：崩溃恢复要重放更多日志，恢复时间变长；
- 经验：以「能容纳高峰期 1~2 分钟的写入量」为目标。假设峰值 5 万 TPS、每事务 redo 500B → 每秒 25MB，2 分钟需要 `25MB × 120 = 3GB`（所以大流量实例会把 redo 调到 GB 级）。

### 6.4 `innodb_log_buffer_size` 为什么默认 16MB

事务的 redo 先写 log buffer，提交时才落盘。缓冲太小会频繁触发写盘；太大浪费内存。16MB 能装下大量小事务的 redo，又不至于占用过多内存。

## 7. 版本演进：MySQL 5.6 / 5.7 / 8.0

| 版本 | 日志相关变化 |
|---|---|
| MySQL 5.6 | binlog 组提交优化（三阶段）；GTID 引入（5.6.5）；redo 仍是 `ib_logfile` |
| MySQL 5.7 | 组提交进一步优化；半同步复制改进；默认 `binlog_format` 逐渐向 ROW 靠拢 |
| MySQL 8.0 | **redo 重构**：去掉 `ib_logfile`，改 `#innodb_redo` 目录 + `innodb_redo_log_capacity`；默认 `binlog_format=ROW`；binlog 默认开启（8.0 起 `log_bin` 默认 ON）；XA 改进 |

几个版本坑：
- 5.7 之前 `innodb_log_file_size` 改大小要停机；8.0 的 `innodb_redo_log_capacity` 支持在线调整；
- 8.0 默认开启 binlog，很多本地开发机器会因此产生大量 binlog 占空间；
- GTID 开启后，`SHOW MASTER STATUS` 里会出现 `Executed_Gtid_Set`。

## 9. 常见误区

| 错误说法 | 正确说法 |
|---|---|
| 「binlog 是 InnoDB 的日志」 | binlog 在 Server 层，任何存储引擎都能用 |
| 「redo 是逻辑日志」 | redo 是物理日志（页 + 字节修改），undo 才是逻辑日志 |
| 「redo 写满就覆盖最旧的」 | 未刷盘的部分不能覆盖，会推进 checkpoint，推不动就阻塞 |
| 「两阶段提交就是分布式事务的 2PC」 | 这里指 redo 与 binlog 的一致性提交，机制类似但对象不同 |
| 「有了 binlog 就不需要 redo」 | binlog 是逻辑日志，崩溃恢复要靠 redo 的物理重放 |
| 「`sync_binlog=1` 性能一定很差」 | 有组提交，多事务合并 fsync |
| 「半同步复制就是强一致」 | 超时会退化为异步，只保证至少一个从库收到 |
| 「`innodb_flush_log_at_trx_commit=2` 绝对不丢」 | MySQL 进程崩溃不丢，机器断电丢约 1 秒 |

## 10. 连续追问 Q&A

### Q1：为什么 redo 是「物理日志」，binlog 是「逻辑日志」？

redo 记录的是「某个页的某个偏移改成了什么」，物理到可以脱离 SQL 语义重放；binlog 记录的是 SQL 或行变更（逻辑操作），需要知道表结构才能重放。物理日志恢复快，逻辑日志可移植（能发到从库）。

### Q2：redo log 和 buffer pool 是什么关系？

UPDATE 先改 Buffer Pool 里的页（变脏页），同时把这次修改写进 redo。redo 保证「脏页还没刷盘就崩溃也能恢复」；Buffer Pool 是内存缓存，redo 是内存数据的保险。

### Q3：checkpoint 是什么？

checkpoint 是「哪些脏页已经刷盘、对应 redo 可以覆盖」的位置标记。checkpoint LSN 之前的 redo 安全可覆盖；之后的部分必须保留。checkpoint 推进依赖刷脏页。

### Q4：LSN 是什么？为什么数据页里也存 LSN？

LSN 是日志的字节偏移，单调递增。数据页头里存 page LSN（这页最后一次修改对应的日志位置），恢复重放时比较 page LSN 和 redo 的 LSN，已经包含的修改跳过，保证重放幂等。

### Q5：两阶段提交到底分哪两个阶段？

01 阶段是 redo 的 prepare；02 阶段是 redo 的 commit。中间夹着写 binlog。崩溃时 prepare 状态 + binlog 完整 → 提交；prepare + binlog 不完整 → 回滚。

### Q6：如果不做两阶段提交，最坏会怎样？

主库 redo 提交了但 binlog 没写：主库有数据、从库没有、备份也没有，主从永久不一致；或者 binlog 写了但 redo 没提交：从库有、主库回滚后没有。

### Q7：组提交优化的是哪个环节？

binlog 的 fsync。三阶段：flush（多个事务的 binlog 写文件）、sync（一次 fsync）、commit（引擎提交）。多个事务共享一次 fsync，把 QPS 从千级提升到万级。

### Q8：binlog 三种格式怎么选？

一致性优先选 ROW（8.0 默认，CDC 工具也只支持 ROW）；日志体积敏感且 SQL 确定性强可用 STATEMENT；MIXED 是折中，但排查困难。生产基本 ROW。

### Q9：主从复制的流程？

从库 IO 线程连主库 dump 线程，拉取 binlog 写 relay log；从库 SQL 线程重放 relay log。GTID 模式下用事务 ID 代替 file+position。

### Q10：半同步和异步的区别？

异步：主库提交即返回，不等从库，主库宕机可能丢；半同步：至少一个从库 ACK 才返回（AFTER_SYNC 更安全），但超时会退化为异步，不是强一致。

### Q11：undo log 什么时候可以删？

`insert undo` 提交后即可删；`update undo` 要等 purge 确认没有 ReadView 需要它。长事务会阻塞 purge。

### Q12：为什么 binlog 不能用来做崩溃恢复？

binlog 是逻辑日志，重放需要重新执行变更，且不保证页级一致；而且崩溃时最后的事务可能只写了一半 binlog。崩溃恢复的「快、准」必须靠 redo 的物理重放，binlog 只用于复制和归档。

### Q13：`innodb_flush_log_at_trx_commit=1` 和 `sync_binlog=1` 之外，还有什么影响持久化？

操作系统缓存、磁盘写缓存（RAID 卡 BBU）、文件系统 barrier 等都会影响；数据库层只能保证「调用 fsync 成功」，硬件层要配合。

## 11. 一张图总结

```
事务提交：
  ┌─────────────────────────────── InnoDB ───────────────────────────────┐
  │ ① 改 Buffer Pool 页（脏页）                                           │
  │ ② 旧值写 undo（回滚 + MVCC）                                          │
  │ ③ 写 redo（prepare，XID）──► fsync ──► redo 文件（环形）             │
  └──────────────────────────────────┬───────────────────────────────────┘
                                     │
  ┌───────────────────── Server ─────▼───────────────────────────────────┐
  │ ④ 写 binlog（ROW/STATEMENT）──► fsync ──► binlog 文件（追加滚动）    │
  └──────────────────────────────────┬───────────────────────────────────┘
                                     │
  ┌──────────────────────────────────▼───────────────────────────────────┐
  │ ⑤ redo 标记 commit ──► 返回客户端成功                                  │
  │ ⑥ 后台刷脏页 → checkpoint 推进 → 旧 redo 可覆盖                       │
  └──────────────────────────────────────────────────────────────────────┘

崩溃恢复：
  从 checkpoint 重放 redo → 未提交用 undo 回滚
  → prepare 事务：binlog 完整则提交，否则回滚
```

## 12. 一句话复盘

> redo 是物理日志、环形写、用三个 LSN 管理覆盖范围，保证「已提交不丢」；undo 记录旧值，兼做回滚和 MVCC；binlog 是 Server 层逻辑日志，负责复制和归档。两者靠两阶段提交绑定：prepare → binlog → commit，崩溃时以 binlog 是否完整裁决提交还是回滚。

## 13. 自测题（先自己答，再看答案）

**1. 崩溃时 redo 里 T 是 prepare，binlog 里 T 完整，恢复后 T 提交还是回滚？**
答案：提交。规则一：binlog 完整说明从库/备份会包含它，主库必须提交，否则主从不一致。

**2. 为什么 redo 写满会阻塞业务？**
答案：write pos 追上 checkpoint pos 时无法继续写，必须先推进 checkpoint（刷脏页）；刷盘速度跟不上写入速度，写入就阻塞。

**3. `innodb_flush_log_at_trx_commit = 2` 在什么情况下会丢数据？**
答案：MySQL 进程崩溃不丢（数据已 write 到 OS cache），但操作系统崩溃/机器断电会丢约 1 秒（还没 fsync 到磁盘）。

**4. 组提交把什么合并了？**
答案：把多个事务的 binlog flush/sync/commit 合并，尤其是一次 fsync 覆盖多个事务，从而在 `sync_binlog=1` 下仍保持较高吞吐。

**5. binlog 为什么不能替代 redo 做崩溃恢复？**
答案：binlog 是逻辑日志，需要重放 SQL/行事件，恢复慢且不保证页级一致；redo 是物理重放，可以精确恢复页。二者用途不同。
