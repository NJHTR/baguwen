# B+ 树索引：为什么不用 B 树、哈希和跳表？

> 精讲层级：从「零基础能看懂」到「页结构级」，每个名词都拆开
> 阅读时间：约 35 分钟

## 0. 一句话先讲明白

索引就是**排好序、按页组织的一张目录**。InnoDB 的目录是一棵 B+ 树：非叶子节点只存「键 + 子页号」，叶子节点按主键顺序存数据并用链表串起来。
一个 16KB 的页能装上千个键，所以只要三层树，就能放下两千多万行数据；查一行只需要从根往下走三层，也就是 3 次磁盘 IO（根页常驻内存时更少）。
B 树、哈希、跳表都能做索引，但它们分别败在「页利用率」「范围查询」「磁盘局部性」上。

---

## 1. 痛点背景：没有索引时，查一行到底多慢

先不看任何索引术语，只看一个朴素的问题：一张 2000 万行的订单表，执行 `SELECT * FROM t_order WHERE id = 12345678`，数据库怎么找？

### 1.1 全表扫描的代价

- 假设每行 1KB，2000 万行就是 `2000 万 × 1KB = 20GB` 数据。
- InnoDB 按页读取，一页 16KB，那么一共 `20GB / 16KB = 131 万` 个页。
- 全表扫描要把这 131 万个页从头读到尾，即使磁盘顺序读 200MB/s，也要 `20GB / 200MB/s = 100 秒`。

### 1.2 索引要解决的两个问题

| 问题 | 全表扫描 | 有索引 |
|---|---|---|
| 找一行要碰多少数据 | 131 万个页 | 3 个页（根、中间、叶子） |
| 复杂度 | O(n) | O(log n) |
| 2000 万行的实际耗时 | 几十秒到几分钟 | 毫秒级 |

### 1.3 为什么不能把整表放进内存

20GB 数据比一台普通数据库服务器的可用内存大得多，而且索引只占数据的很小一部分（通常 5%~10%），把「目录」放内存、把「数据」放磁盘，才是性价比最高的方案。索引的本质，就是**用很小的内存，换掉绝大部分磁盘 IO**。

## 2. 逐步拆解：一个 16KB 页里到底有什么

### 2.1 为什么按「页」读写，而不是按「行」

- 磁盘和文件系统的最小读写单位是块（常见 4KB），一次读 1 个字节和读 4KB 的代价几乎一样。
- 所以数据库不会「读一行」，而是**一次读一整页**，把相邻的行顺带读进来。
- InnoDB 页大小默认 16KB：4KB 的 4 倍，既不会一次读太少（浪费 IO 次数），也不会一次读太多（内存装不下）。

### 2.2 页的七段结构（逐字段）

一个 16KB 的页（`innodb_page_size = 16384`）从前往后是：

| 段 | 大小 | 里面有什么 |
|---|---|---|
| File Header（文件头） | 38B | 页号、上一页/下一页指针、页类型、LSN、校验和 |
| Page Header（页头） | 56B | 槽位数、堆顶位置、记录数、**PAGE_LEVEL（树高）**、索引 ID、段指针 |
| Infimum + Supremum | 26B | 两条伪记录，表示「最小值」和「最大值」，方便页内定位 |
| User Records | 变长 | 真正的行记录（或非叶子的索引项） |
| Free Space | 变长 | 还没分配的空间 |
| Page Directory | 变长 | 稀疏槽位目录，2B/槽，每 6 条记录一个槽 |
| File Trailer | 8B | 旧校验和（4B）+ LSN 低 32 位（4B），用于检测页损坏 |

**固定开销算一遍**：`38 + 56 + 26 + 8 = 128 字节`。16KB = 16384B，去掉 128B 的头尾，还剩 16256B 左右可以放记录（Page Directory 和 Free Space 是动态的，从里面再分）。

### 2.3 行记录（COMPACT / DYNAMIC）里有什么

页里的「User Records」不是干净的列数据，每行都带额外信息：

| 部分 | 大小 | 作用 |
|---|---|---|
| 变长字段长度列表 | 按列数变长 | 记录 varchar 等变长列的实际长度 |
| NULL 位图 | 按列数变长 | 哪些列是 NULL |
| 记录头 | 5B | delete_mask、min_rec_mask、n_owned、heap_no、record_type、next_record |
| DB_TRX_ID | 6B | 最后修改这行的事务 ID（MVCC 用） |
| DB_ROLL_PTR | 7B | 指向 undo log 里的旧版本（回滚/MVCC 用） |
| 主键 / DB_ROW_ID | 8B 或 6B | 聚簇索引的键 |

于是**每行至少有 `5 + 6 + 7 + 8 = 26 字节`的隐藏开销**（不含列数据本身）。

### 2.4 非叶子节点存的是什么

叶子节点存整行；非叶子节点（也叫「内节点」）只存两样东西：

```
[ 键（主键值，8B） ][ 子页号（4B） ]
```

再加上 5B 的记录头，一条非叶子项大约 `8 + 4 + 5 = 17B`。键越短，一个页能放的项越多，这就是「主键用 bigint 而不是长字符串」的最直接理由。

### 2.5 页内怎么找到某一项

页里有几千条记录，不能从头扫。InnoDB 用 **Page Directory（页目录）**：每 6 条记录编成一组，组内最大的那条记录的位置记成一个「槽」，槽只占 2B。

查找时：
1. 在槽数组上做二分（槽本身有序）；
2. 定位到组后，在组内最多 6 条记录里顺着 `next_record` 指针顺序比较。

一个 16000B 的页按每行 1KB 算有 15 行，10 组左右；换成一页几千条非叶子项时，页目录也只要几百到两千个槽，二分 10 次左右就定位完成——这就是「页内查找几乎免费」的原因。

## 3. 完整推导：三层 B+ 树到底能存多少行

这是最容易被面试官当场让算的一道题，一步步来。

### 3.1 一个非叶子页能放多少个键

- 页 16KB，去掉头尾 128B 和页目录/空闲空间，按 15/16 的填充率可用约 `15360B`。
- 每条非叶子项 17B（键 8 + 页号 4 + 头 5）。
- 可得：`15360 / 17 ≈ 903` 个键，也就是**一个非叶子页能指向 903 个子页**。

（很多资料按 14B 估算得到 1170，差别来自是否把记录头算进去。两个数量级一致，下面的结论用 903，结论不变。）

### 3.2 一个叶子页能放多少行

叶子页可用空间同样约 15360B，取决于行大小（行含 26B 隐藏开销）：

| 行大小（含隐藏开销） | 每页行数（≈15360 / 行大小） |
|---|---|
| 1KB | 15 行 |
| 200B | 76 行 |
| 100B | 153 行 |

### 3.3 三层树的总行数

三层 = 根页 + 中间层 + 叶子层。中间层有 `903` 个页，每个中间页指向 903 个叶子页，所以叶子页总数约 `903 × 903 = 81.5 万` 个。

| 行大小 | 叶子页数 | 每页行数 | 总行数 |
|---|---|---|---|
| 1KB | 81.5 万 | 15 | 约 1223 万 |
| 200B | 81.5 万 | 76 | 约 6197 万 |
| 100B | 81.5 万 | 153 | 约 1.25 亿 |

这就是「三层 B+ 树能存两千万行」的来源：**行越大，能存的行越少；主键越短、行越窄，同样三层能装越多。**

### 3.4 为什么树高决定了查询的磁盘 IO 次数

- 根页几乎永远在 Buffer Pool（缓冲池）里，不产生磁盘 IO；
- 第二次往下读一个中间页，第三次读一个叶子页；
- 所以三层树查一行 = 2~3 次磁盘 IO；四层树就多一次。
- 一次 SSD 随机读约 0.1ms，一次内存访问约 100ns，两者差 1000 倍——**多一层树，代价不是「多一点点」，而是「慢一个量级」**。

### 3.5 超过三层会怎样

数据量涨到四层后，每查一行多一次随机 IO，QPS 会明显下降；同时索引维护、DDL、备份成本都随数据量线性增长。所以「单表 2000 万」不是一个拍脑袋的数字，而是「B+ 树即将从三层变四层」的经验警戒线。

## 4. 极简模型：只有两行数据的索引树

把规模缩到最小，先理解形状，再放大。

### 4.1 两行数据的聚簇索引

假设表只有两行：`id = 1` 和 `id = 2`，每行很小。

```
根页（叶子页，同时也是根）
┌─────────────────────────┐
│ Infimum                 │
│ (1, 张三)  → next_record│
│ (2, 李四)  → next_record│
│ Supremum                │
│ Page Directory: 槽 → (2)│
└─────────────────────────┘
```

此时树高只有 1 层，根就是叶子，查询一次页内二分即可。

### 4.2 插入第三条、触发页分裂

假设一个页最多放 3 条记录（把 16KB 缩小成「3 条」的模型页）：

```
插入前：[1, 3, 5] 已满
插入 2：
  新页 A: [1, 2]
  新页 B: [3, 5]
  父页（新的根）: [键 3 → 页 B]
```

要点：
- **中间插入**会触发页分裂：拆成两个页，并把中间键上提到父页；
- **顺序插入**（自增主键）永远追加在最右边，几乎不分裂；
- 这就是「为什么自增主键比 UUID 好」——不是玄学，是页分裂。

### 4.3 把这个模型放大到三层

```
               根页（1 页）
         /          |          \
   中间页(903)   中间页      中间页
     /  |  \      / | \       / | \
  叶子 叶子 叶子 ...（共 81.5 万叶子页）
  每叶 15 行（1KB 行）
```

## 5. 为什么这样设计：四个被否决的方案

### 5.1 否决方案一：哈希索引

| 维度 | 哈希 | B+ 树 |
|---|---|---|
| 等值查询 | O(1)，很快 | O(log n) |
| 范围查询 `id > 100` | 不支持（哈希后无序） | 叶子链表顺序扫 |
| 排序 `ORDER BY id` | 不支持 | 天然有序 |
| 最左前缀 `(a,b,c)` | 不支持 | 支持 |

哈希的致命伤是**只支持等值查询**。MySQL 里哈希只出现在两个角落：MEMORY 引擎的哈希索引、InnoDB 的自适应哈希索引（AHI，对热点页做的缓存加速），主索引不会用哈希。

### 5.2 否决方案二：二叉搜索树 / 红黑树

- 每个节点只存 1 个键，n = 2000 万时树高约 `log2(2000万) ≈ 24 层`。
- 24 层意味着最多 24 次随机磁盘 IO，而 B+ 树只要 3 次。
- 红黑树虽然能自平衡，但「节点数」没变，磁盘 IO 次数也没变。它是内存结构的最优解，不是磁盘结构的最优解。

### 5.3 否决方案三：B 树

B 树和 B+ 树的区别：

| 对比 | B 树 | B+ 树 |
|---|---|---|
| 非叶子是否存数据 | 存 | 不存（只存键 + 页号） |
| 一个页能放的键数 | 少（数据占了空间） | 多（扇出大） |
| 树高 | 更高 | 更矮 |
| 范围查询 | 中序遍历，需要回溯 | 叶子链表直扫 |
| 查询稳定性 | 有时在非叶子就命中，有时要到叶子，不稳定 | 一定到叶子，IO 次数稳定 |

B 树被否决的核心是**扇出小 + 范围查询要回溯**。

### 5.4 否决方案四：跳表

Redis 的 zset 用跳表，为什么 MySQL 不用？

- 跳表是**内存结构**，没有「页」的概念，每个节点单独分配，无法利用磁盘的块读和局部性；
- 跳表查询是 O(log n) 次指针跳转，每次都可能是一次随机内存访问，放到磁盘上就是多次随机 IO；
- B+ 树把上千个键塞进一个 16KB 页，一次 IO 拿一批，才适合磁盘。

**结论：数据结构没有优劣，只有和存储介质是否匹配。**

## 6. 关键参数为什么是这个值

### 6.1 页大小为什么是 16KB

- 文件系统块通常 4KB，页取 4KB 的整数倍，避免「读一页要跨多个块」；
- 页太小：同样数据要读更多页，IO 次数上升；
- 页太大：一次读入的数据用不完，Buffer Pool 能缓存的页数变少，写放大严重；
- 16KB 是「扇出」和「内存利用率」的折中。MySQL 5.7+ 也允许改成 4/8/32/64KB（`innodb_page_size`），但绝大多数生产用默认 16KB。

### 6.2 填充率为什么留 1/16

页不会写满，要留空间给后续插入，减少频繁页分裂。InnoDB 的页填充率通常控制在 15/16 左右（顺序插入可达 15/16，随机插入更低）。

### 6.3 主键为什么推荐 bigint 自增

同样三层树，主键长度直接决定扇出：

| 主键类型 | 键长度 | 非叶子项大小 | 扇出（≈15360/项） | 三层总行数（行 1KB） |
|---|---|---|---|---|
| bigint 自增 | 8B | 17B | 903 | 约 1223 万 |
| char(36) UUID | 36B | 45B | 341 | 约 174 万 |

**同样三层，UUID 主键只能存约 1/7 的数据量**，而且随机 UUID 还会触发页分裂。所以「自增 bigint 主键」不是风格问题，是容量问题。

### 6.4 索引列区分度多少才值得建

区分度 = `不同值个数 / 总行数`（也就是 `cardinality / rows`）。经验上低于 10% 的列单独建索引收益很低（比如性别、状态只有几种值），因为优化器可能算完发现「回表比全表扫还贵」。

## 7. 版本演进：从 5.6 到 8.0

| 版本 | 与索引相关的关键变化 |
|---|---|
| MySQL 5.6 | 引入**索引下推（ICP）**，减少回表；`innodb_page_size` 支持 4/8/16KB |
| MySQL 5.7 | 页大小增加 32KB/64KB（5.7.8）；默认行格式改为 DYNAMIC；在线 DDL 增强 |
| MySQL 8.0 | 真正支持**降序索引**（5.7 声明了但实际忽略）；不可见索引（`INVISIBLE`）用于安全删索引；直方图统计；优化器成本模型更细 |

几个容易踩的版本坑：
- 5.7 的 `DESC` 索引只是语法存在，实际还是升序；
- 8.0 才默认开启 `innodb_stats_persistent`（统计信息持久化）；
- 8.0 的 `information_schema.INNODB_TABLES` 里能看到 `PAGE_SIZE` 字段。

## 8. 亲手验证：建表、看页、看执行计划

> 环境说明：以下命令在 MySQL 8.0 上执行，5.7 的个别视图字段名不同。没有本机实例时按「预期输出」理解。

### 8.1 建表并插入数据

```sql
CREATE TABLE t_btree (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,
  amount DECIMAL(10,2) NOT NULL,
  created_at DATETIME NOT NULL,
  KEY idx_user_status (user_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO t_btree (user_id, status, amount, created_at) VALUES
(1001, 0, 99.00, '2026-01-01 10:00:00'),
(1001, 1, 199.00, '2026-01-02 10:00:00'),
(1002, 0, 9.90, '2026-01-03 10:00:00');
```

预期：`Query OK, 3 rows affected`。

### 8.2 看页大小和表的物理大小

```sql
SHOW VARIABLES LIKE 'innodb_page_size';
-- 预期：innodb_page_size | 16384

SELECT TABLE_NAME, TABLE_ROWS, DATA_LENGTH, INDEX_LENGTH,
       DATA_LENGTH / 16384 AS data_pages
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 't_btree';
-- 预期（3 行数据时）：TABLE_ROWS 约 3，DATA_LENGTH 约 16384（1 个页），data_pages = 1
```

### 8.3 覆盖索引 vs 回表

```sql
EXPLAIN SELECT user_id, status FROM t_btree WHERE user_id = 1001;
-- 预期：type=ref, key=idx_user_status, Extra=Using index

EXPLAIN SELECT amount FROM t_btree WHERE user_id = 1001;
-- 预期：type=ref, key=idx_user_status, Extra=Using where（没有 Using index，需要回表）
```

### 8.4 最左前缀与索引失效

```sql
EXPLAIN SELECT * FROM t_btree WHERE status = 1;
-- 预期：type=ALL, key=NULL（只用第二列，用不上联合索引）

EXPLAIN SELECT * FROM t_btree WHERE user_id + 1 = 1002;
-- 预期：type=ALL, key=NULL（列上做运算，索引失效）
```

## 9. 常见误区

| 错误说法 | 正确说法 |
|---|---|
| 「B+ 树的非叶子也存数据」 | 非叶子只存键和子页号，叶子才存数据/主键 |
| 「索引一建，查询就一定走」 | 优化器按成本选，区分度低、回表多、统计信息过期都可能不走 |
| 「二级索引叶子存的是行地址」 | 存的是主键值；行会移动，不能存物理地址 |
| 「16KB 页是磁盘块大小」 | 磁盘块常见 4KB，16KB 是 InnoDB 的页大小，两者不是一回事 |
| 「三层树能存两千万行是固定的」 | 取决于行大小和主键长度，1KB 行约 1200 万，100B 行能存上亿 |
| 「UUID 主键只是丑一点」 | 键长导致扇出下降约 2/3，还触发页分裂，写入性能明显变差 |
| 「索引越多查询越快」 | 每个索引都要占空间、增加写放大和优化器选择成本 |
| 「范围查询后面的列完全没用」 | 不能用于定位，但可以被 ICP 下推到索引层过滤 |

## 10. 连续追问 Q&A

### Q1：索引到底存在哪里？是文件还是内存？

存在**表空间文件**里（默认 `ibdata1` 或独立表空间 `t_btree.ibd`），索引和数据在同一个 B+ 树里（聚簇索引）。查询时把页读到 **Buffer Pool（缓冲池）** 里，所以「热数据」其实是在内存中的页副本上查的。

### Q2：聚簇索引和二级索引的区别，用一句话说？

聚簇索引的叶子是**整行数据**，二级索引的叶子是**索引列 + 主键**。通过二级索引查非索引列，要拿主键回聚簇索引再查一次，这叫**回表**。

### Q3：一张表能有几个聚簇索引？

只有一个。没主键时用第一个「唯一且非空」的索引；都没有就生成隐藏的 `DB_ROW_ID`（6B）。所以「主键」和「聚簇索引」不完全等价，但通常说同一件事。

### Q4：什么是覆盖索引？为什么 `SELECT *` 不好？

查询需要的列全在索引里（包括主键），就不用回表，`Extra` 显示 `Using index`。`SELECT *` 会要求所有列，几乎必然回表，还会把大字段也读出来。

### Q5：最左前缀的字节级解释是什么？

联合索引 `(a, b, c)` 在 B+ 树里按「a 升序 → a 相同按 b 升序 → b 相同按 c 升序」排列。只给 b 时，b 只在「同一个 a」内部有序，全局无序，没法二分定位。所以只能从最左列开始给条件。

### Q6：为什么 `WHERE a > 1 AND b = 2` 里 b 用不上索引？

因为 a 是范围条件，a 之后的部分不再全局有序，b 无法参与定位；但 b 可以被 ICP 下推到索引层做过滤，减少回表。

### Q7：索引下推（ICP）解决什么问题？

没有 ICP 时，`WHERE name LIKE '张%' AND age = 20` 要先按 name 回表、再在 Server 层过滤 age；有了 ICP，age 在索引层先过滤，只有命中的才回表。`Extra: Using index condition`。

### Q8：页分裂是怎么发生的？为什么自增主键能避免？

往一个已满的页中间插入，就要拆成两页、把中间键上提父页，并更新前后页指针。自增主键永远在最大位置追加，只在最右页分裂，页利用率高、少随机 IO。

### Q9：为什么二级索引叶子不存行地址？

因为行会移动：更新变长字段、页分裂、表重建都会让行地址变化，存地址就要持续维护；存主键则稳定，代价只是回表多一次查找。

### Q10：B+ 树高度怎么查？

可以看 `information_schema.INNODB_TABLES` 里没有直接字段；常用两种方式：① 通过 `mysql.innodb_index_stats` 估算；② 用 `innodb_page_size` 和行数反推；③ 一些工具（如 `innodb_ruby`）能直接解析页结构看 `PAGE_LEVEL`。

### Q11：为什么说索引能加速 `ORDER BY`？

因为索引本身有序，`ORDER BY 索引列` 可以顺着叶子链表读，不用额外排序（`Using filesort`）；但排序顺序必须和联合索引前缀一致、不能中间隔列。

### Q12：InnoDB 的自适应哈希索引（AHI）和哈希索引有什么关系？

AHI 是 InnoDB 在内存里对「热点页」自动建的哈希，加速等值查找，不改变磁盘上的 B+ 树结构。它不保证一致语义（只是缓存），可以关闭（`innodb_adaptive_hash_index = OFF`），线上有时因争用关闭。

## 12. 一句话复盘

> 索引 = 把数据按主键排成 B+ 树。非叶子只放键和页号，靠大扇出把树高压到 3 层；叶子放数据并用链表连接，兼顾等值和范围查询。16KB 页决定了扇出，主键越短能装的行越多，这就是自增 bigint 主键和「2000 万单表警戒线」的由来。

## 13. 自测题（先自己答，再看答案）

**1. 三层 B+ 树、行 1KB、非叶子每条 17B，大约能存多少行？**
答案：非叶子页约 `15360/17 ≈ 903` 个键；三层叶子页约 `903² ≈ 81.5 万`；每叶约 `15360/1024 ≈ 15` 行；总数约 `81.5 万 × 15 ≈ 1223 万` 行。若按 14B 估算扇出 1170，则约 2190 万行。

**2. 为什么 B+ 树的非叶子节点不存数据？**
答案：为了把「扇出」做大。非叶子不存整行，同样 16KB 页能放更多键，树高更低，查询 IO 更少；而且所有查询都到叶子，IO 次数稳定。

**3. 为什么 `WHERE b = 1` 用不上 `(a, b, c)` 联合索引？**
答案：索引按 a→b→c 的优先级排序，b 只在 a 相同的小范围内有序，全局不是有序的，无法二分定位。

**4. 回表的代价具体是什么？**
答案：二级索引定位到主键后，要再查一次聚簇索引，多一次 B+ 树查找 + 一次随机 IO；如果回表行数多，优化器可能干脆选全表扫描。

**5. 为什么说「索引把随机 IO 变成顺序 IO」不准确？**
答案：索引本身也是随机 IO（页不一定相邻），它把「大量随机 IO」变成「少量几次随机 IO」；真正把随机变顺序的是 redo log（WAL）。这句话常被误用。
