# 分布式事务：2PC、TCC、本地消息表到底怎么选？

> 精讲层级：从「零基础能看懂」到「源码级」，每个名词都拆开
> 阅读时间：约 30 分钟
> 配套速查：[分布式事务（深度追问）](../../10-deep-dive/distributed/01-分布式事务.md)

## 0. 一句话先讲明白

**分布式事务 = 一个业务操作跨了两个及以上「各自独立的数据库 / 服务」，要保证最终要么全成功、要么全回滚。**

关键认知：**它和数据库的 `ACID` 不是一回事。**

- 单库事务靠数据库引擎（InnoDB 的 redo/undo/MVCC）保证 **强一致**
- 跨库没有「一个能管所有库的引擎」，所以只能靠**应用层协议**去拼，做到的是 **最终一致**

所以面试里第一句就该说清：

> 「严格意义上的分布式事务（强一致）只有 2PC/XA 这类，代价是阻塞和性能；互联网场景基本都用最终一致：**TCC、本地消息表、事务消息、Saga**。选型取决于业务能不能接受短暂不一致，以及能不能改下游接口。」

---

## 1. 它解决什么问题（先讲痛点）

### 1.1 单机时代：一个注解搞定

```java
@Transactional
public void pay(Long orderId, Long userId, int amount) {
    orderMapper.markPaid(orderId);      // 改订单库
    accountMapper.deduct(userId, amount); // 改账户库
}
```

只要两个表在**同一个数据库**里，一个连接、一个事务，失败自动回滚。

### 1.2 拆成微服务后，`@Transactional` 立刻失效

```
订单服务（order_db）       账户服务（account_db）
      │                          │
      ├─ 标记订单已支付           │
      │                          ├─ 扣减余额
      └──── 网络调用 ────────────►┘
```

此时会出现三种烂摊子：

| 场景 | 结果 |
|---|---|
| 订单标记成功，调用扣款**超时**，实际扣款成功了但你收到超时 | 你以为失败重试 → **扣两次** |
| 订单标记成功，扣款**失败** | 订单已支付，钱没扣 → **资损** |
| 订单标记成功，扣款成功，但**写日志/发通知**失败 | 业务流程不完整 |

**根本原因**：`@Transactional` 的边界是一个数据库连接，跨进程就管不到了。

### 1.3 再明确一次：你要的到底是哪种「一致」

| 级别 | 含义 | 能接受的场景 |
|---|---|---|
| 强一致 | 任何时刻读到的都是已提交的最新值 | 转账、库存扣减（超卖零容忍） |
| 最终一致 | 中间可以短暂不一致，最终会一致 | 下单后发积分、发通知、更新报表 |

**绝大多数业务只需要最终一致。** 强一致的分布式事务（2PC/XA）性能和可用性代价极高，互联网公司基本不用。

## 2. 一步步拆开

### 2.1 方案一：2PC（两阶段提交）

**名词解释**：

- **2PC** = Two-Phase Commit，两阶段提交
- **协调者（Coordinator）**：负责发起和裁决的组件（可以是数据库中间件、Seata 的 TC）
- **参与者（Participant）**：各个本地数据库
- **prepare（准备）**：参与者执行事务但不提交，把 undo/redo 写盘，锁住资源
- **commit/rollback（提交/回滚）**：协调者根据所有参与者的 prepare 结果统一裁决

**时序**：

```
协调者                参与者A              参与者B
  │                     │                    │
  ├── prepare ─────────►│                    │
  ├── prepare ──────────────────────────────►│
  │◄───── ready ────────┤                    │
  │◄──────────────────── ready ──────────────┤
  │                     │                    │
  ├── commit ──────────►│                    │
  ├── commit ───────────────────────────────►│
  │◄───── ack ──────────┤                    │
  │◄──────────────────── ack ────────────────┤
```

**致命问题（这是面试必答）**：

| 问题 | 具体表现 |
|---|---|
| **同步阻塞** | prepare 之后到 commit 之前，参与者一直持有行锁，其他请求全部等待 |
| **协调者单点** | 协调者在 prepare 后崩溃，参与者永远等不到裁决，资源一直锁着 |
| **数据不一致窗口** | 协调者发出 commit 后崩溃，只有部分参与者收到 → 一部分提交了，一部分没提交 |
| **性能差** | 两次网络往返 + 全程持锁，吞吐量骤降 |

**为什么互联网不用 2PC**：它假设「网络可靠、协调者不挂」，而这两条在分布式系统里恰好都不成立。

### 2.2 方案二：3PC（三段提交）

在 2PC 的 prepare 前加一个 **canCommit**，并给参与者加超时机制（超时后自己决定提交）。

- 好处：减少了「参与者永久阻塞」的概率
- 坏处：超时自动提交会引入新的不一致（网络分区时两边判断不同）

**结论**：3PC 只在理论上更优，工程里几乎不用。面试可以一句话带过。

### 2.3 方案三：TCC（Try-Confirm-Cancel）

**名词解释**：

- **Try**：预留资源（冻结而不是扣减）
- **Confirm**：确认使用（把冻结转成真实扣减）
- **Cancel**：释放预留（解冻）

以「转账 100 元」为例：

| 阶段 | 账户 A（付款方） | 账户 B（收款方） |
|---|---|---|
| Try | `frozen += 100`（可用余额减 100） | `available += 100`（待入账加 100） |
| Confirm | `balance -= 100, frozen -= 100` | `frozen -= 100`（转为可用） |
| Cancel | `available += 100, frozen -= 100` | `pending -= 100` |

**TCC 的三个经典异常（必答）**：

1. **空回滚**：Try 没执行（比如网络超时其实没到），却收到了 Cancel
   - 解：Cancel 时判断「是否有 Try 记录」，没有就直接返回成功
2. **悬挂**：Cancel 先执行了，之后 Try 才到
   - 解：Try 前检查是否已有 Cancel 记录，有就拒绝执行
3. **幂等**：Confirm/Cancel 可能重复调用
   - 解：加事务控制表，用「事务 ID + 阶段」做唯一键

**TCC 的代价**：业务侵入极强，每个接口要写三份，还要处理上述三个异常。所以只用于**核心资金链路**。

### 2.4 方案四：本地消息表（最常用、最稳）

**思路**：把「业务操作」和「发消息」放进**同一个本地事务**，再用定时任务投递。

```
本地数据库（同一个事务）：
  BEGIN
    UPDATE order SET status = 'PAID' WHERE id = 1;
    INSERT INTO local_message(id, topic, payload, status) VALUES (..., 'SEND');
  COMMIT

定时任务（每 500ms 扫一次）：
  SELECT * FROM local_message WHERE status = 'SEND' LIMIT 100;
  → 投递到 MQ
  → 收到 ack 后 UPDATE status = 'SENT'
消费者：
  → 处理业务（必须幂等）
  → 处理成功后 ack
```

**为什么能保证最终一致**：

- 业务和消息同库同事务 → 「业务成功但消息没发」不可能发生
- 消息至少投递一次（at-least-once） → 消费者要幂等
- 定时任务失败重试 → 最终一定发出去

**代价**：消息表跟业务库耦合，需要自己写扫描和清理逻辑。

### 2.5 方案五：事务消息（RocketMQ）

RocketMQ 把「本地消息表」做进了 MQ：

```
1. 生产者发 half message（半消息，对消费者不可见）
2. MQ 存下，返回成功
3. 生产者执行本地事务
4. 本地事务成功 → commit；失败 → rollback
5. 如果第 3 步后生产者挂了，MQ 反查（check）生产者的接口，最多查 15 次
```

**比本地消息表好在**：不用自己建表、不用自己写扫描任务。
**局限**：绑定 RocketMQ，Kafka 不支持这种语义（Kafka 事务是「生产+消费」的原子性，不是「业务+消息」）。

### 2.6 方案六：Saga

把长事务拆成一串本地事务，每个都有对应的**补偿操作**：

```
T1 → T2 → T3 → T4
失败时：C4 → C3 → C2 → C1（反向补偿）
```

- **协同式（Choreography）**：每个服务监听事件，自己决定下一步，简单但链路难追踪
- **编排式（Orchestration）**：一个编排器（状态机）统一调度，清晰但引入中心

**适用**：长流程、跨多个团队、无法做资源预留的场景（如订单履约、旅行订票）。
**弱点**：没有隔离性，中间状态对外可见（例如「订单已创建但库存未锁」）。

### 2.7 方案七：Seata AT（自动补偿）

**思路**：不改业务代码，靠数据源代理自动记录前后镜像。

```
一阶段（本地事务）：
  1. 解析 SQL，查出 before image
  2. 执行 SQL
  3. 查出 after image
  4. 把 before/after image 写入 undo_log（同一本地事务）
  5. 向 TC 注册分支事务，申请全局锁（对受影响的主键）
  6. 本地提交

二阶段：
  全局提交 → 异步删除 undo_log（很快）
  全局回滚 → 用 undo_log 反向生成补偿 SQL，校验 after image 未被改动后回滚
```

**核心概念**：

- **TC（Transaction Coordinator）**：事务协调者，独立部署
- **TM（Transaction Manager）**：发起全局事务的一方
- **RM（Resource Manager）**：每个数据源代理
- **全局锁**：防止其他全局事务修改同一行（解决脏写）

**最大坑**：AT 模式默认**读未提交**（本地事务已提交，全局还没提交，别人能看到中间状态）。需要读隔离就加 `@GlobalLock` 或改用 TCC。

## 3. 完整推导

### 3.1 2PC 的失败窗口枚举（面试常考「哪个阶段崩溃会怎样」）

| 崩溃位置 | 后果 |
|---|---|
| 协调者发 prepare 前崩 | 参与者什么都没做，安全 |
| 协调者发完部分 prepare 后崩 | 收到 prepare 的参与者持锁等待；恢复后协调者重新发，或参与者超时回滚 |
| 全部 prepare 成功、协调者 commit 前崩 | 参与者持锁等待，最终由协调者恢复日志后补发 commit |
| 协调者发出部分 commit 后崩 | **部分提交、部分未提交 → 数据不一致**（这是 2PC 最致命的窗口） |
| 参与者 prepare 后崩 | 协调者收不到 ready，超时后整体回滚；参与者恢复后按日志回滚 |

结论：**2PC 只有在「协调者可靠 + 网络可靠」时才正确**。这就是它不适合互联网的根本原因。

### 3.2 TCC 三异常的时序推导

**空回滚**：

```
try 请求 ──X（网络丢包，没到服务）──►
                              cancel 请求 ──► 服务收到 cancel，但从未 try
如果 cancel 直接执行「解冻」，会把用户本来没冻结的钱解冻 → 余额变多
```

**悬挂**：

```
cancel 先到（因为 try 超时被上游判失败）
try 后到（网络延迟）
结果：cancel 解冻了一个还不存在的冻结 → 后续 try 又冻结了 → 这笔钱永远冻着
```

**解法统一成一句话**：**用一张事务控制表，按「事务 ID + 分支 ID」记录状态，Try/Cancel 都先查表再决定是否执行。**

### 3.3 本地消息表为什么是「最终一致」而不是「强一致」

投递是异步的（定时扫描），所以：

- 业务提交后，消息可能延迟 0~500ms 才发出
- 这段时间内，下游看到的是「旧状态」

**这就是最终一致的定义**：允许中间态，只要最终收敛。

如果业务要求「用户付款后立刻能在账户看到钱」，那本地消息表不满足，得用 TCC 或 2PC。

### 3.4 消费幂等的数学必要性

at-least-once 意味着消息可能重复。设重复概率为 p，消费次数 n，则至少重复一次的概率是 `1-(1-p)^n`。
即使 p=0.001%、n=100 万，也几乎必然出现重复。

所以：**只要用了 MQ，幂等就不是可选项**。实现方式：

| 方式 | 做法 | 适用 |
|---|---|---|
| 唯一索引 | 消息 ID / 业务唯一键建唯一索引 | 插入类业务 |
| 状态机 | 只允许 `待支付 → 已支付`，重复消息因状态不符被忽略 | 状态流转 |
| 去重表 | 消费前插入去重记录 | 通用 |

## 4. 极简模型（2 个服务、1 条订单）

```
服务 A（订单）            服务 B（账户）
order(id=1, status)
                          account(uid=1, balance)

目标：订单置为 PAID 且账户扣 100，要么都成功要么都不成功
```

用**本地消息表**走一遍：

```
A 的本地事务：
  order.status = PAID
  insert message(id=1, topic=deduct, payload={uid:1, amt:100})

A 的定时任务：
  查到 message(1)，发给 MQ

B 消费：
  幂等判断：deduct_log 里有没有 msgId=1？
    有 → 直接 ack
    没有 → 开本地事务 { balance -= 100; insert deduct_log(msgId=1); } → ack
```

**关键点**：A 的「置状态 + 写消息」是原子的；B 的「扣钱 + 记日志」也是原子的。两个原子操作被消息串起来，就成了最终一致。

## 5. 为什么这样设计

### 5.1 被否决方案 A：直接远程调用 + 重试

- 做法：A 调 B 的接口，失败就重试 N 次
- 为什么否决：重试解决不了「B 已经成功但响应超时」的情况，会**重复扣款**；而且重试失败后 A 无法回滚已提交的本地事务

### 5.2 被否决方案 B：只做 2PC/XA

- 做法：用数据库 XA 或 Seata XA 模式
- 为什么否决：**全程持锁 + 两次网络往返**，TPS 掉一个数量级；协调者单点；跨云/跨库兼容性差。适合内部低频的强一致场景，不适合高并发电商

### 5.3 被否决方案 C：纯 MQ 不做补偿

- 做法：A 发消息，B 消费，失败就重试到底
- 为什么否决：如果 B 的业务逻辑**不可重入**或**永久失败**（比如账户已注销），消息会一直重试；没有「反向补偿」就没有退路，需要 Saga/TCC 来兜底

## 6. 关键参数为什么是这个值

| 参数 | 常见值 | 为什么 |
|---|---|---|
| 本地消息表扫描间隔 | 500ms ~ 1s | 太频繁浪费 DB；太慢影响时效 |
| 消息最大重试次数 | 16 次左右（RocketMQ 默认） | 指数退避后约覆盖数小时；再失败进死信人工介入 |
| 事务消息回查次数 | 15 次（RocketMQ 默认） | 给生产者足够时间确认本地事务结果 |
| 事务超时时间 | 10s ~ 60s | 太短误杀、太长占锁 |
| Seata 全局锁重试 | 默认 30 次，间隔递增 | 冲突时给彼此让路，避免活锁 |

## 7. 版本演进

| 版本/组件 | 变化 | 影响 |
|---|---|---|
| XA（1991） | 数据库层面的两阶段提交标准 | 强一致但性能差 |
| Seata 0.x | AT 模式 + 全局锁 | 业务无侵入，但读未提交 |
| Seata 1.x | 支持 TCC/Saga/XA 多模式 | 可按场景选 |
| Seata 2.x | 支持 Raft 模式 TC、注册中心简化 | 高可用更好 |
| RocketMQ 4.x | 事务消息 | 半消息 + 回查 |
| RocketMQ 5.x | 事务消息 API 简化、gRPC | 使用更方便 |
| Saga 模式 | 从学术到工程（Seata Saga、Temporal） | 长流程首选 |

## 8. 亲手验证（本地消息表的最小实现）

```java
// 1) 本地事务：业务 + 消息同库提交
@Transactional
public void pay(Long orderId, String msgId) {
    orderMapper.updateStatus(orderId, "PAID");
    messageMapper.insert(new LocalMessage(msgId, "deduct", "{\"orderId\":" + orderId + "}", "SEND"));
}

// 2) 定时投递（伪代码）
@Scheduled(fixedDelay = 500)
public void deliver() {
    List<LocalMessage> list = messageMapper.selectPending(100);
    for (LocalMessage m : list) {
        try {
            mq.send(m.getTopic(), m.getPayload());
            messageMapper.markSent(m.getId());   // 收到 ack 才标记
        } catch (Exception e) {
            messageMapper.incrRetry(m.getId());  // 下次继续
        }
    }
}

// 3) 消费者幂等
@Transactional
public void onDeduct(String msgId, Long uid, int amount) {
    if (deductLogMapper.exists(msgId)) return;       // 幂等
    accountMapper.deduct(uid, amount);
    deductLogMapper.insert(msgId);
}
```

**预期结果**：

- 正常：订单 PAID，账户扣款一次
- 投递前宕机：重启后定时任务继续投递
- 重复投递：消费者因 `deductLog` 已存在直接返回，账户只扣一次

## 9. 常见误区

| 错误说法 | 正确说法 |
|---|---|
| 「分布式事务就是 2PC」 | 2PC 只是强一致方案之一，主流是最终一致（TCC/消息表/Saga） |
| 「用了 MQ 就自动有分布式事务」 | MQ 只保证消息投递，业务与消息的原子性要靠本地消息表或事务消息 |
| 「TCC 的 Cancel 一定在 Try 之后」 | 网络乱序会导致 Cancel 先到（悬挂），必须防 |
| 「Seata AT 没有隔离性问题」 | AT 默认读未提交，全局事务未完成时其他事务能读到中间状态 |
| 「本地消息表可以保证强一致」 | 它是异步投递，只保证最终一致 |
| 「消费幂等是可选优化」 | at-least-once 下重复必然发生，幂等是正确性要求 |
| 「Saga 能回滚所有操作」 | 补偿是「反向业务操作」，不是数据库回滚，比如发出去的短信撤不回 |
| 「分布式事务一定要引入中间件」 | 本地消息表用数据库就能实现，不需要 Seata/RocketMQ |

## 10. 连续追问 Q&A

### Q1：为什么不直接用一个数据库，避免分布式事务？
分库分表的根本原因是单库容量和写入瓶颈。业务增长到一定规模，拆库不可避免；拆分后就必须面对跨库一致性问题。

### Q2：TCC 的 Try 阶段为什么要「预留」而不是直接扣？
因为 Try 之后可能因为其他分支失败而 Cancel。直接扣了再退，中间会有「钱短暂消失」的窗口，且退款逻辑更复杂。

### Q3：本地消息表会不会把业务库拖垮？
会带来额外写入。优化手段：消息表与业务表分表、异步清理已发送记录、控制扫描批次与索引。量大时改用事务消息（MQ 侧承担）。

### Q4：RocketMQ 事务消息的回查机制解决什么问题？
解决「生产者执行完本地事务但没能发出 commit/rollback」的中间态：MQ 主动反查生产者的本地事务状态，决定提交还是丢弃半消息。

### Q5：Kafka 的事务能替代分布式事务吗？
不能。Kafka 事务保证的是「多个 topic/partition 的写入 + offset 提交」的原子性，不覆盖「业务数据库写入 + 消息发送」的原子性。

### Q6：Seata AT 的全局锁和数据库行锁有什么区别？
数据库行锁锁的是「当前本地事务」；全局锁锁的是「某个全局事务正在操作的主键」，跨服务生效，由 TC 维护，防止两个全局事务同时改同一行。

### Q7：如果下游一直失败，最终一致还能保证吗？
不能。要设「最大重试次数 + 死信队列 + 人工补偿」。工程上要监控死信量，而不是假设永远成功。

### Q8：Saga 和 TCC 的区别？
TCC 有资源预留（隔离性好），侵入强；Saga 是「做完了再补偿」，无预留、隔离性弱，但适合长流程和无法预留的场景。

### Q9：什么业务适合 2PC？
低频、强一致、参与方少、能接受秒级延迟的场景，比如内部财务系统的跨库转账。高并发电商不合适。

### Q10：没有分布式事务框架，怎么保证最终一致？
最简单的三步：① 本地事务写业务 + 写消息表；② 定时任务投递；③ 消费端幂等。这套方案不依赖任何中间件。

### Q11：如何验证分布式事务真的生效？
构造故障：在「本地事务提交后、消息投递前」kill 进程，重启后看消息是否补发；在消费端让第一次处理失败，看重试是否幂等。

### Q12：消息表会不会有性能瓶颈？
写放大是主要成本。可以用「同库不同表 + 批量插入 + 定期归档」，或者直接上事务消息把表交给 MQ 管理。

## 12. 一句话复盘

> 分布式事务的本质是「跨库 ACID 失效后的补偿机制」：强一致靠 2PC（阻塞、少用），最终一致靠 TCC（资金）、本地消息表 / 事务消息（通用）、Saga（长流程）。选型只看两件事——业务能否接受中间态、下游接口能否改。所有最终一致方案的前提都是：**消息至少投递一次 + 消费必须幂等**。

## 13. 自测题

**1. 订单服务调账户服务扣款，返回超时，你该怎么办？**
答案：不能直接重试扣款，必须先查账户服务的流水（用业务唯一号查），确认是否已扣；同时上游要幂等，用「订单号」作为幂等键。

**2. 本地消息表的定时任务为什么不能「先标记已发送，再发 MQ」？**
答案：如果标记后发送失败，消息就永久丢了。必须「先发送成功（收到 ack）再标记已发送」，失败则保持待发送状态重试。

**3. TCC 里 Cancel 收到但对应 Try 从没执行，这叫什么？怎么防？**
答案：空回滚。Cancel 执行前先查事务控制表，没有 Try 记录就直接返回成功且不做任何资源操作。

**4. Seata AT 的一阶段为什么能「本地提交」还不破坏一致性？**
答案：因为它同时写了 undo_log 并注册了全局分支；如果全局回滚，二阶段能用 undo_log 反向补偿。本地提交只是提前释放了数据库行锁。

**5. 为什么说「用了 MQ 就必须做幂等」？**
答案：MQ 的投递语义是 at-least-once，网络重试、消费者重启、ack 丢失都会导致重复投递；不做幂等就会重复扣款/重复发货。
