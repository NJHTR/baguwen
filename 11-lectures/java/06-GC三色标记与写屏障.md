# GC 三色标记与写屏障：并发标记为什么会出现「漏标」

## 0. 一句话先讲明白

GC 要判断「哪些对象还活着」，做法是从 GC Roots 出发遍历引用图。如果全程停顿（STW），遍历期间没人改对象图，结果一定正确 —— 但停顿太长。
于是现代收集器**让标记和用户线程并发**，为了记录「标记进行到哪了」，把对象染成**白 / 灰 / 黑**三种颜色。并发期间用户线程可能修改引用，导致**漏标**（把活对象当垃圾回收），必须靠**写屏障 + 增量更新（CMS）或原始快照 SATB（G1）** 补救。

```java
// 三色的语义（不是对象上的字段，而是 GC 内部的数据结构/标记位）
白：还没被访问到        -> 最终会被当作垃圾
灰：自己访问过了，但子引用还没扫完
黑：自己和所有子引用都扫完了
```

三个名词先解释掉：

| 名词 | 是什么 |
|---|---|
| GC Roots | 遍历的起点：栈上局部变量、静态变量、常量、JNI 引用、活动线程 |
| 写屏障（write barrier） | JIT 在「引用赋值」处插入的一小段代码，用来记录引用变化 |
| 卡表（card table） | 把堆切成固定大小（512B）的「卡」，用 1 字节标记这卡里有没有跨代引用 |

---

## 1. 它解决什么问题（先讲痛点，不讲定义）

### 1.1 全停顿标记的问题

最朴素的标记是「暂停所有用户线程 → 从 GC Roots 遍历完 → 恢复」。问题在于**停顿时间与堆大小成正比**：

- 堆 4GB、对象几千万，遍历引用图可能要几百毫秒；
- 堆 32GB 时可能到数秒；
- 对于「接口 P99 要求 200ms」的业务，这是不可接受的。

### 1.2 并发标记带来的新问题

如果标记线程和用户线程同时跑，就会出现这种时序：

```
GC 线程：已经扫过对象 A，把 A 标黑（认为 A 的子引用都检查完了）
用户线程：A.ref = B        ← 新增了一条黑 -> 白的引用
用户线程：C.ref = null     ← 删除了原来灰 -> 白的引用（B 只能从 C 到达了）
GC 线程：继续标记，永远不会再扫 A（因为它黑了），也不会再扫 C（因为那条边没了）
结果：B 一直是白色，被当成垃圾回收 —— 但用户代码其实还在用 B
```

**活对象被回收 = 程序崩溃或数据错乱。** 这就是「漏标」，也是三色标记和写屏障要解决的全部问题。

## 2. 一步步拆开

### 2.1 三色标记的过程

```
初始：所有对象是白；GC Roots 的直接引用标灰
循环：
   从灰色集合取一个对象 X
   把 X 的所有子引用标灰（白 -> 灰）
   把 X 标黑
直到灰色集合为空 -> 剩下的白就是垃圾
```

关键性质：**白只能通过「灰色」被染成别的颜色**。黑色不会再传播，因为它被认为「子引用都处理完了」。

### 2.2 漏标的两个必要条件

漏标不是一个对象「可能漏」，而是**同时满足两条**才漏：

| 条件 | 内容 | 为什么是必要条件 |
|---|---|---|
| 条件一 | 一个**黑色**对象新增了指向**白色**对象的引用 | 黑不会再扫，所以这条新边不会被遍历到 |
| 条件二 | 所有从**灰色**对象指向该白色对象的引用都被删除 | 灰色是唯一还能传播颜色的来源；灰→白的边没了，白就再也没有「变灰」的机会 |

只有条件一：白对象还有其他灰路径可达，仍会被正常标记，不漏。
只有条件二：黑对象新增的那条边会被……不，黑色也不会再扫，但白色对象如果还能从别处灰对象到达就不漏。**两条同时成立才漏。**

### 2.3 两种补救方案

| 方案 | 做法 | 用在哪 |
|---|---|---|
| 增量更新（Incremental Update） | 记录「黑→白」的**新增**引用；把黑重新标灰，重新扫描它的子引用 | CMS |
| 原始快照（SATB, Snapshot At The Beginning） | 记录「灰→白」引用**被删除时的旧值**；按「标记开始那一刻的快照」处理，旧值也当活对象 | G1、Shenandoah |

两者都是在**写屏障**里落地的：

```
增量更新：在「引用被写入」时检查，如果目标对象是白、源对象是黑 -> 把源对象重新标灰/加入队列
SATB   ：在「引用被覆盖」时检查，把被覆盖的旧引用加入 SATB 队列，后续按队列重新标记
```

SATB 的代价是会留下**浮动垃圾**：快照之后才死掉的对象这一轮不会被回收，要等下一轮。

### 2.4 写屏障 ≠ 内存屏障

这是最容易混的一题，必须分清：

| | 写屏障（write barrier） | 内存屏障（memory barrier/fence） |
|---|---|---|
| 是什么 | JVM 在 `oop_store`（引用赋值）处插入的一小段**代码** | CPU/编译器层面的**指令**，用来限制重排序 |
| 目的 | 记录「引用变了」，供 GC 修正 | 保证多核之间的可见性与顺序 |
| 例子 | 卡表标脏、SATB 入队 | `StoreLoad`、`lock` 前缀指令 |
| 谁插入 | JIT 编译时 | 编译器生成指令 / 硬件执行 |

一句话：**写屏障是「GC 的钩子」，内存屏障是「CPU 的顺序约束」**。写屏障内部可能用到内存屏障，但两者不是一回事。

### 2.5 卡表：解决「跨代引用」的扫描成本

新生代回收（Young GC）时，只扫新生代是不够的 —— 老年代可能持有新生代对象的引用。如果每次都扫整个老年代，成本太高。

于是把堆按 **512 字节**切成「卡」，每张卡用 1 字节标记「脏（可能有跨代引用）」。老年代对象写入新生代引用时，写屏障把对应卡标脏；Young GC 只扫脏卡。

**开销估算**：1GB 堆 = `2^30 / 2^9 = 2^21 ≈ 209 万`张卡 × 1 字节 = **2MB**，只占堆的 0.2%。

### 2.6 RSet：G1 的「谁指向我」

G1 把堆切成约 2048 个 Region，回收某个 Region 时要快速知道「还有谁指向我」。所以每个 Region 维护一份 **RSet（Remembered Set）**，记录来自其他 Region 的引用（以卡索引的形式）。

- 卡表是「全局一张、按地址分卡」；
- RSet 是「每个 Region 一份、记录外部指向我的边」。

Young GC / Mixed GC 时，扫 RSet 就能找到所有外部引用，不用扫整个堆。

### 2.7 G1 的 Region 与回收流程

| 概念 | 说明 |
|---|---|
| Region | 堆切成约 2048 块，每块 1~32MB（2 的幂），实测默认 2MB |
| Humongous | 超过单个 Region 一半的大对象，单独占连续 Region |
| CSet（Collection Set） | 本轮要回收的 Region 集合，Young GC 包含所有年轻 Region；Mixed GC 还包含部分老年代 Region |
| 停顿预测模型 | 根据历史数据估算「每个 Region 的回收成本」，在 `MaxGCPauseMillis`（默认 200ms）预算内挑收益最高的 Region |

所以 G1 能「可预测停顿」：不是硬保证，而是**每次只回收一小部分、按收益挑**，把单次停顿控制住。

## 3. 完整推导

### 3.1 为什么「黑→白新增」必须记录

黑色对象的语义是「它的所有子引用都已经被扫描过」。一旦它在标记开始后新增了引用，这条边**不在任何待扫描集合里**：

```
标黑时刻：A.children = {}          （假设当时没有子引用）
之后：    A.children = {B}         （新增）
GC 视角：A 已扫完，不会再看；B 若没有其他灰路径 -> 永远白
```

所以只要允许「黑色对象在标记期间被修改」，就必须在写屏障里记录。

### 3.2 为什么 SATB 记录的是「旧值」而不是「新值」

SATB 的目标是维持「标记开始那一刻的引用快照」：

- 如果一条 `C -> B` 的边在快照里存在，那么即使中途被删除，B 也应当按「快照里可达」处理 → 所以要记录**被删掉的旧值 B**；
- 至于新增的 `A -> B`（快照里不存在），SATB 直接放弃跟踪，按「快照语义」B 不因这条新边而免死。

代价就是「本轮可能多留一些垃圾」（浮动垃圾），换来实现简单、不需要记录新增。

### 3.3 G1 为什么不用增量更新

增量更新需要「把黑重新变灰、重新扫描」，实现上要处理「黑的子引用被反复修改」的情况，复杂度较高；而 G1 的并发标记是**快照式**的，配合 Region 化设计，用 SATB 队列 + 重新标记阶段处理更自然。CMS 是老年代分代式标记，用增量更新成本更低。

**两者是同一问题的两种取舍，不是谁绝对更优。**

### 3.4 数字推导：一次 Full GC 的成本

假设 32GB 堆、每对象平均 32 字节、存活 5 亿个对象：

```
遍历 5 亿个对象 × 平均 3 个引用 = 15 亿次引用遍历
按每次 10ns（内存访问 + 判断）≈ 15 秒
```

这就是为什么「STW 标记」在大堆上不可接受，也是为什么 G1 要把回收拆成多次小停顿（`G1MixedGCCountTarget = 8`，一轮老年代回收分摊到最多 8 次 Mixed GC）。

### 3.5 数字推导：Region 大小怎么来的

G1 默认目标约 2048 个 Region，堆大小除以 2048 再取 2 的幂（1~32MB 之间）：

```
4GB 堆:   4×1024MB / 2048 = 2MB   -> 实测 G1HeapRegionSize = 2097152（2MB）
16GB 堆:  16×1024 / 2048 = 8MB
64GB 堆:  64×1024 / 2048 = 32MB（上限）
```

Region 越小，停顿越可控（每次回收量小），但 RSet 等元数据开销越大；G1 在两者之间自动取。

## 4. 极简模型：3 个对象看懂漏标

```
初始状态（并发标记刚开始）：
  A(黑，已扫完)     C(灰，待扫)     B(白)
  A.ref = null      C.ref = B

用户线程做两件事：
  1) A.ref = B     （黑->白 新增）
  2) C.ref = null  （灰->白 删除）

GC 继续标记：
  A 黑 -> 不再扫
  C 灰 -> 扫它的子引用，但 C.ref 已是 null，扫不到 B
  灰色集合空 -> 结束
  B 仍是白 -> 被回收 -> 但用户代码还在用 B
```

两种方案的修正：

```
增量更新（CMS）：
  写 A.ref = B 时，屏障发现「黑 A 新增了引用」-> 把 A 重新标灰
  GC 重扫 A -> 发现 B -> B 变灰 -> B 存活

SATB（G1）：
  写 C.ref = null 时，屏障把旧值 B 记进 SATB 队列
  标记结束前处理队列 -> B 按存活处理
  代价：B 可能已经是垃圾，本轮多留一轮（浮动垃圾）
```

---

## 5. 为什么这样设计（被否决的四个方案）

**方案 A：干脆全停顿标记（Serial / Parallel 的做法）。** 否决原因：停顿时间与堆大小成正比，大堆上几秒的停顿对在线服务不可接受。小堆、离线批处理仍然可以用，所以它们没有消失，只是不是默认选择。

**方案 B：用引用计数代替标记。** 否决原因：① 循环引用永远回收不了；② 每次引用赋值都要增减计数，写屏障成本极高；③ 计数本身需要原子操作（并发下更贵）。Java 选了「追踪式 GC」。

**方案 C：只用增量更新、不记录删除。** 不行 —— 删除了灰→白的边，白对象可能再也没有灰路径可达，必须靠 SATB 或「重新标记阶段全量重扫」来兜底；前者便宜，后者要 STW 且成本高，所以还是写屏障划算。

**方案 D：不管并发修改，最后做一次全量重扫兜底。** 否决原因：全量重扫等于一次 STW 标记，前面的并发标记白做了；而且重扫期间用户线程还得停。写屏障的摊还成本远低于一次全堆扫描。

**方案 E：把卡表粒度做大（比如 4KB 一张卡）省内存。** 否决原因：卡越大，脏卡里混入的「其实没跨代引用」的对象越多，扫描成本上升；512 字节是「元数据开销（0.2%）」与「扫描精度」的折中。

## 6. 关键参数为什么是这个值

| 参数 | 默认值（JDK 17 实测） | 为什么 |
|---|---|---|
| `MaxGCPauseMillis` | 200 | 目标是「尽量不超过 200ms 停顿」，靠挑 CSet 实现，不是硬保证 |
| `G1HeapRegionSize` | 2MB（ergonomic） | 堆约 2048 个 Region 推算，实测 4GB 堆 → 2MB |
| `InitiatingHeapOccupancyPercent` | 45 | 堆用到 45% 就启动并发标记，给标记留出时间在堆满前完成 |
| `G1SATBBufferSize` | 1024（条/线程） | 线程本地 SATB 队列满后转入全局队列，避免单线程缓冲区无限增长 |
| `G1MixedGCCountTarget` | 8 | 一轮老年代回收分摊到最多 8 次 Mixed GC，控制单次停顿 |
| `G1RSetUpdatingPauseTimePercent` | 10 | RSet 更新最多花停顿预算的 10%，其余留给回收本身 |
| 卡大小 | 512 字节 | 1GB 堆只需 2MB 卡表（0.2%），粒度足够定位跨代引用 |
| `UseG1GC` | true | JDK 9 起的默认收集器（实测 `{ergonomic}`） |

## 7. 版本演进

**JDK 6/7（Serial、Parallel）**：标记阶段全程 STW，算法简单、吞吐高，但停顿随堆线性增长。

**JDK 7/8（CMS）**：第一次把标记做成并发，用**增量更新**写屏障；问题是有内存碎片、可能 `Concurrent Mode Failure`。JDK 9 标记废弃（JEP 291），**JDK 14 移除**（JEP 363）——在 JDK 17 上传 `-XX:+UseConcMarkSweepGC` 会直接报 `Unrecognized VM option`（实测）。

**JDK 8/9（G1）**：Region 化 + **SATB** 写屏障，JDK 9 起成为默认收集器；`MaxGCPauseMillis` 可配置目标停顿。

**JDK 11/15（ZGC）**：JDK 11 实验、JDK 15 转正。用**着色指针**（指针里几位存对象状态）+ **读屏障**把标记、移动、重映射全部并发化，停顿 <1ms。它不需要「三色 + 写屏障」那套，但思想同源：都是「并发 + 屏障 + 记录变化」。

**JDK 21**：分代 ZGC（JEP 439）把 ZGC 也分代，兼顾低延迟与吞吐。GC 日志格式在 JDK 9 起统一为 `-Xlog:gc`（`-XX:+PrintGCDetails` 已废弃）。

## 8. 亲手验证

### 8.1 用 3 个对象模拟漏标与两种屏障

```java
import java.util.*;

public class TriColorDemo {
    enum Color { WHITE, GRAY, BLACK }
    static class Obj {
        final String name; Color color = Color.WHITE; Obj ref;
        Obj(String name) { this.name = name; }
        public String toString() { return name + ":" + color; }
    }
    public static void main(String[] args) {
        // ① 无屏障：漏标
        Obj A = new Obj("A"), B = new Obj("B"), C = new Obj("C");
        A.color = Color.BLACK;                       // A 已扫完
        C.color = Color.GRAY;                        // C 待扫
        C.ref = B;
        A.ref = B;                                   // 条件一：黑 -> 白 新增
        C.ref = null;                                // 条件二：灰 -> 白 删除
        System.out.println("无屏障：B.color=" + B.color + " -> B 被当垃圾回收");

        // ② 增量更新（CMS）：黑对象新增引用时把黑重新标灰
        A.color = Color.BLACK; B.color = Color.WHITE; A.ref = null;
        A.ref = B;
        if (A.color == Color.BLACK) A.color = Color.GRAY;    // 写屏障动作
        System.out.println("增量更新：A 重新变灰，重扫 A 后 B 会被标灰");

        // ③ SATB（G1）：删除灰->白 引用时把旧值记入队列
        B.color = Color.WHITE; C.color = Color.GRAY; C.ref = B;
        Deque<Obj> satb = new ArrayDeque<>();
        satb.add(C.ref);                             // 写屏障动作：记录旧值
        C.ref = null;
        System.out.println("SATB：队列里记录 " + satb.peek() + "，标记时按存活处理（留下浮动垃圾）");
    }
}
```

```bash
javac -encoding UTF-8 TriColorDemo.java
java TriColorDemo
```

预期输出：

```
无屏障：B.color=WHITE -> B 被当垃圾回收
增量更新：A 重新变灰，重扫 A 后 B 会被标灰
SATB：队列里记录 B:WHITE，标记时按存活处理（留下浮动垃圾）
```

import java.util.*;

public class GcProbe {

        List<byte[]> keep = new ArrayList<>();

}
```

javac -encoding UTF-8 GcProbe.java
java -Xmx32m -Xlog:gc GcProbe
java -XX:+PrintFlagsFinal -version | grep -E 'UseG1GC|MaxGCPauseMillis|G1HeapRegionSize|InitiatingHeapOccupancyPercent'
```

预期输出（片段；数值每次运行不同，看格式即可）：

```

```

参数读法：`GC(0)` 第几次、`Pause Young` 年轻代停顿、`(G1 Evacuation Pause)` 触发原因（复制式回收）、`14M->2M(32M)` 回收前 14M → 回收后 2M、堆共 32M、`1.417ms` 停顿。

## 9. 常见误区

| 错误说法 | 正确说法 |
|---|---|
| 「三色是对象上的一个颜色字段」 | 三色是 GC 内部的标记状态，不是 Java 对象的字段 |
| 「只要并发标记就一定会漏标」 | 需同时满足「黑→白新增」和「灰→白删除」两个条件，且需要写屏障兜底 |
| 「写屏障就是内存屏障」 | 写屏障是 GC 记录引用变化的钩子；内存屏障是限制重排的 CPU 指令 |
| 「SATB 记录的是新引用」 | 记录的是**被覆盖的旧引用**，按快照语义处理 |
| 「CMS 和 G1 都用 SATB」 | CMS 用增量更新；G1 用 SATB |
| 「G1 能保证停顿不超过 200ms」 | `MaxGCPauseMillis` 是目标值，靠挑选 CSet 尽量达成，不是硬保证 |
| 「卡表是每个 Region 一份」 | 全局一张按地址分卡；RSet 才是每个 Region 一份 |
| 「JDK 17 还能用 CMS」 | JDK 14 已移除，17 上传该参数直接报 Unrecognized VM option |

## 10. 连续追问 Q&A

### Q1：为什么需要三色标记？两色（活/死）不够吗？
**答**：并发标记必须记录「扫到哪了」。灰色表示「自己看过了但孩子还没看完」，这是唯一还能继续传播颜色的集合；没有灰色，就无法区分「还没扫」和「扫完了」。

### Q2：漏标的两个必要条件是什么？
**答**：① 黑色对象新增了指向白色对象的引用（黑不会再扫）；② 所有从灰色到该白色对象的引用都被删除（没有其他灰路径能染到它）。两条同时成立才会漏。

### Q3：增量更新和 SATB 分别怎么防漏标？
**答**：增量更新在写屏障里发现「黑→白新增」，把黑重新标灰，重新扫描其子引用（CMS）；SATB 在写屏障里记录「灰→白被删」的旧值，按快照语义当存活处理（G1）。

### Q4：为什么 SATB 会产生浮动垃圾？
**答**：它按「标记开始时的快照」处理，快照之后才死掉的对象这一轮仍被当存活，只能等下一轮回收。

### Q5：写屏障和内存屏障的区别？
**答**：写屏障是 JVM 在引用赋值处插入的一段记录代码（供 GC 使用）；内存屏障是 CPU/编译器层面的指令约束（保证可见性和顺序）。前者是「GC 的钩子」，后者是「硬件的顺序规则」。

### Q6：卡表是干什么的？
**答**：把堆按 512B 分卡，用 1 字节省份标记「脏卡」（可能有跨代引用）。Young GC 只扫脏卡，避免扫整个老年代。1GB 堆只需要 2MB 卡表。

### Q7：卡表和 RSet 有什么区别？
**答**：卡表是全局一张，按地址区间标记，用于「老年代 → 新生代」的跨代引用；RSet 是 G1 每个 Region 一份，记录「谁指向我」，用于 Region 级别的回收。

### Q8：G1 怎么做到可预测停顿？
**答**：堆分成约 2048 个 Region，每次只回收 CSet 里的一部分；用历史数据估算每个 Region 的回收成本，在 `MaxGCPauseMillis` 预算内挑「收益/成本」最高的 Region。

### Q9：G1 的 Region 有多大？
**答**：1~32MB 的 2 的幂，默认由堆大小推算（约 2048 个）：4GB 堆 → 2MB（实测 `G1HeapRegionSize=2097152`）。超过半个 Region 的对象进 Humongous 区。

### Q10：为什么 CMS 被废弃？
**答**：标记-清除有内存碎片、可能 `Concurrent Mode Failure`（并发收集跟不上分配，退化成单线程 Full GC），实现复杂。JDK 9 废弃、JDK 14 移除。

### Q11：ZGC 还用三色标记吗？
**答**：ZGC 用**着色指针 + 读屏障**，把对象状态编码在指针的高位里，标记/移动/重映射全部并发。思想同源（并发 + 屏障），实现机制不同，停顿可做到 <1ms。

### Q12：JDK 21 的 GC 有什么变化？
**答**：G1 仍是默认；ZGC 变成分代 ZGC（JEP 439），兼顾低延迟与吞吐；CMS 早已移除；GC 日志统一用 `-Xlog:gc`。

## 11. 一张图总结

```
并发标记
  GC Roots ──► 灰集合 ──► 扫子引用 ──► 对象变黑
                  │
                  └── 用户线程改引用 ──► 可能漏标
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
      增量更新（CMS）                  原始快照 SATB（G1）
   记录「黑->白 新增」             记录「灰->白 被删的旧值」
   黑重新变灰 + 重扫               按快照当存活 -> 浮动垃圾
              │                             │
              └────── 都靠「写屏障」落地 ────┘

辅助结构
  卡表：全局，512B/卡，1GB 堆约 2MB -> 找跨代引用
  RSet：每个 Region 一份 -> 找「谁指向我」
  G1：2048 个 Region（1~32MB）+ CSet + 停顿预测（默认 200ms）
```

## 12. 一句话复盘

> 并发标记必须记录进度，于是有了白/灰/黑三色；灰是唯一还能传播颜色的集合。并发期间「黑色对象新增引用」+「灰到白的引用被删除」会同时掐断所有染色路径，导致活对象被回收。两种补救：增量更新记新增（CMS）、原始快照记被删的旧值（G1），都靠写屏障落地。卡表和 RSet 分别解决「跨代引用」和「Region 外部引用」的扫描成本。

## 13. 自测题（先自己答，再看答案）

**1. 三色的含义分别是什么？哪一色是「还能传播颜色」的？**
答案：白=未访问（会被回收）、灰=自己看过但孩子没扫完、黑=自己和子引用都扫完。只有灰色还能继续传播。

**2. 漏标的两个必要条件？**
答案：① 黑色对象新增指向白色对象的引用；② 所有灰色到该白色对象的引用都被删除。两条同时成立才漏。

**3. 增量更新和 SATB 各记录什么？分别用在哪？**
答案：增量更新记录「黑→白的新增引用」，把黑重新标灰（CMS）；SATB 记录「灰→白被删除时的旧值」，按快照语义处理（G1）。

**4. 写屏障和内存屏障的区别？**
答案：写屏障是 JVM 在引用赋值处插入的记录代码（GC 用）；内存屏障是 CPU/编译器层面的重排约束（可见性/顺序用）。

**5. 1GB 堆的卡表大约多大？怎么算？**
答案：512B 一张卡 → `2^30 / 2^9 = 2^21 ≈ 209 万`张，每张 1 字节 ≈ 2MB，占堆 0.2%。

**6. G1 的 Region 默认多大？`MaxGCPauseMillis` 是保证还是目标？**
答案：4GB 堆时默认 2MB（`G1HeapRegionSize=2097152`）；`MaxGCPauseMillis=200` 是目标值，靠挑 CSet 尽量达成，不是硬保证。
