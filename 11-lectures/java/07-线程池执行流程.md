# 线程池执行一个任务时，线程到底是怎么被复用的？

## 0. 一句话先讲明白

线程池的核心就一句话：**线程不跟着任务走，线程自己活在自己的循环里，任务只是从队列里被取出来执行的一段代码。**

一个工作线程启动后进入一个 `while` 循环：从任务队列里取任务、执行、再取、再执行，直到「队列空了且自己也该被回收了」才退出。所以创建 1 万个任务，真正被创建的线程可能只有 8 个——这就是复用。

而「什么时候创建新线程、什么时候把任务放进队列、什么时候拒绝任务」这套决策，就是 `ThreadPoolExecutor.execute()` 的**四步判断**；决策所需要的数据（池状态 + 线程数）被塞进**一个 32 位整数 `ctl`** 里，高 3 位是状态、低 29 位是线程数。

---

## 1. 痛点背景：不用线程池会发生什么

### 1.1 先解释三个词

| 名词 | 是什么 | 为什么重要 |
|---|---|---|
| 线程（Thread） | 操作系统调度的最小单位，Java 线程一对一映射到内核线程（HotSpot 在 Linux 上用 `clone` 实现） | 创建/销毁都有成本 |
| 上下文切换（context switch） | CPU 从一个线程切到另一个线程，要保存/恢复寄存器、栈指针、程序计数器 | 切换本身不干活，纯开销 |
| 阻塞队列（BlockingQueue） | 一个线程安全、能阻塞取/放的队列 | 线程池的「任务缓冲区」，削峰用 |

### 1.2 具体数字：`new Thread` 到底贵在哪

```
默认线程栈大小：1 MB（64 位 Linux，-Xss 未显式设置时通常是 1MB）
一个请求创建一个线程、处理 20ms 后销毁：
  线程数 = QPS × 0.02
  1000 QPS  -> 20 个线程同时存活（勉强能扛）
  10000 QPS -> 200 个线程 -> 200 MB 栈内存
  突发 5 万 QPS -> 1000+ 线程 -> 1 GB 栈 + 调度器被上下文切换打满
线程创建耗时：0.05 ~ 1 ms（含内核分配 task_struct + 栈）
上下文切换耗时：1 ~ 5 us（同一物理核切换，含缓存失效会更久）
```

**算一笔账**：10 万个「耗时 0.5ms 的短任务」，如果每个任务 `new Thread`，线程创建 + 销毁约 `10 万 × 0.1ms = 10 秒`（纯开销，不含业务），再加上内核 `task_struct` 反复申请释放与调度队列抖动。用线程池复用 8 个线程：创建开销 8 次（可忽略），剩下的时间全在做业务。**这就是线程池存在的第一性理由：把「线程」从「任务」上解耦。**

### 1.3 还有一个更隐蔽的痛点：不可控

`new Thread` 没有任何「上限」概念，流量一冲就无限创建，最终 `java.lang.OutOfMemoryError: unable to create native thread`。线程池把「并发度」变成一个**可配置、可监控、可拒绝**的数字，这是稳定性工程的基础。

## 2. 逐步拆解：七个参数与 execute 四步

### 2.1 七个参数逐个拆

```java
public ThreadPoolExecutor(
    int corePoolSize,                   // 1 核心线程数
    int maximumPoolSize,                // 2 最大线程数
    long keepAliveTime,                 // 3 空闲存活时间
    TimeUnit unit,                      // 4 时间单位
    BlockingQueue<Runnable> workQueue,  // 5 任务队列
    ThreadFactory threadFactory,        // 6 线程工厂
    RejectedExecutionHandler handler)   // 7 拒绝策略
```

| # | 参数 | 精确含义 | 关键边界 |
|---|---|---|---|
| 1 | `corePoolSize` | 常驻线程数上限；**默认不会被回收**（除非开 `allowCoreThreadTimeOut`） | 0 ≤ core ≤ max |
| 2 | `maximumPoolSize` | 线程总数上限（核心 + 临时） | ≥ core，否则构造即抛 `IllegalArgumentException` |
| 3 | `keepAliveTime` | **超出核心数**的那些线程，空闲多久被回收 | 必须 ≥ 0；开核心超时后对核心线程也生效 |
| 4 | `unit` | 时间单位，最终转成纳秒存进 `keepAliveTime` 字段 | `TimeUnit.NANOSECONDS` |
| 5 | `workQueue` | 核心线程占满后，任务的缓冲区 | 有界/无界/容量 0，直接决定 `max` 是否生效 |
| 6 | `threadFactory` | 创建线程的工厂，能改线程名/优先级/守护属性/未捕获异常处理器 | 不设置就全叫 `pool-N-thread-M`，排查问题时很痛苦 |
| 7 | `handler` | 队列满且线程数达 max 时的兜底 | 四种内置 + 自定义 |

**「核心线程」和「最大线程」到底差什么**：只有两点——① 超过 core 的线程会因 `keepAliveTime` 被回收；② `execute` 的扩容路径只在「队列也满了」时才会把线程数从 core 涨到 max。除此之外两者创建方式完全一样（都是 `addWorker` → `new Thread`）。

### 2.2 第一个数字化推导：`ctl` 的 32 位怎么分

```java
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
private static final int COUNT_BITS = Integer.SIZE - 3;          // 32 - 3 = 29
private static final int CAPACITY   = (1 << COUNT_BITS) - 1;      // 2^29 - 1 = 536870911
```

```
 bit 31 30 29 | 28 ................................ 0
 ┌────────────┬─────────────────────────────────────┐
 │  runState  │             workerCount             │
 │   3 bit    │               29 bit                │
 └────────────┴─────────────────────────────────────┘
```

数值推导：

```
低 29 位全 1  -> 2^29 - 1 = 536870911（理论最大线程数，实际远用不到）
高 3 位取值   -> 0 ~ 7，实际只用 5 个状态
RUNNING     = -1 << 29 = 0xE0000000 = -536870912（注意是负数）
SHUTDOWN    =  0 << 29 = 0x00000000 = 0
STOP        =  1 << 29 = 0x20000000 = 536870912
TIDYING     =  2 << 29 = 0x40000000 = 1073741824
TERMINATED  =  3 << 29 = 0x60000000 = 1610612736
```

**为什么必须是 3 位状态而不是 2 位**：2 位只能表示 4 个值，而状态有 5 个（RUNNING / SHUTDOWN / STOP / TIDYING / TERMINATED），不够。只用 3 位是因为状态本来就少，剩下 29 位给线程数绰绰有余（29 位能表示 5.36 亿个线程）。

**为什么要把状态和线程数塞进一个 int**：因为这两者必须**同步变更**。举个例子：状态已经是 STOP 时，绝不允许再创建新线程。如果状态和线程数是两个独立字段，判断+修改之间就可能被别的线程插入（经典的 check-then-act 竞态），要么加锁，要么用两个 CAS（中间态可能不一致）。合并成一个 int 后，一次 `compareAndSet` 就能同时完成「改成 STOP」和「读/写线程数」，不需要锁。

三个位运算辅助方法（把 ctl 拆开）：

```java
private static int runStateOf(int c)     { return c & ~CAPACITY; }   // 取高 3 位
private static int workerCountOf(int c)  { return c &  CAPACITY; }   // 取低 29 位
private static int ctlOf(int rs, int wc) { return rs | wc; }         // 拼回去
```

### 2.3 execute 四步判断（附源码）

```java
public void execute(Runnable command) {
    if (command == null) throw new NullPointerException();
    int c = ctl.get();
    // 第 1 步：工作线程数 < 核心数 -> 建核心线程，并把 command 作为第一个任务
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true)) return;
        c = ctl.get();                       // 失败则重读 ctl 重试（并发下可能已变）
    }
    // 第 2 步：池还在 RUNNING -> 入队
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        if (!isRunning(recheck) && remove(command)) reject(command);      // 池已关闭：回滚 + 拒绝
        else if (workerCountOf(recheck) == 0) addWorker(null, false);    // 线程数为 0：补一个
    }
    // 第 3 步：入队失败（队列满）-> 建非核心线程，直到 max
    else if (!addWorker(command, false)) reject(command);
}
```

注意第 2 步的 **double-check**：`offer` 成功返回后，池状态可能已经被别的线程改成 SHUTDOWN/STOP，所以必须再查一次；而且如果此刻线程数恰好是 0（配置了允许核心线程超时且空闲了很久），任务虽然入队了却没人来取，所以要补一个 worker。

### 2.4 五个状态怎么流转

| 状态 | 触发动作 | 行为 |
|---|---|---|
| `RUNNING` | 初始状态 | 接新任务，处理队列 |
| `SHUTDOWN` | `shutdown()` | 不接新任务，但**继续处理排队中的任务** |
| `STOP` | `shutdownNow()` | 不接新任务、不处理队列、中断正在执行的线程 |
| `TIDYING` | 所有线程都终止后 | 即将执行 `terminated()` 钩子 |
| `TERMINATED` | `terminated()` 执行完 | 线程池彻底结束 |

流转路径只有两条：

```
RUNNING --shutdown()--> SHUTDOWN --队列空且线程数=0--> TIDYING --> TERMINATED
RUNNING --shutdownNow()--> STOP --线程数=0--> TIDYING --> TERMINATED
```

**注意状态是单调往后的**（`RUNNING < SHUTDOWN < STOP < TIDYING < TERMINATED`）。因为 `RUNNING = -1 << 29` 是负数，源码里可以直接用 `if (rs >= SHUTDOWN)` 判断「至少已经关闭」，这是选择把状态放在高位的额外收益。

### 2.5 `addWorker` 里到底做了什么

`addWorker(firstTask, core)` 用一个双层 `for(;;)` 循环做 CAS：

1. 检查池状态是否允许加线程（核心线程要 RUNNING，非核心要 RUNNING 或 SHUTDOWN）
2. 读 `workerCountOf(c)`，若已到上限（core 或 max）就失败返回
3. `compareAndIncrementWorkerCount(c)`：CAS 把线程数 +1，失败就重读 `ctl` 重试
4. 线程数 +1 成功后，`new Worker(firstTask)` → `new Thread(w)` → `t.start()`
5. 若线程启动失败，回滚线程计数并抛 `IllegalThreadStateException`

### 2.6 线程复用发生在 `runWorker` 的循环里

```java
final void runWorker(Worker w) {
    Runnable task = w.firstTask;
    w.firstTask = null;
    w.unlock();                                  // 允许中断
    while (task != null || (task = getTask()) != null) {   // ← 复用就在这里
        w.lock();
        try {
            beforeExecute(w, task);
            task.run();                          // 业务代码
            afterExecute(task, null);
        } finally { task = null; w.completedTasks++; w.unlock(); }
    }
    processWorkerExit(w, false);
}
```

线程启动后并不退出，而是不断 `getTask()` 取下一个任务。**只有 `getTask()` 返回 null，线程才会死。**

### 2.7 第二个数字化推导：`getTask` 什么时候返回 null

```java
boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;   // 是否用「带超时的取」
Runnable r = timed ? workQueue.poll(keepAliveTime, TimeUnit.NANOSECONDS)   // 超时返回 null
                   : workQueue.take();                                      // 永久阻塞
if (r != null) return r;
if ((wc > maximumPoolSize || (timed && timedOut))
        && (wc > 1 || workQueue.isEmpty())) {
    if (compareAndDecrementWorkerCount(ctl)) return null;   // 唯一正常退出路径
    continue;
}
```

把判断拆成两种场景：

| 场景 | `timed` | 取任务方式 | 什么时候死 |
|---|---|---|---|
| 线程数 ≤ core（默认） | false | `take()` 永久阻塞 | 只有异常/中断/池关闭才死 |
| 线程数 > core | true | `poll(keepAliveTime)` | 空闲超过 keepAliveTime 且计数扣减成功 |
| 开了 `allowCoreThreadTimeOut(true)` | true（对核心也生效） | `poll(keepAliveTime)` | 低峰期核心线程也会被回收，池能缩到 0 |

**为什么还需要 `timedOut` 这个标记**：`poll` 超时返回 null 后，如果直接去扣减线程数，可能因为并发失败（比如别人刚加了线程）而 `continue` 回到循环，又 `poll` 一次——不记录「我已经超时过」，就会无限循环「超时→失败→再超时」。`timedOut` 让第二次判断读的是「上一轮确实超时了」这个事实，配合 `wc > 1` 保证池里至少留一个线程处理队列。

## 3. 完整推导：一次 execute 的六种结局

把 `execute` 的每个分支推到具体结果：

```
execute(task)
 ├─ ① 线程数 < core              -> addWorker(task, true)  建核心线程，任务直接跑
 ├─ ② 线程数 >= core，队列未满   -> offer 成功，任务入队
 │      └─ double-check：池已 STOP -> remove + reject
 │      └─ double-check：线程数=0 -> addWorker(null, false) 补位
 ├─ ③ 队列已满，线程数 < max     -> addWorker(task, false) 建临时线程
 ├─ ④ 队列已满，线程数 >= max    -> reject(handler)
 ├─ ⑤ 池状态 >= STOP             -> reject（execute 里 isRunning 为 false 且 offer 也会失败）
 └─ ⑥ command == null            -> NullPointerException
```

**结局⑤ 特别容易被忽略**：`shutdownNow()` 之后再 `execute`，即使队列还空着也会走拒绝——因为 `isRunning(c)` 为 false，直接跳到 `else if (!addWorker(...)) reject(...)`。

### 3.1 第三个数字化推导：线程数到底该设多少

先用**利特尔法则（Little's Law）**：系统内平均任务数 `L = 到达率 λ × 平均停留时间 W`。放线程池里：

```
需要的并发线程数 ≈ 每秒任务数 × 每个任务的平均耗时（秒）
例：1000 QPS，每个任务耗时 20ms(0.02s)
  -> 1000 × 0.02 = 20 个线程（这是下限，要留 buffer 就 1.5~2 倍）
```

再用 **Brian Goetz 的 CPU 利用率公式**：

```
N_threads = N_cpu × U_cpu × (1 + W/C)
  N_cpu = 可用核数（Runtime.getRuntime().availableProcessors()）
  U_cpu = 目标 CPU 利用率（0~1）
  W/C   = 等待时间 / 计算时间
```

| 任务类型 | W/C 大概 | 8 核机器建议 | 理由 |
|---|---|---|---|
| CPU 密集（纯计算） | ≈ 0 | 8 + 1 = 9 | 多 1 个兜住偶发缺页/中断 |
| 混合（算一半等一半） | ≈ 1 | 8 × 2 = 16 | 等待时让出 CPU |
| IO 密集（RPC/DB） | ≈ 3~7 | 32 ~ 64 | 大部分时间在等网络 |

**注意公式的局限**：它假设线程之间互不依赖、没锁竞争、下游不会被打挂。真实场景必须**压测 + 观察队列长度和拒绝数**，而不是背公式。

## 4. 极简模型：2 个线程 + 容量 2 的队列

把参数压到最小，完整走一遍：

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    2,                              // core = 2
    4,                              // max  = 4
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(2),    // 队列容量 2
    new ThreadPoolExecutor.AbortPolicy());
```

提交 7 个任务（每个任务 sleep 100ms），逐个看归属：

| 任务 | 当时线程数 | 队列 | 走哪一步 | 结果 |
|---|---|---|---|---|
| T1 | 0 | 0/2 | 第 1 步（< core） | 新建核心线程 C1 |
| T2 | 1 | 0/2 | 第 1 步（< core） | 新建核心线程 C2 |
| T3 | 2 | 0/2 | 第 2 步 | 入队（占 1） |
| T4 | 2 | 1/2 | 第 2 步 | 入队（占 2，满了） |
| T5 | 2 | 2/2 | 第 3 步（队列满，< max） | 新建临时线程 T1' |
| T6 | 3 | 2/2 | 第 3 步（< max） | 新建临时线程 T2' |
| T7 | 4 | 2/2 | 第 4 步（= max） | `AbortPolicy` 抛异常 |

时间线上看：

```
t=0ms   T1,C1 开始跑；T2,C2 开始跑
t=0ms   T3,T4 在队列里等
t=0ms   T5 -> T1'；T6 -> T2'（因为队列满了，才扩容到 max）
t=0ms   T7 -> 拒绝
t=100ms C1/C2/T1'/T2' 四个线程几乎同时空闲 -> 从队列取 T3,T4 -> 跑
t=200ms 四个线程空闲 -> 线程数从 4 回落到 2（临时线程 keepAlive 到期）
```

**这张表就是「为什么先入队、队列满了才扩容」的最直观证据**：如果先扩到 max 再入队，T5/T6 会变成第 3、4 个线程，而 T3/T4 还在排队——线程空转率反而更高。

## 5. 为什么这样设计：四个被否决的方案

### 5.1 方案一：一个任务一个线程（不使用池）

- 做法：`new Thread(task).start()`，最朴素
- 优点：实现零成本，任务之间完全隔离
- 否决原因：创建/销毁成本 × 任务数；无上限；无法统一监控和拒绝。**线程池的「池」字本质是资源复用 + 集中治理。**

### 5.2 方案二：先扩容到 max，再排队

- 优点：延迟更低（任务立刻有线程接）
- 否决原因：线程是昂贵资源，任务能进队列说明**它可以等**；为「可等的任务」创建真实线程，等于用内存换一点点延迟，还会让线程数在低负载时居高不下。反过来需要「先扩容」语义时，把队列换成容量 0 的 `SynchronousQueue` 即可（`CachedThreadPool` 就是这么干的）——需求被一个参数覆盖，不必改算法。

### 5.3 方案三：无界队列 + 固定线程数（`Executors.newFixedThreadPool`）

- 优点：实现简单，任务永不拒绝
- 否决原因：`LinkedBlockingQueue` 默认容量是 `Integer.MAX_VALUE`（约 21 亿），队列永远不满 ⇒ `maximumPoolSize` 形同虚设 ⇒ 任务堆积到把堆撑爆（`OutOfMemoryError: Java heap space`）。而且失败来得非常晚：不是拒绝时暴露，而是几天后 OOM。

### 5.4 方案四：不设最大线程数，用负反馈自动伸缩（仿 `CachedThreadPool`）

- 优点：弹性好，理论上能扛突发
- 否决原因：`max = Integer.MAX_VALUE` + `SynchronousQueue` ⇒ 每个提交的任务都要立刻有线程接，接不到就新建 ⇒ 突发流量下线程数无上限 ⇒ `unable to create native thread`。线程数失控比任务被拒绝更危险：拒绝只是丢请求，线程爆炸会拖死整台机器。

**设计结论**：默认用「核心线程 + 有界队列 + 有限 max + 拒绝策略」形成**闭环**，把过载显式暴露成拒绝，而不是静默堆积或静默爆炸。这也是为什么大厂规范直接禁止 `Executors` 的快捷工厂方法。

## 6. 关键参数为什么是这个值

| 参数 | 常见取值 | 为什么是这个值 |
|---|---|---|
| `COUNT_BITS` | 29 | int 32 位，状态至少要 3 位（5 个状态），剩余 29 位足够表示线程数 |
| 状态位 | 3 bit | 2 bit 只有 4 个值不够 5 个状态；4 bit 又浪费线程数位数 |
| `CAPACITY` | `2^29-1 = 536870911` | 低 29 位全 1 掩码，位运算取线程数 |
| `keepAliveTime` 默认 | 60 s | `CachedThreadPool` 的经验值：空闲 1 分钟回收，兼顾「偶发复用」和「腾出资源」 |
| 队列容量 | 200 ~ 2000 | 太小频繁扩容/拒绝，太大延迟高且掩盖问题；常用「QPS × 可接受延迟秒数」估算 |
| `corePoolSize` | N_cpu+1（CPU 密集）/ 2N 起（IO 密集） | 见 3.1 的公式，配压测修正 |
| `maximumPoolSize` | 2×core ~ 4×core | 给突发留余量，但要受下游连接池、DB 连接数约束（线程再多，连接池只有 20 个也白搭） |
| `allowCoreThreadTimeOut` | false | 默认不回收核心线程，避免流量抖动时反复创建/销毁 |

**一个容易被忽略的联动**：线程数上限不是独立变量，它必须 ≤ 下游资源的并发上限。比如 DB 连接池 20、Redis 连接池 50，那线程池设到 200 只会让 180 个线程在等连接。

## 7. 版本演进

| 版本 | 变化 | 影响 |
|---|---|---|
| JDK 5 | 引入 `ThreadPoolExecutor`（JSR-166，Doug Lea） | 线程池成为标准库能力 |
| JDK 6 | 增加 `allowCoreThreadTimeOut`、`shutdownNow` 语义完善 | 支持低峰缩容 |
| JDK 7 | `ForkJoinPool` 加入（分治 + 工作窃取） | 适合可拆分的 CPU 密集任务 |
| JDK 8 | `CompletableFuture` 默认用 `ForkJoinPool.commonPool()` | 异步编排普及，但 commonPool 是共享的，容易互相影响 |
| JDK 9 | `ThreadPoolExecutor` 增加 `shutdown` 相关完善；`availableProcessors` 更严格地感知容器 CPU 限额 | 容器化部署时线程数更合理 |
| JDK 19（预览）/ JDK 21（正式） | **虚拟线程**：`Thread.ofVirtual()`、`Executors.newVirtualThreadPerTaskExecutor()` | IO 密集场景不必再纠结线程数；但线程池仍然用于「限流/隔离/资源池」（如连接池），只是不再是「一个任务一个平台线程」 |
| JDK 21 | `ThreadPoolExecutor` 源码基本没变 | 八股考点仍是 `ctl` 与四步判断 |

**虚拟线程为什么没有淘汰线程池**：

1. 虚拟线程是「便宜的线程」，但下游连接（DB 连接、HTTP 连接）仍然有限，需要池化 + 限流
2. 虚拟线程不适合 CPU 密集任务（调度开销比平台线程高）
3. 大量虚拟线程同时打下游会压垮依赖，仍要 `Semaphore` 之类的并发限制

所以在 Java 21 里更准确的表述是：**「线程池」这个词的语义从「复用平台线程」转向「资源池 + 并发限流」**，而 `ThreadPoolExecutor` 的四步判断依然是理解并发限流的入口。

## 8. 亲手验证：看四步判断与回收

### 8.1 四步判断与拒绝

```java
import java.util.concurrent.*;

public class PoolDemo {
    public static void main(String[] args) throws Exception {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                2, 4, 60, TimeUnit.SECONDS, new ArrayBlockingQueue<>(2),
                r -> new Thread(r, "biz-pool-" + System.nanoTime()),
                new ThreadPoolExecutor.AbortPolicy());

        for (int i = 1; i <= 7; i++) {
            final int n = i;
            try {
                pool.execute(() -> {
                    try { Thread.sleep(100); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                });
                System.out.printf("T%d 提交成功  pool=%d queue=%d%n",
                        n, pool.getPoolSize(), pool.getQueue().size());
            } catch (RejectedExecutionException e) {
                System.out.printf("T%d 被拒绝    pool=%d queue=%d%n",
                        n, pool.getPoolSize(), pool.getQueue().size());
            }
        }
        pool.shutdown();
        pool.awaitTermination(3, TimeUnit.SECONDS);
        System.out.println("全部结束");
    }
}
```

预期输出（线程调度有细微差异，但数字应一致）：

```
T1 提交成功  pool=1 queue=0
T2 提交成功  pool=2 queue=0
T3 提交成功  pool=2 queue=1
T4 提交成功  pool=2 queue=2
T5 提交成功  pool=3 queue=2
T6 提交成功  pool=4 queue=2
T7 被拒绝    pool=4 queue=2
全部结束
```

### 8.2 复刻 ctl 的位运算

```java
public class CtlDemo {
    public static void main(String[] args) {
        int COUNT_BITS = 29;
        int CAPACITY = (1 << COUNT_BITS) - 1;
        int RUNNING = -1 << COUNT_BITS, SHUTDOWN = 0 << COUNT_BITS, STOP = 1 << COUNT_BITS;
        System.out.println("CAPACITY   = " + CAPACITY);       // 536870911
        System.out.println("RUNNING    = " + RUNNING);        // -536870912
        System.out.println("SHUTDOWN   = " + SHUTDOWN);       // 0
        System.out.println("STOP       = " + STOP);           // 536870912
        System.out.println("RUNNING<SHUTDOWN ? " + (RUNNING < SHUTDOWN));   // true

        int ctl = RUNNING | 3;                 // 模拟 RUNNING + 3 个线程
        System.out.println("state = " + (ctl & ~CAPACITY));   // -536870912
        System.out.println("count = " + (ctl & CAPACITY));    // 3
    }
}
```

预期输出：

```
CAPACITY   = 536870911
RUNNING    = -536870912
SHUTDOWN   = 0
STOP       = 536870912
RUNNING<SHUTDOWN ? true
state = -536870912
count = 3
```

### 8.3 核心线程回收

```java
import java.util.concurrent.*;
public class RecycleDemo {
    public static void main(String[] args) throws Exception {
        ThreadPoolExecutor p = new ThreadPoolExecutor(2, 2, 100, TimeUnit.MILLISECONDS,
                new LinkedBlockingQueue<>());
        p.execute(() -> System.out.println("跑一次"));
        Thread.sleep(600);
        System.out.println("默认不回收核心线程，poolSize=" + p.getPoolSize());   // 1（只创建了 1 个线程）
        p.allowCoreThreadTimeOut(true);
        Thread.sleep(800);
        System.out.println("允许超时后，poolSize=" + p.getPoolSize());           // 0
        p.shutdown();
    }
}
```

预期见上方注释：核心线程默认常驻（这里只提交了 1 个任务，所以池里只有 1 个线程）；开启 `allowCoreThreadTimeOut` 后空闲超时被回收，缩到 0。

## 9. 常见误区

| 错误说法 | 正确说法 |
|---|---|
| 「线程池先扩到 max，再排队」 | 先核心线程 → 入队 → 队列满才扩到 max → 拒绝，顺序反了 |
| 「`maximumPoolSize` 一定会被用到」 | 队列无界时永远不扩容，max 是死参数 |
| 「核心线程不会死」 | 默认不会；`allowCoreThreadTimeOut(true)` 后会被回收 |
| 「`Worker` 继承 AQS 是为了实现可重入锁」 | 它的 `state` 表示「线程是否正忙」，用于安全地 `interrupt` 空闲线程 |
| 「`submit` 和 `execute` 只是返回值不同」 | `submit` 的异常被 `FutureTask` 吞掉，不 `get()` 就静默失败 |
| 「`shutdown()` 会丢掉队列里的任务」 | 会跑完存量；`shutdownNow()` 才中断并 `drainQueue` |
| 「线程池越大约好」 | 线程数受下游连接池约束，过多只会增加切换和排队 |
| 「`newFixedThreadPool` 安全」 | 无界队列 ⇒ 堆 OOM，规范禁止 |

## 10. 连续追问 Q&A

### Q1：`ctl` 为什么用 `AtomicInteger` 不用 `volatile int` + 锁？

因为要保证「状态 + 线程数」的复合操作原子。`volatile int` 只保证可见性，`workerCountOf(c) < core` 判断和 `+1` 之间会被并发插入。`AtomicInteger.compareAndSet` 把读-判-改做成一个原子操作，配合失败重试，完全不需要锁。

### Q2：`addWorker` 为什么要套一个 `for(;;)`？

因为 `workerCountOf(ctl)` 可能被其他线程改。伪代码：读 ctl → 算线程数 → 判断是否超上限 → CAS 递增。CAS 失败说明有人抢先修改了，必须重读重算。两层循环分别处理「状态是否允许」（外层）和「线程数是否超限」（内层）。

### Q3：`Worker` 继承 `AbstractQueuedSynchronizer`，但从来没人 `acquire` 它，为什么？

因为它用 AQS 的 `state` 当「忙闲标记」而不是当锁用：`runWorker` 执行任务前 `w.lock()`（CAS 0→1），执行完 `w.unlock()`。`interruptIdleWorkers` 里用 `tryLock()` 判断：拿得到锁说明线程空闲，可以安全 `interrupt`；拿不到说明正在跑任务，不能打断。这比单独维护 `volatile boolean busy` 更省，还能复用 AQS 的 CAS 与排队语义。

### Q4：为什么构造 `Worker` 时先把 `state` 置为 -1？

`Worker` 构造器里 `setState(-1)`，是为了在 `t.start()` 之前禁止中断（此时线程还没跑起来，中断会丢失或异常）。`runWorker` 一开始 `w.unlock()` 把状态放开，之后才能正常响应中断。

### Q5：核心线程数设为 0 会怎样？

第一次 `execute` 时 `workerCountOf(c) < 0` 不成立，直接入队；入队成功后 double-check 发现 `workerCountOf(recheck) == 0`，于是 `addWorker(null, false)` 补一个线程。所以 core=0 也能工作，适合「流量间歇、希望完全缩容到 0」的场景，代价是首次请求有建线程延迟。

### Q6：拒绝策略怎么选？

- 必须让调用方知道失败：`AbortPolicy`（默认，抛 `RejectedExecutionException`）
- 不能丢任务但可以变慢：`CallerRunsPolicy`（提交线程自己执行，天然背压，但会阻塞上游 Web 线程）
- 可丢的埋点/日志：`DiscardPolicy`；只关心最新值（如状态刷新）：`DiscardOldestPolicy`

生产上更常见的是**自定义策略**：落库/写 MQ 异步补偿 + 打点告警，而不是简单丢弃。

### Q7：`submit` 提交的任务抛异常为什么没日志？

`submit` 会把任务包装成 `FutureTask`，异常被捕获存进 `outcome` 字段，只有调用 `future.get()` 才会以 `ExecutionException` 抛出来。而 `execute` 路径下异常会冒泡到 `runWorker`，触发 `processWorkerExit(w, true)`（换线程）并交给 `UncaughtExceptionHandler`。

### Q8：`shutdown` 之后还能提交任务吗？

不能。`shutdown()` 后状态是 SHUTDOWN，`execute` 里 `isRunning(c)` 为 false，直接走 `addWorker` 失败分支 → 拒绝。但**已经入队的任务会被继续执行完**（`getTask` 在 SHUTDOWN 下仍会 `take` 队列）。

### Q9：`SynchronousQueue` 为什么能让线程池「先扩容再排队」？

`SynchronousQueue` 容量是 0，`offer` 只有在正好有线程在等任务时才成功，否则立即返回 false。于是 `execute` 的第 2 步必然失败，直接进入第 3 步扩容——效果等价于「先扩线程」。`CachedThreadPool` 就是 `SynchronousQueue` + `max=Integer.MAX_VALUE`。

### Q10：线程池大小估算公式在虚拟线程下还成立吗？

不成立。公式的本质是「用线程数掩盖阻塞」，而虚拟线程的阻塞不占平台线程，所以 IO 密集理论上可以「一任务一虚拟线程」。此时瓶颈转移到**下游资源**：DB 连接池、HTTP 连接、CPU 密集段。正确的做法是给下游加并发限制（`Semaphore` 或连接池），而不是继续调线程数。

## 11. 一张图总结

```
execute(task)
   │
   ├─ workerCount < core ────────────► addWorker(task, true) ──► 新核心线程
   │
   ├─ queue.offer(task) 成功 ────────► 入队
   │        └─ recheck：STOP?  → remove + reject
   │        └─ recheck：wc==0? → addWorker(null, false) 补位
   │
   ├─ 队列满 & wc < max ─────────────► addWorker(task, false) ─► 新临时线程
   │
   └─ 队列满 & wc >= max ────────────► RejectedExecutionHandler

工作线程（复用循环）
   runWorker: while (task != null || (task = getTask()) != null)
                  w.lock() → task.run() → afterExecute → w.unlock()
   getTask: timed ? poll(keepAliveTime) : take()
            超时且 wc 可扣减 → return null → 线程退出（processWorkerExit）
```

---

## 12. 一句话复盘

> 线程池用一个 `while` 循环让线程不跟着任务生死，用「核心线程 → 队列 → 扩容到 max → 拒绝」四步判断控制线程数量，用一个 `ctl` 把状态和线程数合在一起实现无锁的状态机，用「有界队列 + 有限 max + 拒绝策略」把过载显式暴露出来；线程数不是背公式，而是压测 + 观察队列 + 受下游资源约束的结果。

## 13. 自测题（先自己答，再看答案）

**1. `ctl` 为什么用高 3 位放状态、低 29 位放线程数？反过来不行吗？**

答案：可以反过来，但不划算。状态是负数（`RUNNING = -1 << 29`）时，放在高位可以让「状态比较」直接用整数的 `<` / `>=`（负数比正数小），源码里 `rs >= SHUTDOWN` 这类判断到处都是；如果把状态放低位，每取一次状态都要掩码移位。另外 29 位存线程数足够，3 位存状态也刚好够。

**2. 队列满、线程数已达 max，此时提交任务会怎样？**

答案：调用 `RejectedExecutionHandler`。默认 `AbortPolicy` 抛 `RejectedExecutionException`；如果用的是 `CallerRunsPolicy`，则由提交任务的线程自己执行。

**3. 为什么 `getTask` 里需要 `timedOut` 变量？**

答案：防止「poll 超时 → 扣减线程数 CAS 失败 → continue → 再 poll」的抖动。`timedOut` 记录上一轮确实超时过，第二次进入时不再依赖新一轮 `poll` 的结果就允许退出。

**4. 一个 IO 密集服务，8 核，单请求平均耗时 100ms（其中 95ms 在等 DB），QPS 800，线程池该设多少？**

答案：用 Little's Law：800 × 0.1 = 80 个线程（下限）；用公式：8 × 0.8 × (1 + 95/5) ≈ 102。但要先确认 DB 连接池是否能支撑 80+ 并发，否则线程再多也只是在等连接。

**5. 为什么 `submit` 提交的任务抛异常后线程不会被替换？**

答案：`submit` 把任务包进 `FutureTask`，异常被 `FutureTask.run` 捕获放进 `outcome`，不会冒泡到 `runWorker`，所以 `processWorkerExit(w, true)` 不会触发，线程继续复用。`execute` 路径才会「异常 → 线程退出 → 补新线程」。

**6. 线程池的线程是守护线程还是用户线程？会影响 JVM 退出吗？**

答案：默认由 `Executors.defaultThreadFactory` 创建，是非守护线程，所以线程池不 `shutdown` 时 JVM 不会退出。可以自定义 `ThreadFactory` 设置 `setDaemon(true)`，但通常不这么做——而是显式管理生命周期（`@PreDestroy` / `destroy()`）。
