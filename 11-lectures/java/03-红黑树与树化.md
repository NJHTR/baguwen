# 红黑树与树化：为什么阈值是 8 和 64，退化又是 6？

## 0. 一句话先讲明白

JDK 8 的 HashMap 在「单个桶的链表太长」时，会把这条链表换成**红黑树**，让最坏查询从 O(n) 变成 O(log n)。
触发条件是：**桶内链表节点数达到 8，并且整个 table 的容量 ≥ 64**；容量不够 64 时先扩容（`resize`），不树化。
树节点降回 **6** 个时退化回链表（缓冲带，避免 7/8 之间反复转换）。

```java
static final int TREEIFY_THRESHOLD = 8;         // 链表 -> 树
static final int UNTREEIFY_THRESHOLD = 6;       // 树 -> 链表
static final int MIN_TREEIFY_CAPACITY = 64;     // 容量不足这个值，先扩容不树化
```

---

## 1. 它解决什么问题（先讲痛点，不讲定义）

哈希表的核心假设是「hash 打得散，每个桶里没几个元素」。一旦这个假设被破坏，比如：

- 某个类的 `hashCode()` 实现很糟糕，几千个 key 全是同一个值；
- 攻击者故意构造大量 hashCode 相同的 key 发过来（**哈希碰撞攻击**）；
- `hash & (n-1)` 之后大量 key 落到同一个桶。

那么所有元素都会堆在同一个桶里，形成一条长链表。此时：

- 查询变成遍历链表，**O(n)**；
- 插入也要遍历链表（JDK 8 尾插），**O(n)**；
- 一次请求查 1 万次、每次走 1 万节点的链表 = 1 亿次比较，CPU 直接打满。

**JDK 7 在结构上没有兜底手段**：不管碰撞多严重，都是链表。JDK 8 引入红黑树，就是为了让「最坏情况」也保持在 O(log n)：1 万个节点最多比较约 14 次，而不是 1 万次。

这里要分清两个词：

| 名词 | 是什么 |
|---|---|
| 链表 | 一个节点通过 `next` 指向下一个，查找要一个个走，O(n) |
| 红黑树 | 一种自平衡二叉搜索树，用「颜色 + 旋转」维持近似平衡，查找 O(log n) |

## 2. 一步步拆开：树化到底发生了什么

### 2.1 触发点一：put 时的计数

`putVal` 在链表尾部插入新节点后：

```java
for (int binCount = 0; ; ++binCount) {
    if ((e = p.next) == null) {
        p.next = newNode(hash, key, value, null);
        if (binCount >= TREEIFY_THRESHOLD - 1)   // binCount 从 0 起，等价于「要到第 9 个节点」
            treeifyBin(tab, hash);
        break;
    }
    ...
}
```

**注意这个 `-1`**：`binCount` 从 0 开始数，等于「已遍历的节点数减 1」。所以判断成立时，桶里已经有 9 个节点了。
也就是说 —— **「链表到 8 就转红黑树」是被简化的说法，真正调用 `treeifyBin` 是在插入第 9 个节点时。**

实测（反射读 `table[i]` 的类型）：插入第 2~8 个节点时桶里是 `Node`，插入第 9 个时变成 `TreeNode`。

### 2.2 触发点二：`treeifyBin` 里的容量门槛

```java
final void treeifyBin(Node<K,V>[] tab, int hash) {
    int n, index; Node<K,V> e;
    if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)
        resize();                                   // 容量 < 64：只扩容，不树化
    else if ((e = tab[index = (n - 1) & hash]) != null) {
        TreeNode<K,V> hd = null, tl = null;
        do {
            TreeNode<K,V> p = replacementTreeNode(e, null);
            if (tl == null) hd = p; else { p.prev = tl; tl.next = p; }
            tl = p;
        } while ((e = e.next) != null);
        if ((tab[index] = hd) != null)
            hd.treeify(tab);                        // 真正建树
    }
}
```

两个要点：

1. **容量 < 64 时它调用的是 `resize()`**，不是「什么都不做」。也就是说小表遇到长链表，先尝试扩容摊薄。
2. 建树的顺序是：先把 `Node` 链换成 `TreeNode` 双向链（复用 `next`，并用 `prev` 串起来），再调用 `hd.treeify(tab)` 逐个插入成一棵红黑树。

### 2.3 节点长什么样

```java
static class Node<K,V> {              // 链表节点
    final int hash; final K key; V val; Node<K,V> next;
}
static final class TreeNode<K,V> extends LinkedHashMap.Entry<K,V> {
    TreeNode<K,V> parent;             // 父
    TreeNode<K,V> left, right;        // 左右孩子
    TreeNode<K,V> prev;               // 前驱（保留链表能力，便于退化和遍历）
    boolean red;                      // 颜色
}
```

`TreeNode` 之所以还保留 `next`/`prev`，是为了：① 扩容拆树、退化时不用重建链表；② 遍历和删除时能沿链表走；③ `Iterator` 仍然简单。

### 2.4 红黑树的五条性质

| 编号 | 性质 | 作用 |
|---|---|---|
| 1 | 每个节点非红即黑 | 颜色的定义 |
| 2 | 根节点是黑色 | 简化边界 |
| 3 | 叶子（`null`）视为黑色 | 统一「黑高」计算 |
| 4 | 红节点的两个孩子必须是黑 | 不能有连续红节点 |
| 5 | 任一节点到其所有叶子的路径上黑节点数相同（黑高相等） | 保证「最长路径 ≤ 2 倍最短路径」 |

性质 4 + 5 合起来推出：**最长路径最多是最短路径的 2 倍**，所以树高 ≤ 2·log₂(n+1)，查找 O(log n)。这不是严格平衡（AVL 要求左右子树高度差 ≤1），但足够用，且插入删除的调整次数更少。

### 2.5 插入后怎么调整

新节点默认染**红**（染黑会破坏黑高 5，修复代价大）。插入后如果父节点是黑的，直接结束；如果父节点是红的，违反性质 4，分三种情况处理（`fixAfterInsertion`）：

```
情况 1：叔叔是红的        -> 父、叔染黑，祖父染红，当前节点上移到祖父继续检查
情况 2：叔叔是黑的 + 当前是右孩子 -> 对父节点左旋，转成情况 3
情况 3：叔叔是黑的 + 当前是左孩子 -> 父染黑、祖父染红，对祖父右旋，结束
```

左旋/右旋都是 O(1) 的指针操作（改 3 个指针），所以插入调整最多 O(log n) 次变色和 O(1) 次旋转（实际最多 2 次旋转）。

## 3. 完整推导：为什么是 8、6、64

### 3.1 为什么是 8：用泊松分布算概率

JDK 源码注释给的前提：**如果 hashCode 是随机均匀的，一个桶里的节点数近似服从泊松分布**，参数 λ 取约 0.5（源码注释原话是 "with a parameter of about 0.5 on average for the default resizing threshold of 0.75"）。

泊松分布公式：

```
P(k) = e^(-λ) · λ^k / k!
```

代入 λ = 0.5：

| 桶内节点数 k | 概率 P(k) |
|---|---|
| 0 | 0.60653066 |
| 1 | 0.30326533 |
| 2 | 0.07581633 |
| 3 | 0.01263606 |
| 4 | 0.00157952 |
| 5 | 0.00015795 |
| 6 | 0.00001316 |
| 7 | 0.00000094 |
| 8 | **0.00000006** |
| 9 及以上 | 小于千万分之一 |

（上表是用 `Math.exp(-0.5)` 和阶乘逐项算出来的，与 JDK 源码注释里的数字逐位一致。）

**结论**：在哈希均匀的前提下，一个桶里出现 8 个节点的概率是 **6e-8**，即一千万次里不到一次。所以：

- 树化几乎只会在「hashCode 实现糟糕」或「恶意构造」时发生；
- 因此把阈值定在 8，日常根本不会触发，树结构那点额外内存也无所谓；
- 定得再低（比如 4）就会频繁误触发树化，反而拖慢正常场景。

### 3.2 为什么是 8：和链表的成本交叉点

从「查找比较次数」看：

- 链表：平均比较 n/2 次，最坏 n 次；
- 红黑树：比较次数 ≤ 树高 ≤ 2·log₂(n+1)。

代入 n = 8：链表平均 4 次；红黑树上界 `2·log₂(9) = 6.34`，实际约 3~4 次。
n = 6：链表平均 3 次；红黑树上界 `2·log₂(7) = 5.6`，实际 2~3 次。

**两者在 n≈6~8 附近才交叉**，再考虑 `TreeNode` 的内存是 `Node` 的两倍，所以把树化的门槛放在 8 是「划算的临界点」。n 更大时树明显更优，n 更小时链表更简单更快。

### 3.3 为什么是 6：缓冲带

如果树化和退化都用 8：

- 桶内 8 个节点 → 树化；
- 删掉一个变成 7 → 又退化回链表；
- 再插一个变 8 → 又树化……

**来回抖动**，每次都要建树/拆树，成本很高。
所以退化阈值取 6，在 7 和 8 之间留出一格缓冲：树化后要连续删到 6 才退化，退化后要连续插到 9 才再树化。

**注意一个细节**：`UNTREEIFY_THRESHOLD = 6` 主要用在 `TreeNode.split`（扩容拆树时），而 `removeTreeNode` 是**按树的形状**判断「太小了就退化」，不是直接和 6 比较。这是很多人答错的地方。

### 3.4 为什么还要 `MIN_TREEIFY_CAPACITY = 64`

源码注释：

> `MIN_TREEIFY_CAPACITY`: The smallest table capacity for which bins may be treeified. (Otherwise the table is resized if too many nodes in a bin.) Should be at least 4 * TREEIFY_THRESHOLD to avoid conflicts between resizing and treeification thresholds.

两层意思：

1. **容量小的时候，碰撞多半是「桶太少」造成的**。16 个桶放 20 个元素，必然有桶撞；这时候扩容（桶变多）比树化（结构变复杂）更划算；
2. **门槛要足够高（至少 4×8=64）**，否则「扩容」和「树化」两个阈值会互相打架：刚树化完又触发扩容，树白建。

所以逻辑是：桶里到 9 个 → 想树化 → 一看容量才 16 → 先扩容成 32 → 还是不够 64 → 再扩到 64 → 下次再撞才真正树化。

### 3.5 内存账：`TreeNode` 到底多占多少

按 64 位 JVM、开启压缩指针（引用 4 字节、对象头 12 字节、8 字节对齐）逐字段数：

```
Node:       12(头) + 4(hash) + 4(key) + 4(val) + 4(next)                      = 28 -> 对齐 32 字节
LinkedHashMap.Entry: 32 + 4(before) + 4(after)                                = 40 -> 对齐 40 字节
TreeNode:   40 + 4(parent) + 4(left) + 4(right) + 4(prev) + 1(red)            = 57 -> 对齐 64 字节
```

**`TreeNode` 是 `Node` 的 2 倍**（64 vs 32），这正是源码注释里那句 "TreeNodes are about twice the size of regular nodes" 的来历。所以树化只发生在「确实有必要」的时候。

## 4. 极简模型：4 个节点看旋转

把红黑树缩小到 4 个节点，看一次「情况 3」的调整：

```
插入 10、20、30（都往右长，形成一条链）：
        10(黑)
          \
          20(红)
            \
            30(红)          <- 违反性质 4：20 和 30 都是红

调整：父 20 染黑、祖父 10 染红，对祖父 10 左旋
        20(黑)
       /      \
    10(红)   30(红)

现在根黑、没有连续红节点，完成。
```

对比「同样的 3 个节点在链表里」：查 30 要比较 3 次；树里比较 2 次。节点少时差距不大，节点到 8 以上时树开始明显占优 —— 这就是第 3.2 节「成本交叉点」的具体样子。

## 5. 为什么这样设计（被否决的四个方案）

**方案 A：用 AVL 树。** AVL 要求「任意节点左右子树高度差 ≤ 1」，比红黑树更平衡，查找更快（树更矮）。
否决原因：AVL 的**插入/删除要维护平衡因子，旋转次数明显更多**；HashMap 是读写混合结构，插入也是高频操作，写路径更贵不划算。红黑树牺牲一点查找换更少的旋转，更适合 Map。

**方案 B：用跳表。** 跳表查找 O(log n)，实现比红黑树简单（不用旋转），Redis 的 ZSet 就用它。
否决原因：跳表节点要带**多层索引指针**，内存开销比红黑树更大（红黑树只多 2 个指针 + 1 个颜色位）；跳表依赖随机层数，行为不确定；而且 Java 里没有现成可复用的跳表实现，红黑树在 `TreeMap` 里已经写好。**在内存敏感、确定性强这两个维度上红黑树更优。**

**方案 C：一开始就把所有桶建成树（全量树化）。** 既然树快，为什么不干脆全用树？
否决原因：`TreeNode` 是 `Node` 的两倍内存，绝大多数桶只有 0~1 个元素，树化纯属浪费；而且单个节点的桶用链表/直接放最快，根本不需要树。

**方案 D：不树化，只靠扩容。** 碰撞就扩容，桶多了自然散开。
否决原因：对**真正相同的 hashCode**（恶意构造或实现有 bug），扩容完全无效 —— hash 一样，容量再大也还是同一个桶。极端情况下扩容到 2^30 也还是 O(n)，只有树化能把最坏情况压到 O(log n)。

## 6. 关键参数为什么是这个值

| 参数 | 值 | 为什么 |
|---|---|---|
| `TREEIFY_THRESHOLD` | 8 | 泊松概率 6e-8 极低 + 链表/树的成本交叉点在 6~8 |
| `UNTREEIFY_THRESHOLD` | 6 | 留缓冲带，避免 7/8 反复树化/退化 |
| `MIN_TREEIFY_CAPACITY` | 64 | 小桶多个碰撞是容量问题，扩容更便宜；且至少 4×8 避免两个阈值打架 |
| 触发点 | 第 9 个节点 | 源码 `binCount >= TREEIFY_THRESHOLD - 1`，binCount 从 0 起 |
| 节点大小 | Node 32B / TreeNode 64B | 压缩指针下的逐字段累加（见 3.5） |

补充一个源码细节：当 key 实现了 `Comparable` 时，树化会优先用 `compareTo` 排序；否则用 `tieBreakOrder` 按「类名 + identityHashCode」比较。这就是为什么「自定义 key 实现 Comparable 能让树桶更快」。

## 7. 版本演进

**JDK 7**：只有链表 + 扩容，没有红黑树。遇到哈希碰撞攻击能被拖死。

**JDK 8**：引入 `TreeNode`、`TREEIFY_THRESHOLD`、`MIN_TREEIFY_CAPACITY`，这是「防哈希碰撞攻击」的核心改进；同时把链表插入改成尾插。

**JDK 9 / 17**：树化逻辑未变。相关变化只有 `String` 的底层存储（`char[]` → `byte[] + coder`），不影响树化。

**JDK 21**：HashMap 的树化机制仍未变。可以看到 JDK 8 定下的这套阈值到 21 一直沿用，说明当初的设计（泊松推导 + 64 门槛 + 6 缓冲）是站得住的。

## 8. 亲手验证：把红黑树的五条性质逐条校验

用反射取出桶里的 `TreeNode`，顺着 `parent` 找到根，然后递归校验：根必须黑、不能有红红相邻、所有路径黑高相等，并顺便统计节点数和树高。

```java
import java.lang.reflect.Field;
import java.util.*;

public class RbProbe {
    static final class K implements Comparable<K> {
        final int id;
        K(int id) { this.id = id; }
        public int hashCode() { return 1; }                    // 全部撞同一个桶
        public boolean equals(Object o) { return o instanceof K && ((K) o).id == id; }
        public int compareTo(K o) { return Integer.compare(id, o.id); }
        public String toString() { return "K" + id; }
    }
    static Field parent, left, right, red;
    static int nodeCount;
    public static void main(String[] a) throws Exception {
        HashMap<K, Integer> m = new HashMap<>(64);              // 容量先到 64
        for (int i = 0; i < 12; i++) m.put(new K(i), i);
        Field tf = HashMap.class.getDeclaredField("table");
        tf.setAccessible(true);
        Object[] tab = (Object[]) tf.get(m);
        Object bin = null;
        for (int i = 0; i < tab.length; i++) if (tab[i] != null) { bin = tab[i]; break; }
        System.out.println("桶内节点类型 = " + bin.getClass().getSimpleName());
        Class<?> tn = Class.forName("java.util.HashMap$TreeNode");
        parent = tn.getDeclaredField("parent"); parent.setAccessible(true);
        left = tn.getDeclaredField("left"); left.setAccessible(true);
        right = tn.getDeclaredField("right"); right.setAccessible(true);
        red = tn.getDeclaredField("red"); red.setAccessible(true);
        Object root = bin;
        while (parent.get(root) != null) root = parent.get(root);
        System.out.println("root = " + root + "，root.red = " + red.get(root));
        int bh = blackHeight(root);
        System.out.println("黑高 = " + bh + "，节点数 = " + nodeCount
                + "，存在红红相邻 = " + hasRedRed(root)
                + "，五条性质校验通过 = " + (bh > 0 && !hasRedRed(root)));
        System.out.println("树高 = " + height(root) + "（同样 12 个节点的链表，平均查找 6.5 次）");
    }
    static int blackHeight(Object n) throws Exception {
        if (n == null) return 1;                                // null 视为黑
        nodeCount++;
        int l = blackHeight(left.get(n)), r = blackHeight(right.get(n));
        if (l != r || l < 0) return -1;
        return l + (Boolean.TRUE.equals(red.get(n)) ? 0 : 1);
    }
    static boolean hasRedRed(Object n) throws Exception {
        if (n == null) return false;
        if (Boolean.TRUE.equals(red.get(n))) {
            Object l = left.get(n), r = right.get(n);
            if ((l != null && Boolean.TRUE.equals(red.get(l)))
                    || (r != null && Boolean.TRUE.equals(red.get(r)))) return true;
        }
        return hasRedRed(left.get(n)) || hasRedRed(right.get(n));
    }
    static int height(Object n) throws Exception {
        if (n == null) return 0;
        return 1 + Math.max(height(left.get(n)), height(right.get(n)));
    }
}
```

```bash
javac -encoding UTF-8 RbProbe.java
java --add-opens java.base/java.util=ALL-UNNAMED RbProbe
```

预期输出：

```
桶内节点类型 = TreeNode
root = K3=3，root.red = false
黑高 = 4，节点数 = 12，存在红红相邻 = false，五条性质校验通过 = true
树高 = 5（同样 12 个节点的链表，平均查找 6.5 次）
```

这组数字说明了三件事：① 12 个撞桶元素确实树化了；② 根是黑色、没有红红相邻、各路径黑高相等（五条性质全部成立）；③ 树高 5，而 12 节点链表平均要比较 6.5 次、最坏 12 次。

## 9. 常见误区

| 错误说法 | 正确说法 |
|---|---|
| 「链表到 8 就转红黑树」 | 第 9 个节点落入桶时才调用 `treeifyBin`，且容量必须 ≥64 |
| 「退化阈值 6 用于所有删除场景」 | 6 主要用在 `split`；`removeTreeNode` 是按树形状判断退化 |
| 「容量小时也会树化」 | 容量 <64 时 `treeifyBin` 先扩容，不树化 |
| 「红黑树是完全平衡的」 | 只保证最长路径 ≤ 2 倍最短路径，比 AVL 宽松 |
| 「TreeNode 和 Node 一样大」 | TreeNode 约 64 字节，是 Node（32 字节）的两倍 |
| 「树化后查询就是 O(log n) 绝对快」 | 节点少时链表更快；树化是为了兜最坏情况 |
| 「树化的 key 必须有 Comparable」 | 没有也能树化，会退化成按类名 + identityHashCode 比较 |
| 「JDK 7 也会树化」 | JDK 7 只有链表，红黑树是 JDK 8 引入的 |

## 10. 连续追问 Q&A

### Q1：为什么阈值是 8 而不是 4 或 16？
**答**：8 来自泊松分布——哈希均匀时单桶 8 个节点的概率约 6e-8，几乎不会误触发；从成本看，链表平均 n/2 次比较、树 ≤2·log₂(n+1)，交叉点就在 6~8 附近，再考虑 TreeNode 占两倍内存，8 是「划算的临界点」。

### Q2：为什么还要 `MIN_TREEIFY_CAPACITY = 64`？
**答**：小容量的碰撞多半是桶太少造成的，扩容比树化便宜；而且源码注释要求它至少是 `4 × TREEIFY_THRESHOLD`，避免「刚树化又扩容」两个阈值互相打架。

### Q3：退化阈值为什么是 6 而不是 8？
**答**：留缓冲带。如果树化和退化都用 8，删一个就退化、插一个又树化，来回抖动成本很高；6 让结构有稳定区间。

### Q4：树化后为什么还保留 `next`/`prev` 指针？
**答**：一是扩容拆树、退化回链表时不用重建链表；二是遍历和删除时能沿链表走；三是 `Iterator` 的实现可以保持简单。

### Q5：红黑树的五条性质是什么？
**答**：① 节点非红即黑；② 根是黑；③ 叶子（null）视为黑；④ 红节点的孩子必须是黑；⑤ 任一节点到所有叶子的路径黑节点数相同。④+⑤ 推出最长路径 ≤ 2× 最短路径，保证 O(log n)。

### Q6：插入新节点为什么默认染红？
**答**：染黑会让某条路径的黑高 +1，直接违反性质 5，修复代价大；染红只可能违反性质 4（父节点也是红），修复只需变色和最多两次旋转。

### Q7：为什么不用 AVL 树？
**答**：AVL 更平衡、查找更快，但插入删除要维护平衡因子、旋转次数更多；HashMap 读写混合，写路径更贵不划算。红黑树用「稍宽松的平衡」换更少的调整。

### Q8：为什么不用跳表？
**答**：跳表节点要多层指针，内存比红黑树更大；依赖随机层数、行为不确定；且 Java 里没有现成跳表可复用。Redis 用跳表是因为它要支持范围查询和简单实现，场景不同。

### Q9：hashCode 全相同的 key 放进来会怎样？
**答**：全落一个桶。先是链表 O(n)；到 9 个且容量 ≥64 后树化，变成 O(log n)。若 key 实现了 `Comparable` 用 `compareTo` 排序，否则用类名 + identityHashCode 兜底比较。

### Q10：树化会不会在扩容时被破坏？
**答**：不会。扩容时树桶走 `TreeNode.split`，按 `(e.hash & oldCap)` 把树节点分成 lo/hi 两组：某组 ≤6 就退化成链表，否则重建成两棵树。

### Q11：哈希碰撞攻击是什么？JDK 8 怎么缓解？
**答**：攻击者构造大量 hashCode 相同的 key，让 HashMap 退化成链表，单次查询 O(n)，一次请求就能打满 CPU。JDK 8 的缓解手段主要是树化（最坏 O(log n)），另外还有 `String.hashCode` 的随机化机制（`-Djdk.map.althashing.threshold`）。

### Q12：既然树快，为什么初始不直接用树？
**答**：绝大多数桶只有 0~1 个元素，树化纯属浪费（每个 TreeNode 多一倍内存），而且单节点桶直接放最快。树化是「异常兜底」，不是常态。

## 11. 一张图总结

```
插入第 9 个节点进入某桶
        │
        ▼
   treeifyBin(tab, hash)
        │
        ├── table.length < 64 ? ── 是 ──> resize()（先扩容，不树化）
        │
        └── 否 ──> Node 链换成 TreeNode 双向链 ──> hd.treeify() 建红黑树

红黑树（5 条性质）
  ├── 根黑、红节点孩子黑
  ├── 黑高相等 -> 最长路径 ≤ 2×最短路径 -> 查找 O(log n)
  ├── 插入染红 + 三种情况调整（变色 + ≤2 次旋转）
  └── 删除降到「树形状太小」-> 退化成链表（split 时按 ≤6 判断）

扩容时：TreeNode.split 按 (hash & oldCap) 拆成 lo/hi，≤6 的一组退化成链表
内存：Node 32B，TreeNode 64B（约 2 倍）—— 所以树化只做兜底
```

## 12. 一句话复盘

> 链表在极端碰撞下会退化成 O(n)，JDK 8 用红黑树兜底到 O(log n)。阈值 8 来自泊松分布（概率 6e-8，日常根本不会触发）和链表/树的成本交叉点；6 是防抖动的缓冲带；64 是因为小容量碰撞该先扩容，且要避免两个阈值打架。TreeNode 占两倍内存，所以树化只是兜底，不是常态。

## 13. 自测题（先自己答，再看答案）

**1. 单个桶插入第几个节点时会调用 `treeifyBin`？容量是 16 时会树化吗？**
答案：第 9 个（源码 `binCount >= TREEIFY_THRESHOLD - 1`，binCount 从 0 起）。容量 16 < 64 时不会树化，而是先 `resize()`。

**2. λ=0.5 时，一个桶里恰好 8 个节点的概率是多少？**
答案：`e^-0.5 × 0.5^8 / 8! ≈ 6e-8`（约一千万分之一），与 JDK 源码注释一致。

**3. 红黑树怎么保证 O(log n)？**
答案：性质 4（红节点孩子黑）+ 性质 5（黑高相等）推出最长路径 ≤ 2×最短路径，所以树高 ≤ 2·log₂(n+1)。

**4. 为什么退化阈值是 6 而不是 8？**
答案：留缓冲带，避免 7/8 之间反复树化和退化。

**5. `TreeNode` 为什么比 `Node` 大？大约大多少？**
答案：多了 parent/left/right/prev 四个引用和 1 bit 颜色，压缩指针下约 64 字节 vs 32 字节，约 2 倍。

**6. 为什么不用 AVL 或跳表？**
答案：AVL 插入删除旋转太频繁，HashMap 写也多；跳表节点多层指针内存更大且依赖随机层数。红黑树在「内存 + 确定性 + 写成本」上更平衡。
