# 系统设计入门（应届 / 初级版）

> 面试权重：5/5（有余力才深挖，但"能聊"是加分项）
> 适用场景：一面偶尔问一句「如果用户量涨到 100 万你怎么改」；二面/主管面会认真聊项目架构
> 建议投入：3 天（够用即可，不要沉迷）

---

## 写在前面：应届生答系统设计的正确姿势

**错误认知**：系统设计是架构师的题，应届生不用准备。

**正确认知**：应届生被问系统设计，面试官想看的是三件事——
1. **你有没有结构化的思考习惯**（会不会先问需求、先定边界）
2. **你能不能把学过的东西串起来**（缓存、队列、分库分表、限流）
3. **你知不知道自己的方案瓶颈在哪**（不能吹成完美）

所以你不需要设计出微信，你只需要证明"我有一套方法，而且知道取舍"。

> **一句话答案**：系统设计题先问清楚「多少人用、读多写多、要多快、能丢数据吗」，再按「接口设计 → 数据模型 → 核心流程 → 扩展与瓶颈」四步走。

## 1. 答题框架：四步走（务必背下来）

### 第一步：明确需求（2 分钟，别急着画图）

必问的 5 个问题：

| 问题 | 为什么问 | 典型答案 |
|---|---|---|
| 用户量 / QPS 量级？ | 决定要不要分布式 | 10 万用户，峰值 1000 QPS |
| 读多还是写多？比例？ | 决定缓存与分库策略 | 读多写少，10:1 |
| 数据量多大、要存多久？ | 决定分库分表要不要做 | 每条约 1KB，存 1 年 |
| 一致性要求？能丢数据吗？ | 决定事务与队列 | 支付不能丢，点赞可以丢 |
| 延迟要求？ | 决定缓存层级 | 首页 100ms 内 |

**面试话术**：「在动手前我先确认几个约束……」，问完再画，面试官会觉得你专业。

### 第二步：接口设计（API 定义）

把核心接口写出来，3-5 个就够：

```
POST /api/urls         创建短链      入参 {longUrl} 出参 {shortUrl}
GET  /{code}           跳转原文       302 重定向
GET  /api/urls/{code}/stats  访问统计
```

**话术**：「短链跳转用 302 而不是 301，因为 301 会被浏览器永久缓存，我就拿不到点击统计了。」

### 第三步：数据模型

说清表结构 + 索引 + 存储选型：

```sql
CREATE TABLE short_url (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  code VARCHAR(8) NOT NULL UNIQUE,   -- 短码，唯一索引
  long_url VARCHAR(2048) NOT NULL,
  user_id BIGINT,
  created_at DATETIME,
  INDEX idx_user (user_id)
);
```

### 第四步：核心流程 + 扩展与瓶颈

- 核心流程：写出一次读/写请求经过哪些组件（在哪加缓存、在哪加队列）
- 扩展与瓶颈：主动说「这个方案在 QPS 上到 1 万时会因为 X 成为瓶颈，可以改成 Y」

> **加分收尾话术**：「以上是能撑住 1000 QPS 的方案。如果要求再提升一个数量级，我会把 ① 加本地缓存 ② 读写分离 ③ 短码生成改成号段模式预分配。当然这也会带来数据一致性维护成本，要看业务是否值得。」

## 2. 必背的 8 个"万能积木"

面试时把这些积木往里拼就行。

| 积木 | 解决什么 | 一句话说明 | 代价 |
|---|---|---|---|
| **缓存** | 读性能 | 热点数据放 Redis，命中率决定收益 | 一致性、缓存三件套问题 |
| **消息队列** | 削峰、解耦、异步 | 下单后发消息，库存/积分异步处理 | 最终一致、重复消费（要幂等） |
| **读写分离** | 读并发 | 主库写、从库读 | 主从延迟（写后立刻读可能读不到） |
| **分库分表** | 数据量/写并发 | 按 user_id 水平拆 | 跨库 join、分布式事务、分页 |
| **限流** | 保护系统 | 令牌桶/漏桶/滑动窗口 | 误伤正常用户（要分级） |
| **降级** | 保住核心链路 | 非核心功能直接返回兜底 | 功能不完整 |
| **幂等** | 重复请求安全 | 唯一键 / 状态机 / 分布式锁 | 额外存储或性能开销 |
| **CDN / 静态化** | 静态资源与页面 | 图片、JS、HTML 放边缘节点 | 更新延迟 |

**记忆口诀**：**缓、队、读、拆、限、降、幂、CDN**。

## 3. 高频设计题 1：短链系统（最常见）

### 需求
把长 URL 转成 `https://s.cn/aB3xK9`，点击跳转，能统计点击量。日新增 100 万条，读写比 100:1。

### 接口
```
POST /api/urls              {"longUrl": "..."}  →  {"shortUrl": "https://s.cn/aB3xK9"}
GET  /{code}                →  302 Location: longUrl
GET  /api/urls/{code}/stats →  {"pv": 1234, "uv": 89}
```

### 短码怎么生成（这是核心考点，三种方案要能对比）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **哈希截断** | MD5(longUrl) 取前 6 位 Base62 | 相同 URL 天然同码 | 会冲突，要额外查重加重试 |
| **自增 ID + Base62** | 全局自增 ID 转 62 进制 | 绝不会冲突、无碰撞 | 短码可被顺序枚举（不安全） |
| **号段预分配**（推荐） | 从 DB 一次取 1000 个 ID 放内存发 | 高性能、无冲突 | 服务重启会浪费号段 |

**Base62 换算**：6 位 Base62 = 62^6 ≈ 568 亿，够用很久。

**60 秒版回答**：「短码我用**号段模式**：数据库维护一个自增段，服务启动时一次取 1000 个 ID 缓存在内存里发号，用完再取。这样发号是纯内存操作，QPS 很高，也不会像哈希那样冲突。把自增 ID 转 62 进制得到短码。缺点是重启会浪费一段号，但对短链业务完全可接受。如果要求短码不可枚举，就在号段基础上做个简单的乱序映射或加盐。」

### 跳转流程
```
用户点击 → 浏览器请求 /aB3xK9 → 服务先查 Redis（key=code）
  ├─ 命中 → 302 到 longUrl
  └─ 未命中 → 查 MySQL → 回填 Redis（随机过期时间防雪崩）→ 302
点击统计 → 写 MQ → 异步落库（不阻塞跳转）
```

### 追问防守
- **Q：302 和 301 选哪个？** → 302。301 被浏览器永久缓存后，服务端收不到请求，统计和后续改链都做不了。
- **Q：短码被枚举怎么办？** → 号段 + 混淆映射，或者用 `id * 大质数 % 范围` 做简单变换；再加频控。
- **Q：Redis 挂了怎么办？** → 跳转走 MySQL 兜底（加限流保护），并做 Redis 主从 + 哨兵。
- **Q：统计 PV 直接写库行不行？** → 不行，写放大太严重。用 MQ 削峰 + 批量合并写（每 10 秒聚一次）。
- **Q：怎么防止恶意短链？** → 域名黑名单 + 人工审核 + 落地页提示。

## 4. 高频设计题 2：秒杀 / 抢购

### 需求
100 件库存，活动开始 1 秒内 10 万人抢。核心要求：**不超卖、不拖垮系统、公平**。

### 核心思路：层层过滤，把流量挡在数据库前面
```
CDN/前端 → 网关限流 → 应用层校验（活动时间/资格/防重复）
         → Redis 预扣库存（Lua 脚本保证原子）→ 抢到才发 MQ
         → 异步下单落库 → 前端轮询结果
```

### 关键点
1. **库存预热**：活动开始前把库存 `SET stock:item1 100` 到 Redis
2. **原子扣减**：用 Lua 脚本 `if stock > 0 then decr`，避免超卖
3. **一人一单**：`SETNX order:lock:{userId}` 或 Redis Set 去重
4. **异步落库**：MQ 削峰，数据库只处理真正抢到的 100 个请求
5. **超时未支付**：延时队列回补库存（RocketMQ 延时消息 / Redis ZSet 轮询）
6. **前端**：按钮置灰 + 验证码挡脚本 + 静态页

### 追问防守
- **Q：为什么不直接在数据库减库存？** → 10 万请求打 MySQL，行锁排队直接雪崩。Redis 内存操作才能扛住。
- **Q：Redis 扣成功了但下单失败（如 DB 挂了）怎么办？** → 要么回补库存（写补偿队列），要么允许超卖少量（业务上可接受），要主动说出这是最终一致。
- **Q：MQ 消息重复消费导致重复下单？** → 用唯一订单号 + 数据库唯一索引保证幂等。
- **Q：怎么防刷？** → 网关限流 + IP/账号频控 + 活动前置校验（实名/等级）+ 验证码。

## 5. 高频设计题 3：排行榜

### 需求
百万用户按积分排名，实时更新，查 Top 100 和我的排名。

### 核心：Redis ZSet 就是为这个设计的
```bash
ZINCRBY rank:2026-11 10 user:123       # 加分
ZREVRANGE rank:2026-11 0 99 WITHSCORES # Top 100
ZREVRANK rank:2026-11 user:123         # 我的排名（从 0 开始）
```

| 要点 | 做法 |
|---|---|
| 数据量大 | ZSet 单 key 百万级没问题，千万级按前缀分片再归并 |
| 榜单周期 | 按周期建 key（日榜/周榜/总榜），配合过期清理或归档到 DB |
| 同分排序 | ZSet 分数相同按 member 字典序；要精确同分排名需把 分数+时间戳 拼成浮点 |
| 持久化 | DB 存明细用于对账，Redis 只做查询加速 |
| 历史榜 | 快照落 DB，Redis 只留当前周期 |

**60 秒版回答**：「排行榜用 Redis 的有序集合 ZSet，`ZINCRBY` 更新分数是 O(logN)，`ZREVRANGE` 取 Top N 也是 O(logN + N)，天然适合。我的排名用 `ZREVRANK`。数据源是真时的加分行为，我在 DB 里存明细保证可对账，Redis 只做查询层。如果榜单要按日/周/总榜，就按周期建多个 key，老周期定时快照落库后删掉。」

## 6. 高频设计题 4：消息推送 / 站内通知

### 需求
用户下单后收到 App 推送 + 站内消息。用户量 100 万，允许秒级延迟。

### 架构
```
业务系统 → 发消息到 MQ（topic: order_paid）
        → 推送服务消费
            ├─ 站内信：写消息表 + Redis 未读数
            ├─ App 推送：调 APNs / FCM / 厂商通道
            └─ 失败重试：重试队列，3 次后进死信
```

### 追问防守
- **Q：消息要保证不丢吗？** → 分等级：支付/订单类必须不丢（消费确认 + 落库 + 重试），营销类可丢。
- **Q：推送风暴（一次活动给 100 万人推）？** → 按用户分片，多消费者并发；限速匀速推，避免被厂商通道限流。
- **Q：用户已读怎么标记？** → 消息表加 `read_at`，未读数用 Redis `HINCRBY` 或计数器，已读时减。
- **Q：怎么保证不重复推送？** → 消息唯一 ID + 用户维度去重表。

## 7. 高频设计题 5：文件上传 / 图片存储

### 需求
用户上传头像和商品图，要求快、可靠、能抗量。

### 核心链路
```
前端 → 请求后端换取「上传凭证」
     → 前端直传对象存储（OSS/MinIO），不经过应用服务器
     → 上传成功回调后端，记录 fileId + url
     → 访问走 CDN
```

### 关键点
| 问题 | 解法 |
|---|---|
| 大文件上传慢/断 | **分片上传** + 断点续传（记录分片 ETag） |
| 恶意文件 | 后缀白名单 + 文件头魔数校验 + 病毒扫描 |
| 图片太大 | 上传后异步生成多规格缩略图 |
| 访问加速 | CDN + 长缓存 + 图片 URL 加版本号 |
| 私有文件 | 签名 URL（有效期）而非公开链接 |
| 重复文件 | 按内容 hash 去重，秒传 |

## 8. 被问"你们项目如果用户量涨 100 倍怎么办"的标准答法

**不要慌，套四层：**

1. **先定位瓶颈**：「我会先看监控，确认瓶颈在 CPU、数据库还是网络。假设是数据库读写压力。」
2. **加缓存**：「热点数据先上 Redis，读多写少的表加本地 Caffeine 二级缓存。」
3. **拆读写**：「读请求走从库，写请求走主库；再不行按 user_id 分库分表。」
4. **削峰异步**：「非核心链路（日志、通知、统计）走 MQ 异步化。」
5. **兜底**：「加限流和降级，保证核心下单链路可用。」
6. **收尾**：「这些手段的代价是一致性变复杂、运维成本上升，所以我会先在压测环境验证收益再上。」

> 面试官听到这种"先说瓶颈、再上手段、主动说代价"的回答，比听到具体技术名词更满意。

## 9. 系统设计的 10 个"送分回答"

| 问题 | 标准答案要点 |
|---|---|
| 高并发怎么设计？ | 缓存 + 异步 + 限流 + 水平扩展，四件套 |
| 怎么保证接口幂等？ | 唯一索引 / 状态机 / token + Redis |
| 分布式事务怎么办？ | 尽量拆分避免；必须时用本地消息表 / Seata AT / TCC，说明是最终一致 |
| 怎么防止重复下单？ | 前端防抖 + 后端幂等键（userId + 商品 + 时间窗） |
| 限流算法有哪些？ | 计数器、滑动窗口、漏桶、令牌桶（各自适用） |
| 怎么做灰度发布？ | 网关按用户 ID 取模分流 + 开关平台 |
| 分布式 ID 怎么生成？ | UUID（无序）/ 雪花算法（趋势有序、依赖时钟）/ 号段（高性能） |
| 怎么保证消息不丢？ | 生产确认 + 持久化 + 消费手动 ack + 重试 + 死信 |
| 怎么排查线上慢？ | 监控 → 链路追踪 → 日志 → 慢 SQL → 复现压测 |
| 你会怎么设计一个评论系统？ | 接口 → 表（评论/回复）→ 分页（游标）→ 缓存热点 → 异步通知 |

| 6 | 排行榜用什么数据结构？ | Redis ZSet | ZINCRBY / ZREVRANGE / ZREVRANK，O(logN) |
| 7 | 缓存和数据库怎么保持一致？ | 一致性策略 | Cache Aside，先更新库再删缓存 + 延迟双删 + 最终一致 |
| 8 | 怎么保证 MQ 不重复消费？ | 幂等 | 唯一键 / 消费去重表 / 状态机 |

| 11 | 大文件上传怎么做？ | 分片 | 分片 + 断点续传 + 前端直传 OSS + 合并 |
| 12 | 怎么做接口幂等？ | 幂等 | 唯一索引 / token 机制 / 分布式锁 |
| 13 | 分库分表后分页怎么办？ | 分页优化 | 二次查询法 / 游标分页 / 禁止深分页 |
| 14 | 你怎么判断一个设计好不好？ | 取舍思维 | 说清收益、代价、瓶颈、可演进性 |
| 15 | 应届生答系统设计最重要是什么？ | 方法论 | 先问约束，按四步走，主动说瓶颈与取舍 |
