## 1. InnoDB vs MyISAM

**一句话答案**：InnoDB 支持事务、行锁、MVCC、外键和崩溃恢复，是聚簇索引；MyISAM 只有表锁、不支持事务，但计数快、索引文件独立，现代项目一律用 InnoDB。

**原理展开**：
- InnoDB：事务（redo/undo log）、行级锁 + MVCC、外键、崩溃自动恢复、聚簇索引（数据文件就是主键索引）；MySQL 5.5 起是默认引擎。
- MyISAM：表锁（读写互斥，并发差）、不支持事务、不支持外键、崩溃后易损坏需 `repair`；`count(*)` 因为保存了行数所以很快。
- 索引结构差异：InnoDB 主键索引叶子存整行（聚簇），二级索引叶子存主键；MyISAM 索引与数据分离，叶子存的是行地址（非聚簇）。
- 适用场景：InnoDB 覆盖 99% 业务；MyISAM 只在极少数只读/日志归档场景还有价值。
- 面试延伸：`select count(*)` 在 InnoDB 里慢是因为要遍历最小的二级索引逐行统计，不是「没有缓存行数」这么简单。

**面试怎么答（60 秒版）**：InnoDB 和 MyISAM 最核心的区别是 InnoDB 支持事务和行级锁，MyISAM 只有表锁、不支持事务。InnoDB 用聚簇索引，主键索引的叶子节点直接存整行数据；MyISAM 索引和数据是分开存的，叶子存行地址。另外 InnoDB 有 MVCC 和崩溃恢复，MyISAM 崩溃后表容易坏要修复。所以现在业务表基本都用 InnoDB，MyISAM 只在个别只读统计场景还能见到。

**追问陷阱**：
- 错误：「MyISAM 查询更快所以读多写少选它」→ 正确：现代 InnoDB 有缓冲池和行锁，读写混合下全面占优。
- 错误：「InnoDB 的 count 快」→ 正确：正相反，InnoDB 要逐行计数，MyISAM 才保存了行数。

## 2. 索引原理：为什么是 B+ 树

**一句话答案**：B+ 树「矮胖」、非叶子节点只存索引、叶子节点用链表相连，一次 IO 读一页能存上千个 key，三四层就支撑千万级数据，还能高效做范围查询。

**原理展开**：
- 一次磁盘 IO 读一页（InnoDB 默认 16KB），所以索引结构的目标是「用最少的 IO 定位数据」。
- B+ 树特点：非叶子节点只存 key 和子节点指针（不存数据），扇出极大；所有数据都在叶子层，叶子节点按 key 有序且用双向链表连接。
- 算一笔账：一个非叶子节点存约 1000 个 key，三层就能索引约 10 亿行，查任意一行只需 3 次 IO。
- 为什么不用 B 树：B 树每个节点都存数据行，节点能放的 key 变少、树更高（IO 更多），且范围查询要走中序遍历、大量随机 IO。
- 为什么不用哈希索引：等值查询 O(1) 但不支持范围查询、排序、最左前缀，还会因哈希冲突退化；Memory 引擎才用哈希。
- 为什么不用跳表/红黑树：都是内存结构，磁盘上每层节点分散在不同页，随机 IO 次数多。
- 补充：InnoDB 支持自适应哈希索引（AHI，自动为热点等值查询建哈希）；索引下推（ICP，5.6+）把 where 条件下推到存储引擎层减少回表。

**面试怎么答（60 秒版）**：MySQL 索引用 B+ 树，核心原因是磁盘 IO。B+ 树非叶子节点只存索引和指针、不存数据，所以一个 16KB 的页能存上千个 key，三层就能索引上亿行，查一次只要两三次 IO。而且数据全在叶子节点并且用链表连起来，范围查询和排序都很高效。B 树每个节点都存数据，扇出小、树更高，范围查询还要中序遍历；哈希索引只能等值查，不支持范围和排序；红黑树、跳表是内存结构，磁盘上会退化成大量随机 IO。

**追问陷阱**：
- 错误：说「B+ 树查询比 B 树快所以选它」→ 正确：单点查询两者都是 O(log n)，B+ 树赢在扇出大、层数少、范围查询友好。
- 错误：以为索引越多越好 → 正确：索引占空间、拖慢写入（每次 insert 要维护所有索引），一般单表控制在 5 个以内。

## 3. 聚簇索引、二级索引与回表

**一句话答案**：InnoDB 主键索引就是聚簇索引，叶子存整行数据；二级索引叶子只存主键值，查非索引字段要再查一次主键索引，这叫「回表」。

**原理展开**：
- 聚簇索引：组织方式由主键决定，一张表只有一个；没有主键时用唯一非空索引，都没有则用隐藏 `DB_ROW_ID`。
- 二级索引（普通索引）：叶子节点存的是「索引列 + 主键值」，所以查 `select *` 时必须拿主键回聚簇索引再查一次整行。
- 覆盖索引：查询的所有列都在索引里（如联合索引 `(city, age, name)` 查 `name`），不用回表，`EXPLAIN` 的 Extra 显示 `Using index`——这是最实用的优化手段。
- 回表成本：一次查询 = 两次 B+ 树查找 + 可能的随机 IO，所以「`select *` 在二级索引场景比查覆盖字段慢很多」。
- 主键为什么建议自增：自增主键顺序插入，只在末尾追加，页分裂少；UUID 这类随机主键会导致页分裂、碎片和 IO 放大（特别在 InnoDB 这种聚簇索引里）。
- 唯一索引 vs 普通索引：唯一索引写入要检查冲突，性能略差但业务保证强；`change buffer` 对普通索引的写更友好。

**面试怎么答（60 秒版）**：InnoDB 的主键索引是聚簇索引，叶子节点直接存整行数据，所以按主键查最快。二级索引的叶子只存索引字段和主键值，查其他字段要拿主键再查一次聚簇索引，这就是回表，相当于两次 B+ 树查找。要避免回表就用覆盖索引，让查询字段全部落在索引里，explain 会显示 Using index。另外主键建议用自增，因为随机主键插入会造成页分裂和碎片。

**追问陷阱**：
- 错误：「主键索引和唯一索引一样」→ 正确：主键是聚簇索引、唯一且非空、一张表一个；唯一索引是二级索引，可以多个、可为 NULL。
- 错误：认为「索引字段越多越好查」→ 正确：联合索引要遵循最左前缀，否则索引白建。

## 4. 最左前缀与索引失效场景

**一句话答案**：联合索引 `(a,b,c)` 只能从 a 开始连续用；函数运算、隐式类型转换、`%前缀` 模糊匹配、`OR` 连接非索引列、`!=`、违背最左前缀都会让索引失效。

**原理展开**：
- 联合索引 `(a, b, c)`：能命中的是 `a`、`(a,b)`、`(a,b,c)`；单独查 `b` 或 `c` 用不上（因为 B+ 树先按 a 排序）；`a=1 and c=3` 只能用到 a。
- 范围查询会截断：`a=1 and b>2 and c=3` 中 c 用不上索引（5.6+ 有 ICP 可以在引擎层用 c 过滤，但不减少扫描范围）。
- 失效清单：① 列上加函数或运算 `where YEAR(create_time)=2024`、`where id+1=5`；② 隐式类型转换（`varchar` 的 `phone` 与数字比较，MySQL 会把列转成数字）；③ `like '%xx'` 前导模糊；④ `or` 两侧有非索引列；⑤ `!=`、`not in`、`is not null` 等否定条件；⑥ 违背最左前缀；⑦ 索引列区分度太低（如性别），优化器判断全表更快。
- 排序也用索引：`order by a, b` 与索引顺序一致可避免 `Using filesort`，反向扫描也支持；跳过 b 直接 order by c 则用不上。
- 设计原则：区分度高的列放前面、等值查询列放前面、范围列放最后、把高频 `order by/group by` 的列纳入联合索引。

```sql
-- 联合索引 idx_city_age_name (city, age, name)
SELECT name FROM t_user WHERE city = '上海' AND age = 20;      -- 正确：命中，且覆盖索引
SELECT name FROM t_user WHERE age = 20;                        -- 错误：跳过 city，违反最左前缀
SELECT name FROM t_user WHERE city = '上海' AND age > 20;      -- 注意 用到 city+age，name 无法再用于定位
```

**面试怎么答（60 秒版）**：最左前缀是说联合索引按定义顺序排序，所以查询必须从最左列开始连续使用，中间断了后面就用不上。比如 (a,b,c) 索引，查 a、a+b、a+b+c 能命中，单查 b 或 c 不行。索引失效的常见情况有：列上做函数或运算、字段类型和传参类型不一致导致隐式转换、like 以 % 开头、or 两边有一边没索引、用了不等于和 not in，还有就是区分度太低优化器干脆全表扫。写 SQL 时我会用 explain 确认 key 真的有命中。

**追问陷阱**：
- 错误：「加了索引就一定走索引」→ 正确：优化器会估算成本，区分度低或要扫大部分行时会主动全表扫。
- 错误：以为 `like '%xx%'` 也能用索引 → 正确：只有 `like 'xx%'` 前缀匹配可用；真正的中缀搜索要上 ES。

## 5. 执行计划 explain

**一句话答案**：用 `EXPLAIN` 看 `type`（访问类型）、`key`（实际用的索引）、`rows`（预估扫描行数）、`Extra`（是否 filesort/temporary），目标是 type 至少 `range`、Extra 不出现 filesort 和临时表。

**原理展开**：
- `type` 从好到坏：`system` > `const` > `eq_ref` > `ref` > `range` > `index`（全索引扫描）> `ALL`（全表）；生产接口要求至少能到 `range`，出现 `ALL` 要警惕。
- `key` 是实际使用的索引，`possible_keys` 是候选；`key` 为 NULL 表示没走索引。
- `key_len` 可以推断联合索引用到了几个字段（utf8mb4 下一个 varchar(20) 约 82 字节，含长度和 NULL 标记）。
- `rows` 是优化器估算的扫描行数，越大越慢；`filtered` 是过滤后剩余比例，`rows × filtered` 才是真正参与 join 的行数。
- `Extra` 重点：`Using index`（覆盖索引，好）、`Using where`（回表后再过滤）、`Using index condition`（索引下推）、`Using filesort`（额外排序，要优化）、`Using temporary`（用了临时表，group by/去重场景要警惕）。
- `id` 越大越先执行；`select_type` 有 SIMPLE、PRIMARY、SUBQUERY、DERIVED、UNION，出现 DERIVED 说明有子查询物化。
- 进阶：`EXPLAIN ANALYZE`（8.0.18+）能看真实执行耗时，比估算更可信。

**面试怎么答（60 秒版）**：explain 我主要看四列：type 是访问类型，最好到 range 甚至 ref、const，出现 ALL 全表扫描就要优化；key 是实际命中的索引，为 NULL 说明没走索引；rows 是预估扫描行数，越小越好；Extra 里如果出现 Using filesort 或者 Using temporary，说明有额外排序或临时表，也要优化，出现 Using index 说明是覆盖索引比较理想。排查慢 SQL 的流程就是先 explain 定位，再决定加索引还是改 SQL。

**追问陷阱**：
- 错误：只看 `key` 是否命中就放心 → 正确：还要看 `rows` 和 `Extra`，命中索引但扫几百万行一样慢。
- 错误：把 `Using where` 当成好事 → 正确：它表示回表后再过滤，能加进索引变成 `Using index` 更好。

## 6. 事务 ACID 与四种隔离级别

**一句话答案**：ACID 分别是原子性（undo log）、一致性（目标）、隔离性（锁 + MVCC）、持久性（redo log）；隔离级别四种，InnoDB 默认 RR，靠 MVCC + 间隙锁在大部分场景避免幻读。

**原理展开**：
- 原子性靠 undo log 回滚；持久性靠 redo log（WAL：先写日志再刷盘，崩溃可重放）；隔离性靠锁和 MVCC；一致性是前三者共同保障的业务结果。
- 四种隔离级别与问题：读未提交（脏读）→ 读已提交（不可重复读）→ 可重复读（幻读，InnoDB 基本解决）→ 串行化（全加锁，性能差）。
- 三个概念区分：脏读＝读到别人未提交的数据；不可重复读＝同一事务两次读同一行值不同（别人 update 并提交）；幻读＝同一事务两次查同条件，行数变了（别人 insert 并提交）。
- InnoDB 的 RR 通过两种手段处理幻读：快照读靠 MVCC（ReadView），当前读靠 Next-Key Lock（行锁 + 间隙锁）。
- RC 与 RR 的本质差别是 ReadView 生成时机：RC 每条 select 都生成新快照（能读到最新提交），RR 只在第一次 select 生成并复用（整个事务看到同一快照）。
- 大多数互联网公司用 RC：减少间隙锁、提升并发；但要求业务不依赖「可重复读」。

**面试怎么答（60 秒版）**：ACID 里原子性靠 undo log 回滚，持久性靠 redo log 崩溃恢复，隔离性靠锁和 MVCC，一致性是最终目标。隔离级别有四种：读未提交会脏读，读已提交解决脏读但有不可重复读，可重复读在 InnoDB 里通过 MVCC 加间隙锁基本解决了幻读，串行化全加锁性能最差。InnoDB 默认是可重复读，它和读已提交的核心区别是 ReadView 的生成时机：RR 只在事务第一次查询时生成一个快照并一直复用，RC 是每条语句都重新生成。

**追问陷阱**：
- 错误：「RR 完全解决了幻读」→ 正确：快照读没幻读，但当前读（for update）仍可能，靠 Next-Key Lock 兜；这不是绝对保证。
- 错误：「隔离级别越高越好」→ 正确：越高并发越差，互联网常用 RC。

## 7. MVCC 与 ReadView

**一句话答案**：MVCC 靠每行的隐藏事务 ID + undo log 版本链 + ReadView 快照判断可见性，实现「读写不阻塞」，是 RC/RR 隔离级别的底层机制。

**原理展开**：
- 隐藏字段：`DB_TRX_ID`（最后修改该行的事务 id）、`DB_ROLL_PTR`（指向 undo log 的回滚指针）、`DB_ROW_ID`（无主键时的隐藏主键）。
- 版本链：每次 update 都把旧版本写进 undo log，通过回滚指针串成链表，形成「同一行的多个历史版本」。
- ReadView 四个字段：`m_ids`（生成快照时活跃的事务 id 集合）、`min_trx_id`、`max_trx_id`、`creator_trx_id`。
- 可见性判断：行的 `trx_id` 等于自己 → 可见；小于 `min_trx_id` → 已提交，可见；大于等于 `max_trx_id` → 快照后的事务，不可见；在 `m_ids` 里 → 未提交，不可见，顺着版本链往前找。
- RC：每次 select 重新生成 ReadView → 能看到别人新提交的数据 → 不可重复读；RR：首次 select 生成并复用 → 整事务同一快照。
- 当前读：`select ... for update`、`lock in share mode`、`update`、`delete` 不走 MVCC，读最新版本并加锁——这也解释了「加了 for update 就能看到别人已提交的数据」。

**面试怎么答（60 秒版）**：MVCC 是多版本并发控制，目的是让读不加锁也能拿到一致的数据。InnoDB 每行有隐藏的最近修改事务 id 和回滚指针，update 时旧版本会写进 undo log，用回滚指针串成版本链。查询时生成一个 ReadView，里面记录了当前活跃的事务 id，用它和版本链上每个版本的事务 id 比较，找到第一个可见的版本，这就是快照读。可重复读是事务第一次查询时生成 ReadView 一直用到结束，读已提交是每条语句都重新生成，所以两者行为不同。要注意 for update 这类当前读不走 MVCC。

**追问陷阱**：
- 错误：「MVCC 靠加锁实现」→ 正确：恰恰相反，快照读不加锁，读的是历史版本，这也是「读写不阻塞」的原因。
- 错误：「undo log 只为回滚服务」→ 正确：它还承担 MVCC 版本链，所以长事务会导致 undo 无法清理、版本链变长。

## 8. 锁：行锁、间隙锁与死锁排查

**一句话答案**：InnoDB 行锁是加在索引上的，走不到索引会退化成锁全表；RR 默认用 Next-Key Lock（记录锁 + 间隙锁）防幻读；死锁用 `show engine innodb status` 看最近一次死锁。

**原理展开**：
- 粒度：表锁（`lock tables`、意向锁）、行锁（记录锁 Record Lock）、间隙锁（Gap Lock，锁住索引记录之间的间隙）、Next-Key Lock（记录 + 前面的间隙，RR 默认）。
- 共享锁 S（`lock in share mode`）与排他锁 X（`for update`、update/delete）；意向锁 IS/IX 用于快速判断表里有没有行锁，避免逐行检查。
- **关键坑**：行锁加在索引上，如果 where 条件没有索引，InnoDB 会扫全表并锁住所有行（表现为表锁），并发直接崩——所以「更新一定要走索引」。
- 间隙锁只在 RR 及以上且可重复读隔离级别生效；RC 下基本只有记录锁，并发更高但可能出现幻读。
- 死锁成因：两个事务以相反顺序持有并等待对方的锁；InnoDB 有死锁检测，会回滚代价小的事务并报 `Deadlock found`。
- 排查：`show engine innodb status` 看 LATEST DETECTED DEADLOCK 段（含两条 SQL、持锁与等待锁）；`information_schema.innodb_trx` 看当前事务；`innodb_print_all_deadlocks=ON` 把全部死锁打到错误日志。
- 预防：按固定顺序访问资源、缩短事务、走索引减少锁范围、避免大事务里再查别的表、必要时降级到 RC。

**面试怎么答（60 秒版）**：InnoDB 的行锁是加在索引记录上的，所以如果 where 条件没走索引，它会退化成锁全表，这是线上最常见的锁冲突原因。可重复读隔离级别下默认用 Next-Key Lock，也就是记录锁加间隙锁，间隙锁就是用来防止别的事务在间隙里插入造成幻读。死锁是两个事务互相持有对方需要的锁，InnoDB 会自动检测并回滚其中一个，排查用 show engine innodb status 看最近一次死锁详情。预防方法就是固定加锁顺序、缩短事务、让更新走索引。

**追问陷阱**：
- 错误：「行锁就是锁一行」→ 正确：没走索引会锁全表；即使走二级索引，也可能锁到主键索引和间隙。
- 错误：「加锁能避免幻读所以高并发加锁就行」→ 正确：间隙锁会大幅降低并发，很多公司因此选 RC。

## 9. 慢查询优化实战思路

**一句话答案**：先定位（慢日志 + explain），再看是「没索引、索引失效、回表多、扫描行数大」中的哪一类，然后加/改索引、改写 SQL、减少回表，最后才考虑缓存和分库分表。

**原理展开**：
- 开慢日志：`slow_query_log=ON`、`long_query_time=0.5`、`log_queries_not_using_indexes=ON`；用 `pt-query-digest`/`mysqldumpslow` 聚合分析 TOP SQL。
- 定位后三看：`EXPLAIN` 看 type/key/rows/Extra；`SHOW PROFILE` 或 `EXPLAIN ANALYZE` 看各阶段耗时；`SHOW PROCESSLIST` 看是否卡在锁等待或大量排序。
- 常见病因与对策：① 无索引 → 建合适联合索引；② 索引失效（函数、隐式转换、前导 %）→ 改写 SQL；③ 回表多 → 覆盖索引；④ 扫描行数大 → 加筛选条件、分页、归档历史数据；⑤ `filesort`/临时表 → 让排序字段走索引、避免 `select *`；⑥ 锁等待 → 缩短事务。
- 联合索引设计顺序：等值条件列在前、范围列在后、区分度高的列靠左、把 order by 列纳入。
- SQL 改写：子查询改 join、`or` 改 `union all`、大 `in` 改 join 临时表、避免在 where 里对列做运算、避免 `select *`。
- 兜底手段：热点数据加 Redis 缓存、读写分离、归档冷数据、最后才分库分表。

**面试怎么答（60 秒版）**：我排查慢 SQL 的流程是：先开慢查询日志找到具体 SQL，然后用 explain 看访问类型、命中索引和扫描行数。一般问题就几类：没建索引就补联合索引，索引失效大概是列上有函数或者隐式类型转换，回表多就用覆盖索引，扫描行数太大就加筛选条件或者分页。改完再 explain 对比一次。如果 SQL 已经优化到位还是慢，就考虑加缓存、读写分离，最后才是分库分表。我项目里最典型的一次是给用户列表加了一个联合索引，把一条 1 秒多的查询降到了几十毫秒。

**追问陷阱**：
- 错误：一上来就说「加索引」→ 正确：先 explain 定位，因为可能已经命中索引，慢在回表或排序。
- 错误：「把用到的字段都建单列索引」→ 正确：多个单列索引一般只会用一个，联合索引更有效。

## 10. 分库分表入门与分页优化

**一句话答案**：优先垂直拆分（按业务）再水平拆分（按行），分片键决定路由；深分页别用 `limit 1000000,20`，用「延迟关联」或「游标法」。

**原理展开**：
- 垂直拆分：按业务拆库（订单库、用户库）、按冷热拆表（常用字段一张表）；解决的是表太宽、耦合太重。
- 水平拆分：同一张表按分片键（如 `user_id % 4` 或按时间）拆到多个库/表；解决的是单表数据量过大（一般单表超千万行就要评估）。
- 拆分带来的新问题：跨库 join 变难（要么冗余字段、要么应用层聚合）、分布式事务（Seata）、全局唯一 ID（雪花算法/号段模式）、分页与排序变复杂。
- 中间件：ShardingSphere（JDBC 层，最常用）、MyCat；也有应用层自己路由。
- 深分页根因：`limit 1000000, 20` 要先扫描并丢弃前 100 万行，越翻越慢。
- 优化一：延迟关联——先用覆盖索引查出 20 个主键，再 join 回原表取整行。
- 优化二：游标法——记住上一页最后一个 id，`where id > lastId order by id limit 20`，翻页不再随页码变慢（分库分表下最推荐）。
- 其他：业务上限制最大页数（如只允许看前 100 页）、把总数查询单独异步化。

```sql
-- 错误：深分页：扫 100 万行再丢弃
SELECT * FROM t_order ORDER BY id LIMIT 1000000, 20;

-- 正确：延迟关联：先只查主键，再回表取 20 行
SELECT o.* FROM t_order o
JOIN (SELECT id FROM t_order ORDER BY id LIMIT 1000000, 20) t ON o.id = t.id;

-- 正确：游标法：记住上一页最后一个 id
SELECT * FROM t_order WHERE id > 1000020 ORDER BY id LIMIT 20;
```

**面试怎么答（60 秒版）**：分库分表我一般先垂直拆，按业务把订单、用户拆到不同库；单表数据量太大再水平拆，用分片键路由到不同表。但拆完会有跨库 join、分布式事务、全局 ID 和分页的问题，所以不能一上来就拆，先把索引、缓存、读写分离做足。深分页是另一个高频问题，limit 偏移量很大时会先扫掉前面的行，非常慢。我的优化是延迟关联，先用索引查出主键再回表取数据；更好的做法是游标法，用上一页最后一个 id 做条件，翻页性能不随页码退化。

**追问陷阱**：
- 错误：「数据量大就分库分表」→ 正确：先做索引优化、缓存、归档，拆分会显著增加复杂度。
- 错误：分片键用 UUID → 正确：无法范围查询且路由不便，用业务 ID（订单号、用户 ID）或雪花 ID。

## 11. Redis 为什么快（单线程 + IO 多路复用）

**一句话答案**：数据全在内存、命令执行单线程无锁无切换、用 epoll 做 IO 多路复用、数据结构极其精简——所以单机十万级 QPS。

**原理展开**：
- 纯内存操作：内存读写比磁盘快几个数量级，这是最根本的原因。
- 单线程执行命令：避免多线程锁竞争和上下文切换，CPU 缓存友好，实现也简单；代价是**一条慢命令会阻塞所有请求**。
- IO 多路复用：单线程用 epoll 同时监听成千上万个 socket，哪个就绪处理哪个，不用为每个连接开线程。
- 高效数据结构：SDS（O(1) 取长度、预分配、二进制安全）、跳表（ZSet 范围查询）、listpack/quicklist（小对象压缩存储）。
- 渐进式 rehash：全局哈希表扩容时分批迁移，避免一次性 rehash 卡住主线程。
- Redis 6.0 起网络 IO 多线程（读请求、写响应并行），**命令执行仍是单线程**——这句要答对，是常见追问点。

**面试怎么答（60 秒版）**：Redis 快主要有四个原因。第一数据全在内存里，内存比磁盘快几个数量级；第二命令执行是单线程的，没有锁竞争和线程切换开销；第三用 IO 多路复用，一个线程用 epoll 就能管上万个连接；第四数据结构做得很省，比如 SDS、跳表、listpack。要注意单线程指的是命令执行，6.0 之后网络读写是多线程的，但命令还是单线程，所以一条 keys * 这种慢命令照样会把整个实例卡住。

**追问陷阱**：
- 错误：「Redis 6 之后是多线程了」→ 正确：只有网络 IO 多线程，命令执行仍单线程。
- 错误：「单线程所以慢命令无所谓」→ 正确：慢命令会阻塞所有后续请求，必须禁 `keys *`、大 key 全量操作。

## 12. 五种数据结构与典型场景

**一句话答案**：String 做缓存与计数、Hash 存对象、List 做队列、Set 做去重交集、ZSet 做排行榜与延时队列；再往上是 Bitmap、HyperLogLog、GEO、Stream 这些扩展结构。

**原理展开**：
- String：缓存对象、计数器（`INCR`）、分布式锁（`SET NX`）、限流计数、Session；底层 SDS，最大 512MB。
- Hash：存对象的多个字段，可单独更新某字段（用户资料、购物车），小数据量用 listpack 紧凑存储。
- List：`LPUSH + BRPOP` 做简易消息队列、最新 N 条列表、栈；底层 quicklist，两端操作 O(1)。
- Set：去重（点赞用户）、共同关注/好友（`SINTER`）、抽奖（`SRANDMEMBER`）、标签；底层整数集合或哈希表。
- ZSet：排行榜（score 排序）、延时队列（score 存执行时间戳，`ZRANGEBYSCORE` 取到期任务）、滑动窗口限流；底层跳表 + 哈希表。
- 扩展：Bitmap 签到/在线状态、HyperLogLog 做 UV 去重（误差约 0.81%）、GEO 附近的人、Stream 可做带消费组的消息队列。

**面试怎么答（60 秒版）**：五种基础结构我按场景记：String 用来做缓存、计数器和分布式锁；Hash 适合存一个对象的多个字段，比如用户资料；List 可以做简单的消息队列和最新列表；Set 用来去重和求交集，比如共同好友；ZSet 带分数排序，最典型是排行榜，还能用分数存时间戳做延时队列。另外还有 Bitmap 做签到、HyperLogLog 统计 UV、GEO 做附近的人，答题时能说清「用哪个 + 为什么」比背名称重要得多。

**追问陷阱**：
- 错误：用 List 当生产级消息队列 → 正确：没有 ACK 和消费组，可靠场景用 Stream 或 Kafka/RabbitMQ。
- 错误：「HyperLogLog 能精确统计」→ 正确：是基数估算，有约 0.81% 误差，但内存固定 12KB。

## 13. 持久化：RDB vs AOF

**一句话答案**：RDB 是「某一时刻的全量快照」，文件小恢复快但可能丢数据；AOF 是「命令追加日志」，更安全但文件大恢复慢；4.0 起支持混合持久化兼顾两者。

**原理展开**：
- RDB：`bgsave` fork 子进程，利用写时复制（COW）生成快照；文件紧凑、重启恢复快；fork 瞬间阻塞、两次快照之间的数据会丢。
- AOF：追加写命令，三种刷盘策略 `always`（每条都刷，最安全最慢）、`everysec`（默认，最多丢 1 秒）、`no`（交给操作系统，可能丢较多）。
- AOF 重写：`bgrewriteaof` 用最少的命令重建数据集（比如 100 次 `INCR` 压成一条 `SET`），解决文件膨胀。
- 混合持久化（4.0+，`aof-use-rdb-preamble yes`）：AOF 重写时前半段写 RDB 格式、后半段追加增量命令，重启先加载 RDB 再重放增量，又快又安全。
- 选型：纯缓存允许丢数据只开 RDB；数据重要开 AOF `everysec` + 混合持久化。
- 注意：RDB 快照期间写入会触发 COW 复制内存页，写多的实例要预留内存，否则可能 OOM。

**面试怎么答（60 秒版）**：RDB 是把某一时刻的全量数据做成快照，用 bgsave fork 子进程写盘，优点是文件小、恢复快，缺点是两次快照之间的数据会丢，fork 时也有短暂阻塞。AOF 是把写命令追加到文件里，默认每秒刷盘，最多丢一秒的数据，但文件大、恢复要重放命令。Redis 4.0 之后支持混合持久化，AOF 重写时前半部分是 RDB，后面追加增量命令，兼顾恢复速度和安全。缓存场景可以只用 RDB，重要数据我一般开 AOF 加混合持久化。

**追问陷阱**：
- 错误：「RDB 会丢数据所以生产不能用」→ 正确：看业务；纯缓存丢了重建即可，没必要背 AOF 的开销。
- 错误：把 `appendfsync always` 当成最佳实践 → 正确：每条都刷盘性能极差，默认 `everysec` 才是常规选择。

## 14. 内存淘汰策略与过期删除

**一句话答案**：先设 `maxmemory` 再选淘汰策略，默认 `noeviction` 写满就报错；实际常用 `allkeys-lru` 或 `volatile-lru`；过期 key 靠「惰性删除 + 定期删除」清理。

**原理展开**：
- 必须设 `maxmemory`（通常物理内存的 60%~75%），不设会一直吃内存直到 OOM 或影响其他进程。
- 八种策略：`noeviction`（默认，写操作直接报错）、`allkeys-lru`/`allkeys-lfu`/`allkeys-random`（所有 key 里淘汰）、`volatile-lru`/`volatile-lfu`/`volatile-random`/`volatile-ttl`（只在设置了过期时间的 key 里淘汰）。
- 选型：纯缓存用 `allkeys-lru`；缓存和持久数据混在一个实例时用 `volatile-*`，避免误删没有 TTL 的重要数据。
- Redis 的 LRU 是**近似 LRU**：随机采样 5 个 key 挑最久未使用的淘汰，为了省内存不做全局淘汰链表。
- LFU（4.0+）按访问频率淘汰，适合热点长期稳定的场景；LRU 适合新数据更可能被访问的场景。
- 过期删除：惰性删除（访问到才判断过期）+ 定期删除（每秒 10 次随机抽查），所以可能有「已过期但还没删」的 key 占内存。

**面试怎么答（60 秒版）**：Redis 的内存淘汰要先配 maxmemory，否则写满会报错。策略有八种，默认是 noeviction 不淘汰直接报错，实际常用 allkeys-lru，如果实例里既有缓存又有重要数据就用 volatile-lru，只淘汰设了过期时间的 key。要说明 Redis 的 LRU 是近似实现，随机采样挑最久没用的淘汰，不是严格全局 LRU。过期的 key 也不是到点就删，而是访问时惰性判断加定期随机抽查，所以内存占用和实际有效数据会有差异。

**追问陷阱**：
- 错误：「设了过期时间 Redis 到点就删」→ 正确：惰性 + 定期删除，可能短期仍占内存。
- 错误：用 `volatile-lru` 但大部分 key 没设 TTL → 正确：内存满了也淘汰不掉，直接报错。

## 15. 缓存穿透 / 击穿 / 雪崩（必考三件套）

**一句话答案**：穿透是查不存在的数据打到库、击穿是单个热点 key 失效瞬间打到库、雪崩是大量 key 同时失效或 Redis 宕机；解法分别是空值 + 布隆过滤、互斥锁 / 逻辑过期、随机 TTL + 高可用 + 降级。

**原理展开**：
- 穿透：请求的数据缓存和数据库都没有（如伪造的 id），每次都被透传到 DB。解法：① 缓存空值并设短 TTL；② 布隆过滤器提前拦截（有误判、不支持删除）；③ 参数合法性校验 + 接口限流。
- 击穿：某个高并发访问的热点 key 刚好过期，瞬间所有请求打向 DB。解法：① 互斥锁（只让一个线程回源，其他等待或返回降级数据）；② 逻辑过期（value 带过期时间、不设物理 TTL，异步线程更新，读不阻塞）；③ 热点 key 永不过期 + 后台刷新。
- 雪崩：大量 key 在同一时刻过期，或 Redis 整体不可用，请求全部打向 DB 导致 DB 被打挂。解法：① 过期时间加随机值打散；② 多级缓存（本地 Caffeine + Redis）；③ Redis 高可用（主从 + 哨兵/集群）；④ 限流、熔断、降级兜底；⑤ 缓存预热。
- 三者一句话区分：穿透是「数据本来就不存在」，击穿是「一个热点挂了」，雪崩是「一片缓存都没了」。
- 延伸考点：布隆过滤器用 bitmap + 多个哈希函数，判断「一定不存在」很准，「可能存在」有误判，所以只能挡穿透不能当缓存用。

**面试怎么答（60 秒版）**：这三个都是缓存失效导致请求打到数据库，但成因不同。穿透是查一条根本不存在的数据，缓存永远不命中，解法是缓存空值加短过期时间，或者前面加布隆过滤器挡住不存在的 id。击穿是单个热点 key 过期的一瞬间大量请求打库，解法是加互斥锁只让一个线程去查库回填，或者用逻辑过期让读请求一直读旧值、后台异步更新。雪崩是大量 key 同时过期或者 Redis 挂了，解法是过期时间加随机、做多级缓存、Redis 做主从高可用，再加限流降级兜底。

**追问陷阱**：
- 错误：把击穿和雪崩混为一谈 → 正确：击穿是单个热点，雪崩是大面积/整体不可用。
- 错误：缓存空值不设过期 → 正确：数据后来真的出现了也读不到，必须设短 TTL 或主动清理。

## 16. 缓存与数据库一致性

**一句话答案**：推荐 Cache Aside「先更新数据库、再删除缓存」，接受最终一致；并发极端场景用延迟双删，可靠性要求高就订阅 binlog 异步删缓存。

**原理展开**：
- 读流程：先读缓存，命中直接返回；未命中查库并把结果写回缓存（可设 TTL 兜底）。
- 写流程：**先更新 DB，再删除缓存**（不是更新缓存）。删而更的原因：并发写会让旧值覆盖新值；缓存可能是复杂聚合值，不一定用得上。
- 反过来的「先删缓存再更新 DB」有明确缺陷：删完缓存、DB 还没更新时，读请求会把旧值回填，脏数据长期滞留。
- 「先更 DB 再删缓存」的残留风险：缓存删除失败、或主从延迟导致读到旧值再回填，概率低但存在，可用重试/消息补偿。
- 延迟双删：更新前删一次，更新后延迟（如 500ms~1s，覆盖主从延迟和读回填窗口）再删一次。
- 最可靠：用 Canal 订阅 binlog，异步删缓存，业务代码零侵入且不依赖应用重试；强一致场景干脆读写都走 DB 或加分布式锁，但通常没必要。

**面试怎么答（60 秒版）**：缓存和数据库一致性我一般用 Cache Aside，写操作是先更新数据库再删除缓存，而不是更新缓存，因为并发下更新缓存容易出现旧值覆盖新值。这两个操作不是原子的，所以极端情况还是可能不一致，比如删缓存失败或者主从延迟导致旧值被回填，这是概率很小的问题，一般接受最终一致，再用过期时间兜底。要求高一点可以用延迟双删，更新完延迟几百毫秒再删一次。最稳的是订阅 binlog 异步删缓存。强一致代价太高，一般业务不需要。

**追问陷阱**：
- 错误：「先删缓存再更新 DB 更好，因为缓存一定被清了」→ 正确：中间窗口的读请求会把旧值写回缓存。
- 错误：「直接更新缓存就行，省一次查询」→ 正确：并发写会乱序覆盖，且缓存值可能是复杂计算结果。

## 17. 分布式锁

**一句话答案**：用 `SET key uniqueValue NX PX 30000` 一条命令原子加锁，释放时用 Lua 先比对 value 再删除；生产直接上 Redisson，它解决了续期、可重入和误删。

**原理展开**：
- 加锁必须一条命令完成：`SET lock:order:1001 uuid NX PX 30000`；`SETNX` + `EXPIRE` 两条命令之间宕机会造成死锁。
- value 存唯一标识（UUID + 线程 id）的意义：A 的锁超时释放后 B 拿到锁，A 执行完不能把 B 的锁删掉——所以释放要用 Lua 脚本「先 GET 比较再 DEL」保证原子。
- 锁超时与续期：业务执行时间不确定，短了会提前释放，长了会阻塞；Redisson 用**看门狗**在后台每 1/3 过期时间续期，直到主动解锁。
- 可重入：Redisson 用 Hash 存「线程标识 + 重入次数」，同一线程再次加锁只加计数。
- 主从架构缺陷：主节点加锁成功后宕机，锁还没同步到从节点，新主上别人也能拿到锁（RedLock 有争议，极端一致场景才考虑）。
- 用途：防重复提交、库存扣减、缓存重建互斥、定时任务多实例只跑一个；与幂等的区别是锁只保证「同时只有一个能进」，不保证重复请求结果一致。

```java
// 加锁：一条命令保证「不存在才设置 + 过期时间」的原子性
String res = jedis.set(lockKey, requestId, SetParams.setParams().nx().px(30000));
// 释放：Lua 先比对本次请求的标识，避免误删别人的锁
String script = "if redis.call('get', KEYS[1]) == ARGV[1] "
              + "then return redis.call('del', KEYS[1]) else return 0 end";
jedis.eval(script, Collections.singletonList(lockKey), Collections.singletonList(requestId));
```

**面试怎么答（60 秒版）**：分布式锁我用 Redis 的 SET NX PX 一条命令加锁，value 存一个唯一标识，释放的时候用 Lua 脚本先比较 value 再删除，避免把别人的锁删掉。只用 SETNX 加 EXPIRE 两条命令是不安全的，中间宕机就死锁了。业务执行时间不确定的问题用续期解决，Redisson 的看门狗会自动续；它底层还用 Hash 实现了可重入。要说局限的话，主从切换可能会丢锁，要求极高一致性的场景得用 RedLock 或者换 ZooKeeper。

**追问陷阱**：
- 错误：释放锁直接 `DEL` → 正确：可能删掉别人新加的锁，必须 Lua 比对 value。
- 错误：「分布式锁能保证接口幂等」→ 正确：只保证同一时刻互斥，超时释放后重复请求仍会进来。

## 18. 高可用：主从、哨兵、集群

**一句话答案**：主从做读写分离与数据备份、故障需人工切换；哨兵在主从之上做自动故障转移；Cluster 用 16384 个槽分片，同时解决容量与高并发。

**原理展开**：
- 主从复制：从库启动时全量同步（主库生成 RDB），之后增量传播写命令；支持读写分离，但主库挂掉需要人工切换，写无法扩展。
- 哨兵 Sentinel：一组哨兵进程监控主从，主观下线 + 多数派确认客观下线后，用 Raft 选出 leader 执行故障转移（选从库提升为主、通知其他从库改主、通知客户端），解决高可用但不解决容量。
- Cluster 集群：把数据按 `CRC16(key) % 16384` 映射到 16384 个槽，每个主节点负责一部分槽，每个主节点可带从节点；去中心化，节点间用 gossip 通信。
- Cluster 的代价：多 key 操作（mget/事务/Lua）要求 key 在同一槽，可用 hash tag（`{user}:1`、`{user}:2`）强制同槽；不支持多数据库；客户端要支持 MOVED/ASK 重定向。
- 读写分离的坑：主从延迟导致写完立刻读从库读不到，强一致场景要读主库或用半同步复制。
- 演进顺序：单机 → 主从（备份+读扩展）→ 哨兵（自动切换）→ 集群（容量+并发）。

**面试怎么答（60 秒版）**：Redis 高可用分三层。主从复制解决数据备份和读扩展，但主挂了要人工切换。哨兵在主从之上做监控和自动故障转移，主库挂了自动选一个从库提升，客户端从哨兵拿到新地址，但它不扩展容量。集群是把数据按 16384 个槽分到多个主节点，每个主节点带从节点，同时解决容量和高并发，代价是跨槽的多 key 操作不支持，要用 hash tag 让相关 key 落到同一个槽。

**追问陷阱**：
- 错误：「哨兵能提升容量」→ 正确：哨兵只做高可用，容量要靠 Cluster 或业务拆分。
- 错误：「Cluster 里 mget 一定可用」→ 正确：跨槽会报错，得用 hash tag 或改成分批单键查询。

## 19. 热 key 与大 key

**一句话答案**：热 key 是单 key 访问量过高打满某个分片，用本地缓存、key 拆分、读写分离解决；大 key 是 value 过大导致网络与阻塞，用拆分、压缩、`UNLINK` 异步删除解决。

**原理展开**：
- 热 key：某个 key 的 QPS 远超其他 key，在 Cluster 下会打满单个节点；因为命令单线程执行，还会拖慢该节点上所有请求。
- 发现热 key：`redis-cli --hotkeys`（需 LFU 策略）、`slowlog`、客户端埋点统计、监控平台；`MONITOR` 能看到但开销大，别在生产长开。
- 热 key 处理：① 本地缓存（Caffeine）挡一层，注意一致性；② key 拆分——`hot:item:1` ~ `hot:item:10` 加随机后缀分散到不同节点；③ 读写分离 + 多从库分摊读；④ 限流兜底。
- 大 key 判定（经验值）：String 超 10KB、Hash/List/Set/ZSet 元素超 5000 个即视为大 key。
- 大 key 危害：网络传输阻塞（一次几十 MB）、`DEL` 同步释放内存会阻塞主线程、Cluster 内存分布不均、过期删除时卡顿。
- 大 key 处理：业务上拆分存储（大 Hash 按字段拆、大 List 分段）、压缩 value、用 `UNLINK` 异步删除（4.0+）、用 `HSCAN/SSCAN` 分批遍历而不是 `HGETALL`、禁止 `keys *`。

**面试怎么答（60 秒版）**：热 key 是某个 key 的访问量特别高，因为 Redis 命令单线程，会把那个节点打满。解决办法是加本地缓存挡在最前面，或者把这个 key 拆成多个副本加随机后缀分散到不同节点，读多的话还可以靠读写分离摊到多个从库。大 key 是 value 特别大或者集合元素特别多，会影响网络传输，删除时还会阻塞主线程。处理就是用 UNLINK 异步删、把大结构拆小、遍历用 SCAN 分批，不要在线上用 keys * 和 hgetall。这两个问题都要配监控提前发现。

**追问陷阱**：
- 错误：用 `keys *` 找热 key 或大 key → 正确：会阻塞整个实例，用 `--bigkeys`/`--hotkeys` 或离线分析。
- 错误：直接 `DEL` 大 key → 正确：同步释放内存阻塞主线程，用 `UNLINK` 或分批删除。

### 加分项：深挖到此 · binlog 与主从复制

- binlog 是 Server 层日志，记录所有修改（逻辑日志），用于主从复制与数据恢复；redo log 是 InnoDB 层物理日志，用于崩溃恢复。经典问题「两阶段提交」：redo log 与 binlog 通过内部 XA 保证一致，先 prepare redo、再写 binlog、最后 commit。
- 三种格式：`STATEMENT`（记 SQL，可能因函数/时间不一致）、`ROW`（记每行变更，最安全、日志大，生产主流）、`MIXED`。
- 主从复制流程：主库 dump 线程发 binlog → 从库 IO 线程写 relay log → SQL 线程重放；延迟主要来自从库单线程重放（5.7+ 支持并行复制）与大事务。
- 主从延迟带来的业务问题：写完立刻读从库读不到（可用强制走主库 / 半同步复制）；缓存双删策略也要考虑延迟。

### 加分项：深挖到此 · 索引下推与优化器成本

- 索引下推 ICP：没有 ICP 时，联合索引 `(city, age)` 只能按 city 定位，回表后再过滤 age；有了 ICP，age 条件下推到存储引擎在索引层过滤，减少回表次数，Extra 显示 `Using index condition`。
- 优化器基于成本选择索引：成本 ≈ 扫描行数 × IO 代价 + CPU 代价；索引区分度低或需要回表很多时，可能选择全表扫描（所以「明明有索引却没走」要先看 rows 估算）。
- `ANALYZE TABLE` 更新统计信息；索引基数 `Cardinality` 可在 `show index from t` 观察，基数太低说明区分度差。
- 覆盖索引 + 最左前缀 + 索引下推三者一起，才是「索引优化」的完整答案，只答「加索引」是初级水平。
